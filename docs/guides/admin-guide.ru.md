# Руководство администратора / DevOps

*Read in [English](admin-guide.md).*

Для тех, кто разворачивает, настраивает и поддерживает
`structured_log_server` в рабочем состоянии. Если вы пользуетесь
приложением изо дня в день, а не эксплуатируете его — см.
[Руководство пользователя](user-guide.ru.md); если вы интегрируете с ним
своё приложение — см. [Руководство разработчика](developer-guide.ru.md).

## Что вы разворачиваете

Один self-hosted сервис, `structured_log_server` — один процесс: без
брокера сообщений, без внешнего кэша и (при бэкенде хранения по
умолчанию) без отдельного сервера БД. Рядом с ним `structured_log_admin_client` —
веб-приложение, которое общается с сервером по его HTTP API.
Поддерживаемый вариант — развернуть их вместе, за одним nginx; именно он
описан в этом руководстве. Ничто не мешает запустить сервер отдельно
и направить на его API другой клиент (см.
[Руководство разработчика](developer-guide.ru.md)), но именно связка из
`deploy/` протестирована и документирована от начала до конца.

**Почему один origin, и почему кросс-доменный доступ по умолчанию
выключен.** Сервер не отправляет заголовков `Access-Control-Allow-*`,
пока вы явно не включите CORS (ниже), а значит браузер откажется
пускать admin-клиент к серверу с другого хоста/порта — это не ошибка, а
осознанное поведение по умолчанию. Развёртывание клиента и API за одним nginx-origin
(как делает поставляемый `docker-compose.yml`) снимает вопрос целиком:
каждый запрос клиента — same-origin. Включайте
`--cors-allowed-origins` только если у вас есть конкретная причина
обслуживать клиент откуда-то ещё (локальная разработка с отдельно
размещённым API, другая, осознанно выбранная топология развёртывания).

## Быстрый старт: Docker Compose

Быстрее всего правильно развернуть систему с помощью того, что уже лежит в
[`deploy/`](../../deploy/):

```bash
cd deploy
cp .env.example .env    # поправьте, если нужен нестандартный порт/логин
./deploy.sh
```

Это соберёт web-бандл admin-клиента (тем же Flutter SDK, версия которого
уже закреплена в репозитории, — ничего отдельно устанавливать не нужно),
соберёт оба Docker-образа, сгенерирует случайный JWT-секрет подписи
(JSON Web Token — ключ, которым сервер подписывает каждый выдаваемый
токен сессии) в `deploy/secrets/jwt_secret` (один раз, при первом запуске — в
`.gitignore`, монтируется только для чтения, никогда не попадает ни в
переменную окружения, ни в compose-файл, который могли бы закоммитить)
и запустит три контейнера за одним nginx:

| Сервис | Что это |
|---|---|
| `server` | API — не публикуется на хост, доступен только через `proxy` |
| `web` | nginx: только статика admin-клиента. Не знает о существовании `server` — тоже не публикуется наружу |
| `proxy` | Готовый nginx, ставящий `web` и `server` за один origin, на котором публикуется клиент |

```bash
open http://localhost:8080    # или ваш STRUCTURED_LOG_PUBLIC_PORT
```

На пустой базе сервер автоматически создаёт первого администратора и
печатает временный пароль **один раз**, лог-строкой уровня warning —
сохраните его, пока он не прокрутился за пределы экрана:

```bash
docker compose logs server | grep -i 'temporary password'
```

Эта учётная запись обязана сменить пароль при первом входе; все
остальные эндпоинты отказывают ей до этого момента. Альтернативы (пароль
по вашему выбору или полное отключение автосоздания) — в разделе
[«Автосоздание первого администратора»](#автосоздание-первого-администратора)
ниже.

```bash
docker compose logs -f server    # JSON-строки, одна на запрос
docker compose ps                # состояние контейнеров, включая health
docker compose down              # остановить, том с данными остаётся
docker compose down -v           # остановить и удалить том с базой данных
```

`./deploy.sh` пересобирает то, что изменилось, при повторном
развёртывании; `./deploy.sh --rebuild` принудительно собирает оба
образа с нуля (полезно после обновления Dart/Flutter SDK или когда
слой кэша выглядит устаревшим).

## Запуск без Docker

Всё описанное выше — лишь удобная обёртка Docker Compose над двумя
вещами, которые можно запустить и напрямую:

```bash
cd backend/structured_log_server
dart pub get
dart run build_runner build --delete-conflicting-outputs   # генерирует код drift/freezed/router

export STRUCTURED_LOG_JWT_SECRET="$(openssl rand -hex 32)"
dart run bin/server.dart serve --db-path=/var/lib/structured_log/logs.db
```

Для backend'а SQLite по умолчанию нужен только Dart SDK (3.0+) и больше
ничего. `dart compile exe bin/server.dart -o structured-log-server`
даёт самостоятельный нативный бинарник, если не хочется тащить SDK на
прод-хост, — ровно это внутри и делает сборочная стадия Docker-образа.
Admin-клиент, если вы обслуживаете его сами вне поставляемой
nginx-связки, — статическая Flutter web-сборка:

```bash
cd frontend/structured_log_admin_client
flutter build web --release --dart-define=STRUCTURED_LOG_BASE_URL=https://your-api-host
```

раздавайте `build/web/` любым статическим файловым сервером; если этот
хост отличается от хоста API, см. замечание про CORS выше.

## Kubernetes

В [`deploy/k8s/`](../../deploy/k8s/) — настоящие манифесты: общий
Kustomize `base/` для обоих backend'ов хранения плюс по overlay на
каждый (`overlays/sqlite/`, `overlays/postgres/`), и два скрипта
(`build-images.sh`, `create-secrets.sh`). Этот раздел объясняет их
неочевидные части; всё описанное при написании проверено вручную на
локальном кластере (`minikube`, ingress-nginx). Сами команды
`kubectl`/`kustomize` — в
[deploy/k8s/README.ru.md](../../deploy/k8s/README.ru.md).

### Ровно одна реплика

Сервер обязан работать ровно в одной реплике, всегда — это не вопрос
подбора ресурсов. Поток записей в реальном времени (`GET /v1/logs/stream`)
раздаётся broadcast'ом внутри процесса, без внешнего pub/sub (см.
[architecture/live-streaming.md](../architecture/live-streaming.ru.md)).
Вторая реплика имела бы собственный, отдельный broadcast, и клиент,
подключённый к одной реплике, молча пропустил бы записи логов, которые
балансировщик направил в `POST /v1/logs` на другую. Это верно для
**обоих** backend'ов хранения; переход на PostgreSQL этого не меняет —
`server-deployment.yaml` обоих overlay'ев фиксирует `replicas: 1`.
Масштабируйте **web** deployment (статический nginx admin-клиента)
свободно — он не хранит состояния, `base/web-deployment.yaml` по
умолчанию держит 2.

### Путь монтирования секретов

Секреты монтируются в `/etc/structured-log/secrets`, намеренно не в
`/run/secrets`. Этот путь конфликтует со штатным монтированием токена
service account у Kubernetes
(`/var/run/secrets/kubernetes.io/serviceaccount` — `/run` и `/var/run` в
образе это один и тот же каталог). Монтирование туда тома `Secret` на
практике привело к тому, что контейнер вовсе не стартовал
(`unable to create mountpoint: read-only file system`).

### enableServiceLinks: false

Каждая спека пода задаёт `enableServiceLinks: false` — это убирает шум,
а не исправляет ошибку. Kubernetes добавляет в под переменные
окружения в стиле Docker-links для каждого видимого ему Service'а
(`<SVC>_SERVICE_HOST`, `_PORT`, ...). Service с именем
`server` порождает переменные с префиксом `STRUCTURED_LOG_SERVER_...`,
которые совпадают с собственной конвенцией префикса `STRUCTURED_LOG_`
этого проекта. Резолвер с этим и так справляется — на нераспознанную
переменную `STRUCTURED_LOG_*` он только выдаёт предупреждение и никогда
не прерывает запуск (см. [«Что можно настроить»](#что-можно-настроить)
выше), — но незачем нарочно создавать ему такие поводы.

### Overlay SQLite: стратегия Recreate

Overlay SQLite задаёт `strategy: type: Recreate`, а не `RollingUpdate`,
который используется по умолчанию. `Recreate` удаляет старый под до
запуска нового. Иначе во время rolling update два пода какое-то время
работали бы одновременно и оба писали бы в один файл SQLite на одном
ReadWriteOnce-томе. Это подтверждено прямым удалением пода (`kubectl delete
pod -l app=structured-log-server`, не просто повторный `apply`) при
тестировании: новый под поднялся на том же PVC без новой строки
«temporary password» в логе — bootstrap-администратор и все уже
созданные проекты сохраняются после пересоздания пода, как и должен
гарантировать `ReadWriteOnce`.

**Overlay PostgreSQL** подключается к Service `postgres` внутри
кластера (минимальный `StatefulSet`,
`overlays/postgres/postgres-statefulset.yaml`) по короткому DNS-имени —
либо направьте `STRUCTURED_LOG_DB_POSTGRES_HOST` на собственный
инстанс и вовсе пропустите этот файл. Проверено тем же способом, что
путь с SQLite: сервер нашёл Service по имени и прошёл `/healthz` без
какой-либо специальной сетевой настройки сверх обычного
`ClusterIP`-сервиса.

### Маршрутизация Ingress

`Ingress` сам распределяет запросы по путям: `/v1` — напрямую на Service
`server`, всё остальное — на `web`. Ни один из образов не знает о
существовании другого: `web` — обычный статический файловый сервер,
которому ничего не известно о backend'е, а `server` понятия не имеет, что
кто-то на него проксирует. Так сделано намеренно: раньше адрес `server`
был зашит в собственный nginx-конфиг `web`, а значит, имя `server` должно
было разрешаться уже для того, чтобы образ просто *запустился* —
независимо от того, доходил ли трафик этого конкретного развёртывания
до него этим путём вообще (найдено при развёртывании именно такой
схемы: разбиение на `site`, `web` и `server`, каждый со своим путём на
одном Ingress, причём `/v1` и так шёл прямо на `server` — внутренний
proxy `web` был мёртвым кодом, который всё равно мог уронить
контейнер в crash loop). `Ingress` — как раз тот слой, который должен
знать, куда ведёт каждый путь; дублировать эту работу внутри `web` было
ошибкой, а не возможностью, которую стоило сохранять.

Origin один, поэтому настраивать CORS в этой схеме нигде не нужно. Так же
устроено и поставляемое развёртывание Docker Compose: там то же самое
разделение делает отдельный контейнер `proxy` вместо `Ingress` (см.
[`deploy/proxy/`](../../deploy/proxy/)), потому что у Compose нет
собственного слоя маршрутизации по путям.

Пересоздать администратора на непустой базе — так же, как
[в пути Docker Compose](#автосоздание-первого-администратора), разовым
вызовом `kubectl run`/`kubectl exec`, запускающим `create-admin` на
том же PVC или с тем же подключением к Postgres — отдельного манифеста
Kubernetes `Job` под это не нужно, это та же CLI-команда, что и везде.

## Выбор backend'а хранения

`--db-backend` выбирает один из двух вариантов. Решение принимается
один раз, при развёртывании на **пустой** базе: переключить backend на
работающей системе нельзя, и встроенного способа миграции с одного на
другой нет. В HTTP API, в
модели данных и в том, что видит клиент, разницы между ними нет —
различается только эксплуатация.

### SQLite (по умолчанию)

```bash
dart run bin/server.dart serve --db-backend=sqlite --db-path=/data/logs.db
# или просто: --db-path=/data/logs.db  (sqlite — backend по умолчанию)
```

Один файл, никакого отдельного сервиса запускать и мониторить не
нужно. Режим WAL (write-ahead logging SQLite, позволяющий читателям и
писателю обращаться к базе одновременно) и 5-секундный busy timeout
заданы жёстко и не настраиваются — именно для того, чтобы второй короткоживущий процесс
(`create-admin`, ниже) мог обратиться к тому же файлу, пока сервер
работает, не падая с ошибкой. Чтения получают собственный пул
дополнительных соединений рядом с единственным писателем
(`--db-read-pool-size`, по умолчанию `2`, `0`–`16`), чтобы медленный
поиск не стоял в очереди за приёмом логов; записи (приём, любая
административная мутация) всегда идут через единственное
соединение-писатель: масштабировать запись сознательно не стали, это не
недосмотр.

**Подходит,** если развёртывание живёт на одном сервере, эксплуатационные
расходы должны оставаться низкими или умеренными, а резервное копирование
на уровне файла (ниже) оператора устраивает. С этого стоит начинать
большинству развёртываний.

### PostgreSQL

```bash
export STRUCTURED_LOG_DB_POSTGRES_PASSWORD='...'
dart run bin/server.dart serve \
  --db-backend=postgres \
  --db-postgres-host=db.internal \
  --db-postgres-database=structured_log \
  --db-postgres-username=structured_log
```

| Настройка | По умолчанию | Примечания |
|---|---|---|
| `--db-postgres-host` / `-port` / `-database` / `-username` | порт `5432` | Обязательны (кроме порта) при выбранном backend'е |
| `STRUCTURED_LOG_DB_POSTGRES_PASSWORD` / `_FILE` | — | Секрет: флага нет, та же конвенция смонтированного файла, что у JWT-секрета |
| `--db-postgres-pool-size` | `10` (1–64) | Один пул, общий для чтения и записи — собственная модель конкурентных писателей PostgreSQL не нуждается в разделении на чтение/запись, как у SQLite. `--db-read-pool-size` здесь ни на что не влияет; значение, отличное от дефолта, только логирует предупреждение при старте |
| `--db-postgres-ssl-mode` | `require` | `require` (шифрование, сертификат не проверяется — обычный случай за сетью управляемого провайдера), `verify-full` (шифрование и проверка), либо `disable` (без TLS — для локальной разработки с инстансом, где TLS не настроен) |

**Подходит:** оператору, у которого уже есть PostgreSQL и который хочет
обслуживать хранилище логов теми же средствами резервного
копирования/HA/мониторинга, либо тому, кому при высокой нагрузке записи нужны
именно нативные конкурентные писатели PostgreSQL вместо модели SQLite
«один писатель + WAL».

**Docker Compose с PostgreSQL.** Поставляемый `deploy/docker-compose.yml`
идёт с SQLite как эталонным путём. Чтобы поднять тот же стенд на
PostgreSQL, добавьте рядом `docker-compose.override.yml` (Compose
подхватывает его автоматически) — например:

```yaml
services:
  server:
    environment:
      STRUCTURED_LOG_DB_BACKEND: postgres
      STRUCTURED_LOG_DB_POSTGRES_HOST: postgres
      STRUCTURED_LOG_DB_POSTGRES_DATABASE: structured_log
      STRUCTURED_LOG_DB_POSTGRES_USERNAME: structured_log
      STRUCTURED_LOG_DB_POSTGRES_PASSWORD_FILE: /run/secrets/postgres_password
      STRUCTURED_LOG_DB_POSTGRES_SSL_MODE: disable   # два контейнера в одной приватной сети
    volumes:
      - ./secrets/postgres_password:/run/secrets/postgres_password:ro
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: structured_log
      POSTGRES_PASSWORD_FILE: /run/secrets/postgres_password
      POSTGRES_DB: structured_log
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./secrets/postgres_password:/run/secrets/postgres_password:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U structured_log -d structured_log"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  pgdata:
```

со сгенерированным файлом секрета в `deploy/secrets/postgres_password`
(та же конвенция, что у `deploy/secrets/jwt_secret` —
`openssl rand -base64 24 | tr -d '\n' > deploy/secrets/postgres_password
&& chmod 600 deploy/secrets/postgres_password`), затем `./deploy.sh` как
обычно.

## Автосоздание первого администратора

На по-настоящему пустой базе (в таблице `users` вообще нет строк)
сервер сам создаёт первого администратора, ещё до открытия порта:

```bash
--bootstrap-admin-enabled           # по умолчанию: true
--bootstrap-admin-username=admin    # логин по умолчанию
STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD или ..._FILE   # опционально
```

Если пароль не задан, сервер сгенерирует его и напечатает **один
раз** в лог старта с пометкой «временный» — именно так и происходит в
быстром старте выше. Задайте пароль сами, если не хотите выискивать его
в логе. В любом случае эта учётная запись помечается как *основной*
администратор, и позже это различие пригодится (см.
[«Удаление администратора»](#удаление-администратора) ниже).

Чтобы пересоздать администратора на базе, где пользователи **уже
есть** (условие автосоздания там никогда не срабатывает — например,
все учётные записи admin случайно заблокировали), используйте явную
команду:

```bash
STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD="$(openssl rand -base64 18)" \
  dart run bin/server.dart create-admin \
  --db-path=/data/logs.db \
  --bootstrap-admin-username=admin
```

В отличие от автосоздания, пароль, заданный так, **не** требует
принудительной смены при первом входе: вы ввели его сами, и это то же
самое, что пароль, выбранный оператором напрямую. `create-admin` нужно
только подключение к базе (без JWT-секрета, без остальной конфигурации),
и команда отказывается запускаться, если активный, неудалённый
администратор уже существует.

## Управление сервером изо дня в день

### Управление пользователями

Большая часть повседневного администрирования — создание пользователей,
выдача ролей, управление группами/проектами, чтение журнала аудита —
происходит через UI admin-клиента, под учётной записью с ролью `admin`;
о том, что там можно сделать (создание учётных записей, сброс паролей,
блокировка/удаление, защиты основного администратора и единственного
owner'а группы), см.
[Руководство пользователя](user-guide.ru.md#если-вы-admin-пользователи-и-журнал-аудита). Отдельного пути управления
пользователями, доступного только оператору, нет: ту же роль `admin`, под которой вы вошли бы для
этого сами, можно выдать любому, кому она нужна. Всё, что делает UI, идёт
через тот же HTTP API, документированный в
[api/http-api.md](../api/http-api.md), так что скриптовое управление
пользователями/проектами напрямую через этот API (массовый онбординг,
CI-пайплайн, создающий проект на каждый сервис) поддерживается
наравне с UI — подробнее об этом в
[Руководстве разработчика](developer-guide.ru.md#вызов-api-управления).

### Просмотр конфигурации

```bash
dart run bin/server.dart --print-config
```

печатает каждую настройку, её итоговое значение и **откуда она взялась**
(`cli`/`env`/`default`) — секреты показываются как `***` плюс источник,
чтобы подтвердить, что секрет взят оттуда, откуда ожидалось, не видя
значения. Команда завершается с кодом `0`, не запуская сервер. `--help`
генерируется из той же таблицы параметров, поэтому не может разойтись с
тем, что парсер на самом деле принимает.

### Что можно настроить

Каждая настройка — это CLI-флаг, переменная окружения
(`STRUCTURED_LOG_` + имя флага в `SCREAMING_SNAKE_CASE`) или встроенное
значение по умолчанию; источники проверяются в этом порядке приоритета.
Настройки читаются один раз при старте и не перечитываются, пока процесс
работает (сигнала для перечитывания конфигурации и эндпоинта для правки
настроек нет; любое изменение требует перезапуска). **У секретов вообще нет
CLI-флага** — только переменная окружения или вариант `_FILE`,
указывающий на смонтированный файл, та же конвенция, что уже
используют Docker/Kubernetes secrets, — потому что аргумент процесса
виден любому пользователю хоста через `ps` и оседает в истории shell.

Полный справочник по каждому флагу:
[operations/configuration.md](../operations/configuration.ru.md). То, что
вы, скорее всего, действительно будете менять:

| Что | Настройки |
|---|---|
| Сеть | `--http-host` (`0.0.0.0`), `--http-port` (`8080`) |
| Хранилище | `--db-backend`, `--db-path` или `--db-postgres-*` (выше), `--db-read-pool-size` (только SQLite, `2`) |
| Секрет подписи | `STRUCTURED_LOG_JWT_SECRET`/`_FILE` — **обязателен**, никогда не генерируется автоматически, не короче 32 байт |
| Лимит приёма | `--max-ingest-body-bytes` (`10485760`, 10 МиБ) |
| Автосоздание админа | `--bootstrap-admin-enabled`/`-username`, `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD`/`_FILE` |
| Хранение и очистка | `--retention-purge-interval-seconds` (`3600`), `--audit-retention-days`/`--auth-event-retention-days` (не задано = вечно), `--audit-purge-batch-size` (`500`) |
| Собственная диагностика | `--log-level` (`info`), `--log-format` (`console`/`json`), `--log-file`, `--log-max-file-bytes`/`-files` |
| Ограничение частоты | `--rate-limit-enabled` (`true`), `--rate-limit-bucket-capacity`/`-refill-per-minute` (`10`/`10`), `--rate-limit-max-keys` (`10000`) |
| Обратный прокси | `--trusted-proxy-hops` (`0`) |
| Живой поток | `--sse-heartbeat-interval-seconds` (`25`) |
| Кросс-доменный доступ | `--cors-allowed-origins` (не задано = выключено) |

**Ничего не запускается, пока всё не проверено.** Конфигурация
разбирается и проверяется *до* открытия порта или обращения к базе;
все проблемы выводятся за один проход, и процесс завершается с кодом
**`78`** (`EX_CONFIG`), отличным от рантайм-сбоя, так что супервизор
процесса или restart-policy контейнера могут отличить «поправь
конфигурацию» от «попробуй ещё раз». Неизвестный флаг останавливает
запуск (почти наверняка опечатка); неизвестная переменная
`STRUCTURED_LOG_*` вызывает только предупреждение: окружение контейнера
принадлежит не только вам, поэтому из-за чужой переменной сервис не должен
падать, но и промолчать о ней нельзя.

## За обратным прокси

Задайте `--trusted-proxy-hops` равным числу прокси, реально стоящих
перед сервером (поставляемая связка Compose, один nginx, использует
`1`). Сервер отсчитывает столько хопов справа от `X-Forwarded-For`,
чтобы найти реальный адрес вызывающего, по которому ограничитель
частоты считает бакеты. Ошибка в любую сторону — серьёзная проблема:

- **Слишком низкое значение:** все клиенты за прокси делят одно ведро
  — один активный пользователь ограничивает всех.
- **Слишком высокое значение:** клиент может подделать собственный
  адрес в заголовке, которому сервер теперь доверяет, полностью обходя
  ограничитель.

## Кросс-доменный доступ (CORS)

Выключен по умолчанию (см. [выше](#что-вы-разворачиваете)). Включайте
только когда admin-клиент (или ваш собственный клиент) действительно
раздаётся не с того origin, что API:

```bash
--cors-allowed-origins=https://admin.example.com,http://localhost:3000
```

Через запятую, точные origin (схема + хост + порт), с учётом регистра,
без wildcard. `Origin`, которого нет в списке, не получает заголовков
CORS вовсе: никакой ошибки в ответе, их просто нет — точно так же выглядит
и ответ на same-origin запрос.

## Хранение, квоты и журнал аудита

Два независимых механизма хранения, которые легко перепутать:

- **Хранение логов на проект** (`retention_days`, обязателен для
  каждого проекта — ни один проект не может отказаться от политики
  хранения): периодическая фоновая очистка
  (`--retention-purge-interval-seconds`) удаляет записи проекта, которые
  старше заданного срока. Очистка идёт с задержкой, а не в реальном времени:
  при высокой нагрузке она может немного отставать от заданного срока —
  это осознанный компромисс, а не ошибка. Проект также может ограничить
  себя по числу записей и/или общему объёму (`max_entries`/
  `max_bytes`, оба опциональны, задаются через UI или
  `PATCH /v1/projects/:id`) — как только любой лимит достигнут,
  дальнейший приём для этого проекта отклоняется поштучно (не весь
  батч целиком), пока очистка не освободит место или лимит не поднимут.
- **Хранение журнала административного аудита**
  (`--audit-retention-days` для административных действий,
  `--auth-event-retention-days` для попыток входа — отдельные
  настройки, обе **не заданы по умолчанию**, то есть записи хранятся
  бессрочно) управляет самим журналом аудита, а не данными приложений.
  Поэтому после обновления сервер никогда не начнёт молча удалять историю —
  очистку нужно включить явно. Вручную удалить запись аудита не может
  никто и ни через какой эндпоинт — удаляют что-либо только эти две
  настроенные политики, и каждый проход очистки, который что-то удалил,
  оставляет собственную запись аудита (`audit.purged`), так что на вопрос
  «куда делась прошлогодняя история» всегда есть ответ в самом
  журнале.

## Резервное копирование

**SQLite.** База данных — один файл по пути `--db-path`. С остановленным
сервером обычное копирование файла безопасно. С работающим — лучше
`sqlite3 /data/logs.db ".backup '/backup/logs-$(date +%F).db'"`
(online backup API SQLite), а не прямое копирование файла: в режиме WAL
файл посреди записи не обязательно согласован сам с собой, а обычное
копирование на это рассчитывает. Внутри
поставляемого развёртывания Compose база лежит на именованном томе
`data`:

```bash
docker run --rm -v structured-log_data:/data -v "$PWD":/backup alpine \
  tar czf /backup/data.tgz -C /data .
```

**PostgreSQL.** Обычные `pg_dump`/`pg_basebackup`/уже имеющийся у вас
инструментарий бэкапов — как раз эту часть эксплуатации оператор,
выбравший этот backend, обычно уже наладил для остальных своих
сервисов.

**Секреты.** `deploy/secrets/jwt_secret` (и, если вы запускаете
PostgreSQL через override выше, `deploy/secrets/postgres_password`) не
копируются шагами выше, и не стоит бездумно пересоздавать их при
пересборке: замена JWT-секрета делает недействительными все уже выданные
access-токены и разом выводит из системы всех пользователей. Потеря и
перегенерация секрета — осознанное и разрушительное действие, а не рутина.

## Мониторинг и здоровье

```bash
curl http://localhost:8080/healthz
# {"status": "ok"}
```

Эндпоинт не требует аутентификации и отвечает, пока HTTP-стек
обслуживает запросы, — направьте на него health check балансировщика
или оркестратора напрямую. Если процесс полностью упал, эндпоинт не
возвращает статус ошибки: соединение просто отклоняется или обрывается
по таймауту, и это само по себе сигнал.

Собственная диагностика сервера (`--log-level`/`--log-format`/
`--log-file`) отделена от данных логов, которые он хранит для
тенантов — задайте `--log-format=json` для контейнерного
развёртывания, чтобы коллектор логов разбирал её как структурированные
данные, а не как консольный вывод для человека (поставляемое
развёртывание Compose уже так и делает). Пароли, токены, секретные
ключи и тела запросов никогда не попадают в этот вывод: так заложено в
устройство сервера, а не достигается маскированием задним числом.

## Чеклист безопасности

- **JWT-секрет подписи обязателен и никогда не генерируется за вас.**
  Если бы сервер придумывал его сам при старте, каждый перезапуск молча
  делал бы недействительными все токены — вместо понятного отказа при
  запуске вы видели бы в проде необъяснимые выходы из системы. Задайте
  секрет один раз и не меняйте; помните, что его ротация выводит из
  системы всех.
- **Любой секрет идёт через окружение или смонтированный файл, никогда
  через флаг.** Если хочется передать секрет CLI-аргументом — такого
  флага действительно нет, и это сделано сознательно, а не упущение,
  которое нужно обходить.
- **Браузерные security-заголовки поставляются вместе с образами —
  кроме HSTS.** Образ `web` ставит `Content-Security-Policy`,
  `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` и
  `Permissions-Policy` на всё, что отдаёт, а proxy добавляет к ответам
  API те два, которые имеют смысл для JSON. `Strict-Transport-Security`
  среди них **нет**: ни один из контейнеров не терминирует TLS, а HSTS
  на месяцы вперёд требует HTTPS для всего имени хоста — такое решение
  принимает владелец сертификата. Добавьте его на своём терминаторе, рядом с
  редиректом с HTTP.
- **Политика клиента рассчитана на один origin.** Её `connect-src
  'self'` соответствует тому развёртыванию, которое поставляет этот
  репозиторий: API отвечает на `/v1/` того же хоста. Если вы отдаёте
  API с другого origin и открываете его через `--cors-allowed-origins`,
  укажите этот origin и в `nginx.conf` образа клиента — иначе браузер
  отклонит запрос ещё до того, как дело дойдёт до CORS, и панель будет
  выглядеть сломанной, а в журнале сервера не окажется ничего.
- **Админ-панель не обращается ни к кому, кроме вашего сервера.**
  Web-бандл собирается с `--no-web-resources-cdn`, поэтому движок
  рендеринга и шрифты берутся из образа, а не из CDN Google. Это важно
  по двум причинам: панель работает на хосте без выхода в интернет, и
  браузеры операторов не сообщают третьей стороне о вашем развёртывании
  при каждой загрузке.
- **TLS для собственного listener'а сервера — задача вашего обратного
  прокси**; сам сервер работает по обычному HTTP (завершайте TLS на
  nginx/вашем балансировщике, как и для большинства подобных сервисов).
  Для backend'а PostgreSQL на настоящем сетевом хопе держите
  `--db-postgres-ssl-mode` в значении по умолчанию `require` или строже —
  `disable` годится только для одного хоста/локальной разработки.
- **С версии, где появился `--refresh-token-cookie`, TLS перестал быть
  необязательным для всего, кроме `localhost`** — и его отсутствие не
  сообщает о себе ничем. Refresh-токен попадает в браузер в cookie с
  атрибутом `Secure`; по обычному HTTP браузер выбрасывает её молча, и
  выглядит это так: вход прошёл, панель открылась, а минут через
  пятнадцать — снова экран входа, и так по кругу. Сервер этого не
  обнаружит и предупредить не сможет: за прокси он видит обычный HTTP
  независимо от того, чем пользовался браузер. `http://localhost`
  браузеры считают доверенным, `http://10.0.0.5:8080` — нет. Если TLS
  сейчас нет, задайте `--refresh-token-cookie=off` — тогда токен снова
  хранит сам клиент, как до этой версии.
- **Клиент и API на разных адресах.** `auto` (по умолчанию) не ставит
  cookie тому origin, который вы сами перечислили в
  `--cors-allowed-origins`: перечислив его, вы объявили его чужим.
  Здесь есть тонкость, ради которой стоит выставить настройку: `SameSite`
  оперирует понятием *site* (регистрируемый домен), а не origin, поэтому
  `admin.example.com` рядом с `api.example.com` — это разные origin, но
  один site, и cookie там работает. Для такой раскладки задайте
  `--refresh-token-cookie=on` явно. А вот при разных доменах ничего не
  поможет: браузеры отказываются от third-party cookie, и там клиент
  хранит токен сам.
- **Ограничение частоты действует именно на auth-эндпоинты** — попытки
  входа, смену пароля — а не общий трафик API, и блокировки учётной
  записи после неудачных попыток нет (осознанное решение: логины в этой
  системе не секретны, так что такая блокировка дала бы атакующему
  способ намеренно заморозить чужой аккаунт). Если развёртывание уже стоит за
  собственным шлюзом с ограничением частоты, `--rate-limit-enabled=false`
  позволит не дублировать его.
- **Неверно заданный `--trusted-proxy-hops` — реальная уязвимость**, а
  не просто неудобство — см. [выше](#за-обратным-прокси).
- **Создавайте первого администратора осознанно.** Либо сразу
  сохраните сгенерированный временный пароль, либо задайте
  `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD_FILE` сами до первого
  запуска — не оставляйте учётную запись с неизвестным вам паролем,
  который вы так и не сохранили.

### Удаление администратора

Самого первого администратора, когда-либо созданного на данной базе
(*основной* администратор — это конкретная учётная запись, а не
«последний оставшийся admin, кем бы он ни был»),
удалить нельзя никогда — ни ему самому, ни другому админу, сколько бы
других администраторов ни существовало. Его всё ещё можно
**заблокировать**, и об этом нюансе эксплуатации стоит знать:
блокировка основного администратора при отсутствии других активных
админов фактически закрывает доступ всем, хотя ни одна учётная запись
не удалена. Держите больше одного активного администратора, если это
для вашего развёртывания важно.

Удаление учётной записи **единственного owner'а**
группы сразу отклоняется (`409 sole_group_owner`), пока владение не
передано кому-то другому: сервер не допустит, чтобы после удаления
группа осталась без owner'а, и не будет угадывать, кому передать владение.

## Обновление

Остановите старый процесс, разверните новый бинарник/образ, запустите.
Отдельного шага миграции вручную нет: версия схемы проверяется и, если
база была записана более старой схемой, обновляется на месте
автоматически при следующем запуске — тот же механизм независимо от
backend'а хранения. Более новый бинарник, запущенный на базе, записанной
версией **впереди** того, что он понимает, вовсе отказывается
стартовать и называет в ошибке обе версии, вместо того чтобы читать
таблицы, которых не понимает. Если вы видите эту ошибку, значит, бинарник
откатили на версию старше базы; восстановите бэкап, снятый до запуска
более новой версии, либо снова обновитесь до неё.

Конфигурация никогда не мигрируется автоматически между версиями за
пределами того, что определяет сама таблица параметров — настройка,
убранная в новой версии, просто перестаёт читаться; добавленная
приходит со своим документированным значением по умолчанию, пока вы не
зададите её явно.

## Безопасная остановка сервера

`SIGTERM`/`SIGINT` запускают штатное завершение: первыми
останавливаются задача очистки по retention и broadcast потока в
реальном времени, выполняющимся запросам дают завершиться, соединение с базой (или пул
соединений, под PostgreSQL) закрывается последним. `docker compose
down`/`docker stop` отправляют ровно этот сигнал, так что путь по
умолчанию уже безопасен — менять ничего не нужно. Жёсткое завершение
(`SIGKILL` или потеря питания) — единственный случай, когда запись может
остаться незавершённой; но и режим WAL у SQLite, и механизмы надёжности
самого PostgreSQL сохраняют базу согласованной даже тогда — вы потеряете
только то, что ещё не закоммитилось, но повреждённого файла не получите.

## Диагностика

| Симптом | Вероятная причина |
|---|---|
| Процесс сразу завершается с кодом `78` | Проблема конфигурации — перезапустите с `--print-config` (если он до этого доходит) или прочитайте ошибку старта, которая называет каждую найденную проблему, а не только первую |
| «STRUCTURED_LOG_JWT_SECRET is required» | Секрет подписи действительно не задан нигде, где смотрел резолвер, — проверьте точное имя переменной окружения и что путь `_FILE`, если используется, реально существует и читается |
| «The signing secret must be at least 32 bytes in UTF-8» | Секрет задан, но слишком короток, чтобы служить ключом HMAC-SHA256. Замените на `openssl rand -base64 48`; учтите, что смена секрета обесценивает все уже выданные токены — всем придётся войти заново |
| `create-admin` отказывает: «An active administrator already exists» | Работает как задумано — эта команда срабатывает только на базе вовсе без активного админа; заблокируйте/переназначьте существующего, либо удалите его (с учётом защиты основного администратора выше) |
| Backend Postgres: «connection refused» / таймаут при старте | Сервер проверяет подключение как часть валидации старта и завершается с кодом `78`, а не падает на первом запросе — проверьте хост/порт/сетевую доступность *изнутри* контейнера, если используете Compose |
| Admin-клиент показывает «Сервер недоступен» | Обычно проблема CORS или same-origin, если клиент обслуживается с другого хоста, чем API — см. [выше](#что-вы-разворачиваете) — либо сам процесс сервера действительно упал; проверьте `/healthz` напрямую |
| Все внезапно разлогинены | JWT-секрет изменился (рестарт с другим значением/файлом), либо у всех сессий был поднят `token_version` чем-то (смена пароля затрагивает только одну эту учётную запись, так что массовое разлогинивание указывает именно на секрет) |
| Батч приёма отклонён целиком с `413` | Батч превышает `--max-ingest-body-bytes` — поднимите лимит, либо пусть отправляющее приложение делит на батчи поменьше (`structured_log_remote_sync`, эталонный клиент, уже батчит по размеру — см. [Руководство разработчика](developer-guide.ru.md)) |

Во всех случаях, которых здесь нет, `--print-config` плюс собственный
диагностический лог сервера (временно `--log-level=debug`) — самый
быстрый способ понять, в чём дело: в конфигурации, в сети или это
повод завести issue.
