# Руководство контрибьютора

*Read in [English](contributor-guide.md).*

Для тех, кто пишет код *в* этом репозитории — в любом его пакете, не
только в `structured_log_server`. Если вы вместо этого интегрируете
своё приложение с уже работающей системой — см.
[Руководство разработчика](developer-guide.ru.md); оно для потребителей
системы, это — для тех, кто меняет саму систему.

Это руководство проводит вас от чистого чекаута до первого зелёного PR. Оно
не заменяет [AGENTS.md](../../AGENTS.md) — файл в корне репозитория
остаётся исчерпывающим, постоянно обновляемым справочником по
конвенциям этого workspace, каждой неочевидной ловушке, уже однажды
найденной, и полным разбором каждого пакета; читайте раздел про пакет,
который трогаете, перед нетривиальным изменением. Это руководство —
точка входа в него.

## Workspace одной картинкой

Монорепозиторий на [Melos](https://melos.invertase.dev/) +
[FVM](https://fvm.app/), пакеты сгруппированы по тому, чем они
являются, каждый перечислен по полному пути в
[melos.yaml](../../melos.yaml):

| Категория | Что там лежит |
|---|---|
| `emb/` | Библиотеки, предназначенные для **встраивания** в чужое приложение: `structured_log` (ядро логирования), его Flutter-скины просмотрщика логов (`structured_log_flutter`/`_material`/`_fluent`/`_cupertino`) и `structured_log_http` (отправляет логи на сервер) |
| `backend/` | Самостоятельные серверные процессы: `structured_log_server` |
| `frontend/` | Самостоятельные клиентские приложения с UI: `structured_log_admin_client` и его библиотека презентационных компонентов `structured_log_admin_ui` |
| `packages/` | Всё, что не подпадает ни под одну из трёх категорий выше: `structured_log_e2e`, сквозные тесты через всю систему |

У каждого пакета — свой `README.md`/`README.ru.md`; у нескольких есть
ещё `doc/ARCHITECTURE.md` — внутренний дизайн для контрибьюторов
(`emb/structured_log/doc/ARCHITECTURE.md` — эталонный пример).
[docs/architecture/](../architecture/) покрывает дизайн, общий для
`structured_log_server`/`structured_log_http`/`structured_log_admin_client`
вместе, — потому что для кросс-пакетного протокольного решения
собственная документация ни одного отдельного пакета не подходящее
место.

## Настройка окружения

```bash
# 1. Запиньте Flutter SDK, который использует этот workspace (см. .fvmrc)
#    — не "stable", а точную версию, чтобы она не «уплывала» между
#    сессиями сама по себе.
fvm install
fvm use

# 2. Установите сам melos (корневой pubspec.yaml существует только ради
#    этого — сам он не пакет из списка packages в melos.yaml).
dart pub get

# 3. Свяжите каждый пакет с каждым, от которого он зависит внутри этого
#    workspace (пишет pubspec_overrides.yaml на пакет; они в
#    .gitignore, перегенерировать можно этой же командой в любой момент).
dart run melos bootstrap
```

Нужен Dart/Flutter SDK (через FVM — не системная установка, пин
существует именно затем, чтобы у всех был один и тот же тулчейн) и, для
Postgres-тестов `structured_log_server` и поставляемого стенда
`deploy/`, — Docker.

**Пин CI и локальный пин независимы, и это известная ловушка.**
[.github/workflows/ci.yml](../../.github/workflows/ci.yml) использует
`dart-lang/setup-dart`/`subosito/flutter-action` на канале `stable`
напрямую, не FVM, — так что CI всегда гоняется на SDK, актуальном на
момент запуска job, а ваш локальный пин `.fvmrc` тем временем может
тихо отстать. `dart format` меняет вывод между версиями SDK, так что
устаревший локальный пин проявляется как расхождение `dart format
--set-exit-if-changed` между вашей машиной и CI на коде, который ни
одна из сторон на самом деле не переформатировала неправильно. Если
столкнулись с этим — `fvm use <версия-из-CI>` и заново `melos
bootstrap`, прежде чем считать проблему в своём коде.

Проверьте настройку:

```bash
dart run melos run analyze
dart run melos run test
```

Если `melos` установлен глобально в `PATH` и работает, обычный `melos
<cmd>` (без `dart run`) сработает так же — но если этот бинарник собран
против другого Dart SDK, чем запинен в этом workspace, предпочитайте
`dart run melos` (`dev_dependencies` корневого `pubspec.yaml` существуют
ровно для этого запасного пути).

## Повседневные команды

Запускаются из корня репозитория; Melos разводит каждую по пакетам:

```bash
dart run melos run analyze        # dart analyze, каждый пакет
dart run melos run format:check   # dart format --set-exit-if-changed, каждый пакет
dart run melos run format         # dart format (пишет), каждый пакет
dart run melos run lint           # analyze + format:check вместе
dart run melos run test           # test:dart + test:flutter (ниже)
dart run melos run test:e2e       # packages/e2e — НЕ часть `test`, см. ниже
dart run melos run generate       # build_runner для structured_log_server + structured_log_admin_client
```

`test` на деле — два шага под капотом (`test:dart` — обычный `dart
test` для чисто-Dart пакетов; `test:flutter` — `flutter test` для всего
на Flutter), разделены потому что используют разные test runner'ы, а не
потому что один из них опционален. `test:e2e` отдельно намеренно:
каждый кейс в `structured_log_e2e` поднимает `bin/server.dart`
настоящим OS-процессом (`dart run`-компиляция на каждый тестовый файл)
и требует уже существующего сгенерированного кода сервера и
admin-клиента — сначала `generate`.

Для одного пакета за раз — зайдите в него и пользуйтесь инструментом
напрямую, Melos — это удобство разводки, а не обязательное требование:

```bash
cd backend/structured_log_server
dart pub get
dart test                                    # всё, кроме тегированных наборов
dart test --exclude-tags integration --exclude-tags postgres   # быстрый внутренний цикл
dart test --tags integration                 # поднимает настоящий процесс сервера
dart test --tags postgres --concurrency=1    # нужен настоящий PostgreSQL — см. ниже
```

```bash
cd frontend/structured_log_admin_client
flutter test
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/user_flow_test.dart -d web-server --browser-name=chrome
```

### Кодогенерация

`structured_log_server` и `structured_log_admin_client` — два пакета, в
которых используется `build_runner` (`drift`/`freezed`/`json_serializable`,
плюс `shelf_router_generator`/`retrofit_generator` соответственно) —
осознанное, узкое исключение из в остальном действующей в этом
workspace конвенции «без магии, без кодогенерации» (см.
[architecture/README.md](../architecture/README.ru.md#принципы-повторяющиеся-во-всём-дизайне)).
Сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) **не коммитятся**
— ни один из двух пакетов не компилируется со свежего чекаута, пока не
запустить:

```bash
dart run melos run generate
# или внутри одного из двух пакетов:
dart run build_runner build --delete-conflicting-outputs
```

Запускайте это заново при любом изменении таблицы `drift`, модели
`freezed`, аннотации `@Route` или интерфейса `@RestApi` у `retrofit` —
устаревший сгенерированный файл падает громко (отсутствующий символ), а
не молча.

### Тесты, которым нужен настоящий PostgreSQL

У `structured_log_server` есть тег тестов `postgres`
(`dart_test.yaml`) для диалект-чувствительного пути кода
(`--db-backend=postgres`) — исключён из прогона по умолчанию, и ему
нужен живой инстанс плюс `--concurrency=1` (файлы этого тега делят одну
физическую базу без пер-файловой изоляции, которую всем остальным
тестам даёт SQLite'шный `NativeDatabase.memory()`, и портят друг другу
фикстуры при запуске вместе на дефолтной параллельности):

```bash
docker run -d --name pg-dev -p 5432:5432 \
  -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=structured_log_test postgres:16-alpine

STRUCTURED_LOG_TEST_POSTGRES_PASSWORD=dev \
  dart test --tags postgres --concurrency=1
```

CI гоняет этот же тег против сервис-контейнера GitHub Actions — про тот
же backend со стороны *эксплуатации*, если сюда привело именно это, см.
[operations/configuration.md](../operations/configuration.ru.md) и
[admin-guide.md](admin-guide.ru.md#kubernetes).

## Внесение изменения: OpenSpec — для поведения, обычный коммит — для остального

Этот репозиторий фиксирует нетривиальные проектные решения как
**OpenSpec-изменения** в [openspec/changes/](../../openspec/changes/) —
четыре документа: `proposal.md` (что и зачем), `design.md` (каждая
рассмотренная альтернатива и почему она отклонена), `specs/*.md`
(нормативные требования) и `tasks.md` (чек-лист реализации). Все четыре
написаны **на русском** (идентификаторы, флаги и код остаются как
есть). Нужен ли вашему изменению этот набор артефактов — первое, что
стоит выяснить, а не то, о чём вспоминают в конце:

- **Новая возможность или изменение существующего контракта** (новый
  эндпоинт, новая настройка конфигурации, выбор backend'а хранения,
  правило RBAC (role-based access control, управление доступом на
  основе ролей)) — сначала заведите OpenSpec-изменение. Скилл
  `openspec-new-change` разворачивает его каркас; `openspec-apply-change`
  проводит по `tasks.md` раздел за разделом по мере реализации;
  `openspec-archive-change` закрывает его после мёржа.
  [add-postgres-backend](../../openspec/changes/add-postgres-backend/) —
  полный, недавний пример, стоящий прочтения от начала до конца — от
  proposal до полностью отмеченного `tasks.md`, включая места, где
  исходный план оказался неверным и был пересмотрен против реальных
  фактов.
- **Багфикс, исправление документации, обновление зависимости, рефакторинг
  без изменения поведения** — достаточно обычного коммита; proposal/
  design/specs не нужны. Эти три продуктовых руководства (включая это) и
  раздел про развёртывание в Kubernetes добавлены именно так.

Если сомневаетесь, `openspec-onboard` (скилл в этом репозитории)
объясняет процесс с нуля; `openspec-explore` — способ только для
чтения посмотреть, что сейчас активно или уже заархивировано, ничего не
запуская.

## Git-конвенции

- **Сначала ветка, коммитить напрямую в `master` или `develop` нельзя.**
  Открывайте PR в `develop` (интеграционная ветка); `master` — релизы.
- **[Conventional Commits](https://www.conventionalcommits.org/)**:
  `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `perf:`, `test:`,
  `build:`, `ci:`, `revert:` — ломающее изменение получает `!` после
  типа или футер `BREAKING CHANGE:`. Это не только стиль: `melos
  version` читает эту историю, чтобы автоматически подобрать нужный
  semver-бамп каждого пакета, отталкиваясь от последнего тега вида
  `<package>-v<version>`.
- **`CHANGELOG.md` никогда не редактируется вручную.** Пишет его только
  `melos version` — не для добавления записи, и не для «уборки» после
  прогона, который его переформатировал. Это осознанное решение
  мейнтейнера, а не пробел.
- Каждый пакет версионируется независимо — своя линия тегов, свой
  changelog.

## Перед открытием PR

Одни и те же четыре проверки, каждый раз, зеркалят собственный
финальный чеклист [AGENTS.md](../../AGENTS.md):

1. `dart analyze` (или `flutter analyze`) — чисто, без предупреждений.
2. Тесты зелёные — набор самого пакета как минимум; прогоните `melos
   run test` по всему workspace, если изменение правдоподобно
   затрагивает другой пакет.
3. `dart format --set-exit-if-changed .` — отформатировано.
4. Если изменение затрагивает публичное поведение — собственные
   `README.md`/`README.ru.md` пакета обновлены под него — **кроме**
   `CHANGELOG.md`, который вручную не трогают никогда (выше).

CI ([.github/workflows/ci.yml](../../.github/workflows/ci.yml)) обязан
быть зелёным на каждой джобе перед мёржем PR — по джобе на
пакет-с-тестами, плюс `server` (наборы SQLite + integration +
PostgreSQL, тремя отдельными шагами, чтобы в логе было видно, какой
упал), `admin-client-flow` (вождение реальным браузером пути оператора,
не `flutter test` — ловит дефекты, которые харнесс с подставным вводом
структурно не может воспроизвести) и `e2e` (вся система, одно дерево
процессов, `packages/e2e`). Воспроизведите любую из них локально
командами из [«Повседневных команд»](#повседневные-команды) выше,
прежде чем пушить, — дешевле, чем круг через Actions.

## Дисциплина тестирования, которую стоит перенять

Две привычки, на которые этот репозиторий сильно опирается, — стоит
усвоить осознанно, а не подхватить со временем сами собой:

- **Мутационно проверяйте новый регресс-тест, прежде чем ему доверять.**
  Написав тест, который должен ловить конкретный баг, временно
  откатите фикс и убедитесь, что тест реально краснеет — затем верните
  фикс обратно. Тест, остающийся зелёным в обоих случаях, проверяет не
  то, что вы думаете. Так проверен почти каждый регресс-тест,
  добавленный за всю историю этого репозитория, а не изредка, как
  дополнительный шаг.
- **Тянитесь к настоящему инстансу перед большим рефакторингом, а не
  после.** Не один план в истории `design.md` этого репозитория
  начинался с утверждения документации, которое при проверке против
  реально работающего кода оказывалось неверным, — пойманное ранней
  проверкой, до того как сотни мест были тронуты на ложной предпосылке,
  а не найденное на полпути и откаченное. Когда план собирается
  тронуть много мест, потратьте пять минут на проверку его предпосылки
  против настоящей системы сначала.

## Куда дальше

- **[AGENTS.md](../../AGENTS.md)** — авторитетный, постоянно
  поддерживаемый справочник: неочевидное поведение каждого пакета,
  каждая ловушка тулчейна, уже однажды найденная, полный список команд,
  CI в деталях. Читайте раздел про пакет, который меняете, перед чем-то
  крупнее тривиального фикса.
- **[docs/architecture/](../architecture/)** — почему дизайн системы
  `structured_log_server` устроен именно так, по темам, с отсылкой к
  конкретным решениям.
- **[openspec/changes/](../../openspec/changes/)** — полная запись
  решений по каждому нетривиальному изменению, активные и
  заархивированные; лучшее место увидеть, *как* решение было принято,
  а не только чем оно закончилось.
- Собственный `README.md` каждого пакета и (где есть)
  `doc/ARCHITECTURE.md`.
