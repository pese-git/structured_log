# Руководство контрибьютора

*Read in [English](contributor-guide.md).*

Для тех, кто пишет код *в* этом репозитории — в любом его пакете, не
только в `structured_log_server`. Если вы вместо этого интегрируете
своё приложение с уже работающей системой — см.
[Руководство разработчика](developer-guide.ru.md): оно для тех, кто
пользуется системой, а это — для тех, кто меняет её саму.

Это руководство проведёт вас от чистого чекаута до первого зелёного PR. Оно
не заменяет [AGENTS.md](../../AGENTS.md): этот файл в корне репозитория
остаётся исчерпывающим, постоянно обновляемым справочником по
конвенциям workspace, по всем уже найденным неочевидным ловушкам и
по устройству каждого пакета. Перед нетривиальным изменением прочитайте
в нём раздел про пакет, который меняете; это руководство лишь подводит
к нему.

## Workspace в общих чертах

Монорепозиторий на [Melos](https://melos.invertase.dev/) +
[FVM](https://fvm.app/); пакеты сгруппированы по назначению, и
каждый перечислен по полному пути в
[melos.yaml](../../melos.yaml):

| Категория | Что там лежит |
|---|---|
| `emb/` | Библиотеки, предназначенные для **встраивания** в чужое приложение: `structured_log` (ядро логирования), его Flutter-скины просмотрщика логов (`structured_log_flutter`/`_material`/`_fluent`/`_cupertino`) и `structured_log_remote_sync` (отправляет логи на сервер) |
| `backend/` | Самостоятельные серверные процессы: `structured_log_server` |
| `frontend/` | Самостоятельные клиентские приложения с UI: `structured_log_admin_client` и его библиотека презентационных компонентов `structured_log_admin_ui` |
| `packages/` | Всё, что не подпадает ни под одну из трёх категорий выше: `structured_log_e2e`, сквозные тесты через всю систему |

У каждого пакета — свой `README.md`/`README.ru.md`; у нескольких есть
ещё `doc/ARCHITECTURE.md` — внутренний дизайн для контрибьюторов
(`emb/structured_log/doc/ARCHITECTURE.md` — эталонный пример).
В [docs/architecture/](../architecture/) описан дизайн, общий для
`structured_log_server`/`structured_log_remote_sync`/`structured_log_admin_client`,
потому что решению о протоколе между пакетами не место в документации
какого-то одного из них.

## Настройка окружения

```bash
# 1. Запиньте Flutter SDK, который использует этот workspace (см. .fvmrc)
#    — не "stable", а точную версию, чтобы она не «уплывала» между
#    сессиями сама по себе.
fvm install
fvm use

# 2. Установите сам melos (корневой pubspec.yaml существует только ради
#    этого — сам он не пакет из списка packages в melos.yaml).
dart pub get

# 3. Свяжите каждый пакет с каждым, от которого он зависит внутри этого
#    workspace (пишет pubspec_overrides.yaml на пакет; они в
#    .gitignore, перегенерировать можно этой же командой в любой момент).
dart run melos bootstrap
```

Нужен Dart/Flutter SDK (через FVM, а не системная установка: версия
закреплена именно для того, чтобы у всех был один и тот же тулчейн) и, для
Postgres-тестов `structured_log_server` и поставляемого стенда
`deploy/`, — Docker.

**Пин CI и локальный пин независимы, и это известная ловушка.**
[.github/workflows/ci.yml](../../.github/workflows/ci.yml) использует
`dart-lang/setup-dart`/`subosito/flutter-action` на канале `stable`
напрямую, без FVM, — так что CI всегда работает на SDK, последнем на
момент запуска джобы, а ваш локальный пин `.fvmrc` тем временем может
незаметно отстать. Вывод `dart format` меняется от версии к версии SDK,
поэтому устаревший локальный пин проявляется как расхождение `dart format
--set-exit-if-changed` между вашей машиной и CI на коде, который на
самом деле ни одна из сторон не отформатировала неправильно. Если
столкнулись с этим — `fvm use <версия-из-CI>` и заново `melos
bootstrap`, прежде чем искать проблему в своём коде.

Проверьте настройку:

```bash
dart run melos run analyze
dart run melos run test
```

Если `melos` установлен глобально в `PATH` и работает, обычный `melos
<cmd>` (без `dart run`) сработает так же. Но если этот бинарник собран
под другую версию Dart SDK, чем закреплена в этом workspace, используйте
`dart run melos` (`dev_dependencies` корневого `pubspec.yaml` нужны
именно для этого запасного варианта).

## Повседневные команды

Запускаются из корня репозитория; Melos выполняет каждую в нужных пакетах:

```bash
dart run melos run analyze        # dart analyze, каждый пакет
dart run melos run format:check   # dart format --set-exit-if-changed, каждый пакет
dart run melos run format         # dart format (пишет), каждый пакет
dart run melos run lint           # analyze + format:check вместе
dart run melos run test           # test:dart + test:flutter (ниже)
dart run melos run test:e2e       # packages/e2e — НЕ часть `test`, см. ниже
dart run melos run generate       # build_runner для structured_log_server + structured_log_admin_client
```

На самом деле `test` состоит из двух шагов (`test:dart` — обычный `dart
test` для пакетов на чистом Dart; `test:flutter` — `flutter test` для всего
на Flutter). Разделены они потому, что используют разные test runner'ы, а
не потому, что один из них необязателен. `test:e2e` вынесен отдельно
намеренно: каждый кейс в `structured_log_e2e` поднимает `bin/server.dart`
настоящим OS-процессом (`dart run`-компиляция на каждый тестовый файл)
и требует уже существующего сгенерированного кода сервера и
admin-клиента — сначала `generate`.

Чтобы работать с одним пакетом, зайдите в его каталог и вызывайте
инструмент напрямую: Melos лишь упрощает запуск по пакетам и не
обязателен:

```bash
cd backend/structured_log_server
dart pub get
dart test                                    # всё, кроме тегированных наборов
dart test --exclude-tags integration --exclude-tags postgres   # быстрый внутренний цикл
dart test --tags integration                 # поднимает настоящий процесс сервера
dart test --tags postgres --concurrency=1    # нужен настоящий PostgreSQL — см. ниже
```

```bash
cd frontend/structured_log_admin_client
flutter test
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/user_flow_test.dart -d web-server --browser-name=chrome
```

### Кодогенерация

`structured_log_server` и `structured_log_admin_client` — два пакета, в
которых используется `build_runner` (`drift`/`freezed`/`json_serializable`,
плюс `shelf_router_generator`/`retrofit_generator` соответственно). Это
осознанное и узкое исключение из правила «без магии, без
кодогенерации», которое в остальном действует в этом workspace (см.
[architecture/README.md](../architecture/README.ru.md#принципы-повторяющиеся-во-всём-дизайне)).
Сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) **не коммитятся**
— ни один из двух пакетов не компилируется со свежего чекаута, пока не
запустить:

```bash
dart run melos run generate
# или внутри одного из двух пакетов:
dart run build_runner build --delete-conflicting-outputs
```

Запускайте это заново при любом изменении таблицы `drift`, модели
`freezed`, аннотации `@Route` или интерфейса `@RestApi` у `retrofit`;
устаревший сгенерированный файл заметен сразу (появляется ошибка об
отсутствующем символе), а не остаётся незамеченным.

### Тесты, которым нужен настоящий PostgreSQL

У `structured_log_server` есть тег тестов `postgres`
(`dart_test.yaml`) для кода, зависящего от диалекта
(`--db-backend=postgres`). Он исключён из прогона по умолчанию, и ему
нужен работающий инстанс плюс `--concurrency=1`: файлы этого тега делят
одну физическую базу, без изоляции на уровне файла, которую всем остальным
тестам даёт SQLite'шный `NativeDatabase.memory()`, и при параллельном
запуске по умолчанию портят друг другу фикстуры:

```bash
docker run -d --name pg-dev -p 5432:5432 \
  -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=structured_log_test postgres:16-alpine

STRUCTURED_LOG_TEST_POSTGRES_PASSWORD=dev \
  dart test --tags postgres --concurrency=1
```

CI прогоняет этот же тег против сервис-контейнера GitHub Actions. Если
вас интересует тот же backend со стороны *эксплуатации*, см.
[operations/configuration.md](../operations/configuration.ru.md) и
[admin-guide.md](admin-guide.ru.md#kubernetes).

## Внесение изменения: OpenSpec — для поведения, обычный коммит — для остального

Нетривиальные проектные решения в этом репозитории оформляются как
**OpenSpec-изменения** в [openspec/changes/](../../openspec/changes/) —
четыре документа: `proposal.md` (что и зачем), `design.md` (каждая
рассмотренная альтернатива и почему она отклонена), `specs/*.md`
(нормативные требования) и `tasks.md` (чек-лист реализации). Все четыре
написаны **на русском** (идентификаторы, флаги и код остаются как
есть). Нужен ли вашему изменению этот набор артефактов, стоит выяснить
в самом начале, а не вспоминать об этом в конце:

- **Новая возможность или изменение существующего контракта** (новый
  эндпоинт, новая настройка конфигурации, выбор backend'а хранения,
  правило RBAC (role-based access control, управление доступом на
  основе ролей)) — сначала заведите OpenSpec-изменение. Скилл
  `openspec-new-change` разворачивает его каркас; `openspec-apply-change`
  проводит по `tasks.md` раздел за разделом по мере реализации;
  `openspec-archive-change` закрывает его после мёржа.
  [add-postgres-backend](../../openspec/changes/archive/2026-10-01-add-postgres-backend/) —
  полный недавний пример, который стоит прочитать целиком: от proposal
  до полностью отмеченного `tasks.md`, включая места, где исходный план
  оказался неверным и был пересмотрен по реальным фактам.
- **Багфикс, исправление документации, обновление зависимости, рефакторинг
  без изменения поведения** — достаточно обычного коммита; proposal/
  design/specs не нужны. Эти три продуктовых руководства (включая это) и
  раздел про развёртывание в Kubernetes добавлены именно так.

Если сомневаетесь, `openspec-onboard` (скилл в этом репозитории)
объясняет процесс с нуля, а `openspec-explore` позволяет, ничего не
меняя, посмотреть, что сейчас открыто или уже заархивировано.

## Git-конвенции

- **Сначала ветка, коммитить напрямую в `master` или `develop` нельзя.**
  Открывайте PR в `develop` (интеграционная ветка); `master` — релизы.
- **[Conventional Commits](https://www.conventionalcommits.org/)**:
  `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `perf:`, `test:`,
  `build:`, `ci:`, `revert:`; ломающее изменение помечается `!` после
  типа или футером `BREAKING CHANGE:`. Дело не только в стиле: `melos
  version` читает эту историю, чтобы автоматически подобрать нужный
  semver-бамп каждого пакета, начиная от последнего тега вида
  `<package>-v<version>`.
- **`CHANGELOG.md` никогда не редактируется вручную.** Пишет его только
  `melos version`; руками его не трогают ни ради новой записи, ни ради
  «уборки» после прогона, который его переформатировал. Это осознанное решение
  мейнтейнера, а не пробел в процессе.
- Каждый пакет версионируется независимо — своя линия тегов, свой
  changelog.

## Перед открытием PR

Каждый раз выполняйте одни и те же четыре проверки — они повторяют
финальный чеклист из [AGENTS.md](../../AGENTS.md):

1. `dart analyze` (или `flutter analyze`) — чисто, без предупреждений.
2. Тесты зелёные — как минимум набор самого пакета; если изменение может
   затронуть другой пакет, прогоните `melos run test` по всему
   workspace.
3. `dart format --set-exit-if-changed .` — отформатировано.
4. Если изменение затрагивает публичное поведение, обновлены
   `README.md`/`README.ru.md` самого пакета — но **не**
   `CHANGELOG.md`, который вручную не трогают никогда (см. выше).

Перед мёржем PR CI ([.github/workflows/ci.yml](../../.github/workflows/ci.yml))
должен быть зелёным на каждой джобе: по джобе на каждый пакет с тестами,
плюс `server` (наборы SQLite + integration + PostgreSQL тремя отдельными
шагами, чтобы в логе было видно, какой упал), `admin-client-flow` (путь
оператора в настоящем браузере, а не `flutter test`: так ловятся дефекты,
которые харнесс с подставным вводом в принципе не может воспроизвести) и
`e2e` (вся система, одно дерево процессов, `packages/e2e`). Прежде чем
пушить, воспроизведите любую из них локально командами из
[«Повседневных команд»](#повседневные-команды) выше — это дешевле, чем
круг через Actions.

## Дисциплина тестирования, которую стоит перенять

На двух привычках во многом держится этот репозиторий; их стоит усвоить
сознательно, а не ждать, пока они придут сами со временем:

- **Проверяйте новый регресс-тест мутацией, прежде чем ему доверять.**
  Написав тест, который должен ловить конкретный баг, временно
  откатите исправление и убедитесь, что тест действительно краснеет, —
  затем верните исправление. Тест, который зелёный в обоих случаях,
  проверяет не то, что вы думаете. Так проверен почти каждый регресс-тест
  за всю историю этого репозитория — это правило, а не редкий
  дополнительный шаг.
- **Сверяйтесь с настоящим инстансом до большого рефакторинга, а не
  после.** Не один план в истории `design.md` этого репозитория
  начинался с утверждения из документации, которое при сверке с
  реально работающим кодом оказывалось неверным. Ошибку ловила ранняя
  проверка — до того, как на ложной предпосылке переписали сотни мест, а
  не на полпути, когда пришлось бы всё откатывать. Если план затрагивает
  много мест, сначала потратьте пять минут и сверьте его исходное
  допущение с настоящей системой.
