# Руководство разработчика

*Read in [English](developer-guide.md).*

Для тех, кто пишет код, работающий с `structured_log_server` снаружи:
отправляет в него логи приложения или программно запрашивает их и
следит за новыми записями. Если сервер вам не нужен вообще (только `structured_log`
и, по желанию, просмотрщик внутри собственного Flutter-приложения) —
см. [Руководство по внедрению](embedding-guide.ru.md), самостоятельный
аналог этого руководства. Если вы разворачиваете сам сервер — см.
[Руководство администратора / DevOps](admin-guide.ru.md); если вы
пользуетесь admin-клиентом изо дня в день — см.
[Руководство пользователя](user-guide.ru.md).

Есть два способа интеграции; второй требует знать о системе чуть больше,
чем первый:

1. **Доставить логи на сервер** — Dart-приложение использует
   [`structured_log`](#логирование-с-structured_log) плюс
   [`structured_log_remote_sync`](#отправка-логов-на-сервер); любое другое
   приложение обращается напрямую к
   [эндпоинту приёма по HTTP](#из-любого-другого-языка).
2. **Читать логи с сервера программно** —
   [запрос](#запрос-логов) и
   [живая лента](#подписка-на-живую-ленту-из-кода) через тот же HTTP API,
   которым пользуется admin-клиент.

## Логирование с `structured_log`

Базовая библиотека ([`emb/structured_log`](../../emb/structured_log/),
[опубликована на pub.dev](https://pub.dev/packages/structured_log)) —
обычное структурированное логирование для Dart, без сторонних
runtime-зависимостей кроме `meta`; всё остальное в этом руководстве
построено на ней:

```dart
import 'package:structured_log/structured_log.dart';

void main() {
  final log = getLogger();
  log.info('user_login', context: {'user_id': 42, 'ip': '127.0.0.1'});
}
```

`bind()` привязывает контекст к логгеру, не меняя исходный (возвращает
новый экземпляр). `withCorrelation()` привязывает фиксированный
типизированный набор полей корреляции (`session_id`, `request_id`,
`connection_generation`, `tool_call_id`, `message_id`, `operation_id`).
Эти поля без дополнительной настройки понимают и фильтры сервера, и
просмотрщик логов admin-клиента. Используйте их вместо произвольных
ключей контекста с тем же смыслом: тогда запрос можно проследить целиком
по одному из этих id, а не по имени поля, которое совпадает лишь по
договорённости:

```dart
final log = getLogger().withCorrelation(requestId: 'req-42');
log.info('request_started');
log.error('request_failed', context: {'status': 500});
```

Шесть уровней, от менее к более серьёзному: `trace` < `debug` < `info` <
`warning` < `error` < `critical`. Полный API — процессоры,
маршрутизация по нескольким sink'ам, файловый/ротируемый вывод — в
[`emb/structured_log/README.md`](../../emb/structured_log/README.md).

## Отправка логов на сервер

### Из Dart-приложения: `structured_log_remote_sync`

[`structured_log_remote_sync`](../../emb/structured_log_remote_sync/) — обычная
`OutputFunction`: она подключается к `LogSink`, не требуя менять то, как
вы вызываете `structured_log` выше, и никогда не задерживает вызывающий
код — записи ставятся в очередь и отправляются фоновым future. До
переименования он публиковался как `structured_log_http` (с `HttpLogOutput`);
тот пакет больше не развивается и только перенаправляет сюда.

```dart
import 'package:structured_log/structured_log.dart';
import 'package:structured_log_remote_sync/structured_log_remote_sync.dart';

final output = RemoteSyncLogOutput(
  serverUrl: 'https://logs.example.com',
  projectSecretKey: 'slk_...',    // от owner/admin, см. ниже
);

StructlogConfiguration.configure(
  sinks: [LogSink(name: 'server', output: output)],
);

getLogger().info('startup', context: {'version': '1.4.0'});

// Дождитесь перед выходом из процесса — иначе записи в очереди могут потеряться.
await output.flushed;
```

Секретный ключ проекта получают один раз; это делает тот, у кого есть
доступ `owner`/`admin`, в admin-клиенте
(**Группы → проект → Секретные ключи → Создать**) или через
`POST /v1/projects/:id/secret-keys` — значение показывается ровно один
раз, при создании; храните его так же, как любой другой секрет
приложения (переменная окружения, смонтированный файл секрета —
никогда не коммитьте в систему контроля версий).

Что пакет делает сам:

- **Батчинг** по размеру или таймауту, что наступит раньше.
- **Повтор с экспоненциальной задержкой** при сетевых
  сбоях/таймаутах/5xx, но не при 4xx: на отозванный ключ сервер всегда
  будет отвечать 401, так что повтор только задержит записи, стоящие за
  ним в очереди.
- **`Retry-After` соблюдается**, и пауза останавливает весь отправщик, а
  не один отклонённый батч: если лимитер ответил «не раньше T», это
  относится ко всему соединению. Соблюдается до `maxRetryAfter` (по умолчанию 5 минут) —
  заголовок приходит от прокси перед API, сам сервер приём логов не
  ограничивает.
- **Вытеснение из буфера**: если сервер какое-то время недоступен,
  буфер ограниченного размера в памяти первыми вытесняет *самые старые*
  неотправленные записи — с неограниченной очередью сбой логирования
  превратился бы в сбой приложения, а это в корне неверно.
- **Сообщение об ошибках**: ошибки пишутся в `stderr`, а не выбрасываются
  исключениями — что бы ни происходило внутри пакета, сам вызов
  `log.info(...)` упасть не может.

Полный справочник параметров:
[`emb/structured_log_remote_sync/README.md`](../../emb/structured_log_remote_sync/README.md).

Во время разработки держите консольный sink рядом с серверным: у каждого
свой фильтр, так что локально вы видите всё, а на сервер отправляете,
например, только `info` и выше:

```dart
StructlogConfiguration.configure(sinks: [
  LogSink(name: 'console', output: coloredConsoleOutput),
  LogSink(name: 'server', output: output, minLevel: LogLevel.info),
]);
```

### Из любого другого языка

Использовать `structured_log` вовсе не обязательно: `POST /v1/logs` —
обычный HTTP-эндпоинт. Аутентифицируйтесь секретным ключом проекта,
отправьте JSON-массив записей — и всё:

```bash
curl -X POST https://logs.example.com/v1/logs \
  -H "Authorization: Bearer slk_..." \
  -H "Content-Type: application/json" \
  -d '[
    {"event": "payment_failed", "level": "error",
     "timestamp": "2026-03-05T14:29:59.981Z",
     "category": "checkout", "order_id": "ord_44821"},
    {"event": "request_completed", "level": "info",
     "timestamp": "2026-03-05T14:30:00.100Z"}
  ]'
```

Запись — произвольный JSON-объект. Фиксированный смысл несут только
`event`, `level` и `timestamp` (`level` должен быть одним из
`trace`/`debug`/`info`/`warning`/`error`/`critical`). Всё остальное —
`category`, `logger`, шесть полей корреляции и любой произвольный ключ —
необязательно и в ответах на последующие запросы возвращается точно
таким, каким было отправлено, байт в байт. **Не отправляйте `id`,
`project_id` или `received_at`** — эти три имени зарезервированы под
поля, которые сервер проставляет в ответах, и запись, содержащая
любое из них, отклоняется (только эта запись, не весь батч).

Ответ всегда `202`, даже если отклонены некоторые или все записи: сам
запрос выполнен успешно, а результат по каждой записи — в теле ответа:

```json
{
  "accepted": 8,
  "rejected": [
    {"index": 3, "error": "validation_error", "message": "level: must be one of trace, debug, info, warning, error, critical"},
    {"index": 7, "error": "quota_exceeded", "message": "project max_entries limit reached"}
  ]
}
```

Проверяйте `rejected`, если вам важны отказы по отдельным записям:
клиент, который смотрит только на HTTP-статус, их не заметит. Этот эндпоинт отвечает
ошибкой верхнего уровня только в трёх случаях: неверный/неизвестный/
отозванный секретный ключ (`401`), сам проект заблокирован
(`403 project_blocked`, весь батч, ничего не оценивается), либо тело
запроса превышает настроенный лимит размера (`413`, весь батч).

**Отправляйте записи батчами, а не по одной за запрос.** Минимального
размера батча нет, но у каждого запроса есть фиксированные накладные
расходы, сколько бы записей в нём ни было. Приложение, которое пишет
больше нескольких строк лога в секунду, должно накапливать их и
отправлять вместе; на Dart это автоматически делает
`structured_log_remote_sync`.

## Запрос логов

`GET /v1/logs` требует **access-токен** человека (а не секретный ключ
проекта: эти два креденшела не взаимозаменяемы, и если предъявить
эндпоинту не тот, он ответит `401` — так же, как если бы креденшела не
было вовсе). Как получить токен — см.
[«Вход от имени пользователя»](#вход-от-имени-пользователя) ниже.

```bash
curl -G https://logs.example.com/v1/logs \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -d project_id=7 \
  -d level=warning \
  -d from=2026-03-05T00:00:00Z \
  -d limit=50
```

Обязателен ровно один из `project_id`/`group_id` (запрос по группе
охватывает все проекты в ней). Среди необязательных фильтров — `level`
(минимальный, включительно), `category`/`logger` (точное совпадение),
`from`/`to` (диапазон по `timestamp`), любое из шести полей корреляции
(точное совпадение), `q` (полнотекстовый, по событию и содержимому) и
`context.<key>=<value>` для точного совпадения по любому произвольному
полю, которое вы отправили, например `context.order_id=ord_44821`.

**Пагинация**: `{"items": [...], "next_cursor": "<строка, nullable>"}`
— записи идут от новых к старым по `id`; чтобы получить следующую
страницу, передайте `next_cursor` в параметре `cursor`. `next_cursor: null`
означает конец списка. Общего счётчика `total` нет: при таких объёмах
подсчёт всего результата обошёлся бы дороже, чем стоит сама цифра.
`limit` по умолчанию равен 50; если запросить больше 200, значение молча
уменьшается до 200, а не отклоняется.

Полный справочник параметров и ответа:
[api/http-api.md](../api/http-api.md#get-v1logs),
[api/models.md#logentry](../api/models.md#logentry).

## Подписка на живую ленту из кода

`GET /v1/logs/stream` принимает те же фильтры, что `GET /v1/logs` выше, и
ещё `since_id`, который закрывает промежуток между последней показанной
страницей и моментом открытия подписки (передайте в нём последний
полученный `id`: сервер дошлёт пропущенное, а затем будет присылать новые
записи по мере появления, без потерь и без повторов). Это Server-Sent
Events, обычный HTTP-ответ с потоковым телом — без рукопожатия WebSocket и
без отдельного протокола:

```bash
curl -N https://logs.example.com/v1/logs/stream \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -G -d project_id=7 -d level=warning
```

```text
: connected

id: 918273
event: log
data: {"event": "payment_failed", "level": "error", ...}

: ping
```

В `data:` приходит одна запись [`LogEntry`](../api/models.md#logentry) в
виде JSON — в той же форме, что возвращает `GET /v1/logs`. Комментарии `: ping`
приходят каждые `--sse-heartbeat-interval-seconds` (по умолчанию 25с)
как keep-alive — игнорируйте строки, начинающиеся с `:`.
**Авторизация перепроверяется на каждом heartbeat, а не только при
подключении**: если ваш доступ отозван или проект заблокировали, пока
соединение открыто, вы увидите терминальный кадр `event: end`
(`data: {"reason": "token_revoked"}` или `"project_blocked"`), а не
просто замолчавшее соединение. Обрабатывайте этот кадр так же, как
`401`/`403`, пришедший вне обычного ответа, и при необходимости
переподключайтесь со свежим токеном.

**Почему не браузерный `EventSource`:** он не умеет отправлять
заголовок `Authorization`, а токен в query-строке URL осел бы в логах
прокси и сервера. Поэтому браузерному клиенту нужно читать поток
через `fetch`/`ReadableStream` (или аналогичный HTTP-клиент с поддержкой потоков)
с явно заданным заголовком, тем же способом, что
`structured_log_admin_client`, а не нативным API `EventSource`.

## Вход от имени пользователя

Management/query API (всё, кроме `POST /v1/logs`, где нужен секретный
ключ проекта) работает на короткоживущих access-токенах JWT
(JSON Web Token), которые выдаёт стандартный OAuth2-эндпоинт
password-grant (`POST /v1/auth/token`). Этот эндпоинт настолько точно
повторяет формат token-эндпоинта Keycloak, что с ним работает готовая
клиентская библиотека OAuth2, но никакого Keycloak или другого
провайдера идентичности за ним на самом деле нет:

```bash
# Form-encoded (RFC 6749), не JSON — единственный эндпоинт в этом API,
# отступающий от общего JSON-конверта, специально ради совместимости с OAuth2-клиентами.
curl -X POST https://logs.example.com/v1/auth/token \
  -d grant_type=password -d username=alice -d password='...'
```

```json
{"access_token": "eyJ...", "refresh_token": "...", "token_type": "Bearer", "expires_in": 900, "refresh_expires_in": 2592000}
```

Срок жизни access-токена намеренно короткий (15 минут; refresh-токен
действует 30 дней — оба значения фиксированы и пока не вынесены в
настройки). Когда запрос получает `401`, обновите токен, а не
запрашивайте пароль заново:

```bash
curl -X POST https://logs.example.com/v1/auth/token \
  -d grant_type=refresh_token -d refresh_token=$REFRESH_TOKEN
```

Если сервер так настроен, он дополнительно возвращает refresh-токен
как cookie `HttpOnly` и сообщает об этом полем
`refresh_token_cookie_set: true`. **Для вас при этом не меняется
ничего.** В теле по-прежнему есть `refresh_token`, поле, которое вы
присылаете, по-прежнему важнее cookie на каждом эндпоинте, принимающем
токен, а клиент, который не хранит cookie (`curl`, скрипт, любой
не-браузерный клиент), может о ней вовсе не знать. Cookie нужна
браузерному клиенту, ведь его `localStorage` может прочитать любой скрипт
на том же origin. Поле же названо по тому, что сделал сервер, а не по
тому, где лежит токен: вызывающий без `Origin` тоже получает cookie,
хотя никогда ею не воспользуется.

Чтобы явно завершить сессию, вызовите `DELETE /v1/auth/token` (RFC 7009:
эндпоинт всегда отвечает `200`, был токен действителен или нет, так что
по ответу нельзя проверить чужую сессию). **Самостоятельного
создания учётной записи нет** — каждую создаёт администратор или owner
группы (`POST /v1/users`); стройте интеграцию с расчётом на это, а не на
сценарий регистрации, поскольку `POST /v1/auth/register` в этом
развёртывании не существует (см.
[«Что не реализовано»](#что-не-реализовано) ниже).

Только что созданная или сброшенная администратором учётная запись
помечена `must_change_password: true` — любой эндпоинт, кроме
`POST /v1/auth/change-password` (и небольшого списка исключений для
поддержания сессии и самоудаления), отвечает
`403 must_change_password`, пока флаг не снят. Если вы автоматизируете
создание учётных записей, предусмотрите этот шаг: новая учётная запись
сначала годится только для смены собственного пароля.

Что важно не упустить, автоматизируя этот шаг: успешный
`POST /v1/auth/change-password` отзывает refresh-токены учётной записи.
Если передать свой токен в `current_refresh_token`, сессия, которой вы
пользуетесь, сохранится после смены пароля. Если не передать, ваш же
скрипт выйдет из системы вместе со всеми остальными сессиями: иначе
сервер не может понять, какая сессия обращается к нему, — вторым
способом была бы cookie, а у скрипта её нет. `keep_other_sessions: true`
отменяет отзыв полностью; это разумно для скрипта, который заводит
учётную запись, в которую ещё никто не входил.

Полный контракт, включая механизм отзыва `token_version` и формы
ошибок: [architecture/auth.md](../architecture/auth.ru.md),
[api/errors.md](../api/errors.md).

## Вызов API управления

Каждому действию UI admin-клиента — созданию групп/проектов/команд,
ротации секретных ключей, выдаче ролей, управлению пользователями,
чтению журнала аудита — соответствует один документированный
HTTP-эндпоинт; полный список — в
[api/http-api.md](../api/http-api.md). Несколько вещей, которые стоит
знать, если вы автоматизируете заведение ресурсов скриптами:

```bash
# Создать проект внутри группы, которой вы владеете/администрируете
curl -X POST https://logs.example.com/v1/groups/3/projects \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "checkout-service", "retention_days": 30, "max_entries": 1000000}'

# Создать для него секретный ключ (значение возвращается только в этот раз)
curl -X POST https://logs.example.com/v1/projects/7/secret-keys \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"label": "ci-pipeline"}'

# Выдать пользователю доступ на чтение к нему
curl -X POST https://logs.example.com/v1/role-assignments \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"subject_type": "user", "subject_id": 42, "role": "user", "scope_type": "project", "scope_id": 7}'
```

`subject_type` — `user` или `team`; `scope_type` — `group` или
`project` — полный набор см. в
[api/http-api.md](../api/http-api.md#post-v1role-assignments).

Правила ролей совпадают с
[Руководством пользователя](user-guide.ru.md#что-позволяет-ваша-роль):
`admin` имеет доступ ко всему; `owner` может действовать внутри групп,
которыми владеет (и может выдавать там `owner`/`user`, но никогда
`admin`); `user` — только чтение. В токене вызывающего записаны его
роли на момент выдачи токена — см.
[architecture/auth.md](../architecture/auth.ru.md), если вы пишете
что-то, что должно учитывать, *когда именно* изменение прав
вступает в силу для уже выданного токена.

## Обработка ошибок

Каждый эндпоинт, кроме token-эндпоинта, использует один JSON-конверт:

```json
{"error": "validation_error", "message": "человеко-читаемый текст", "details": {"...": "опционально, специфично для кода"}}
```

Только token-эндпоинт отвечает в форме RFC 6749 §5.2
(`{"error": "invalid_grant", "error_description": "..."}`) ради
совместимости с OAuth2-клиентами — не рассчитывайте на `error`/`message`
именно на этом эндпоинте. Ответ `429 too_many_requests` (ограничение
частоты, только на auth-эндпоинтах) приходит со стандартным заголовком
`Retry-After` и означает, что действие действительно не выполнено, —
повторить его после указанного интервала безопасно. Полный каталог —
каждая пара статус/код и где она встречается:
[api/errors.md](../api/errors.md).

## Встраивание просмотрщика логов во Flutter-приложение

Это не связано с `structured_log_remote_sync` выше и работает полностью
локально, без сервера; три готовых скина описаны в
[Руководстве по внедрению](embedding-guide.ru.md#2-headless-ядро-просмотрщика-structured_log_flutter).
Можно использовать что-то одно, оба механизма вместе (показывать те же
записи в локальном просмотрщике приложения *и* отправлять их на сервер)
или ни один из них.

## Ограничение частоты и бережное отношение к серверу

Ограничение частоты действует только на эндпоинты аутентификации
(вход, смена пароля и подобные чувствительные действия) —
`POST /v1/logs` ограничивают квота проекта и его секретный ключ, а не
частота запросов, а management-эндпоинты — права доступа по ролям, а не
счётчик запросов. Как часто вызывать `GET /v1/logs` или открывать поток,
ограничивают только возможности вашей инфраструктуры и ресурсы сервера.
Разумно собирайте записи в батчи (см. выше), а если нужны обновления,
близкие к реальному времени, держите одно долгоживущее соединение
`GET /v1/logs/stream` вместо частого опроса `GET /v1/logs` в цикле.

## Что не реализовано

Этот раздел — для полноты: следующие возможности описаны в других
документах дизайна этого репозитория, и вы можете на них наткнуться.
Самостоятельная регистрация (`POST /v1/auth/register`), самостоятельное
восстановление пароля по email и обязательное подтверждение email входят
в изначально предложенный дизайн и встречаются в
[architecture/auth.md](../architecture/auth.ru.md) и (пока) в
[api/http-api.md](../api/http-api.md), но в работающем сервере нет ни
одной из трёх — таких маршрутов не существует. Каждую
учётную запись создаёт администратор или owner группы, и забытый
пароль сбрасывается тем же способом (`PATCH /v1/users/:id`), а не
восстанавливается самим пользователем.
