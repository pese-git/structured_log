# Руководство разработчика

*Read in [English](developer-guide.md).*

Для тех, кто пишет внешний по отношению к `structured_log_server` код —
отправляет в него логи приложения или программно запрашивает их и
следит за ними. Если сервер вам не нужен вообще (только `structured_log`
и, по желанию, просмотрщик внутри собственного Flutter-приложения) —
см. [Руководство по внедрению](embedding-guide.ru.md), самостоятельный
аналог этого руководства. Если вы разворачиваете сам сервер — см.
[Руководство администратора / DevOps](admin-guide.ru.md); если вы
пользуетесь admin-клиентом изо дня в день — см.
[Руководство пользователя](user-guide.ru.md).

Два способа интеграции, примерно по возрастанию того, сколько нужно
знать о системе:

1. **Доставить логи на сервер** — Dart-приложение использует
   [`structured_log`](#логирование-с-structured_log) плюс
   [`structured_log_remote_sync`](#отправка-логов-на-сервер); любое другое
   приложение обращается напрямую к
   [эндпоинту приёма по HTTP](#из-любого-другого-языка).
2. **Читать логи обратно программно** —
   [запрос](#запрос-логов) и
   [живая лента](#живая-лента-программно) через тот же HTTP API,
   которым пользуется admin-клиент.

## Логирование с `structured_log`

Базовая библиотека ([`emb/structured_log`](../../emb/structured_log/),
[опубликована на pub.dev](https://pub.dev/packages/structured_log)) —
обычное структурированное логирование для Dart, без сторонних
runtime-зависимостей кроме `meta`, и на ней строится всё остальное в
этом руководстве:

```dart
import 'package:structured_log/structured_log.dart';

void main() {
  final log = getLogger();
  log.info('user_login', context: {'user_id': 42, 'ip': '127.0.0.1'});
}
```

`bind()` привязывает контекст к логгеру неизменяемо (возвращает новый
экземпляр); `withCorrelation()` привязывает фиксированный, типизированный
набор полей корреляции (`session_id`, `request_id`,
`connection_generation`, `tool_call_id`, `message_id`, `operation_id`),
которые нативно понимают и фильтры сервера, и просмотрщик логов
admin-клиента — предпочитайте их произвольным ключам контекста с тем
же смыслом, чтобы запрос можно было проследить целиком по одному из
этих id, а не по совпавшему по соглашению имени поля:

```dart
final log = getLogger().withCorrelation(requestId: 'req-42');
log.info('request_started');
log.error('request_failed', context: {'status': 500});
```

Шесть уровней, от менее к более серьёзному: `trace` < `debug` < `info` <
`warning` < `error` < `critical`. Полный API — процессоры,
мульти-sink роутинг, файловый/ротируемый вывод — в
[`emb/structured_log/README.md`](../../emb/structured_log/README.md).

## Отправка логов на сервер

### Из Dart-приложения: `structured_log_remote_sync`

[`structured_log_remote_sync`](../../emb/structured_log_remote_sync/) — обычная
`OutputFunction` — подключается к `LogSink` без изменения того, как вы
вызываете `structured_log` выше, и никогда не блокирует вызывающий
код: записи ставятся в очередь и отправляются фоновым future. До
переименования он публиковался как `structured_log_http` (с `HttpLogOutput`);
тот пакет больше не развивается и только перенаправляет сюда.

```dart
import 'package:structured_log/structured_log.dart';
import 'package:structured_log_remote_sync/structured_log_remote_sync.dart';

final output = RemoteSyncLogOutput(
  serverUrl: 'https://logs.example.com',
  projectSecretKey: 'slk_...',    // от owner/admin, см. ниже
);

StructlogConfiguration.configure(
  sinks: [LogSink(name: 'server', output: output)],
);

getLogger().info('startup', context: {'version': '1.4.0'});

// Дождитесь перед выходом из процесса — иначе записи в очереди могут потеряться.
await output.flushed;
```

Получение секретного ключа проекта — одноразовая настройка, которую
делает тот, у кого есть доступ `owner`/`admin`, в admin-клиенте
(**Группы → проект → Секретные ключи → Создать**) или через
`POST /v1/projects/:id/secret-keys` — значение показывается ровно один
раз, при создании; храните его так же, как любой другой секрет
приложения (переменная окружения, смонтированный файл секрета —
никогда не коммитьте в систему контроля версий).

Что даётся из коробки:

- **Батчинг** по размеру или таймауту, что наступит раньше.
- **Повтор с экспоненциальной задержкой** при сетевых
  сбоях/таймаутах/5xx, никогда при 4xx — на отозванный ключ сервер будет
  отвечать 401 всегда, так что повтор только задержит то, что стоит за
  ним в очереди.
- **`Retry-After` соблюдается**, и пауза держит весь отправщик, а не
  один отклонённый батч: лимитер, сказавший «не раньше T», говорит о
  соединении. Соблюдается до `maxRetryAfter` (по умолчанию 5 минут) —
  заголовок приходит от прокси перед API, сам сервер приём логов не
  ограничивает.
- **Вытеснение из буфера**: ограниченный в памяти буфер вытесняет
  *самые старые* неотправленные записи первыми, если сервер недоступен
  какое-то время — неограниченная очередь превратила бы простой
  логирования в простой приложения, что в корне неверно.
- **Сообщение об ошибках**: ошибки уходят в `stderr`, а не бросаются
  исключением — что бы ни делал этот пакет, сам вызов `log.info(...)`
  упасть не может.

Полный справочник параметров:
[`emb/structured_log_remote_sync/README.md`](../../emb/structured_log_remote_sync/README.md).

Держите консольный sink рядом с серверным во время разработки — каждый
фильтрует независимо, так что вы видите всё локально, отправляя на
сервер только `info` и выше, например:

```dart
StructlogConfiguration.configure(sinks: [
  LogSink(name: 'console', output: coloredConsoleOutput),
  LogSink(name: 'server', output: output, minLevel: LogLevel.info),
]);
```

### Из любого другого языка

Использовать `structured_log` вовсе не обязательно — `POST /v1/logs` —
обычный HTTP-эндпоинт. Аутентифицируйтесь секретным ключом проекта,
отправьте JSON-массив записей — и всё:

```bash
curl -X POST https://logs.example.com/v1/logs \
  -H "Authorization: Bearer slk_..." \
  -H "Content-Type: application/json" \
  -d '[
    {"event": "payment_failed", "level": "error",
     "timestamp": "2026-03-05T14:29:59.981Z",
     "category": "checkout", "order_id": "ord_44821"},
    {"event": "request_completed", "level": "info",
     "timestamp": "2026-03-05T14:30:00.100Z"}
  ]'
```

Запись — произвольный JSON-объект. Фиксированный смысл несут только
`event`, `level` и `timestamp` (`level` обязан быть одним из
`trace`/`debug`/`info`/`warning`/`error`/`critical`); всё остальное —
`category`, `logger`, шесть полей корреляции и любой произвольный ключ
— опционально и в каждом последующем ответе на запрос возвращается
в точности таким, каким было отправлено, байт в байт. **Не отправляйте `id`,
`project_id` или `received_at`** — эти три имени зарезервированы под
поля, которые сервер проставляет в ответах, и запись, содержащая
любое из них, отклоняется (только эта запись, не весь батч).

Ответ всегда `202`, даже если часть или все записи отклонены — сам
запрос выполнился успешно; результат по каждой записи — в теле ответа:

```json
{
  "accepted": 8,
  "rejected": [
    {"index": 3, "error": "validation_error", "message": "level: must be one of trace, debug, info, warning, error, critical"},
    {"index": 7, "error": "quota_exceeded", "message": "project max_entries limit reached"}
  ]
}
```

Проверяйте `rejected`, если вам важны отдельные отказы — клиент,
смотрящий только на HTTP-статус, их пропустит. Этот эндпоинт отвечает
ошибкой верхнего уровня только в трёх случаях: неверный/неизвестный/
отозванный секретный ключ (`401`), сам проект заблокирован
(`403 project_blocked`, весь батч, ничего не оценивается), либо тело
запроса превышает настроенный лимит размера (`413`, весь батч).

**Батчите, не отправляйте по одной записи за запрос.** Искусственного
минимального размера батча нет, но у каждого запроса есть
фиксированные накладные расходы независимо от того, сколько записей он
несёт — приложение, генерирующее больше нескольких строк лога в
секунду, должно накапливать их и отправлять вместе — именно это
`structured_log_remote_sync` делает автоматически, если вы на Dart.

## Запрос логов

`GET /v1/logs`, аутентифицируется **access-токеном** человека (не
секретным ключом проекта — эти два креденшела не взаимозаменяемы, и
если эндпоинту предъявить не тот, он отвечает `401`, точно как на
отсутствующий). Как получить токен — см.
[«Аутентификация как человек»](#аутентификация-как-человек) ниже.

```bash
curl -G https://logs.example.com/v1/logs \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -d project_id=7 \
  -d level=warning \
  -d from=2026-03-05T00:00:00Z \
  -d limit=50
```

Обязателен ровно один из `project_id`/`group_id` (запрос по группе
охватывает все проекты в ней); опциональные фильтры включают `level`
(минимальный, включительно), `category`/`logger` (точное совпадение),
`from`/`to` (диапазон по `timestamp`), любое из шести полей корреляции
(точное совпадение), `q` (полнотекстовый, по событию и содержимому) и
`context.<key>=<value>` для точного совпадения по любому произвольному
полю, которое вы отправили, например `context.order_id=ord_44821`.

**Пагинация**: `{"items": [...], "next_cursor": "<строка, nullable>"}`
— сначала новые по `id`; передайте `next_cursor` обратно как `cursor`
для следующей страницы. `next_cursor: null` означает конец — общего
счётчика `total` нет (при таком масштабе подсчёт полного результата
обошёлся бы дороже, чем стоит сама цифра). `limit` по умолчанию 50 и молча
приводится к 200, если запросить больше, а не отклоняется.

Полный справочник параметров и ответа:
[api/http-api.md](../api/http-api.md#get-v1logs),
[api/models.md#logentry](../api/models.md#logentry).

## Живая лента программно

`GET /v1/logs/stream` — те же фильтры, что у `GET /v1/logs` выше, плюс
`since_id`, чтобы бесшовно перекрыть промежуток между последней
отрисованной страницей и моментом открытия подписки (запросите его с
последним увиденным `id`; сервер докатит пропущенное, затем продолжит
вживую, без потерь и без дублей). Это Server-Sent Events, обычный
HTTP-ответ со стримящимся телом — никакого рукопожатия WebSocket,
никакого отдельного протокола:

```bash
curl -N https://logs.example.com/v1/logs/stream \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -G -d project_id=7 -d level=warning
```

```text
: connected

id: 918273
event: log
data: {"event": "payment_failed", "level": "error", ...}

: ping
```

`data:` несёт одну запись [`LogEntry`](../api/models.md#logentry) как
JSON — ту же форму, что возвращает `GET /v1/logs`. Комментарии `: ping`
приходят каждые `--sse-heartbeat-interval-seconds` (по умолчанию 25с)
как keep-alive — игнорируйте строки, начинающиеся с `:`.
**Авторизация перепроверяется на каждом heartbeat, а не только при
подключении**: если ваш доступ отозван или проект заблокировали, пока
соединение открыто, вы увидите терминальный кадр `event: end`
(`data: {"reason": "token_revoked"}` или `"project_blocked"`), а не
тихо замолчавшее соединение — относитесь к этому так же, как к
внеполосному `401`/`403`, и при необходимости переподключайтесь со
свежим токеном.

**Почему не браузерный `EventSource`:** он не умеет отправлять
заголовок `Authorization`, а токен в query-строке URL осел бы в логах
прокси и сервера — так что браузерному клиенту нужно читать поток
через `fetch`/`ReadableStream` (или эквивалентный стримящий HTTP-клиент)
с явно заданным заголовком, тем же способом, что
`structured_log_admin_client`, а не нативным API `EventSource`.

## Аутентификация как человек

Management/query API (всё, кроме `POST /v1/logs`, где нужен секретный
ключ проекта) работает на короткоживущих access-токенах JWT
(JSON Web Token), выдаваемые через стандартный OAuth2-эндпоинт
password-grant (`POST /v1/auth/token`). По форме этот эндпоинт повторяет
token-эндпоинт Keycloak — настолько близко, что с ним может работать
готовая клиентская библиотека OAuth2, — но никакого Keycloak или
другого провайдера идентичности за ним на самом деле нет:

```bash
# Form-encoded (RFC 6749), не JSON — единственный эндпоинт в этом API,
# отступающий от общего JSON-конверта, специально ради совместимости с OAuth2-клиентами.
curl -X POST https://logs.example.com/v1/auth/token \
  -d grant_type=password -d username=alice -d password='...'
```

```json
{"access_token": "eyJ...", "refresh_token": "...", "token_type": "Bearer", "expires_in": 900, "refresh_expires_in": 2592000}
```

Access-токен короткоживущий намеренно (15 минут; refresh-токен живёт 30
дней — оба значения фиксированы, сейчас не вынесены в настройку) —
когда запрос отвечает `401`, обновляйте его, а не запрашивайте пароль
заново:

```bash
curl -X POST https://logs.example.com/v1/auth/token \
  -d grant_type=refresh_token -d refresh_token=$REFRESH_TOKEN
```

Если сервер так настроен, он дополнительно возвращает refresh-токен
как cookie `HttpOnly` и сообщает об этом полем
`refresh_token_cookie_set: true`. **Для вас при этом не меняется
ничего.** Тело по-прежнему несёт `refresh_token`, присланное вами поле
по-прежнему имеет приоритет над cookie на каждом эндпоинте, который токен
принимает, а клиент, не хранящий cookie — `curl`, скрипт, что угодно не
браузерное, — может о ней вовсе не знать. Она нужна
браузерному клиенту, чей `localStorage` читает любой скрипт на его
origin; а поле названо по тому, что сделал сервер, а не по тому, где
лежит токен, — потому что вызывающий без `Origin` получает cookie,
которой никогда не воспользуется.

Отзовите сессию явно через `DELETE /v1/auth/token` (RFC 7009 — всегда
отвечает `200`, независимо от того, был ли токен действителен, так что ответ
нельзя использовать, чтобы прощупать чужую сессию). **Самостоятельного
создания учётной записи нет** — каждую создаёт администратор или owner
группы (`POST /v1/users`); рассчитывайте интеграцию на это, а не на
сценарий регистрации, поскольку `POST /v1/auth/register` в этом
развёртывании не существует (см.
[«Что не реализовано»](#что-не-реализовано) ниже).

Только что созданная или сброшенная администратором учётная запись
помечена `must_change_password: true` — любой эндпоинт, кроме
`POST /v1/auth/change-password` (и небольшого списка исключений для
поддержания сессии и самоудаления), отвечает
`403 must_change_password`, пока флаг не снят. Если вы автоматизируете
создание учётных записей, заложите этот шаг в план, а не считайте
свежую учётную запись сразу пригодной для чего-либо кроме смены своего
пароля.

Что важно не упустить, автоматизируя этот шаг: успешный
`POST /v1/auth/change-password` отзывает refresh-токены учётной записи.
Передайте свой токен в `current_refresh_token` — и сессия, которой вы
пользуетесь, переживёт смену; не передадите — ваш же скрипт выйдет из
системы вместе со всем остальным, потому что другого способа понять,
какая сессия спрашивает, у сервера нет — вторым способом была бы
cookie, а у скрипта её нет. `keep_other_sessions: true`
отменяет отзыв целиком — разумно для скрипта, который заводит учётную
запись, куда ещё никто не входил.

Полный контракт, включая механизм отзыва `token_version` и формы
ошибок: [architecture/auth.md](../architecture/auth.ru.md),
[api/errors.md](../api/errors.md).

## Вызов management API

Всё, что делает UI admin-клиента — создание групп/проектов/команд,
ротация секретных ключей, выдача ролей, управление пользователями,
чтение журнала аудита — это один документированный HTTP-эндпоинт на
каждое действие, полный список в
[api/http-api.md](../api/http-api.md). Несколько вещей, о которых
стоит знать, если вы скриптуете провижининг:

```bash
# Создать проект внутри группы, которой вы владеете/администрируете
curl -X POST https://logs.example.com/v1/groups/3/projects \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "checkout-service", "retention_days": 30, "max_entries": 1000000}'

# Создать для него секретный ключ (значение возвращается только в этот раз)
curl -X POST https://logs.example.com/v1/projects/7/secret-keys \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"label": "ci-pipeline"}'

# Выдать пользователю доступ на чтение к нему
curl -X POST https://logs.example.com/v1/role-assignments \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"subject_type": "user", "subject_id": 42, "role": "user", "scope_type": "project", "scope_id": 7}'
```

`subject_type` — `user` или `team`; `scope_type` — `group` или
`project` — полный набор см. в
[api/http-api.md](../api/http-api.md#post-v1role-assignments).

Правила ролей совпадают с
[Руководством пользователя](user-guide.ru.md#что-позволяет-ваша-роль):
`admin` имеет доступ ко всему; `owner` может действовать внутри групп,
которыми владеет (и может выдавать там `owner`/`user`, но никогда
`admin`); `user` — только чтение. Токен вызывающего несёт снимок его
действующих ролей на момент выдачи — см.
[architecture/auth.md](../architecture/auth.ru.md), если вы пишете
что-то, что должно учитывать, *когда именно* изменение прав
вступает в силу для уже выданного токена.

## Обработка ошибок

Каждый эндпоинт, кроме token-эндпоинта, использует один JSON-конверт:

```json
{"error": "validation_error", "message": "человеко-читаемый текст", "details": {"...": "опционально, специфично для кода"}}
```

Только token-эндпоинт отвечает в форме RFC 6749 §5.2
(`{"error": "invalid_grant", "error_description": "..."}`) ради
совместимости с OAuth2-клиентами — не рассчитывайте на `error`/`message`
именно на этом эндпоинте. `429 too_many_requests` (ограничение
частоты, только на auth-эндпоинтах) несёт стандартный заголовок
`Retry-After` и означает, что действие в самом деле не выполнилось —
повторить после указанного интервала безопасно. Полный каталог, каждая
пара статус/код и где она встречается:
[api/errors.md](../api/errors.md).

## Встраивание живого просмотрщика во Flutter-приложение

Не связано с `structured_log_remote_sync` выше и полностью локально, без
сервера — три готовых скина см. в
[Руководстве по внедрению](embedding-guide.ru.md#2-headless-ядро-просмотрщика-structured_log_flutter).
Можно использовать один, другой, оба вместе (дублировать те же записи
в локальный просмотрщик приложения *и* отправлять их на сервер) или ни
того, ни другого.

## Ограничение частоты и бережное отношение к серверу

Ограничение частоты действует только на эндпоинты аутентификации
(вход, смена пароля и подобные чувствительные действия) —
`POST /v1/logs` управляется квотой проекта и его секретным ключом, а
не частотой запросов, а management-эндпоинты — доступом по ролям, а не
счётчиком запросов. Ограничения на то, как часто можно вызывать
`GET /v1/logs` или открывать поток, сверх того, что выдержит ваша
собственная инфраструктура и ресурсы сервера, нет — батчите приём
разумно (выше) и предпочитайте одно долгоживущее соединение
`GET /v1/logs/stream` опросу `GET /v1/logs` в плотном цикле, если вам
нужны обновления, близкие к реальному времени.

## Что не реализовано

Упомянуто для полноты: эти возможности описаны в других документах
дизайна этого репозитория, и вы можете на них наткнуться:
самостоятельная регистрация (`POST /v1/auth/register`),
самостоятельное восстановление пароля по email и обязательное
подтверждение email — часть изначально предложенного дизайна и
встречаются в [architecture/auth.md](../architecture/auth.ru.md) и
(пока) в [api/http-api.md](../api/http-api.md), но ни одного из трёх
нет в работающем сервере — такого маршрута не существует. Каждую
учётную запись создаёт администратор или owner группы, и забытый
пароль сбрасывается тем же способом (`PATCH /v1/users/:id`), а не
восстанавливается самим пользователем.
