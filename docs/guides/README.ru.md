# Руководства

*Read in [English](README.md).*

Пять продуктовых руководств по `structured_log`: часть — про
**самостоятельное** использование, часть — про использование **вместе
с self-hosted сервером** (это различие объясняет
[docs/README.ru.md](../README.ru.md)), и ещё одно — про вклад в сам
репозиторий. Каждое — по задачам: *как этим пользоваться*, для одного
из тех, кто реально этим занимается, а не *почему всё устроено именно
так* (это остальная часть [docs/](../README.md) — запись архитектуры и
дизайна, для тех, кто разбирается во внутреннем устройстве системы или
проверяет его):

**Самостоятельно — без сервера:**

| Руководство | Для кого | На какой вопрос отвечает |
|---|---|---|
| [Руководство по внедрению](embedding-guide.ru.md) | Тот, кому нужно структурированное логирование — и, по желанию, просмотрщик логов внутри приложения — в собственном Dart/Flutter-приложении, без всякого сервера | «Как добавить `structured_log` (и, может быть, живой просмотр логов внутри приложения) в своё приложение?» |

**Вместе с self-hosted сервером:**

| Руководство | Для кого | На какой вопрос отвечает |
|---|---|---|
| [Руководство пользователя](user-guide.ru.md) | Любой, кто вошёл в admin-клиент — читает, ищет и следит за логами в реальном времени, а для `owner`/`admin` — управляет группами, проектами и доступом | «Как найти нужный лог? Что мне доступно с моей ролью?» |
| [Руководство администратора / DevOps](admin-guide.ru.md) | Тот, кто разворачивает, настраивает и эксплуатирует сервер | «Как это запустить, поддерживать в рабочем состоянии и восстановить, если что-то пошло не так?» |
| [Руководство разработчика](developer-guide.ru.md) | Тот, кто пишет код *против* self-hosted сервера снаружи него — отправляет логи из приложения, вызывает HTTP API напрямую или запрашивает/следит за логами программно | «Как доставить логи моего приложения в `structured_log_server` и как читать их обратно программно?» |

**Вклад в этот репозиторий:**

| Руководство | Для кого | На какой вопрос отвечает |
|---|---|---|
| [Руководство контрибьютора](contributor-guide.ru.md) | Тот, кто пишет код *в* этом репозитории — в любом пакете, самостоятельном или серверном | «Как поднять окружение разработки и провести изменение так, как этого ждёт этот репозиторий?» |

Каждое руководство самодостаточно — начните с того, которое
соответствует вашей роли, а не с этой страницы. Там, где руководству
нужна точная деталь на уровне протокола (каждое поле, каждый код
ошибки), оно ссылается на справочную документацию, а не повторяет её:
[api/http-api.md](../api/http-api.md),
[api/models.md](../api/models.md), [api/errors.md](../api/errors.md),
[operations/configuration.md](../operations/configuration.md).

## Что реально, а чего нет

Каждая возможность, описанная в этих руководствах, существует в
работающей системе на момент написания — проверено по фактической
таблице маршрутов и CLI, а не по более раннему черновику дизайна. Три
потока, описанные в [architecture/auth.md](../architecture/auth.md) и
[api/http-api.md](../api/http-api.md), здесь намеренно **не**
освещаются, потому что не реализованы: самостоятельная регистрация,
самостоятельное восстановление пароля по email и подтверждение email.
Те документы описывают весь изначально предложенный дизайн, включая
части, которые пока не сделаны; эти руководства описывают продукт таким,
какой он есть сегодня. Каждую учётную запись создаёт администратор, и
забытый пароль сбрасывает тоже он — см. раздел
[«Управление пользователями»](admin-guide.ru.md#управление-пользователями)
руководства администратора.
