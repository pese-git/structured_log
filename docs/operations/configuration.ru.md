# Конфигурация

*Read in [English](configuration.md).*

Всё, что `structured_log_server` читает при запуске, откуда именно и что
происходит, когда прочитанное ему не нравится. Обоснование решений —
decision 47 в
[design.md](../../openspec/changes/add-structured-log-server/design.md),
контракт поведения —
[specs/log-server-config](../../openspec/changes/add-structured-log-server/specs/log-server-config/spec.md).

## Три источника, один порядок

**Аргумент командной строки → переменная окружения → значение по
умолчанию.** Флаг всегда выигрывает у переменной, переменная — у
встроенного дефолта. Конфигурация читается один раз при старте и не
меняется, пока процесс жив: перечитывания по SIGHUP нет, эндпоинта
«изменить настройки» нет — любое изменение означает рестарт.

Имена выводятся друг из друга механически, поэтому в таблице ниже одна
строка на параметр, а не две:

```
--http-port  ↔  STRUCTURED_LOG_HTTP_PORT
--db-path    ↔  STRUCTURED_LOG_DB_PATH
```

kebab-case во флаге, те же слова в SCREAMING_SNAKE с префиксом
`STRUCTURED_LOG_` в окружении. Пустая переменная считается
**незаданной** — в `docker-compose` пустое значение получается слишком
легко, чтобы трактовать его как осмысленное.

## Секреты не ездят в аргументах

Флага `--jwt-secret` не существует. Секреты принимаются **только** из
окружения либо из файла, путь к которому задан в `_FILE`-переменной, —
той же конвенцией, что уже используют Docker и Kubernetes для
смонтированных секретов:

```bash
STRUCTURED_LOG_JWT_SECRET=...                      # напрямую
STRUCTURED_LOG_JWT_SECRET_FILE=/run/secrets/jwt    # из смонтированного файла
```

Та же конвенция применялась бы к паролю SMTP, будь отправка email
реализована (пока нет — см. таблицу «Справочник» ниже); она уже
применяется к `STRUCTURED_LOG_DB_POSTGRES_PASSWORD` и к
`STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD` — паролю первого администратора
на пустой базе.

Аргументы процесса видны в `ps` любому пользователю машины, оседают в
истории shell и в логах супервизора — поэтому флага нет вовсе, а не
«есть, но с предупреждением». Задать обе формы одного секрета — это
**ошибка конфигурации**, а не молчаливый приоритет: на практике такое
сочетание означает недописанную миграцию с одного способа на другой, и
тихий выбор победителя прячет её до первых странностей с токенами.
Завершающий перевод строки в файле отбрасывается, так что
`echo secret > file` хранит ровно то, что набрано.

**JWT-секрет обязателен и никогда не генерируется автоматически.**
Сервер, придумывающий секрет при старте, молча инвалидирует все выданные
токены на каждом рестарте: оператор видит не понятный отказ при запуске,
а необъяснимые разлогинивания в проде.

## Ничего не стартует, пока всё не проверено

Конфигурация разбирается и проверяется **до** открытия порта и до
создания файла базы данных. Все проблемы сообщаются разом — три неверных
значения обнаруживаются за один запуск, а не за три, — и процесс
завершается с кодом **`78`** (`EX_CONFIG` из `sysexits.h`), отличным от
кода рантайм-сбоя: systemd, Docker-restart-policy или Kubernetes по нему
отличают «рестарт не поможет» от «упало, стоит попробовать ещё раз».

Две осознанные асимметрии:

- **Неизвестный флаг останавливает запуск** — `--htp-port` — это опечатка,
  и именно такие опечатки CLI и должен ловить.
- **Неизвестная переменная `STRUCTURED_LOG_*` только предупреждает** —
  окружение контейнера принадлежит не только нам, и падать из-за чужой
  переменной недопустимо. Но и молчать нельзя: `STRUCTURED_LOG_PROT=9000`
  иначе стоил бы оператору часа поисков «почему он игнорирует порт».

Значения разбираются строго: булевы принимают `true/false/1/0/yes/no`
(без учёта регистра) и ничего больше — `…=off` это ошибка, а не тихий
`false`, который выключил бы защиту, считавшуюся включённой. Длительности
и размеры — целые числа с единицей **в имени**
(`--access-token-ttl-seconds`, `--audit-retention-days`,
`--max-batch-bytes`), а не строки вида `30m`/`10MB`: это ещё один
маленький язык со своими неоднозначностями.

## Как посмотреть, что сервер взял на самом деле

```bash
dart run bin/server.dart --print-config
```

печатает каждый параметр с итоговым значением **и источником**
(`cli` / `env` / `default`) и выходит с кодом `0`, ничего не запуская.
Секреты показываются как `***` плюс источник — этого достаточно, чтобы
убедиться, что секрет подхвачен оттуда, откуда ожидалось, и ничего
сверх. Это прямой ответ на самый частый вопрос эксплуатации: *почему
сервер работает не с теми настройками, которые я задал?*

`--help` порождается из тех же описаний параметров, что использует
парсер, поэтому разойтись с реальным набором опций он не может.

## Какие настройки нужны какой команде

Не каждая настройка нужна каждой подкоманде. Например, `create-admin`
([auth.md](../architecture/auth.ru.md)) нужен только путь к базе — не
стоит блокировать его на JWT-секрете, которым он не пользуется.
Настройки автосоздания администратора (`--bootstrap-admin-username`,
`STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD`) читает только обычный запуск
сервера, и ни одна из них не обязательна: незаданный пароль означает
просто, что он будет сгенерирован.

## Файл базы данных

Заданы жёстко и не настраиваются — записаны здесь, потому что определяют цену сбоя и отката. Применимо только при `--db-backend=sqlite` (по умолчанию); для другого backend'а — раздел «PostgreSQL» ниже.

- **Режим WAL, `synchronous=NORMAL`.** Закоммиченная запись переживает падение *процесса*; при потере питания *машиной* могут пропасть последние несколько коммитов. База при этом не портится ни в том, ни в другом случае. `FULL` (значение SQLite по умолчанию) делал бы fsync на каждой пачке приёма.
- **`busy_timeout` 5 секунд.** Второй процесс на том же файле — `create-admin`, запущенный при работающем сервере, — дожидается конца записи, а не падает сразу.
- **Версия схемы.** Сборка, запущенная на базе, записанной **более новой** схемой, отказывается стартовать с сообщением, называющим обе версии, а не читает таблицы, которых не понимает. После неудачного деплоя нужно выкатить новую версию или восстановить резервную копию, сделанную до обновления. Более старые базы обновляются на месте при старте.

## PostgreSQL

`--db-backend=postgres` заменяет движок хранения на управляемый
оператором сервер PostgreSQL — осознанная альтернатива дефолтному
SQLite-файлу, а не его замена. Ничего наблюдаемого через HTTP API между
двумя вариантами не меняется; выбор чисто эксплуатационный (обоснование
решения — [add-postgres-backend](../../openspec/changes/add-postgres-backend/design.md)).

- **Подключение, а не путь к файлу**: `--db-postgres-host`/`-port`/`-database`/`-username`
  плюс секрет `STRUCTURED_LOG_DB_POSTGRES_PASSWORD`/`…_FILE` (та же
  конвенция смонтированного файла, что у JWT-секрета). Все четыре —
  хост/база/пользователь/пароль — обязательны при выбранном backend'е,
  проверяются при старте, как и любая другая настройка.
- **Один пул, а не два.** Разделение чтения и записи у SQLite
  (`--db-read-pool-size`) существует, чтобы обойти ограничение
  «один файл — один писатель»; у MVCC PostgreSQL такого ограничения нет,
  поэтому чтение и запись делят один пул размером `--db-postgres-pool-size`
  (по умолчанию `10`). `--db-read-pool-size` при этом backend'е
  игнорируется — заданный отличным от дефолта, он только предупреждает
  при старте, так же как неизвестная переменная `STRUCTURED_LOG_*`.
- **TLS включён по умолчанию.** `--db-postgres-ssl-mode` по умолчанию
  `require` (шифрование есть, но сертификат сервера не проверяется —
  обычный случай для управляемого Postgres за собственной сетью
  провайдера). `verify-full` — когда важна проверка сертификата,
  `disable` — для локальной среды разработки вовсе без TLS.
- **Тюнинг уровня `PRAGMA` выше не применяется** и не имеет здесь
  аналога — WAL и `busy_timeout` существуют, чтобы обойти
  однопользовательский файл SQLite, а не то, что нужно PostgreSQL.
- **Старт отказывает быстро, так же как при плохом `--db-path`.**
  Недоступный хост или неверные учётные данные ловятся проверкой
  соединения до открытия порта, с выходом `78` — а не сбоем в рантайме
  на первом запросе.
- **Вне периметра:** встроенного пути перевода существующей SQLite-базы
  в PostgreSQL (или наоборот) нет. Backend выбирается один раз, на
  пустой базе, при первом развёртывании.

## Примеры

```bash
# Первый старт: достаточно пути к базе и JWT-секрета — первый
# администратор создаётся автоматически, со сгенерированным временным
# паролем, однократно выведенным в лог старта
STRUCTURED_LOG_JWT_SECRET=$(openssl rand -hex 32) \
  dart run bin/server.dart --db-path /data/logs.db
```

```bash
# Разработка: всё флагами, секрет из окружения
STRUCTURED_LOG_JWT_SECRET=dev-only-secret \
  dart run bin/server.dart --db-path ./dev.db --http-port 8080
```

```bash
# Контейнер: настройки из окружения, секрет из смонтированного файла
docker run \
  -e STRUCTURED_LOG_DB_PATH=/data/logs.db \
  -e STRUCTURED_LOG_HTTP_PORT=8080 \
  -e STRUCTURED_LOG_JWT_SECRET_FILE=/run/secrets/jwt \
  -e STRUCTURED_LOG_AUTH_EVENT_RETENTION_DAYS=90 \
  -e STRUCTURED_LOG_TRUSTED_PROXY_HOPS=1 \
  -v /srv/logs:/data -v /srv/secrets/jwt:/run/secrets/jwt:ro \
  structured-log-server
```

```bash
# Разовое переопределение: то же окружение, другой порт
dart run bin/server.dart --http-port 9090
```

```bash
# Против PostgreSQL вместо дефолтного SQLite-файла
STRUCTURED_LOG_JWT_SECRET=$(openssl rand -hex 32) \
STRUCTURED_LOG_DB_POSTGRES_PASSWORD=... \
  dart run bin/server.dart \
  --db-backend postgres \
  --db-postgres-host db.internal --db-postgres-database structured_log \
  --db-postgres-username structured_log
```

