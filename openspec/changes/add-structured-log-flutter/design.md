## Context

`structured_log` сейчас — flat single-package репозиторий; Melos уже подключён, но, по [AGENTS.md](AGENTS.md), используется только для скриптов (analyze/format/test), а не для оркестрации нескольких пакетов. Пакет `structured_log` уже опубликован на pub.dev (0.2.0), имена `structured_log_flutter`/`structured_log_material` на момент написания свободны.

UI-направление для Material-скина уже проработано визуально: макеты списка, развёрнутой записи (bottom sheet) и двух вариантов empty-state («логов ещё нет» / «нет записей по фильтру») в светлой и тёмной теме собраны в canvas Claude Design — [Log Viewer UI Concepts](https://claude.ai/code/artifact/400091b3-da51-4f73-a1fb-2ce779515de0) (там же черновые макеты для Cupertino/Fluent, оставленные вне рамок этого change). `design.md` опирается на эти макеты как на источник требований к UI, не переизобретая их заново.

## Goals / Non-Goals

**Goals:**
- Дать Flutter-приложениям, использующим `structured_log`, in-app просмотрщик логов, не нарушая принцип нулевых runtime-зависимостей самого `structured_log`.
- Отделить headless-логику (буферизация, фильтрация, поиск) от конкретной дизайн-системы, чтобы Cupertino/Fluent-скины в будущем переиспользовали её без дублирования.
- Довести Material-скин до состояния «можно реально использовать в приложении», а не до макета.
- Не менять публичное поведение, версию и релизный процесс `structured_log`.

**Non-Goals:**
- Реализация `structured_log_cupertino` / `structured_log_fluent` — только макеты, реализация в отдельных будущих change.
- DevTools-расширение.
- Перехват ошибок через `FlutterError.onError`/`PlatformDispatcher.onError`.
- Публикация новых пакетов на pub.dev в стабильную версию — эта change доводит их до рабочего состояния в репозитории; решение о публикации — отдельно, за мейнтейнером.

## Decisions

1. **Monorepo на Melos с плоской раскладкой пакетов в корне репозитория** (`structured_log/`, `structured_log_flutter/`, `structured_log_material/`), пакеты перечислены явным списком по имени в `melos.yaml` — по образцу уже существующего у того же автора [cherrypick](https://github.com/pese-git/cherrypick), где используется тот же стек (Melos + FVM + OpenSpec).
   Альтернативы:
   - Отдельный репозиторий для `structured_log_flutter`/`structured_log_material`. Отклонено: усложняет синхронизацию с изменениями API `structured_log`, требует дублирования части CI/тулинга.
   - Вложенная раскладка `packages/<name>/` с glob-манифестом (`packages: [packages/**]`) — изначально рассматривалась как вариант, поскольку это распространённый паттерн в экосистеме Dart/Flutter (например, `flutter/packages`). Отклонена в пользу плоской раскладки ради единообразия с `cherrypick`: у автора уже есть рабочая, проверенная конвенция на том же тулинге, и переключение контекста между проектами дешевле, чем формальное преимущество вложенности (визуальное отделение пакетов от `doc/`/`.github/`/`openspec/`) — а эту неоднозначность `cherrypick` и так решает явным списком пакетов в `melos.yaml`.

2. **Headless/skin-разделение: `structured_log_flutter` не импортирует Material/Cupertino/Fluent.** `LogViewerController` — конкретный `ChangeNotifier`, а не абстрактный интерфейс/DI-контракт.
   Альтернатива — абстрактный `LogViewerRenderer`, который каждый скин имплементирует. Отклонено: неидиоматично для Flutter (виджеты и так композируемы), лишняя индирекция без практической пользы при одном первом скине.

3. **Формат данных записи: переиспользуется `Map<String, dynamic>` из `structured_log` напрямую**, без отдельной типизированной модели (`LogRecord` и т.п.).
   Альтернатива — типизированная модель. Отклонено сейчас как избыточное дублирование сериализации; можно добавить позже без breaking change, если появится конкретная потребность (например, для DevTools-расширения).

4. **Явное подключение `LogBuffer` через `LogSink(output: buffer.capture)`, без авто-регистрации.**
   Альтернатива — вызов вида `enableViewer()`, автоматически регистрирующий синк. Отклонено: нарушает принцип «никакой магии», принятый для `structured_log` (см. [AGENTS.md](AGENTS.md)), и потребовал бы изменений в самом core-пакете.

5. **Первый и единственный в этой change скин — Material 3** (не Cupertino/Fluent одновременно).
   Альтернатива — сразу все три. Отклонено ранее в обсуждении: риск не довести ни один скин до продакшен-качества; Material выбран как дающий наибольший охват при наименьших усилиях (идёт в комплекте с Flutter SDK).

6. **Именование пакетов: `structured_log_material` / `structured_log_cupertino` / `structured_log_fluent`**, без промежуточного `_flutter`.
   Альтернатива — `structured_log_flutter_material` и т.п. Отклонено: material/cupertino/fluent однозначно про Flutter и без уточняющего сегмента; более короткое имя чище смотрится в списке пакетов на pub.dev.

7. **CI: добавить Flutter-ветку в существующий [.github/workflows/ci.yml](.github/workflows/ci.yml)**, не заводить отдельный workflow-файл.
   Альтернатива — отдельный workflow для Flutter-пакетов. Отклонено пока: два workflow усложняют обзор статуса PR за счёт минимального выигрыша; пересмотреть, если суммарное время CI станет проблемой.

## Risks / Trade-offs

- [Риск] Перенос путей (`git mv`) ломает локальные клоны и IDE-конфигурацию контрибьюторов → [Митигейшн] один атомарный коммит с переносом + синхронное обновление `AGENTS.md`/README/CI в том же PR; явно помечено как **BREAKING** в `proposal.md`.
- [Риск] Рост времени CI из-за установки Flutter SDK на нескольких ОС → [Митигейшн] для `structured_log_flutter`/`structured_log_material` на старте гонять CI только на `ubuntu-latest` (в отличие от `structured_log`, где три ОС нужны из-за файловой ротации в `async_file_output.dart` — у Flutter-виджетов такой ОС-чувствительности нет); расширять на три ОС только при появлении реальной причины.
- [Риск] `LogBuffer` — неограниченный по времени, но ограниченный по размеру кольцевой буфer: при высокой частоте логов старые записи вытесняются молча → [Митигейшн] задокументировать поведение и `capacity` по умолчанию явно в спецификации и dartdoc; буфер не позиционируется как постоянное хранилище.
- [Риск] Headless/skin-разделение может оказаться преждевременной абстракцией, если Cupertino/Fluent так и не будут реализованы → [Митигейшн] осознанный trade-off, зафиксированный здесь; пересмотреть объединение пакетов, если через несколько релизов станет ясно, что второй скин не появится.
- [Риск] Палитра цветов уровней логирования может разойтись между `structured_log_flutter` (контроллер) и `structured_log_material` (виджеты), если хардкодить её в нескольких местах → [Митигейшн] canonical-таблица цветов уровней живёт в одном месте (в `structured_log_material`, единственном потребителе на момент этой change) и требование об этом зафиксировано в спецификации.

## Migration Plan

1. `git mv` существующих файлов пакета в `structured_log/` (плоско, в корень репозитория) одним коммитом — поведение, версия и CHANGELOG не меняются.
2. Обновить `melos.yaml` (workspace с явным списком `packages: [structured_log, structured_log_flutter, structured_log_material]`, по образцу `cherrypick`), пути в `AGENTS.md`/`CLAUDE.md`, ссылки в README.
3. `melos bootstrap` + `melos run analyze`/`test` — убедиться, что `structured_log` не сломан переносом.
4. Скаффолдинг `structured_log_flutter/`: pubspec, barrel-файл, `LogBuffer`, `LogViewerController`, юнит-тесты.
5. Скаффолдинг `structured_log_material/`: pubspec с зависимостью `structured_log_flutter` (path в monorepo), виджеты по макетам из Claude Design canvas, виджет-тесты, `example/`.
6. Добавить Flutter-ветку в CI workflow.
7. Откат: поскольку `structured_log` не переиздаётся на pub.dev в рамках этой change, откат — это `git revert` соответствующих коммитов; риска для существующих потребителей `structured_log` нет.
