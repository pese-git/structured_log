## Why

Пагинация в `structured_log_server` есть у трёх списков — `GET /v1/logs`, `GET /v1/audit-log`, `GET /v1/users`, — и у каждого она сделана по-своему: верхнего предела `limit` нет нигде (спецификация требует его для логов, код не выполняет), «конец списка» сообщается по-разному (аудит и пользователи — пробой `limit+1`, логи отдают курсор даже на последней странице), а `limit=0`/нецелое значение падает по-разному (`assert`, `FormatException`, пустая страница с `page.last`). Остальные списки — `GET /v1/groups`, `GET /v1/projects` — не ограничены вовсе, причём проверка прав `canRead` выполняется в Dart **после** `select.get()`: стоимость запроса растёт от всех строк таблицы, а не от тех, что видит вызывающий. Клиент повторяет это: дашборд забирает все группы и проекты ради трёх карточек, селектор области в логах рисует их все, а поиск получателя роли обрезает ответ до 20 строк и выбрасывает `next_cursor`.

Пока групп и проектов десятки, это не видно. Менять контракт дешевле сейчас, до появления клиентов, привыкших к «список приходит целиком».

## What Changes

- **Единый контракт пагинации** для всех курсорных списков сервера: `limit` (по умолчанию 50, верхний предел 200, значение выше предела приводится к пределу), курсор по `id`, `next_cursor` отсутствует/`null` на последней странице (проба `limit+1` везде, включая `GET /v1/logs`), недопустимое `limit`/`cursor` — `400` структурированной ошибкой, а не `500`/`assert`.
- **BREAKING (для клиентов, читающих `GET /v1/groups` и `GET /v1/projects` целиком):** оба списка получают `limit`/`cursor` и `next_cursor` в ответе, порядок — по убыванию `id`. Без параметров ответ — первая страница из 50 элементов, а не весь список.
- Проверка `canRead` для групп и проектов переезжает из Dart в SQL: сервер вычисляет множество видимых групп/проектов по ролям вызывающего (`admin` — без ограничения) и накладывает его как условие запроса, чтобы страница и курсор считались по видимым строкам.
- Клиент `structured_log_admin_client`:
  - дашборд запрашивает первые 3 проекта (`limit=3`), а не весь список;
  - селектор области в логах и поисковые пикеры групп/проектов работают через `?name=` и подгрузку по курсору;
  - поиск получателя роли (`searchUsers`) перестаёт выбрасывать `next_cursor`;
  - аудит передаёт `limit` явно, экран групп подгружает следующую страницу;
  - лента логов не делает лишнего пустого запроса в конце и ограничивает число накопленных записей.
- Индекс `(project_id, id)` для `log_entries` **не добавляется**: замер на 2 млн записей показал, что существующий `idx_log_entries_project_id` уже обслуживает `ORDER BY id DESC` (у любого индекса SQLite последним ключом лежит `rowid`, а `id` — это `rowid`); см. `design.md`, решение 11.
- Документация: `docs/api/http-api.md`/`.ru.md` (общий раздел про пагинацию, пределы), `AGENTS.md`.

Вне объёма (сознательно):

- Постраничная навигация с номерами и `total` — курсорная модель её не поддерживает, а `COUNT(*)` по логам и аудиту дорог; экраны остаются на «показать ещё»/подгрузке при прокрутке.
- Сортировка групп и проектов по имени: курсор пришлось бы делать составным `(name, id)`. Список остаётся в порядке `id`, поиск по имени — через `?name=`.
- Списки, ограниченные размером одной группы/проекта — команды, участники команды, секретные ключи, выдачи ролей (`GET /v1/role-assignments` с фильтром). Их пагинация не вводится; решение и условия пересмотра — в `design.md`.
- `GET /v1/logs/stream` — у него собственный механизм (`since_id`, страницы по 500 при догоне), он не меняется.

## Capabilities

### New Capabilities

- `log-server-pagination`: общий контракт курсорной пагинации списков сервера (пределы `limit`, семантика `next_cursor`, ошибки), а также пагинированный перечень групп `GET /v1/groups`, для которого до сих пор не было требования вовсе.

### Modified Capabilities

- `log-server-api`: «Пагинация результатов запроса» получает верхний предел и ссылку на общий контракт; «Перечисление доступных проектов плоским списком» становится пагинированным.
- `log-server-audit`: пагинация `GET /v1/audit-log` подчиняется общему контракту (предел, ошибки).
- `admin-client-resource-management`: экраны и пикеры, читающие группы, проекты и пользователей, работают постранично и не теряют элементы за пределами первой страницы.
- `admin-client-log-browser`: конец истории определяется по отсутствию `next_cursor`; накопленный список ограничен.

## Impact

- Капабилити `log-server-api`, `log-server-audit`, `admin-client-*` описаны в ещё не заархивированной change `add-structured-log-server` (в `openspec/specs/` их нет) — дельты этой change читаются поверх неё, и при архивации порядок «сначала `add-structured-log-server`, потом эта» (как у `add-server-cors` и `unify-server-auth`).
- `backend/structured_log_server/lib/src/http/routes/` — `logs_route.dart`, `audit_log_route.dart`, `users_route.dart`, `groups_route.dart`, `projects_route.dart`; новый общий разбор `limit`/`cursor` вместо трёх копий `int.parse`.
- `backend/structured_log_server/lib/src/storage/` — `log_store.dart` (проба `limit+1`), запросы групп/проектов с SQL-фильтром видимости; схема БД не меняется.
- `backend/structured_log_server/lib/src/rbac/` — функция, превращающая набор ролей в условие видимости для SQL; она обязана давать те же результаты, что `canRead` (сверяется тестом на совпадение).
- `frontend/structured_log_admin_client/lib/features/` — `dashboard`, `resources`, `log_browser`, `users`, `audit`; retrofit-интерфейсы и DTO списков получают `next_cursor`. Список групп/проектов в ответе меняет форму (`next_cursor` рядом с `items`) — клиентский DTO и мок `lib/testing/mock_server.dart` обновляются вместе с ним.
- `packages/e2e` — сквозные тесты обходят списки страницами.
- Совместимость: единственный потребитель `GET /v1/groups`/`/v1/projects` — `structured_log_admin_client` из этого же репозитория, так что ломающее изменение контракта обновляется одним PR с клиентом.
