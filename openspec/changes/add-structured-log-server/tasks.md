Проверка по IP — самая ранняя, до разбора тела запроса (отклонённый по IP запрос не стоит серверу даже парсинга); ключ субъекта берётся из уже разобранного тела (`username`/`email`) или из `sub` для аутентифицированных `POST /v1/auth/change-password`/`DELETE /v1/users/me`, поэтому его ведро проверяется непосредственно перед проверкой кредов, а списывается/восстанавливается по её исходу — хендлер сообщает middleware исход попытки (общий результат-тип, не throw)
- [x] 28.6 Ответ `429`: заголовок `Retry-After` (целые секунды по тому ведру, которое освободится позже) и общий JSON-конверт `{"error": "too_many_requests", ...}` — в том числе для `POST`/`DELETE /v1/auth/token`, единственное отступление от RFC-конверта (decision 43 `design.md`); запрошенное действие не выполняется (пароль не проверяется, письмо не отправляется, токены не выпускаются)
- [x] 28.7 Нормализация ключа субъекта (регистр `username`/`email`) — то же правило, что уже используется при поиске пользователя, чтобы ограничитель нельзя было обойти сменой регистра. **По факту нормализации нет, и это и есть «то же правило»:** поиск пользователя регистрозависим (`CREATE UNIQUE INDEX idx_users_username ON users (username)` без `COLLATE NOCASE`, `t.username.equals(...)`), то есть `Alice` и `alice` — разные учётные записи. Задача сформулирована в предположении регистронезависимого поиска, которое для этой схемы не выполняется
- [x] 28.8 (`test/http/rate_limit_middleware_test.dart`, `test/http/rate_limit/`) Юнит-тесты на сценарии из `specs/log-server-rate-limit/spec.md`: приём/чтение логов и management не ограничиваются, доступ восстанавливается сам по времени, перебор не запирает аккаунт жертвы, успешный вход восстанавливает ведро субъекта, перебор одного `username` упирается в ведро субъекта, распыление по разным `username` — в ведро IP, несуществующий email ограничивается неотличимо от существующего, предел числа ключей соблюдается, `429` несёт `Retry-After` и общий конверт на token-эндпоинте, отклонённый запрос не отправляет письмо и не проверяет пароль, подделанный `X-Forwarded-For` игнорируется по умолчанию, при `trustedProxyHops = 1` учитывается адрес клиента, отключённый ограничитель не возвращает `429`
