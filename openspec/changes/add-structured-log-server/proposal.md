## Why

`structured_log` сейчас умеет только писать записи локально (консоль, файл, ротация) — нет способа собрать логи с нескольких запущенных инстансов приложения (или с устройства пользователя) в одном месте, чтобы искать и фильтровать их централизованно. Разработчикам, которые уже используют структурированное логирование в нескольких сервисах/устройствах, для отладки продакшен-инцидентов нужен централизованный приёмник логов — без завязки на сторонний SaaS и без тяжёлой инфраструктуры (ELK и т.п.), в том же экосистеме Dart, что и остальной воркспейс. Поскольку сервис с самого начала предназначен для нескольких команд/проектов одновременно (а не для одного доверенного приложения), ему нужна мультитенантность: пользователи, группы, проекты, ролевой доступ и ограничение на объём хранимой истории на проект — иначе один проект может исчерпать общее хранилище или один сотрудник — увидеть чужие логи.

## What Changes

- **Реструктурировать репозиторий** под категории пакетов, которых раньше не существовало: `emb/` (встраиваемые в приложения библиотеки — `structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`, новый `structured_log_http`), `backend/` (`structured_log_server`), `frontend/` (`structured_log_admin_client`), `packages/` (зарезервировано под будущее, пустая). **BREAKING** для локальных клонов контрибьюторов (пути меняются для четырёх уже опубликованных пакетов), хотя сами опубликованные на pub.dev артефакты не затрагиваются — см. design.md, decision 23.
- Добавить `backend/structured_log_server/`: самостоятельный Dart HTTP-сервис (`shelf` + `shelf_router`) с:
  - **Мультитенантной моделью данных**: `User`, `Group` (владеет `Project`-ами), `Team` (набор пользователей внутри группы для массовой выдачи прав), `Project` (принадлежит группе, имеет квоты хранения), `ProjectSecretKey` (секретный ключ на приём логов), `RoleAssignment` (выдача роли `admin`/`owner`/`user` пользователю или команде на область видимости: глобально/группа/проект).
  - **RBAC**: `admin` — полный доступ ко всему; `owner` — владеет конкретной группой и её проектами, управляет командами/проектами/квотами/секретными ключами внутри неё и может выдавать роли `owner`/`user` (но не `admin`) на свою группу или её проекты пользователю/команде; `user` — доступ только к явно разрешённым группам/проектам (чтение и поиск логов), без права управления или выдачи прав другим.
  - **OAuth2/OIDC-совместимую аутентификацию по username/паролю** для management/query API, по образцу Keycloak: единый `POST /v1/auth/token` (form-encoded, RFC 6749) с `grant_type=password` (первичная выдача) или `grant_type=refresh_token` (ротация пары), стандартные поля ответа (`access_token`/`refresh_token`/`expires_in`/`token_type`) и формат ошибок (`error`/`error_description`); `DELETE /v1/auth/token` (form-encoded, RFC 7009) отзывает refresh-токен, отвечая успехом независимо от его валидности, чтобы не раскрывать статус чужого токена. Свои пользователи/пароли/RBAC — настоящий Keycloak не разворачивается, унифицирован только протокольный контракт. Эффективные роли пользователя зашиты в claims access-токена (снапшот на момент выдачи, по духу Keycloak), а немедленный отзыв обеспечивается не пересчётом ролей из БД на каждый запрос, а дешёвой проверкой счётчика `User.token_version` (point-lookup по индексированному PK), инкрементируемого при любом изменении прав пользователя.
  - **Самостоятельную регистрацию пользователей** (`POST /v1/auth/register` — username/пароль, без прав до явной выдачи роли owner/admin), включаемую/выключаемую оператором сервера через CLI-флаг или переменную окружения (по умолчанию выключена); создание пользователя администратором (`POST /v1/users`) остаётся доступно независимо от этого флага.
  - **Восстановление пароля по email**: `User.email` — новое поле (не идентификатор для входа, только контакт для восстановления), обязательное при самостоятельной регистрации (`POST /v1/auth/register`) и опциональное при создании пользователя администратором; `POST /v1/auth/password-reset` (JSON, всегда 202 независимо от существования email — без раскрытия зарегистрированных адресов) создаёт одноразовый короткоживущий токен восстановления и отправляет его через интерфейс `EmailSender` (референс-реализация — `SmtpEmailSender`); `POST /v1/auth/password-reset/confirm` устанавливает новый пароль по токену и инкрементирует `User.token_version`, немедленно отзывая текущие сессии — тем же механизмом, что уже используется для смены пароля.
  - **Обязательное подтверждение email перед входом**: новое поле `User.email_verified_at` (nullable) — как только у учётной записи задан `email` (при самостоятельной регистрации всегда, при создании администратором — если он его указал), сервер тем же интерфейсом `EmailSender` отправляет одноразовый короткоживущий токен подтверждения на новый адрес `POST /v1/auth/verify-email`; пока `email_verified_at` не установлен, `grant_type=password` на `POST /v1/auth/token` отклоняется (`invalid_grant`, с дополнительным нестандартным полем `reason: "email_not_verified"` поверх RFC-конверта — аддитивное расширение, безопасное для обычных OAuth2-клиентов, но дающее `structured_log_admin_client` машиночитаемый сигнал отличить эту причину отказа от неверного пароля). Учётные записи без `email` (nullable, создание администратором без него — включая самого `create-admin`) под это правило не подпадают вовсе — им нечего подтверждать. `POST /v1/auth/verify-email/resend` (JSON, всегда 202, тот же анти-enumeration паттерн, что `password-reset`) переотправляет письмо, инвалидируя прежние неиспользованные токены подтверждения. По прямому требованию пользователя — пересматривает более раннюю ревизию Non-Goals этой же change («верификация email... не реализуется»), см. design.md decision 40.
  - **Редактирование учётной записи администратором и обязательный временный пароль**: `PATCH /v1/users/:id` (только `admin`) — частичное обновление `email`/`display_name`/`password` существующего пользователя (не `username`, не `is_active`/`deleted_at`/`is_primary_admin`/роли — у них уже есть отдельные эндпоинты, decision 25). Установка `password` этим путём — как и при создании через `POST /v1/users` — SHALL **всегда** (без возможности отключить) помечать `User.must_change_password = true` и отзывать все refresh-токены цели (тот же механизм, что блокировка, decision 25), заставляя предъявить новый пароль через `grant_type=password`, а не продолжить старую сессию. Пока `must_change_password = true`, любой JWT-аутентифицированный эндпоинт, кроме нового `POST /v1/auth/change-password`, `DELETE /v1/users/me`, `POST /v1/auth/token` (`grant_type=refresh_token`) и `DELETE /v1/auth/token`, отклоняется (403 `must_change_password`) — новый `POST /v1/auth/change-password` (JSON `{current_password, new_password}`, доступен любой аутентифицированной роли только над собой) проверяет текущий пароль, обновляет хэш, инкрементирует `token_version` и снимает `must_change_password`. Самостоятельная регистрация (`POST /v1/auth/register`) этот флаг никогда не устанавливает — пользователь выбрал пароль сам. Изменение `email` через `PATCH /v1/users/:id` на новое значение сбрасывает `User.email_verified_at` и переотправляет письмо подтверждения тем же механизмом, что регистрация (`log-server-email-verification`). По прямому требованию пользователя, см. design.md decisions 41/42.
  - **Ограничение частоты auth-эндпоинтов и аудит аутентификации**: сервер сам ограничивает частоту запросов к `POST /v1/auth/token`, `POST /v1/auth/register`, обоим эндпоинтам восстановления пароля и подтверждения email, `POST /v1/auth/change-password` и `DELETE /v1/users/me` — token bucket в памяти по двум независимым ключам (клиентский IP — на каждом запросе; субъект попытки (`username`/`email`/`sub`) — только на неудачных, с полным восстановлением при успехе), ответ `429` + `Retry-After` в общем JSON-конверте (единственное отступление от RFC-конверта token-эндпоинта). Блокировки учётной записи **нет** — никакого состояния в БД, никакого административного `unlock`, доступ восстанавливается сам по времени (по прямому выбору пользователя: блокировка дала бы возможность намеренно запереть чужой аккаунт, зная лишь `username`). `X-Forwarded-For` учитывается только при явно настроенном числе доверенных прокси; весь ограничитель отключается одним флагом конфигурации. Одновременно закрытый набор `action` аудита пополняется аутентификационными событиями `auth.login_succeeded`/`auth.login_failed`/`auth.logged_out`/`auth.throttled` (без `grant_type=refresh_token` — продление уже принятого решения о доступе, самое частотное из всех событий); `metadata` несёт `client_ip`/`user_agent`/причину отказа и никогда — пароль или `username` несуществующей учётной записи. По прямому требованию пользователя, см. design.md decisions 43/44/45.
  - **Срок хранения аудита**: два независимых, задаваемых конфигурацией сервера срока — для административных действий и для аутентификационных событий (последние несут `client_ip`/`user_agent` и порождаются внешним трафиком, поэтому их разумно хранить короче). Оба по умолчанию **не заданы** — поведение из коробки не меняется, апгрейд сервера ничего не удаляет молча. Удаление выполняет уже существующий periodic purge job (decision 14), порциями, чтобы не блокировать приём логов; проход, удаливший хотя бы одну запись, оставляет `audit.purged` (`actor_user_id: null`, число удалённых и граница возраста) — иначе исчезновение истории неотличимо от заметания следов. Ручного удаления записей аудита не существует ни для какой роли, и сроки не меняются через API — политика удаления журнала действий администраторов не должна быть подконтрольна тем, чьи действия он фиксирует. Действующие сроки возвращаются в ответе `GET /v1/audit-log`. По прямому требованию пользователя, см. design.md decision 46.
  - **Конфигурация при запуске**: сервер настраивается аргументами командной строки и переменными окружения с приоритетом CLI → env → значение по умолчанию; имена выводятся друг из друга механически (`--http-port` ↔ `STRUCTURED_LOG_HTTP_PORT`). Секреты (JWT-signing-секрет, пароль SMTP) принимаются **только** из окружения или из файла по пути в `*_FILE`-переменной — флага командной строки для них не существует, а одновременное задание обеих форм считается ошибкой. JWT-секрет обязателен и не генерируется автоматически. Вся конфигурация проверяется до открытия порта: все ошибки выводятся списком за один запуск, код выхода `78` (`EX_CONFIG`) отличает плохую конфигурацию от рантайм-сбоя. Неизвестный аргумент останавливает запуск, неизвестная переменная с префиксом `STRUCTURED_LOG_` — предупреждает. `--print-config` показывает эффективные значения с источником каждого (`cli`/`env`/`default`), маскируя секреты. По прямому требованию пользователя, см. design.md decision 47.
  - **Собственное логирование через `structured_log`**: и `structured_log_server`, и `structured_log_admin_client` логируют свою работу через тот же пакет, который публикует воркспейс, — структурными полями и `BoundLogger.bind()`, без `print()`/`debugPrint` (проверяется тестом-стражем). Для сервера уровень, формат (`console`/`json`) и файл с ротацией задаются конфигурацией (`log-server-config`), файловый вывод асинхронный; для клиента уровень определяется режимом сборки. Диагностика сервера отделена и от `log_entries` (данные тенантов), и от аудита (факты, которые нельзя отключить). **Пересматривает часть decision 19**: клиенту разрешена зависимость на `structured_log` как на библиотеку логирования общего назначения — запрет общего пакета типов контракта и зависимостей на `structured_log_server`/`structured_log_http` остаётся. По прямому требованию пользователя, см. design.md decision 48.
  - **Автосоздание первого администратора при старте**: если таблица пользователей пуста, сервер сам создаёт администратора — логин из `STRUCTURED_LOG_BOOTSTRAP_ADMIN_USERNAME` (по умолчанию `admin`), пароль из `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD`(`_FILE`) либо сгенерированный случайно и однократно выведенный в лог с пометкой «временный». Учётная запись получает `is_primary_admin = true` и `must_change_password = true`, то есть до смены пароля не может ничего, кроме его смены; `email` не собирается, поэтому обязательное подтверждение адреса её не блокирует. На непустой базе не создаётся ничего (заданные параметры при этом сопровождаются предупреждением), автосоздание выключается флагом, а `create-admin` остаётся для повторного bootstrap. **Пересматривает decision 12**, который отклонял автосоздание из-за риска дефолтных кредов: предсказуемого пароля теперь не существует ни в одном режиме. По прямому требованию пользователя, см. design.md decision 49.
  - **Аутентификацию за интерфейсом `IdentityProvider`**: всё описанное выше (username/пароль, JWT, `roles`/`token_version`) — реализация `LocalIdentityProvider`, подключаемая через единый интерфейс (`verifyAccessToken` → идентичность + опциональный список ролей), а не зашитая напрямую. Это сделано специально, чтобы позже local-реализацию можно было заменить на Keycloak/другой OIDC-провайдер (передав другую реализацию `IdentityProvider` при старте сервера), не переделывая RBAC. Сама реализация под Keycloak — вне рамок этой change, вводится только интерфейс и рефакторинг под него.
  - **Блокировку пользователей и проектов администратором**: `POST /v1/users/:id/block`/`unblock` и `POST /v1/projects/:id/block`/`unblock` — доступны только роли `admin` (не `owner`, даже в своей группе), для любого пользователя/проекта независимо от группы. Блокировка пользователя переиспользует существующий `User.is_active` и дополнительно отзывает все его refresh-токены; `grant_type=refresh_token` теперь также проверяет `is_active`, закрывая возможность получить новый access-токен по ещё не истёкшему refresh-токену уже заблокированного пользователя. Блокировка проекта (`Project.is_blocked`) немедленно останавливает и приём (`POST /v1/logs` → 403 `project_blocked`), и прямой запрос логов этого проекта (`GET /v1/logs?project_id=...` → 403 `project_blocked`, перекрывая обычную авторизацию), не отзывая его секретные ключи — обратимо через `unblock`; запрос по `group_id`, включающей заблокированный проект, молча исключает его записи, не отклоняя весь запрос.
  - **Аудит административных действий**: отдельная таблица `audit_log_entries` (actor/action/target/metadata/created_at), запись создаётся в той же транзакции, что и каждая мутирующая management-операция (создание/блокировка пользователей и проектов, изменение квоты, создание/отзыв секретных ключей, выдача/отзыв ролей, подтверждение восстановления пароля — закрытый список действий, не приём/запрос самих логов). `GET /v1/audit-log` — только `admin`, с фильтрами (`actor_user_id`/`action`/`target_type`/`target_id`/диапазон времени) и keyset-пагинацией.
  - **Удаление аккаунта — собственного или, для администратора, чужого**: `DELETE /v1/users/me` (доступен любой роли, только над собственной учётной записью, требует подтверждения текущим паролем) и `DELETE /v1/users/:id` (только `admin`, над любой другой учётной записью, без пароля цели — авторизация собственной admin-сессией; отклоняет `:id`, равный самому вызывающему, 400 — самоудаление только через `/me`) необратимо через API помечают `User.deleted_at` (soft-delete), переиспользуя тот же переключатель `is_active`/отзыв refresh-токенов/инкремент `token_version`, что и блокировка администратором, и дополнительно каскадно удаляют прямые `role_assignments` и членство в командах удаляемого пользователя. Оба эндпоинта отклоняют удаление (409 `sole_group_owner`, со списком блокирующих групп в теле ответа) пользователя, являющегося единственным `owner` хотя бы одной группы — владение сначала нужно передать вручную через уже существующий `POST /v1/role-assignments`, затем повторить удаление. `username`/`email` удалённого аккаунта остаются занятыми (уникальность — глобальная, без исключения по `deleted_at`) до тех пор, пока строка физически не вычищена из БД — soft-delete намеренно не освобождает идентификатор сразу же; `unblock` отказывает на удалённых аккаунтах независимо от того, кем они удалены, чтобы не обходить необратимость через block/unblock.
  - **Защита основного администратора от удаления**: ровно один пользователь за всю историю системы помечается `User.is_primary_admin = true` — тот, что создан первым bootstrap — автоматическим при пустой базе (decision 49) либо командой `create-admin` (см. design.md, decision 28); оба эндпоинта удаления (`DELETE /v1/users/me` и `DELETE /v1/users/:id`) отклоняют запрос (403 `cannot_delete_primary_admin`), если целевая учётная запись — основной администратор, независимо от того, сколько ещё активных `admin` есть в системе. Это защита по идентичности конкретного аккаунта, а не по количеству оставшихся администраторов (последнее в объём этой доработки не входит, см. Non-Goals); блокировка (`POST /v1/users/:id/block`) основного администратора остаётся разрешённой — под защитой только удаление, буквально по формулировке требования.
  - **Приём логов по секретному ключу проекта**: `POST /v1/logs` аутентифицируется не JWT, а `Authorization: Bearer <project-secret-key>`, однозначно определяющим `project_id` — так что приложениям, которые только шлют логи, не нужен пользовательский аккаунт.
  - **Квоты на хранение истории на проект**: срок хранения (`retention_days`, автоматическая периодическая очистка устаревших записей) и лимиты объёма (`max_entries`/`max_bytes`, с отказом в приёме конкретных записей батча при превышении, аналогично существующей частичной валидации батча).
  - Поиск/фильтрацию (`GET /v1/logs` — по `level`/`category`/`logger`/диапазону времени/correlation id/полнотекстовому `q`/произвольным `context.*`-полям, обязательно в границах одного `project_id` или `group_id`, к которому у вызывающего есть доступ) и `GET /healthz`.
  - **Живую доставку новых записей по SSE**: `GET /v1/logs/stream` (`Content-Type: text/event-stream`, та же обязательная область `project_id`/`group_id` и те же фильтры, что и `GET /v1/logs`, плюс проверка RBAC/блокировки проекта — по духу той же авторизации, что query-эндпоинт) отдаёт только записи, принятые сервером **после** открытия соединения — начальную историю клиент по-прежнему получает через обычную пагинацию `GET /v1/logs` (см. design.md, decision 29). Реализовано через in-process broadcast (единственный isolate — см. Non-Goals про много-isolate масштабирование), без внешнего pub/sub. Аутентификация — тем же access-JWT, что management/query API, заголовком `Authorization: Bearer`, а не query-параметром (не раскрывать токен в логах прокси) — что осознанно исключает потребление потока браузерным `EventSource` (тот не умеет произвольные заголовки), но не мешает `structured_log_admin_client`, который читает поток обычным HTTP-клиентом (`dio`) со стримингом тела ответа, а не через `EventSource`. Соединение живёт дольше срока действия access-токена, поэтому сервер периодически (по тому же интервалу, что heartbeat) ревалидирует `token_version`/`is_active`/`deleted_at`/блокировку проекта и закрывает поток терминальным SSE-событием при их изменении, а не держит открытым до естественного истечения токена — не пропуская тем самым уже существующую гарантию мгновенного отзыва (decision 6/25/27) в этом единственном долгоживущем канале.
  - Хранилище — `drift` поверх embedded SQLite (см. предыдущую ревизию design.md), файл на диске, WAL-режим.
  - **Внутренняя архитектура и технологический стек кода сервера**: организация `lib/src/` — `feature-first` (по фиче: `auth`, `users`, `projects`, `logs`, `live_stream`, `audit`, ...), внутри каждой фичи — простая слоистая архитектура (не полный Clean Architecture — `structured_log_server` без UI-слоя, которому она в первую очередь адресована), а не единый плоский список файлов по техническому типу; `fpdart` (`Either`/`Option`) для ожидаемых, часть потока управления составляющих исходов (ошибка валидации, отказ RBAC, превышение квоты, `invalid_grant` и т.п.) вместо исключений там, где вызывающий код обязан явно обработать оба исхода — не для программных ошибок, которые остаются исключениями; `freezed` (+ `json_serializable`) для неизменяемых моделей и sealed-объединений (например, результатов RBAC-проверки, доменных ошибок) — расширяет уже принятое для этого пакета исключение из принципа «никакой кодогенерации» (см. design.md, decision 2), тот же `build_runner`, что уже нужен `drift`, покрывает и генерацию `freezed`/`json_serializable` в одном прогоне.

Зависит только от `flutter` sdk и `fluent_ui`; `structured_log_admin_client` зависит от неё, не наоборот — presentation-виджеты этого пакета технически не могут импортировать `Bloc`/repository-код. `example/` — приложение-галерея компонентов, по аналогии с `structured_log_material_example`/`structured_log_fluent_example`.

  - **Аутентификация**: экран логина (`grant_type=password`) и регистрации (`POST /v1/auth/register`, с понятным сообщением, если сервер отвечает 403 — регистрация выключена оператором), токены — в secure storage (не в открытых `SharedPreferences`), автоматический `grant_type=refresh_token` при 401 с одной повторной попыткой исходного запроса, принудительный logout при неудачном refresh, `DELETE /v1/auth/token` при явном выходе. Экран «Забыли пароль?» (запрос по email, одинаковое сообщение независимо от существования адреса) и экран установки нового пароля по токену восстановления (введённому вручную или подставленному из query-параметра ссылки в web-сборке). После успешной регистрации — экран «подтвердите email» (с действием «отправить письмо ещё раз») вместо немедленного перехода к логину; тот же экран подтверждения (токен вручную или из query-параметра ссылки в web-сборке) показывает результат по клику на ссылку из письма; отказ логина с `reason: "email_not_verified"` показывает то же самое объяснение с предложением отправить письмо повторно, а не обобщённую ошибку неверных кредов. Действие «удалить аккаунт» в настройках (только над своей учётной записью, с предупреждением о необратимости и подтверждением паролем). Действие «сменить пароль» в настройках (`POST /v1/auth/change-password`, текущий + новый пароль) — доступно всегда, не только когда пароль временный. Принудительный экран смены пароля сразу после входа, если сервер отвечает `403 must_change_password` на первый же запрос основного экрана — блокирует навигацию куда-либо ещё, кроме выхода, пока пароль не сменён.
  - **Управление ресурсами**: списки/создание/редактирование (`PATCH /v1/users/:id` — email/display_name/пароль, admin only) пользователей и групп (admin), команд и их состава (owner/admin), проектов с квотами и текущим использованием (owner/admin — просмотр/редактирование; user — только просмотр разрешённых), секретных ключей проектов (создание/список метаданных/отзыв, с одноразовым показом значения при создании), выдача/отзыв ролей (`RoleAssignment`) пользователю или команде, блокировка/разблокировка и удаление (`DELETE /v1/users/:id`, без пароля, с понятным сообщением при конфликте единственного владельца группы) любого пользователя, блокировка любого проекта (все — действия, видимые и доступные только `admin`) — элементы UI, требующие прав, которых нет у текущего пользователя, скрыты, но конечная проверка — всегда на сервере. Экран редактирования пользователя показывает поле нового пароля с явным предупреждением, что оно немедленно завершит все его текущие сессии и потребует смены пароля при следующем входе.
  - **Просмотр аудита** (только `admin`, скрыто из навигации для остальных): список записей `GET /v1/audit-log` с фильтрами по действию/цели/времени/инициатору, постраничная подгрузка курсором.
  - **Просмотр и поиск логов, в стиле истории чата**: выбор области (`project_id`/`group_id`, к которой есть доступ), фильтры, соответствующие параметрам `GET /v1/logs` (уровень/категория/logger/диапазон времени/correlation id/`q`/`context.*`), детальный просмотр записи. Список ведёт себя как лента чата: по умолчанию показаны самые свежие записи (прокрученные к концу списка), новые записи, доставленные по `GET /v1/logs/stream`, дописываются в конец и лента следует за ними, пока пользователь у нижнего края; прокрутка вверх останавливает автослежение и подгружает более ранние записи постранично курсором `GET /v1/logs` (не дописывая новые поверх того, что пользователь сейчас читает) — возврат к нижнему краю восстанавливает автослежение. Отдельное действие «пауза»/«возобновить» замораживает видимый список независимо от прокрутки (по образцу уже существующего `LogViewerController.paused` из `structured_log_flutter` — тот же принцип: приём в фоне не останавливается, застывает только то, что отображено), возобновление показывает пропущенное и возвращает к живому краю. Не переиспользует `LogViewerController`/`LogBuffer` из `structured_log_flutter` или виджеты `structured_log_material`/`fluent` — те рассчитаны на локальный `LogBuffer` (лог из текущего процесса), а не на удалённые query/SSE API; это разные источники данных, и объединение — отдельная будущая работа (см. Non-Goals); принцип паузы позаимствован, реализация — нет.
  - Без зависимости на `structured_log_server`/`structured_log_http`/`structured_log` — чистый REST-клиент поверх задокументированного HTTP-контракта, никакого общего Dart-кода с бэкендом.
  - **Внутренняя архитектура и технологический стек кода клиента**: `feature-first` (по фиче: `auth`, `users`, `projects`, `teams`, `log-browser`, `audit`, ...), внутри каждой фичи — Clean Architecture (`domain`/`application`/`infrastructure`/`presentation`); `fpdart` для тех же ожидаемых исходов, что на сервере (ошибка сети, `invalid_grant`, отказ по правам), пробрасываемых `Either`-ом из `infrastructure`/`application`-слоя в `presentation`; `freezed` (+ `json_serializable`) для неизменяемых моделей/DTO и состояний BLoC; DI — `cherrypick` (собственная библиотека того же автора, уже давшая название конвенции `emb/`-раскладки воркспейса — `AGENTS.md`); управление состоянием — `flutter_bloc` (`Bloc`/`Cubit`) — конкретная реализация «собственного маленького state-слоя» просмотрщика логов из более ранней ревизии design.md (decision 21), не абстрактный ChangeNotifier; HTTP — `dio` + `retrofit` (типизированные, кодогенерируемые интерфейсы клиента для обычных JSON request/response эндпоинтов; `GET /v1/logs/stream` — исключение, реализован вручную поверх того же `dio` с тем же interceptor'ом токена, так как долгоживущее потоковое тело с собственным разбором SSE-кадров не укладывается в типизированную модель одного запроса/ответа retrofit); UI-кит — `fluent_ui` (не Material) — пересматривает более раннюю ревизию decision 18/`design.md`. ## Capabilities

### New Capabilities
- `log-server-api`: HTTP-контракт `structured_log_server` — батч-приём по секретному ключу проекта, query/фильтрация с пагинацией и проверкой доступа по RBAC, health-check.
- `log-server-storage`: мультитенантная схема хранения (users/groups/teams/projects/project_secret_keys/role_assignments/project_usage/log_entries), индексы под частые фильтры, JSON1-фильтрация по произвольным `context`-полям, миграция схемы при старте.
- `log-server-auth`: интерфейс `IdentityProvider` и его local-реализация — регистрация пользователей (переключаемая), аутентификация по username/паролю (создание/обновление/отзыв access- и refresh-токенов, роли пользователя — снапшотом в claims), хранение паролей, `token_version`-проверка для немедленного отзыва, безвозвратное удаление собственного (`DELETE /v1/users/me`) или, для `admin`, чужого (`DELETE /v1/users/:id`) аккаунта — с общей проверкой единственного владельца группы и каскадным отзывом ролей/членства в командах — и отказ в доступе удалённым аккаунтам, защита основного администратора (`is_primary_admin`) от удаления по обоим эндпоинтам, аутентификация приёма логов по секретному ключу проекта.
- `log-server-rbac`: роли `admin`/`owner`/`user`, области видимости (global/group/project), выдача ролей пользователю или команде, правила о том, кто кому какую роль может выдать, каскадное обновление `token_version` при изменении прав, блокировка/разблокировка, редактирование (`PATCH /v1/users/:id`) и удаление любого пользователя, блокировка/разблокировка любого проекта — все ролью `admin`.
- `log-server-quotas`: квоты проекта на хранение (retention_days, max_entries, max_bytes), периодическая очистка по retention (тот же проход, что чистит аудит по его собственным срокам — `log-server-audit`), отказ в приёме при превышении лимита объёма.
- `log-server-password-reset`: восстановление пароля по email — `User.email` (опционально), интерфейс `EmailSender` и его референс-реализация `SmtpEmailSender`, одноразовые короткоживущие токены восстановления (`password_reset_tokens`), `POST /v1/auth/password-reset`/`POST /v1/auth/password-reset/confirm`, инкремент `token_version` при смене пароля.
- `log-server-email-verification`: обязательное подтверждение `email` перед входом — `User.email_verified_at`, таблица `email_verification_tokens`, переиспользует интерфейс `EmailSender`, `POST /v1/auth/verify-email`/`POST /v1/auth/verify-email/resend`, `grant_type=password` отклоняется с `reason: "email_not_verified"` до подтверждения.
- `log-server-forced-password-change`: обязательный временный пароль при задании пароля администратором (создание или `PATCH /v1/users/:id`) — `User.must_change_password`, отзыв refresh-токенов цели, блокировка (`403 must_change_password`) всех JWT-эндпоинтов, кроме закрытого списка (смена пароля/логаут/refresh/самоудаление), до момента, пока пользователь не сменит пароль через новый `POST /v1/auth/change-password`.
- `log-server-config`: резолюция конфигурации при старте — приоритет CLI → env → default, механическое соответствие имён аргументов и переменных (`STRUCTURED_LOG_*`), секреты только из окружения или `*_FILE`, обязательный JWT-секрет без автогенерации, проверка всех значений до открытия порта с кодом выхода `78`, `--help`/`--version`/`--print-config` с маскированием секретов, плюс настройки собственного логирования сервера (уровень, формат, файл с ротацией).
- `log-server-rate-limit`: ограничение частоты auth-эндпоинтов без блокировки учётной записи — token bucket в памяти по ключам «клиентский IP» и «субъект попытки», закрытый список ограничиваемых путей, `429` с `Retry-After` в общем JSON-конверте (в том числе на token-эндпоинте), определение клиентского IP с явно настраиваемым доверием `X-Forwarded-For`, полное отключение конфигурацией.
- `log-server-audit`: таблица `audit_log_entries`, закрытый список аудируемых действий (включая аутентификационные `auth.login_succeeded`/`auth.login_failed`/`auth.logged_out`/`auth.throttled`, но не `grant_type=refresh_token`, плюс `audit.purged`), запись в той же транзакции, что мутирующая операция (кроме `auth.*`/`audit.purged`, у которых мутации нет), раздельный срок хранения для аутентификационных и административных записей (по умолчанию не ограничен, без ручного удаления и без настройки через API), `GET /v1/audit-log` (`admin` only, фильтры, keyset-пагинация, действующие сроки хранения в ответе).
- `log-server-live-stream`: `GET /v1/logs/stream` (SSE) — живая доставка новых записей лога в той же области видимости/с теми же фильтрами и проверкой RBAC/блокировки проекта, что `GET /v1/logs`, in-process broadcast в рамках одного isolate, catch-up по `since_id`, heartbeat с периодической ревалидацией авторизации и терминальным событием при её потере.
- `structured-log-http-sender`: клиентский `HttpLogOutput` в `structured_log_http` — батчинг, сериализованная доставка, retry/backoff, `flushed` для ожидания перед выходом из процесса.
- `admin-client-auth`: экраны логина/регистрации/подтверждения email/восстановления пароля/удаления аккаунта/смены пароля (в т.ч. принудительной при `must_change_password`), хранение токенов, автоматический refresh при 401, централизованная обработка 429 с показом времени ожидания (без автоматического повтора), logout — в `structured_log_admin_client`.
- `admin-client-resource-management`: UI управления пользователями (включая редактирование — email/display_name/сброс пароля)/группами/командами/проектами/квотами/секретными ключами/выдачей ролей/блокировкой/удалением пользователей — в `structured_log_admin_client`.
- `admin-client-log-browser`: UI поиска/просмотра логов через `GET /v1/logs`, лента в стиле истории чата с живой доставкой через `GET /v1/logs/stream` (`log-server-live-stream`), автослежение за нижним краем, подгрузка более ранних записей по прокрутке вверх, пауза/возобновление живого обновления — в `structured_log_admin_client`.
- `admin-client-audit-log`: UI просмотра аудит-лога через `GET /v1/audit-log` (`admin` only), включая аутентификационные события с `client_ip`/`user_agent`/причиной отказа и показ действующих сроков хранения — в `structured_log_admin_client`.

### Modified Capabilities
(нет — публичный API `structured_log` не меняется; новые пакеты подключаются к нему только через уже существующие `LogSink`/`OutputFunction`; `log-server-quotas` получает одно небольшое дополнение — текущее использование в ответе `GET /v1/projects/:id`, нужное `structured_log_admin_client` для отображения квоты; `log-server-storage`/`log-server-api` получают поле `Project.is_blocked` и его enforcement на `POST`/`GET /v1/logs`; `log-server-storage` дополнительно получает `User.deleted_at` (уникальность `username`/`email` остаётся глобальной), `User.is_primary_admin`, `User.email_verified_at` и `User.must_change_password`; `log-server-auth` дополнительно получает отказ `unblock` на удалённых аккаунтах, защиту основного администратора от удаления и отказ `grant_type=password` для неподтверждённого email; `log-server-audit` получает новые действия `email.verified`, `user.updated`, `password.changed`, аутентификационные `auth.login_succeeded`/`auth.login_failed`/`auth.logged_out`/`auth.throttled` и `audit.purged` в закрытом списке (последние четыре — единственные, к которым не применяется правило «аудит в одной транзакции с мутацией», поскольку мутации у них нет); `log-server-auth` дополнительно получает `429` от ограничителя частоты перед обработкой гранта — единственный ответ token-эндпоинта не в RFC 6749-конверте — все добавления не breaking, только новые поля/поведение поверх уже спроектированного контракта)

## Impact

- Структура репозитория: `git mv` четырёх существующих пакетов в `emb/`; новые категории `backend/`, `frontend/`, `packages/` (последняя пустая) в корне. Пути в `melos.yaml`, `.github/workflows/ci.yml`, `AGENTS.md`/`CLAUDE.md`, корневых README обновляются в том же коммите.
- Новые пакеты: `backend/structured_log_server/` (`lib/`, `bin/server.dart`, `test/`, `example/`), `emb/structured_log_http/` (`lib/`, `test/`, `example/`), `frontend/structured_log_admin_ui/` (`lib/`, `test/`, `example/` — галерея компонентов) и `frontend/structured_log_admin_client/` (`lib/`, `test/`) — все перечисляются в `melos.yaml` (`packages:`) с новыми путями; первые два чистый Dart, последние два — Flutter; `structured_log_admin_client` дополнительно получает path-зависимость на `structured_log_admin_ui` внутри workspace.
- Зависимости: `structured_log_server` добавляет `shelf`, `shelf_router`, `drift`, `sqlite3`, `dart_jsonwebtoken`, `bcrypt`, `mailer`, `fpdart`, `freezed_annotation`, `json_annotation` (+ dev-зависимости `drift_dev`, `build_runner`, `freezed`, `json_serializable`) — первые сторонние runtime-зависимости в воркспейсе за пределами `meta`/`fluent_ui`; `structured_log_http` зависит только от `structured_log`; `structured_log_admin_ui` — только `flutter` sdk и `fluent_ui` (никаких `fpdart`/`freezed`/`cherrypick`/`flutter_bloc`/`dio`/`retrofit` — decision 39); `structured_log_admin_client` — `flutter` sdk, `structured_log_admin_ui`, `fluent_ui`, `dio`, `retrofit`, `flutter_secure_storage`, `fpdart`, `freezed_annotation`, `json_annotation`, `cherrypick`, `flutter_bloc` (+ dev-зависимости `build_runner`, `freezed`, `json_serializable`, `retrofit_generator`) — без зависимости на любой другой пакет этого воркспейса, кроме `structured_log_admin_ui`.
- CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)): существующие `test`/`flutter` job'ы обновляют `working-directory`/матрицу под новые пути (`emb/...`); новый Dart-only job для `backend/structured_log_server`/`emb/structured_log_http` — начиная с `ubuntu-latest` из-за нативной библиотеки sqlite3, с шагом кодогенерации (`drift`+`freezed`/`json_serializable`, один прогон `build_runner`) перед `analyze`/`test`; `frontend/structured_log_admin_ui` и `frontend/structured_log_admin_client` добавляются в существующую матрицу job'а `flutter` (наравне с `structured_log_flutter`/`material`/`fluent`), последний — с тем же шагом кодогенерации (`freezed`/`json_serializable`/`retrofit_generator`) перед `analyze`/`test` — не требует нового job'а.
