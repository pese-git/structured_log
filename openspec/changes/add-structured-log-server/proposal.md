## Why

`structured_log` сейчас умеет только писать записи локально (консоль, файл, ротация) — нет способа собрать логи с нескольких запущенных инстансов приложения (или с устройства пользователя) в одном месте, чтобы искать и фильтровать их централизованно. Разработчикам, которые уже используют структурированное логирование в нескольких сервисах/устройствах, для отладки продакшен-инцидентов нужен централизованный приёмник логов — без завязки на сторонний SaaS и без тяжёлой инфраструктуры (ELK и т.п.), в том же экосистеме Dart, что и остальной воркспейс. Поскольку сервис с самого начала предназначен для нескольких команд/проектов одновременно (а не для одного доверенного приложения), ему нужна мультитенантность: пользователи, группы, проекты, ролевой доступ и ограничение на объём хранимой истории на проект — иначе один проект может исчерпать общее хранилище или один сотрудник — увидеть чужие логи.

## What Changes

- Добавить `structured_log_server/`: самостоятельный Dart HTTP-сервис (`shelf` + `shelf_router`) с:
  - **Мультитенантной моделью данных**: `User`, `Group` (владеет `Project`-ами), `Team` (набор пользователей внутри группы для массовой выдачи прав), `Project` (принадлежит группе, имеет квоты хранения), `ProjectSecretKey` (секретный ключ на приём логов), `RoleAssignment` (выдача роли `admin`/`owner`/`user` пользователю или команде на область видимости: глобально/группа/проект).
  - **RBAC**: `admin` — полный доступ ко всему; `owner` — владеет конкретной группой и её проектами, управляет командами/проектами/квотами/секретными ключами внутри неё и может выдавать роли `owner`/`user` (но не `admin`) на свою группу или её проекты пользователю/команде; `user` — доступ только к явно разрешённым группам/проектам (чтение и поиск логов), без права управления или выдачи прав другим.
  - **OAuth2/OIDC-совместимую аутентификацию по username/паролю** для management/query API, по образцу Keycloak: единый `POST /v1/auth/token` (form-encoded, RFC 6749) с `grant_type=password` (первичная выдача) или `grant_type=refresh_token` (ротация пары), стандартные поля ответа (`access_token`/`refresh_token`/`expires_in`/`token_type`) и формат ошибок (`error`/`error_description`); `POST /v1/auth/logout` (form-encoded) отзывает refresh-токен. Свои пользователи/пароли/RBAC — настоящий Keycloak не разворачивается, унифицирован только протокольный контракт. Авторизация по ролям пересчитывается из БД на каждый запрос, не кешируется в самом токене, чтобы отозванный доступ действовал немедленно.
  - **Самостоятельную регистрацию пользователей** (`POST /v1/auth/register` — username/пароль, без прав до явной выдачи роли owner/admin), включаемую/выключаемую оператором сервера через CLI-флаг или переменную окружения (по умолчанию выключена); создание пользователя администратором (`POST /v1/users`) остаётся доступно независимо от этого флага.
  - **Приём логов по секретному ключу проекта**: `POST /v1/logs` аутентифицируется не JWT, а `Authorization: Bearer <project-secret-key>`, однозначно определяющим `project_id` — так что приложениям, которые только шлют логи, не нужен пользовательский аккаунт.
  - **Квоты на хранение истории на проект**: срок хранения (`retention_days`, автоматическая периодическая очистка устаревших записей) и лимиты объёма (`max_entries`/`max_bytes`, с отказом в приёме конкретных записей батча при превышении, аналогично существующей частичной валидации батча).
  - Поиск/фильтрацию (`GET /v1/logs` — по `level`/`category`/`logger`/диапазону времени/correlation id/полнотекстовому `q`/произвольным `context.*`-полям, обязательно в границах одного `project_id` или `group_id`, к которому у вызывающего есть доступ) и `GET /healthz`.
  - Хранилище — `drift` поверх embedded SQLite (см. предыдущую ревизию design.md), файл на диске, WAL-режим.
- Добавить `structured_log_http/`: лёгкий клиентский пакет (`structured_log` — единственная зависимость) с `HttpLogOutput` — `OutputFunction`, отправляющий записи батчами по HTTP на `structured_log_server`, аутентифицируясь секретным ключом проекта, с retry/backoff на сетевых ошибках и 5xx (не на 4xx), по эталонному паттерну сериализованной очереди `_SerializedAsyncOutput` из `structured_log/lib/src/async_file_output.dart`.
- Явно вне рамок этого change: server-rendered HTML/веб-UI (чистый JSON API; интеграция Flutter-виджетов — отдельный будущий change), FTS5-поиск (на MVP — `LIKE`), много-isolate масштабирование сервера, Windows в CI нового job'а на старте, сброс пароля, refresh-токены/ротация JWT-сессий (единый access-токен с ограниченным сроком жизни), SSO/MFA, аудит-лог изменений прав доступа, алерты о приближении к квоте, кросс-групповые команды (`Team` принадлежит ровно одной `Group`).

## Capabilities

### New Capabilities
- `log-server-api`: HTTP-контракт `structured_log_server` — батч-приём по секретному ключу проекта, query/фильтрация с пагинацией и проверкой доступа по RBAC, health-check.
- `log-server-storage`: мультитенантная схема хранения (users/groups/teams/projects/project_secret_keys/role_assignments/project_usage/log_entries), индексы под частые фильтры, JSON1-фильтрация по произвольным `context`-полям, миграция схемы при старте.
- `log-server-auth`: регистрация пользователей (переключаемая), аутентификация по username/паролю (создание/обновление/отзыв access- и refresh-токенов), хранение паролей, аутентификация приёма логов по секретному ключу проекта.
- `log-server-rbac`: роли `admin`/`owner`/`user`, области видимости (global/group/project), выдача ролей пользователю или команде, правила о том, кто кому какую роль может выдать.
- `log-server-quotas`: квоты проекта на хранение (retention_days, max_entries, max_bytes), периодическая очистка по retention, отказ в приёме при превышении лимита объёма.
- `structured-log-http-sender`: клиентский `HttpLogOutput` в `structured_log_http` — батчинг, сериализованная доставка, retry/backoff, `flushed` для ожидания перед выходом из процесса.

### Modified Capabilities
(нет — публичный API `structured_log` не меняется; новые пакеты подключаются к нему только через уже существующие `LogSink`/`OutputFunction`)

## Impact

- Новые пакеты в корне воркспейса: `structured_log_server/` (`lib/`, `bin/server.dart`, `test/`, `example/`) и `structured_log_http/` (`lib/`, `test/`, `example/`) — оба перечисляются в `melos.yaml` (`packages:`), оба чистый Dart (без Flutter).
- Зависимости: `structured_log_server` добавляет `shelf`, `shelf_router`, `drift`, `sqlite3`, `dart_jsonwebtoken`, `bcrypt` (+ dev-зависимости `drift_dev`, `build_runner`) — первые сторонние runtime-зависимости в воркспейсе за пределами `meta`/`fluent_ui`; `structured_log_http` зависит только от `structured_log`.
- CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)): нужен новый job для этих двух Dart-пакетов (текущий `test`-job жёстко привязан к `working-directory: structured_log`, не матрица) — начиная с `ubuntu-latest` из-за нативной библиотеки sqlite3, с шагом кодогенерации drift перед `analyze`/`test`.
- Документация: `AGENTS.md` (разделы «Структура»/«CI»), корневые `README.md`/`README.ru.md` — короткое упоминание двух новых пакетов.
- Опубликованные пакеты (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) и их потребители не затрагиваются.
