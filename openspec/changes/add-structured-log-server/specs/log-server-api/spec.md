## ADDED Requirements

### Requirement: Батч-приём записей лога
Сервер SHALL предоставлять эндпоинт `POST /v1/logs`, принимающий JSON-тело в виде списка записей (каждая запись — объект, соответствующий форме `Map<String, dynamic>` из `structured_log`: `event`, `level`, `timestamp` и произвольные дополнительные поля), и SHALL сохранять каждую валидную запись из батча.

#### Scenario: Успешный приём батча
- **WHEN** отправлен `POST /v1/logs` с валидным JSON-массивом из нескольких записей и корректной аутентификацией
- **THEN** сервер отвечает 202 (или 200) и все записи батча становятся доступны через query-эндпоинт

#### Scenario: Частично невалидный батч
- **WHEN** батч содержит записи, часть из которых не проходит валидацию (например, отсутствует обязательное поле `level` или его значение не входит в набор `LogLevel`)
- **THEN** сервер сохраняет валидные записи батча, отклоняет невалидные и возвращает в ответе информацию о том, какие записи (по индексу в батче) были отклонены и почему

#### Scenario: Превышение лимита размера батча
- **WHEN** размер JSON-тела запроса превышает сконфигурированный лимит
- **THEN** сервер отвечает 413 и не сохраняет ни одной записи из этого запроса

### Requirement: Аутентификация по API-ключу
Каждый запрос к `POST /v1/logs` и `GET /v1/logs` SHALL требовать заголовок `Authorization: Bearer <api-key>` с одним из сконфигурированных на старте сервера ключей; конфигурация SHALL допускать более одного одновременно активного ключа.

#### Scenario: Запрос без ключа отклоняется
- **WHEN** запрос к `POST /v1/logs` или `GET /v1/logs` отправлен без заголовка `Authorization` или с неверным ключом
- **THEN** сервер отвечает 401 и не выполняет запрошенную операцию

#### Scenario: Один из нескольких активных ключей принимается
- **WHEN** сервер сконфигурирован с несколькими активными API-ключами и запрос использует любой из них
- **THEN** запрос авторизуется успешно

### Requirement: Health-check без аутентификации
Сервер SHALL предоставлять эндпоинт `GET /healthz`, не требующий аутентификации, отвечающий 200 при готовности сервера обслуживать запросы (хранилище инициализировано и доступно).

#### Scenario: Health-check отвечает 200 на готовом сервере
- **WHEN** отправлен `GET /healthz` без заголовка `Authorization` на запущенный, готовый сервер
- **THEN** сервер отвечает 200

### Requirement: Запрос и фильтрация записей лога
Сервер SHALL предоставлять эндпоинт `GET /v1/logs`, поддерживающий независимо комбинируемые query-параметры фильтрации: `level` (минимальный уровень), `category`, `logger`, `from`/`to` (диапазон по `timestamp`), любой из полей корреляции (`session_id`, `request_id`, `connection_generation`, `tool_call_id`, `message_id`, `operation_id`), `q` (полнотекстовый поиск по `event` и содержимому записи) и `context.<key>` (точное совпадение произвольного пользовательского поля контекста).

#### Scenario: Фильтрация по уровню и диапазону времени
- **WHEN** отправлен `GET /v1/logs?level=warning&from=<iso8601>&to=<iso8601>`
- **THEN** ответ содержит только записи с уровнем не ниже `warning`, чей `timestamp` попадает в указанный диапазон

#### Scenario: Фильтрация по произвольному полю context
- **WHEN** отправлен `GET /v1/logs?context.user_id=42`
- **THEN** ответ содержит только записи, у которых значение ключа `user_id` в исходном контексте равно `42`

#### Scenario: Комбинация нескольких фильтров
- **WHEN** запрос указывает одновременно `category`, `session_id` и `q`
- **THEN** ответ содержит только записи, удовлетворяющие всем указанным условиям одновременно

### Requirement: Пагинация результатов запроса
Эндпоинт `GET /v1/logs` SHALL поддерживать пагинацию через `limit` (с разумным значением по умолчанию и верхним пределом) и курсорный параметр, основанный на `id` записи; ответ SHALL включать информацию, достаточную для запроса следующей страницы.

#### Scenario: Запрос следующей страницы через курсор
- **WHEN** первый запрос `GET /v1/logs?limit=50` возвращает курсор следующей страницы, и этот курсор передан в повторном запросе
- **THEN** второй запрос возвращает следующие записи, не пересекающиеся с уже полученными

### Requirement: Ошибки возвращаются в структурированном JSON-формате
Любой отклонённый запрос (400/401/413/500) SHALL возвращать тело ответа в виде JSON-объекта с машиночитаемым кодом ошибки и человекочитаемым сообщением.

#### Scenario: Структура ответа об ошибке
- **WHEN** сервер отклоняет запрос по любой причине (валидация, авторизация, лимит размера, внутренняя ошибка)
- **THEN** тело ответа — JSON-объект с полями, однозначно идентифицирующими тип ошибки и причину, а не пустое тело или сырой текст исключения
