## ADDED Requirements

### Requirement: Батч-приём записей лога по секретному ключу проекта
Сервер SHALL предоставлять эндпоинт `POST /v1/logs`, аутентифицируемый заголовком `Authorization: Bearer <project-secret-key>` (не JWT), однозначно резолвящим `project_id` через `log-server-auth`; тело запроса — JSON-список записей (каждая запись — объект, соответствующий форме `Map<String, dynamic>` из `structured_log`), которые SHALL сохраняться с этим `project_id`.

#### Scenario: Успешный приём батча
- **WHEN** отправлен `POST /v1/logs` с валидным JSON-массивом записей и заголовком `Authorization: Bearer <действующий секретный ключ проекта P>`
- **THEN** сервер отвечает 202 (или 200), все записи батча сохраняются с `project_id = P` и становятся доступны через query-эндпоинт вызывающим с доступом к `P`

#### Scenario: Неверный или отозванный секретный ключ отклоняется
- **WHEN** `POST /v1/logs` отправлен без заголовка `Authorization`, с ключом, не существующим в системе, или с ключом, для которого `revoked_at` установлено
- **THEN** сервер отвечает 401 и не сохраняет ни одной записи из этого запроса

#### Scenario: Частично невалидный или превышающий квоту батч
- **WHEN** батч содержит записи, часть из которых не проходит валидацию (например, отсутствует `level` или его значение не входит в набор `LogLevel`) или для которых приём привёл бы к превышению квоты проекта (`log-server-quotas`)
- **THEN** сервер сохраняет валидные записи, не превышающие квоту, отклоняет остальные и возвращает в ответе информацию о том, какие записи (по индексу в батче) отклонены и по какой причине (`validation_error` или `quota_exceeded`)

#### Scenario: Превышение лимита размера батча
- **WHEN** размер JSON-тела запроса превышает сконфигурированный лимит
- **THEN** сервер отвечает 413 и не сохраняет ни одной записи из этого запроса

### Requirement: Health-check без аутентификации
Сервер SHALL предоставлять эндпоинт `GET /healthz`, не требующий аутентификации, отвечающий 200 при готовности сервера обслуживать запросы (хранилище инициализировано и доступно).

#### Scenario: Health-check отвечает 200 на готовом сервере
- **WHEN** отправлен `GET /healthz` без заголовка `Authorization` на запущенный, готовый сервер
- **THEN** сервер отвечает 200

### Requirement: Запрос и фильтрация записей лога с явной областью видимости и проверкой RBAC
Сервер SHALL предоставлять эндпоинт `GET /v1/logs`, аутентифицируемый JWT-токеном пользователя (`log-server-auth`), требующий ровно один из параметров `project_id` или `group_id`, определяющий область видимости запроса; сервер SHALL проверять через `log-server-rbac`, что у аутентифицированного пользователя (прямо или через членство в команде) есть право на эту область, и SHALL отвечать 403, если права нет, или 404, если указанный `project_id`/`group_id` не существует.

#### Scenario: Запрос в рамках проекта, на который есть доступ
- **WHEN** аутентифицированный JWT-токеном пользователь с ролью на `project_id = P` (прямо или через команду) отправляет `GET /v1/logs?project_id=P`
- **THEN** сервер возвращает записи, принадлежащие проекту `P`

#### Scenario: Запрос без прав на указанную область отклоняется
- **WHEN** аутентифицированный пользователь без `RoleAssignment`, покрывающего указанный `project_id`/`group_id`, отправляет `GET /v1/logs?project_id=P` (или `group_id=G`)
- **THEN** сервер отвечает 403 и не возвращает ни одной записи

#### Scenario: Запрос по группе агрегирует все её проекты только при гранте на уровне группы
- **WHEN** пользователь с `RoleAssignment(role: user, scope: group:G)` отправляет `GET /v1/logs?group_id=G`, где `G` содержит несколько проектов
- **THEN** сервер возвращает записи из всех проектов `G`, отфильтрованные по остальным параметрам запроса

Дополнительные параметры фильтрации (комбинируются с обязательной областью видимости): `level` (минимальный уровень), `category`, `logger`, `from`/`to` (диапазон по `timestamp`), поля корреляции (`session_id`, `request_id`, `connection_generation`, `tool_call_id`, `message_id`, `operation_id`), `q` (полнотекстовый поиск по `event` и содержимому записи), `context.<key>` (точное совпадение произвольного пользовательского поля контекста).

#### Scenario: Фильтрация по уровню и диапазону времени в пределах разрешённой области
- **WHEN** отправлен `GET /v1/logs?project_id=P&level=warning&from=<iso8601>&to=<iso8601>` вызывающим с доступом к `P`
- **THEN** ответ содержит только записи проекта `P` с уровнем не ниже `warning`, чей `timestamp` попадает в указанный диапазон

#### Scenario: Фильтрация по произвольному полю context
- **WHEN** отправлен `GET /v1/logs?project_id=P&context.user_id=42` вызывающим с доступом к `P`
- **THEN** ответ содержит только записи проекта `P`, у которых значение ключа `user_id` в исходном контексте равно `42`

### Requirement: Пагинация результатов запроса
Эндпоинт `GET /v1/logs` SHALL поддерживать пагинацию через `limit` (с разумным значением по умолчанию и верхним пределом) и курсорный параметр, основанный на `id` записи; ответ SHALL включать информацию, достаточную для запроса следующей страницы.

#### Scenario: Запрос следующей страницы через курсор
- **WHEN** первый запрос `GET /v1/logs?project_id=P&limit=50` возвращает курсор следующей страницы, и этот курсор передан в повторном запросе
- **THEN** второй запрос возвращает следующие записи проекта `P`, не пересекающиеся с уже полученными

### Requirement: Ошибки возвращаются в структурированном JSON-формате
Любой отклонённый запрос (400/401/403/404/413/507/500) SHALL возвращать тело ответа в виде JSON-объекта с машиночитаемым кодом ошибки и человекочитаемым сообщением.

#### Scenario: Структура ответа об ошибке
- **WHEN** сервер отклоняет запрос по любой причине (валидация, авторизация, доступ, квота, лимит размера, внутренняя ошибка)
- **THEN** тело ответа — JSON-объект с полями, однозначно идентифицирующими тип ошибки и причину, а не пустое тело или сырой текст исключения
