## ADDED Requirements

### Requirement: Просмотр логов требует явного выбора области видимости
Приложение SHALL требовать от пользователя выбрать ровно одну область (конкретный проект или конкретную группу из доступных ему) перед выполнением запроса `GET /v1/logs`, зеркаля требование `log-server-api` — приложение SHALL не пытаться агрегировать логи из нескольких областей одним запросом.

#### Scenario: Экран логов недоступен без выбранной области
- **WHEN** пользователь открывает раздел логов, не выбрав ни проект, ни группу
- **THEN** приложение показывает селектор области вместо списка записей, и запрос `GET /v1/logs` не выполняется

#### Scenario: Селектор области ограничен доступными пользователю ресурсами
- **WHEN** пользователь открывает селектор области
- **THEN** предлагаются только проекты/группы, на которые у него есть роль (прямая или через команду) — согласно `log-server-rbac`

### Requirement: Элементы управления фильтрами соответствуют параметрам запроса
Приложение SHALL предоставлять элементы управления для каждого параметра фильтрации `GET /v1/logs` (`log-server-api`): минимальный уровень, категория, logger, диапазон времени, поля корреляции, полнотекстовый поиск (`q`), и SHALL позволять комбинировать их одновременно в одном запросе.

#### Scenario: Комбинация фильтров формирует один запрос
- **WHEN** пользователь одновременно задаёт минимальный уровень и текст полнотекстового поиска
- **THEN** приложение выполняет один `GET /v1/logs` запрос с обоими параметрами, а не два отдельных запроса

### Requirement: Подгрузка более ранних записей при прокрутке к верхнему краю
Список результатов SHALL подгружаться постранично с использованием курсора, возвращаемого `GET /v1/logs` (`log-server-api`), а не загружать все записи сразу; первая страница (без курсора) — самые новые записи (`log-server-api`, направление по умолчанию), список отображается в хронологическом порядке (старые сверху, новые снизу); при приближении прокрутки к верхнему краю уже загруженного списка приложение SHALL автоматически подгружать следующую (более раннюю) страницу и добавлять её сверху, не сдвигая и не изменяя то, что уже показано внизу.

#### Scenario: Подгрузка следующей страницы не дублирует записи
- **WHEN** пользователь дважды подряд прокручивает список к верхнему краю
- **THEN** отображаемый список не содержит повторяющихся записей между первой и второй подгруженными страницами

#### Scenario: Смена фильтров сбрасывает пагинацию и живую подписку
- **WHEN** пользователь меняет любой фильтр или выбранную область после того, как уже подгружено несколько страниц и/или открыта живая подписка
- **THEN** приложение выполняет новый запрос с первой (самой новой) страницы, закрывает текущую подписку `GET /v1/logs/stream` и открывает новую с обновлёнными параметрами, не продолжая пагинацию по старому курсору и не смешивая события старой и новой подписки

### Requirement: Лента логов ведёт себя как история чата — автослежение за самыми свежими записями
Приложение SHALL открывать `GET /v1/logs/stream` (`log-server-live-stream`) с теми же областью/фильтрами, что текущий `GET /v1/logs`, сразу вслед за загрузкой первой страницы, и SHALL дописывать доставленные по нему записи в конец списка. Пока пользователь прокручен к нижнему (самому свежему) краю списка, каждая новая запись SHALL сопровождаться автоматической прокруткой к ней; если пользователь прокручен выше нижнего края, новые записи SHALL не переносить его прокрутку принудительно — вместо этого SHALL показываться индикатор количества не просмотренных новых записей, по действию с которым список прокручивается к концу и автослежение возобновляется.

#### Scenario: Список сам следует за новыми записями, пока пользователь внизу
- **WHEN** пользователь находится в самом низу списка (или ещё не прокручивал), и по живой подписке доставлена новая запись
- **THEN** эта запись появляется в конце списка, который автоматически прокручивается так, чтобы она была видна

#### Scenario: Прокрутка вверх не прерывается новыми записями
- **WHEN** пользователь прокрутил список выше нижнего края и читает более ранние записи, и в это время по живой подписке доставлена новая запись
- **THEN** видимая позиция прокрутки не меняется принудительно; вместо этого показывается индикатор новых событий

#### Scenario: Индикатор новых событий возвращает к живому краю
- **WHEN** пользователь, прокрученный выше нижнего края с накопленными новыми событиями, нажимает на индикатор новых событий
- **THEN** список прокручивается к концу, показывая накопленные записи, и автослежение возобновляется

### Requirement: Живое обновление можно приостановить и возобновить независимо от прокрутки
Приложение SHALL предоставлять отдельное действие «пауза»/«возобновить», не зависящее от позиции прокрутки: во время паузы видимый список SHALL оставаться неизменным, даже если по живой подписке `GET /v1/logs/stream` продолжают поступать новые записи (подписка не закрывается на время паузы); возобновление SHALL показать поступившие за время паузы записи и вернуть список к живому краю.

#### Scenario: Во время паузы список не меняется
- **WHEN** пользователь ставит ленту логов на паузу, и в это время по живой подписке доставлено несколько новых записей
- **THEN** видимый список не меняется, пока пауза не снята

#### Scenario: Возобновление показывает пропущенное
- **WHEN** пользователь снимает паузу после того, как во время неё пришло несколько новых записей
- **THEN** эти записи появляются в списке, и список прокручивается к живому краю

#### Scenario: Слишком долгая пауза приводит к перезагрузке, а не к частичному списку
- **WHEN** пауза удерживается достаточно долго, чтобы клиентский буфер накопленных событий переполнился
- **THEN** возобновление перезагружает актуальную первую страницу и открывает новую живую подписку с этого места, а не показывает заведомо неполный «рваный» буфер

### Requirement: Детальный просмотр записи показывает полный контекст
Приложение SHALL предоставлять детальный вид отдельной записи лога, показывающий все её поля (`event`, `level`, `timestamp`, `received_at`, `category`, `logger`, поля корреляции, произвольный `context`), доступный из списка результатов.

#### Scenario: Детальный вид показывает произвольные пользовательские поля контекста
- **WHEN** открыт детальный вид записи, содержащей пользовательские поля `context`, не входящие в стандартный набор
- **THEN** эти поля отображаются в детальном виде, а не только стандартные `event`/`level`/`timestamp`
