## ADDED Requirements

### Requirement: Три роли с фиксированной семантикой
Система SHALL поддерживать ровно три роли: `admin` (полный доступ ко всем ресурсам сервиса), `owner` (полный доступ к конкретной группе и её проектам/командам, плюс право выдавать роли `owner`/`user` в её рамках) и `user` (доступ только к явно разрешённым группам/проектам, без права управления или выдачи ролей).

#### Scenario: admin действует без явного RoleAssignment на каждый ресурс
- **WHEN** пользователь имеет `RoleAssignment(role: admin, scope: global)` и обращается к любому ресурсу (группе, проекту, логам) без отдельного гранта именно на этот ресурс
- **THEN** доступ разрешается

#### Scenario: user без явного гранта на ресурс не имеет доступа
- **WHEN** пользователь не имеет ни одного `RoleAssignment` (прямого или через команду), покрывающего запрошенную группу/проект
- **THEN** доступ к этой группе/проекту запрещён, независимо от того, есть ли у пользователя доступ к другим группам/проектам

### Requirement: Резолвинг эффективных ролей из хранилища не зависит от источника аутентификации
RBAC-логика SHALL уметь резолвить эффективные роли пользователя (прямые `RoleAssignment` и унаследованные через членство в командах) напрямую из `role_assignments`/`team_members`/`teams` по идентификатору пользователя, независимо от того, какая реализация `IdentityProvider` (`log-server-auth`) его аутентифицировала. Этот путь SHALL использоваться, когда `IdentityProvider` не предоставляет собственный список ролей (`VerifiedIdentity.roles == null`).

#### Scenario: Резолвинг из БД даёт тот же результат, что и снапшот в токене
- **WHEN** для одного и того же пользователя с одним и тем же набором `RoleAssignment` эффективные роли резолвятся один раз через снапшот в claims access-токена (local-провайдер) и один раз напрямую из `role_assignments`/`team_members` (fallback-путь)
- **THEN** оба способа возвращают одинаковый набор `{role, scope_type, scope_id}` — резолвинг из БД является источником истины, которому снапшот в токене обязан соответствовать на момент выдачи

### Requirement: Область видимости роли определяет её действие
`RoleAssignment` со `scope_type: global` SHALL действовать на все ресурсы сервиса; `scope_type: group` SHALL действовать на указанную группу и все её текущие и будущие проекты/команды; `scope_type: project` SHALL действовать только на указанный проект.

#### Scenario: Грант на уровне группы покрывает новый проект, созданный позже
- **WHEN** пользователь имеет `RoleAssignment(role: user, scope: group:G)`, а затем в `G` создаётся новый проект `P`
- **THEN** пользователь немедленно имеет доступ к `P` без отдельного гранта на `P`

#### Scenario: Грант на уровне проекта не даёт доступа к остальным проектам той же группы
- **WHEN** пользователь имеет только `RoleAssignment(role: user, scope: project:P)`, где `P` принадлежит группе `G`, содержащей также проект `P2`
- **THEN** у пользователя нет доступа к `P2` и нет доступа к агрегированному запросу по `group_id: G`

### Requirement: Выдача роли команде действует на всех её текущих участников
`RoleAssignment` с `subject_type: team` SHALL резолвиться в эффективные права каждого текущего участника этой команды при выдаче/обновлении его access-токена, без создания отдельных записей на каждого участника. «Немедленно» здесь означает: на следующий успешный запрос токена (первичный или через `refresh_token`) этого участника — механизм, которым это обеспечивается для уже выданных токенов (инвалидация через `User.token_version`), определён в `log-server-auth`.

#### Scenario: Новый участник команды получает её права со следующим токеном
- **WHEN** команда `T` имеет `RoleAssignment(role: user, scope: project:P)`, и в `T` добавлен новый участник `U`
- **THEN** ближайший access-токен, выданный `U` (`grant_type=password` или `refresh_token`), содержит в `roles` доступ к `P` через членство в `T`, без отдельного `RoleAssignment` на `U`

#### Scenario: Удаление участника из команды немедленно убирает унаследованные права
- **WHEN** участник `U` состоит в команде `T` с `RoleAssignment(role: user, scope: project:P)`, и `U` удалён из `T`
- **THEN** `token_version` пользователя `U` увеличивается, уже выданные ему access-токены перестают приниматься, а любой новый токен `U` не содержит доступа к `P` через эту команду (если у него нет отдельного прямого гранта)

### Requirement: Правила выдачи и отзыва ролей ограничены ролью и областью выдающего
Создание/отзыв `RoleAssignment` через `POST /v1/role-assignments`/`DELETE /v1/role-assignments/:id` SHALL быть ограничено: `admin` может выдать/отозвать любую роль на любой области; `owner` группы `G` может выдать/отозвать только роли `owner` или `user` на область `group:G` или `project:P` (где `P` принадлежит `G`), пользователю или команде внутри `G`; `user` не может создавать/отзывать `RoleAssignment` ни при каких обстоятельствах.

#### Scenario: owner не может выдать роль admin
- **WHEN** пользователь с `RoleAssignment(role: owner, scope: group:G)` отправляет `POST /v1/role-assignments` с `role: admin`
- **THEN** сервер отвечает 403 и не создаёт запись

#### Scenario: owner не может выдавать права за пределами своей группы
- **WHEN** пользователь с `RoleAssignment(role: owner, scope: group:G)` отправляет `POST /v1/role-assignments` с `scope: project:P2`, где `P2` принадлежит другой группе `G2`
- **THEN** сервер отвечает 403 и не создаёт запись

#### Scenario: user не может выдавать роли
- **WHEN** пользователь, чьи все `RoleAssignment` имеют `role: user`, отправляет `POST /v1/role-assignments` с любыми параметрами
- **THEN** сервер отвечает 403 и не создаёт запись

### Requirement: Создание пользователей и групп ограничено ролью admin
`POST /v1/users` и `POST /v1/groups` SHALL быть доступны только пользователям с `RoleAssignment(role: admin, scope: global)`.

#### Scenario: owner не может создать новую группу
- **WHEN** пользователь с `RoleAssignment(role: owner, scope: group:G)` (без роли `admin`) отправляет `POST /v1/groups`
- **THEN** сервер отвечает 403 и не создаёт группу

### Requirement: Управление командами, проектами, квотами и секретными ключами ограничено owner/admin в рамках группы
`POST`/`PATCH`/`DELETE` на `teams`, `projects` (включая квоты `retention_days`/`max_entries`/`max_bytes`) и `project_secret_keys` внутри группы `G` SHALL быть доступны пользователям с `RoleAssignment(role: admin, scope: global)` или `RoleAssignment(role: owner, scope: group:G)` (прямо или через команду); пользователям только с ролью `user` на `G` или её проекты SHALL быть доступно только чтение (`GET`), не изменение.

#### Scenario: user с доступом на чтение не может ротировать секретный ключ проекта
- **WHEN** пользователь с `RoleAssignment(role: user, scope: project:P)` отправляет `POST /v1/projects/P/secret-keys`
- **THEN** сервер отвечает 403 и не создаёт новый ключ
