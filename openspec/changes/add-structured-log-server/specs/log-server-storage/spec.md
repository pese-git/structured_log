## ADDED Requirements

### Requirement: Хранение записи лога с привязкой к проекту и сохранением исходного контекста
Каждая принятая запись SHALL сохраняться в SQLite с обязательной привязкой к `project_id` (проект, определённый секретным ключом, которым была аутентифицирована запись) и с полным исходным JSON-содержимым (включая произвольные пользовательские поля `context`, не имеющие фиксированной схемы) без потери данных.

#### Scenario: Произвольное пользовательское поле переживает round-trip
- **WHEN** сохранена запись с пользовательским полем `context`, отсутствующим в типизированных колонках схемы
- **THEN** это поле присутствует и доступно в исходном виде при последующем запросе этой записи вызывающим с доступом к её проекту

#### Scenario: Запись всегда привязана к ровно одному проекту
- **WHEN** запись сохранена через `POST /v1/logs`, аутентифицированный секретным ключом проекта `P`
- **THEN** сохранённая запись имеет `project_id = P`, и запрос с `project_id`, отличным от `P`, эту запись не возвращает

### Requirement: Типизированные колонки под часто фильтруемые поля
Схема хранения SHALL выделять отдельные индексированные колонки для `project_id`, `timestamp`, `level`, `category`, `logger`, `session_id`, `request_id`, чтобы фильтрация по ним не требовала полного сканирования таблицы; составной индекс SHALL покрывать `(project_id, level, timestamp)` как самый частый паттерн запроса (область видимости + уровень + диапазон времени).

#### Scenario: Фильтрация по проекту и уровню использует индекс
- **WHEN** выполняется запрос с фильтром по `project_id` и `level` на таблице с большим числом записей нескольких проектов
- **THEN** план выполнения запроса использует индекс, покрывающий `project_id`/`level`, а не полное сканирование таблицы

### Requirement: received_at и size_bytes фиксируются независимо от содержимого записи
Каждая сохранённая запись SHALL иметь `received_at` (момент приёма сервером, независимо от клиентского `timestamp`) и `size_bytes` (размер сериализованной записи в байтах, используемый для квоты `max_bytes` — `log-server-quotas`).

#### Scenario: received_at не совпадает с timestamp при задержке доставки
- **WHEN** клиент отправляет запись со значением `timestamp` в прошлом (отложенная доставка батчингом/retry на клиенте)
- **THEN** сохранённая запись содержит оба значения: исходный `timestamp` и `received_at`, равный фактическому моменту приёма сервером

### Requirement: Фильтрация по произвольным полям context через JSON1
Хранилище SHALL поддерживать точное совпадение по значению произвольного пользовательского ключа внутри сохранённого JSON-контекста без необходимости заранее объявлять этот ключ в схеме.

#### Scenario: Запрос по незаранее известному ключу контекста
- **WHEN** сохранены записи одного проекта с разными значениями пользовательского ключа `context.order_id`, не входящего в типизированные колонки
- **THEN** запрос с фильтром на конкретное значение `order_id` возвращает только записи с этим значением

### Requirement: Мультитенантные сущности управления доступом
Хранилище SHALL предоставлять таблицы `users` (id, username уникален, password_hash, display_name, created_at, is_active, token_version — целочисленный счётчик, по умолчанию 0), `groups` (id, name, created_at), `teams` (id, group_id — ровно одна группа, name, created_at), `team_members` (team_id, user_id — связь многие-ко-многим), `projects` (id, group_id, name, retention_days, max_entries, max_bytes, created_at), `project_secret_keys` (id, project_id, key_hash, label, created_at, revoked_at — nullable) и `role_assignments` (id, subject_type — user|team, subject_id, role — admin|owner|user, scope_type — global|group|project, scope_id — nullable для global, created_at).

#### Scenario: username уникален по всей системе
- **WHEN** отправлен запрос на создание пользователя (регистрация или через admin) с `username`, уже занятым другим пользователем
- **THEN** сервер отклоняет запрос и не создаёт вторую запись с тем же `username`

#### Scenario: Проект всегда принадлежит ровно одной группе
- **WHEN** создан проект через management API
- **THEN** сохранённая запись `projects` имеет непустой `group_id`, ссылающийся на существующую `groups`

#### Scenario: Команда принадлежит ровно одной группе
- **WHEN** создана команда через management API
- **THEN** сохранённая запись `teams` имеет непустой `group_id`, и все последующие члены этой команды (`team_members`) не привязываются к какой-либо другой группе через эту команду

#### Scenario: RoleAssignment хранит область видимости согласованно с её типом
- **WHEN** сохранён `role_assignments` со `scope_type: global`
- **THEN** `scope_id` этой записи — `null`; для `scope_type: group` или `scope_type: project` `scope_id` — непустая ссылка на существующую `groups`/`projects` соответственно

### Requirement: Хранение refresh-токенов
Хранилище SHALL предоставлять таблицу `refresh_tokens` (id, user_id, token_hash, created_at, expires_at, revoked_at — nullable) для отзываемых refresh-токенов пользователей (`log-server-auth`); `token_hash` SHALL быть хэшем токена, не самим токеном в открытом виде.

#### Scenario: Отозванный refresh-токен помечен, а не удалён
- **WHEN** refresh-токен отозван через `DELETE /v1/auth/token` или через ротацию при `grant_type=refresh_token`
- **THEN** соответствующая запись `refresh_tokens` остаётся в хранилище с непустым `revoked_at`, а не удаляется — это позволяет отличить «токен не существовал» от «токен существовал, но уже отозван» при обнаружении повторного использования

### Requirement: Учёт использования хранилища на проект
Хранилище SHALL поддерживать таблицу `project_usage` (project_id — PK, entry_count, total_bytes), обновляемую атомарно в той же транзакции, что вставка батча записей лога и что периодическая очистка по retention (`log-server-quotas`), чтобы проверка текущего использования была дешёвым point-lookup, а не агрегирующим запросом по `log_entries`.

#### Scenario: Использование растёт при вставке и уменьшается при очистке
- **WHEN** в проект `P` вставлен батч из `N` записей суммарным размером `S` байт, а затем периодическая очистка удаляет `M` из них суммарным размером `T` байт
- **THEN** `project_usage.entry_count` для `P` равен (предыдущее значение + N − M), а `total_bytes` — (предыдущее значение + S − T)

### Requirement: Миграция схемы при старте сервера
При старте сервер SHALL проверять текущую версию схемы файла базы данных и применять недостающие миграции идемпотентно, не теряя уже сохранённые данные.

#### Scenario: Повторный запуск на существующей базе не теряет данные
- **WHEN** сервер останавливается и повторно запускается с уже существующим файлом базы данных, содержащим записи и мультитенантные сущности
- **THEN** после повторного запуска все ранее сохранённые данные остаются доступны через management/query API

### Requirement: Режим журналирования WAL
База данных SHALL быть сконфигурирована в режиме `journal_mode=WAL`, чтобы чтение через query API не блокировалось конкурентной записью батча.

#### Scenario: Запрос не блокируется параллельной вставкой
- **WHEN** выполняется `GET /v1/logs` одновременно с выполняющейся вставкой батча через `POST /v1/logs`
- **THEN** запрос на чтение успешно завершается без ошибки блокировки базы данных
