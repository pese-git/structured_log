## ADDED Requirements

### Requirement: Хранение записи лога с сохранением исходного контекста
Каждая принятая запись SHALL сохраняться в SQLite с полным исходным JSON-содержимым (включая произвольные пользовательские поля `context`, не имеющие фиксированной схемы) без потери данных, даже если запись содержит поля, не отражённые в типизированных колонках.

#### Scenario: Произвольное пользовательское поле переживает round-trip
- **WHEN** сохранена запись с пользовательским полем `context`, отсутствующим в типизированных колонках схемы (например, произвольный вложенный объект)
- **THEN** это поле присутствует и доступно в исходном виде при последующем запросе этой записи

### Requirement: Типизированные колонки под часто фильтруемые поля
Схема хранения SHALL выделять отдельные индексированные колонки для `timestamp`, `level`, `category`, `logger`, `session_id`, `request_id`, чтобы фильтрация по ним не требовала полного сканирования таблицы.

#### Scenario: Фильтрация по уровню использует индекс
- **WHEN** выполняется запрос с фильтром по `level` на таблице с большим числом записей
- **THEN** план выполнения запроса использует индекс по колонке `level` (или составной индекс, включающий `level`), а не полное сканирование таблицы

### Requirement: received_at фиксируется независимо от клиентского timestamp
Каждая сохранённая запись SHALL иметь поле `received_at`, устанавливаемое сервером в момент приёма, независимо от значения `timestamp`, присланного клиентом.

#### Scenario: received_at не совпадает с timestamp при задержке доставки
- **WHEN** клиент отправляет запись со значением `timestamp` в прошлом (например, отправка была отложена батчингом/retry на клиенте)
- **THEN** сохранённая запись содержит оба значения: исходный `timestamp` и `received_at`, равный фактическому моменту приёма сервером

### Requirement: Фильтрация по произвольным полям context через JSON1
Хранилище SHALL поддерживать точное совпадение по значению произвольного пользовательского ключа внутри сохранённого JSON-контекста без необходимости заранее объявлять этот ключ в схеме.

#### Scenario: Запрос по незаранее известному ключу контекста
- **WHEN** сохранены записи с разными значениями пользовательского ключа `context.order_id`, не входящего в типизированные колонки
- **THEN** запрос с фильтром на конкретное значение `order_id` возвращает только записи с этим значением

### Requirement: Миграция схемы при старте сервера
При старте сервер SHALL проверять текущую версию схемы файла базы данных и применять недостающие миграции идемпотентно, не теряя уже сохранённые данные.

#### Scenario: Повторный запуск на существующей базе не теряет данные
- **WHEN** сервер останавливается и повторно запускается с уже существующим файлом базы данных, содержащим записи
- **THEN** после повторного запуска все ранее сохранённые записи остаются доступны через query API

### Requirement: Режим журналирования WAL
База данных SHALL быть сконфигурирована в режиме `journal_mode=WAL`, чтобы чтение через query API не блокировалось конкурентной записью батча.

#### Scenario: Запрос не блокируется параллельной вставкой
- **WHEN** выполняется `GET /v1/logs` одновременно с выполняющейся вставкой батча через `POST /v1/logs`
- **THEN** запрос на чтение успешно завершается без ошибки блокировки базы данных
