## ADDED Requirements

### Requirement: Каждый проект обязан иметь квоту хранения
При создании проекта `retention_days` SHALL быть обязательным полем; `max_entries` и `max_bytes` SHALL быть опциональными (отсутствие значения означает отсутствие лимита по этому измерению).

#### Scenario: Создание проекта без retention_days отклоняется
- **WHEN** отправлен запрос на создание проекта без поля `retention_days`
- **THEN** сервер отвечает 400 и не создаёт проект

#### Scenario: Проект может быть создан без ограничения по объёму
- **WHEN** отправлен запрос на создание проекта с `retention_days`, но без `max_entries`/`max_bytes`
- **THEN** проект создаётся, и приём логов в него не отклоняется по причине `quota_exceeded` (ограничение действует только по `retention_days`)

### Requirement: Периодическая очистка по сроку хранения
Сервер SHALL периодически (с конфигурируемым интервалом) удалять записи `log_entries`, чей `received_at` старше `retention_days` их проекта, и уменьшать соответствующий `project_usage` на количество и суммарный размер удалённых записей.

#### Scenario: Запись старше retention_days удаляется при следующем цикле очистки
- **WHEN** запись проекта с `retention_days = 30` имеет `received_at` старше 30 дней назад, и наступает очередной цикл периодической очистки
- **THEN** эта запись удаляется из `log_entries`, а `project_usage` этого проекта уменьшается на её количество и размер

#### Scenario: Запись в пределах срока хранения не затрагивается очисткой
- **WHEN** запись проекта с `retention_days = 30` имеет `received_at` моложе 30 дней назад
- **THEN** цикл периодической очистки эту запись не удаляет

### Requirement: Отказ в приёме записей, превышающих лимит объёма
При приёме батча (`POST /v1/logs`) сервер SHALL для каждой записи проверять, не привело бы её добавление к превышению `max_entries` или `max_bytes` проекта (если они заданы), используя текущее значение `project_usage`; записи, приводящие к превышению, SHALL отклоняться индивидуально (частичный приём батча, как при ошибках валидации в `log-server-api`) с кодом ошибки `quota_exceeded` и HTTP-статусом `507`.

#### Scenario: Запись, укладывающаяся в лимит, принимается
- **WHEN** у проекта `max_entries = 1000`, текущее `project_usage.entry_count = 999`, и батч содержит одну валидную запись
- **THEN** эта запись принимается, и `project_usage.entry_count` становится 1000

#### Scenario: Запись, превышающая лимит количества, отклоняется
- **WHEN** у проекта `max_entries = 1000`, текущее `project_usage.entry_count = 1000`, и батч содержит ещё одну запись
- **THEN** эта запись отклоняется с кодом `quota_exceeded`, `project_usage.entry_count` остаётся 1000, а ответ сервера — `507` с телом, перечисляющим эту запись как отклонённую

#### Scenario: Запись, превышающая лимит объёма в байтах, отклоняется
- **WHEN** у проекта `max_bytes` задан, и `project_usage.total_bytes` плюс размер очередной записи батча превысил бы `max_bytes`
- **THEN** эта запись отклоняется с кодом `quota_exceeded`, не увеличивая `project_usage.total_bytes`

#### Scenario: Записи внутри одного батча учитываются последовательно
- **WHEN** батч содержит несколько записей, и лимит `max_entries` был бы превышен на N-й записи батча (первые N−1 — в пределах лимита)
- **THEN** первые N−1 записей принимаются, N-я и последующие отклоняются с кодом `quota_exceeded`

### Requirement: Владелец/администратор может изменять квоту существующего проекта
`PATCH /v1/projects/:id`, доступный `owner` группы проекта или `admin` (см. `log-server-rbac`), SHALL позволять изменять `retention_days`, `max_entries` и `max_bytes` без пересоздания проекта или его секретных ключей.

#### Scenario: Повышение лимита сразу разрешает приём ранее отклонявшихся записей
- **WHEN** проект отклонял записи по `quota_exceeded` из-за `max_entries`, и владелец группы увеличивает `max_entries` через `PATCH /v1/projects/:id`
- **THEN** последующие батчи, укладывающиеся в новый лимит, принимаются без дальнейших `quota_exceeded`-отказов по этой причине
