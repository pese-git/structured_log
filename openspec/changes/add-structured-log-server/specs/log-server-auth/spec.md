## ADDED Requirements

### Requirement: Самостоятельная регистрация пользователя, переключаемая конфигурацией сервера
Сервер SHALL предоставлять `POST /v1/auth/register`, принимающий `username`, пароль, обязательный `email` и опционально `display_name`; при уникальных `username` и `email` SHALL создавать нового `User` без единого `RoleAssignment` (то есть без доступа ни к одному ресурсу до явной выдачи роли). Доступность этого эндпоинта SHALL управляться конфигурацией сервера (`registrationEnabled`, задаваемой CLI-флагом или переменной окружения при старте); по умолчанию SHALL быть выключена. Обязательность `email` действует только для этого эндпоинта — при создании пользователя администратором (`POST /v1/users`) `email` остаётся опциональным (см. `log-server-password-reset`), так что колонка `User.email` в схеме хранения — `nullable`. Заданный этим путём `email` SHALL считаться неподтверждённым до завершения flow из `log-server-email-verification`, который блокирует `grant_type=password` для этой учётной записи, пока он не пройден.

#### Scenario: Успешная регистрация при включённой конфигурации
- **WHEN** сервер запущен с `registrationEnabled = true`, и отправлен `POST /v1/auth/register` с ещё не занятыми `username`/`email` и паролем
- **THEN** сервер отвечает 201, создаёт нового пользователя с сохранённым `email`, и у этого пользователя нет ни одного `RoleAssignment`

#### Scenario: Регистрация отклоняется при выключенной конфигурации
- **WHEN** сервер запущен с `registrationEnabled = false` (или без явного указания — значение по умолчанию), и отправлен `POST /v1/auth/register`
- **THEN** сервер отвечает 403 и не создаёт пользователя

#### Scenario: Занятый username отклоняется
- **WHEN** `registrationEnabled = true`, и отправлен `POST /v1/auth/register` с `username`, уже существующим в системе
- **THEN** сервер отвечает 409 и не создаёт вторую запись

#### Scenario: Занятый email отклоняется
- **WHEN** `registrationEnabled = true`, и отправлен `POST /v1/auth/register` с `email`, уже сохранённым у другого пользователя
- **THEN** сервер отвечает 409 и не создаёт вторую запись

#### Scenario: Отсутствие email отклоняется
- **WHEN** `registrationEnabled = true`, и отправлен `POST /v1/auth/register` без поля `email` (или с пустым значением)
- **THEN** сервер отвечает 400 и не создаёт пользователя

#### Scenario: Создание пользователя администратором не зависит от флага регистрации
- **WHEN** `registrationEnabled = false`, и пользователь с ролью `admin` отправляет `POST /v1/users`
- **THEN** пользователь создаётся независимо от значения `registrationEnabled`

### Requirement: Пароли хранятся хэшированными
Сервер SHALL хранить `password_hash` пользователя через адаптивный алгоритм хэширования (`bcrypt`), никогда не сохраняя и не логируя пароль в открытом виде.

#### Scenario: В базе данных нет пароля в открытом виде
- **WHEN** создан пользователь с паролем (через регистрацию или management API)
- **THEN** значение, сохранённое в колонке `password_hash`, не совпадает с исходным паролем и не может быть тривиально обращено без подбора

### Requirement: Единый OAuth2-совместимый token-эндпоинт (RFC 6749)
Сервер SHALL предоставлять `POST /v1/auth/token`, принимающий тело `application/x-www-form-urlencoded` с обязательным полем `grant_type`, различающий два сценария: `grant_type=password` (поля `username`, `password`) и `grant_type=refresh_token` (поле `refresh_token`). При успехе SHALL возвращать JSON-тело со стандартными полями RFC 6749 §5.1: `access_token`, `token_type` (`"Bearer"`), `expires_in`, `refresh_token`, `refresh_expires_in`. Любая ошибка этого эндпоинта (неверные креды, недействительный `grant_type`, недостающее поле) SHALL возвращать тело в формате RFC 6749 §5.2: `{"error": "<invalid_grant|invalid_request|unsupported_grant_type>", "error_description": "..."}` (отказ по причине неподтверждённого email — `log-server-email-verification` — SHALL дополнительно нести нестандартное поле `reason: "email_not_verified"` поверх этой формы) — этот формат применяется к `POST /v1/auth/token` и `DELETE /v1/auth/token`, отдельно от общего JSON-конверта ошибок остального API (`log-server-api`). Оба сценария (`password` и `refresh_token`) SHALL заново резолвить эффективные роли пользователя и текущее значение `token_version` при каждой выдаче — не копировать их из ранее выданного токена (см. следующее требование).

#### Scenario: grant_type=password с верными кредами выдаёт пару токенов
- **WHEN** отправлен `POST /v1/auth/token` (form-encoded) с `grant_type=password`, `username` и `password`, совпадающими с активным (`is_active = true`) пользователем
- **THEN** сервер отвечает 200 с телом, содержащим `access_token` (валидная подпись, корректный `sub`), `token_type: "Bearer"`, `expires_in`, `refresh_token`, `refresh_expires_in`

#### Scenario: grant_type=password с неверным паролем отклоняется в формате RFC 6749
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=password` и неверным паролем для существующего `username`
- **THEN** сервер отвечает 400 (или 401) с телом `{"error": "invalid_grant", ...}` и не выдаёт токены

#### Scenario: grant_type=password для неактивного пользователя отклоняется
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=password` и корректными кредами пользователя, у которого `is_active = false`
- **THEN** сервер отвечает с телом `{"error": "invalid_grant", ...}` и не выдаёт токены

#### Scenario: grant_type=password для неподтверждённого email отклоняется
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=password` и корректными кредами пользователя, у которого `email` задан, но не подтверждён (`log-server-email-verification`)
- **THEN** сервер отвечает телом `{"error": "invalid_grant", "reason": "email_not_verified", ...}` и не выдаёт токены

#### Scenario: Неизвестный grant_type отклоняется
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type`, отличным от `password` и `refresh_token`
- **THEN** сервер отвечает с телом `{"error": "unsupported_grant_type", ...}`

### Requirement: grant_type=refresh_token хранится хэшированным и ротируется при использовании
Refresh-токен SHALL храниться на сервере как хэш случайно сгенерированной строки (не как пароль пользователя, не как JWT). При `grant_type=refresh_token` сервер SHALL проверять хэш предъявленного `refresh_token`, срок действия, отсутствие отзыва **и `is_active` пользователя, к которому привязан токен**; при успехе SHALL отзывать предъявленный refresh-токен и выдавать новую пару (ротация). Предъявление уже отозванного refresh-токена SHALL приводить к отзыву всех refresh-токенов этого пользователя.

#### Scenario: Неактивный пользователь не может получить новый access-токен через refresh, даже с действительным refresh-токеном
- **WHEN** пользователь заблокирован (`is_active = false` — `log-server-rbac`), но у него остался не отозванный, не истёкший refresh-токен, выданный до блокировки, и он предъявлен с `grant_type=refresh_token`
- **THEN** сервер отвечает ошибкой `invalid_grant` и не выдаёт новую пару токенов — та же защита, что действует для отозванного/истёкшего токена, применяется независимо от того, был ли сам этот конкретный refresh-токен явно отозван

#### Scenario: Успешное обновление ротирует токен
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=refresh_token` и валидным, не отозванным, не истёкшим `refresh_token`
- **THEN** сервер отвечает новой парой токенов, а предъявленный refresh-токен становится отозванным и больше не принимается ни в одном последующем запросе с `grant_type=refresh_token`

#### Scenario: Истёкший или отозванный refresh-токен отклоняется
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=refresh_token`, чей `expires_at` уже наступил, либо `revoked_at` уже установлен
- **THEN** сервер отвечает телом `{"error": "invalid_grant", ...}` и не выдаёт новую пару токенов

#### Scenario: Повторное использование отозванного refresh-токена отзывает все токены пользователя
- **WHEN** refresh-токен `A` пользователя был отозван (ротацией или через `DELETE /v1/auth/token`), и затем `A` повторно предъявлен с `grant_type=refresh_token`
- **THEN** сервер отвечает ошибкой `invalid_grant`, и все остальные ещё не отозванные refresh-токены этого пользователя также становятся отозванными

### Requirement: Отзыв refresh-токена через DELETE /v1/auth/token (RFC 7009)
Сервер SHALL предоставлять `DELETE /v1/auth/token`, принимающий тело `application/x-www-form-urlencoded` с полем `refresh_token` (тот же путь, что создаёт токен через `POST`, но с методом, выражающим удаление ресурса — по образцу того, как Keycloak трактует отзыв токена как revocation, а не как отдельную стороннюю операцию), немедленно помечающий предъявленный refresh-токен отозванным; уже выданный вместе с ним access-токен SHALL оставаться технически валидным до истечения своего короткого срока действия. Вслед за RFC 7009 §2.2 сервер SHALL отвечать успехом (200, пустое тело) независимо от того, был ли предъявленный токен валиден, уже отозван или не существовал — чтобы не давать вызывающему возможность через код ответа проверять валидность чужого токена; единственная причина ответить ошибкой (400, формат RFC 6749 §5.2) — отсутствие поля `refresh_token` в запросе.

#### Scenario: Отозванный токен больше не работает
- **WHEN** выполнен `DELETE /v1/auth/token` с действующим `refresh_token` в form-encoded теле, а затем этот же токен предъявлен с `grant_type=refresh_token` на `POST /v1/auth/token`
- **THEN** сервер отвечает ошибкой `invalid_grant` на повторное использование

#### Scenario: Отзыв всегда отвечает успехом, не раскрывая валидность токена
- **WHEN** выполнен `DELETE /v1/auth/token` с `refresh_token`, который уже отозван, истёк или никогда не существовал
- **THEN** сервер отвечает 200 с пустым телом — так же, как при отзыве действительного токена, без различимой по ответу разницы

#### Scenario: Отсутствие refresh_token в теле отклоняется
- **WHEN** выполнен `DELETE /v1/auth/token` без поля `refresh_token` в form-encoded теле
- **THEN** сервер отвечает 400 с телом `{"error": "invalid_request", ...}`

### Requirement: Пользователь может безвозвратно удалить собственный аккаунт
Сервер SHALL предоставлять `DELETE /v1/users/me`, доступный любому аутентифицированному пользователю (`admin`/`owner`/`user`) исключительно над собственной учётной записью, принимающий JSON-тело `{"password": "..."}` с текущим паролем как подтверждением. При совпадении пароля и прохождении проверок единственного владельца группы и основного администратора (см. «Требование: Удаление блокируется, если пользователь — единственный владелец группы» и «Требование: Основной (первый) администратор не может быть удалён» ниже) сервер SHALL атомарно: установить `deleted_at` (текущее время) и `is_active = false`, отозвать все refresh-токены этого пользователя, инкрементировать `token_version`, а также отозвать его прямые роли и членство в командах (см. «Требование: Успешное удаление отзывает прямые роли и членство пользователя в командах» ниже). Удаление SHALL быть необратимым через API — сервер не SHALL предоставлять способ снять `deleted_at`.

#### Scenario: Успешное удаление собственного аккаунта завершает текущую сессию
- **WHEN** аутентифицированный пользователь отправляет `DELETE /v1/users/me` с верным текущим паролем, не являясь единственным владельцем ни одной группы
- **THEN** сервер отвечает успехом, его `deleted_at` установлен, `is_active` — `false`, а уже выданный ему access-токен перестаёт приниматься на следующем запросе (несовпадение `token_version`)

#### Scenario: Неверный пароль отклоняет удаление
- **WHEN** аутентифицированный пользователь отправляет `DELETE /v1/users/me` с неверным паролем
- **THEN** сервер отвечает 401 (или 400) и не удаляет аккаунт

#### Scenario: Через этот эндпоинт можно удалить только собственный аккаунт
- **WHEN** аутентифицированный пользователь пытается удалить чужую учётную запись через `DELETE /v1/users/me` (эндпоинт не принимает идентификатор пользователя — он всегда действует на вызывающего)
- **THEN** удалён может быть только сам вызывающий, независимо от его роли; удаление чужой учётной записи доступно `admin`-у отдельным эндпоинтом (см. «Требование: Администратор может безвозвратно удалить любую другую учётную запись» ниже)

### Requirement: Администратор может безвозвратно удалить любую другую учётную запись
Сервер SHALL предоставлять `DELETE /v1/users/:id`, выполняющий над указанным пользователем те же атомарные действия и те же проверки (единственного владельца группы, основного администратора), что `DELETE /v1/users/me` выполняет над вызывающим, но не требующий подтверждения паролем цели — вызывающий уже аутентифицирован собственной сессией с ролью `admin` (ограничение доступа к этому эндпоинту — `log-server-rbac`). Эндпоинт SHALL отклонять (400) вызов, где `:id` равен идентификатору самого вызывающего — самоудаление выполняется только через `DELETE /v1/users/me`.

#### Scenario: Администратор удаляет чужую учётную запись без пароля цели
- **WHEN** пользователь с ролью `admin` отправляет `DELETE /v1/users/:id` для другого пользователя, не являющегося единственным владельцем ни одной группы
- **THEN** сервер удаляет указанную учётную запись (`deleted_at`, `is_active = false`, отзыв refresh-токенов, инкремент `token_version`, отзыв ролей/членства в командах), не запрашивая пароль этого пользователя

#### Scenario: Администратор не может удалить себя через этот эндпоинт
- **WHEN** пользователь с ролью `admin` отправляет `DELETE /v1/users/:id`, где `:id` — его собственный идентификатор
- **THEN** сервер отвечает 400 и не удаляет аккаунт — самоудаление доступно только через `DELETE /v1/users/me`

### Requirement: Удаление блокируется, если пользователь — единственный владелец группы
Перед применением любых изменений `DELETE /v1/users/me` и `DELETE /v1/users/:id` SHALL проверить, не является ли целевой пользователь единственным обладателем `RoleAssignment(role: owner, scope: group:G)` (прямо или через команду) хотя бы для одной группы `G` — то есть не существует другого пользователя/команды с ролью `owner` на ту же `G`. Если такая группа (или несколько) найдена, сервер SHALL отклонить запрос с 409 и кодом `sole_group_owner`, включив в тело ответа идентификаторы блокирующих групп, и SHALL не выполнять удаление частично — ни в одной из затронутых таблиц не должно быть изменений.

#### Scenario: Единственный владелец группы не может быть удалён до передачи прав
- **WHEN** пользователь — единственный `owner` группы `G` (нет другого пользователя/команды с ролью `owner` на `G`) — отправляет `DELETE /v1/users/me` (или `admin` отправляет `DELETE /v1/users/:id` для него)
- **THEN** сервер отвечает 409 с кодом `sole_group_owner` и списком, включающим `G`, не изменяя ни `deleted_at`, ни какие-либо `role_assignments`

#### Scenario: После передачи владения удаление проходит успешно
- **WHEN** единственному владельцу группы `G` выдана роль `owner` ещё одному пользователю (или команде) на `G`, после чего исходный владелец повторно инициирует удаление своего аккаунта
- **THEN** сервер больше не находит `G` среди групп с единственным владельцем и выполняет удаление

#### Scenario: Совладелец группы не блокируется проверкой
- **WHEN** пользователь имеет `RoleAssignment(role: owner, scope: group:G)`, и на ту же `G` есть ещё как минимум один `owner` (пользователь или команда)
- **THEN** проверка единственного владельца не блокирует его удаление по причине `G`

### Requirement: Основной (первый) администратор не может быть удалён
`User.is_primary_admin` SHALL быть установлен ровно один раз — на пользователе, созданном самым первым успешным вызовом bootstrap-команды `create-admin`, и никогда не изменяться никаким другим путём после этого (ни через API, ни повторным `create-admin`). Перед применением любых изменений `DELETE /v1/users/me` и `DELETE /v1/users/:id` SHALL проверять, не установлен ли у целевого пользователя `is_primary_admin = true`; если установлен — сервер SHALL отклонить запрос с 403 и кодом `cannot_delete_primary_admin`, не внося никаких изменений в БД. Эта проверка не зависит от того, сколько ещё активных `admin` есть в системе — основной администратор защищён по идентичности, а не по счётчику оставшихся `admin`.

#### Scenario: Основной администратор не может удалить себя
- **WHEN** пользователь с `is_primary_admin = true` отправляет `DELETE /v1/users/me` с верным паролем
- **THEN** сервер отвечает 403 с кодом `cannot_delete_primary_admin` и не изменяет `deleted_at`/`is_active` этого пользователя

#### Scenario: Другой администратор не может удалить основного администратора
- **WHEN** пользователь с ролью `admin` (не основной) отправляет `DELETE /v1/users/:id`, где `:id` — основной администратор
- **THEN** сервер отвечает 403 с кодом `cannot_delete_primary_admin` и не удаляет учётную запись, даже если в системе есть другие активные `admin`

#### Scenario: Не-основной администратор может быть удалён обычным образом
- **WHEN** `admin`, у которого `is_primary_admin = false`, удаляется — самостоятельно или другим `admin` — и не является единственным владельцем ни одной группы
- **THEN** удаление проходит успешно тем же путём, что и для любого другого пользователя — защита распространяется только на основного администратора, не на роль `admin` в целом

#### Scenario: Повторный create-admin не создаёт второго основного администратора
- **WHEN** `create-admin` выполняется повторно (например, потому что единственный активный `admin` на момент проверки был заблокирован, а не основной администратор) при том, что `is_primary_admin` уже установлен у существующего пользователя
- **THEN** новый администратор, созданный этим вызовом, получает `is_primary_admin = false` — флаг остаётся установленным ровно на одном пользователе за всю историю сервера

### Requirement: Успешное удаление отзывает прямые роли и членство пользователя в командах
При успешном выполнении `DELETE /v1/users/me` или `DELETE /v1/users/:id` сервер SHALL в той же транзакции, что установка `deleted_at`/`is_active`, удалить все записи `role_assignments`, где `subject_type: user` и `subject_id` равен удаляемому пользователю, и удалить его из всех `team_members`. Это безопасно ровно потому, что предыдущее требование гарантирует: среди этих записей нет ни одной, дающей ему единственное владение группой.

#### Scenario: Удаление убирает прямые роли пользователя
- **WHEN** у пользователя есть прямой `RoleAssignment(role: user, scope: project:P)`, не связанный с единственным владением какой-либо группой, и его аккаунт удалён (самостоятельно или администратором)
- **THEN** после удаления соответствующая запись `role_assignments` больше не существует

#### Scenario: Удаление убирает членство в командах
- **WHEN** пользователь состоит в команде `T`, и его аккаунт удалён
- **THEN** после удаления он больше не числится участником `T`, а `RoleAssignment`, выданные самой `T`, остаются нетронутыми для её остальных участников

### Requirement: Удалённый аккаунт не может аутентифицироваться
Удалённая (`deleted_at IS NOT NULL`) учётная запись SHALL быть неотличима с точки зрения аутентификации от заблокированной (`is_active = false`) — `grant_type=password` и `grant_type=refresh_token` SHALL её отклонять по тем же уже существующим проверкам `is_active`, без отдельного, нового кода проверки специально для удалённых аккаунтов.

#### Scenario: Удалённый пользователь не может войти по паролю
- **WHEN** удаливший свой аккаунт пользователь отправляет `POST /v1/auth/token` с `grant_type=password` и своими прежними `username`/паролем
- **THEN** сервер отвечает ошибкой `invalid_grant` — так же, как для заблокированного администратором пользователя

### Requirement: unblock не может реактивировать удалённый аккаунт
`POST /v1/users/:id/unblock` (`log-server-rbac`) SHALL отклоняться (400), если у целевого пользователя установлен `deleted_at` — блокировка и удаление используют общий переключатель `is_active`, но `unblock` не SHALL быть способом обойти необратимость удаления.

#### Scenario: Попытка разблокировать удалённого пользователя отклоняется
- **WHEN** `admin` отправляет `POST /v1/users/:id/unblock` для пользователя с установленным `deleted_at` (удалившего аккаунт самостоятельно через `DELETE /v1/users/me`, либо удалённого другим `admin` через `DELETE /v1/users/:id`)
- **THEN** сервер отвечает 400 и не изменяет `is_active` этого пользователя

### Requirement: Эффективные роли пользователя встроены в access-токен
Access-токен SHALL содержать claim `roles` — плоский снапшот эффективных прав пользователя на момент выдачи (прямых `RoleAssignment` и унаследованных через членство в командах), в форме массива объектов `{role, scope_type, scope_id}`, а также claim `tv`, равный значению `User.token_version` на момент выдачи. Middleware авторизации на management-эндпоинтах и `GET /v1/logs` SHALL проверять доступ по содержимому `roles`, не выполняя запрос к `role_assignments`/`team_members`/`teams` для этой проверки.

#### Scenario: roles содержит и прямые, и унаследованные через команду права
- **WHEN** пользователь имеет прямой `RoleAssignment(role: user, scope: project:P1)` и состоит в команде с `RoleAssignment(role: owner, scope: group:G2)`, и для него создаётся access-токен
- **THEN** claim `roles` этого токена содержит оба эффективных права — `{role: user, scope_type: project, scope_id: P1}` и `{role: owner, scope_type: group, scope_id: G2}`

#### Scenario: Middleware авторизации не обращается к таблицам ролей на каждый запрос
- **WHEN** обрабатывается запрос к `GET /v1/logs` с валидным access-токеном
- **THEN** решение о доступе принимается на основе claim `roles` из токена (после проверки `token_version` — см. следующее требование), без отдельного запроса к `role_assignments`/`team_members`/`teams`

### Requirement: token_version обеспечивает немедленный отзыв прав, несмотря на снапшот в токене
`User` SHALL иметь поле `token_version` (целое число, по умолчанию 0). Сервер SHALL атомарно увеличивать `token_version` пользователя при: создании/отзыве `RoleAssignment`, где subject — сам пользователь; изменении его членства в команде; создании/отзыве `RoleAssignment`, где subject — команда (каскадно для всех текущих участников этой команды); деактивации пользователя (`is_active = false`); смене пароля. Каждый запрос к management-эндпоинтам и `GET /v1/logs` SHALL требовать заголовок `Authorization: Bearer <access-token>` с действительным, не истёкшим access-токеном, чей claim `tv` SHALL совпадать с текущим `token_version` пользователя в хранилище — несовпадение SHALL приводить к 401, независимо от того, что записано в `roles` токена.

#### Scenario: Запрос без токена или с истёкшим access-токеном отклоняется
- **WHEN** запрос к management-эндпоинту или `GET /v1/logs` отправлен без заголовка `Authorization`, с неподписанным сервером токеном или с токеном, чей `exp` уже наступил
- **THEN** сервер отвечает 401 и не выполняет запрошенную операцию

#### Scenario: Отозванный после выдачи токена доступ действует немедленно
- **WHEN** пользователь получил валидный access-токен, затем администратор/владелец отозвал все его `RoleAssignment` (это увеличивает `token_version` пользователя), после чего пользователь повторно обращается к `GET /v1/logs` с тем же (ещё не истёкшим по `exp`) access-токеном
- **THEN** сервер отвечает 401, поскольку claim `tv` этого токена больше не совпадает с текущим `token_version`, независимо от того, что записано в `roles`

#### Scenario: Отзыв прав команде немедленно затрагивает всех её участников
- **WHEN** команда `T` с несколькими участниками имеет `RoleAssignment(role: user, scope: project:P)`, и этот `RoleAssignment` отзывается
- **THEN** `token_version` увеличивается у каждого текущего участника `T` одной операцией, и уже выданные им access-токены перестают приниматься

#### Scenario: После инвалидации токена клиент получает актуальные права через refresh
- **WHEN** access-токен отклонён с 401 из-за несовпадения `tv`, и клиент выполняет `POST /v1/auth/token` с `grant_type=refresh_token` и своим (ещё не отозванным) refresh-токеном
- **THEN** сервер выдаёт новый access-токен с текущим `token_version` в `tv` и заново резолвленным `roles`, отражающим актуальные права

### Requirement: Проверка access-токена реализована за интерфейсом IdentityProvider
Проверка access-токена на management-эндпоинтах и `GET /v1/logs` SHALL выполняться через реализацию интерфейса `IdentityProvider` (`verifyAccessToken(bearerToken) -> VerifiedIdentity?`), а не через код, жёстко завязанный на конкретный способ выдачи/проверки токена. Встроенная (local) реализация этого интерфейса SHALL инкапсулировать всё поведение, описанное в требованиях выше этого раздела (проверка подписи/срока действия JWT, `token_version`-проверка), так что эти детали не являются частью самого интерфейса. `VerifiedIdentity` SHALL содержать опциональный список ролей (`roles`); когда он равен `null`, вызывающий код (`log-server-rbac`) SHALL резолвить эффективные роли пользователя из `role_assignments`/`team_members` самостоятельно, вместо того чтобы требовать этот список от каждой реализации `IdentityProvider`.

#### Scenario: Local-реализация заполняет roles
- **WHEN** запрос аутентифицирован access-токеном, выданным встроенной (local) реализацией `IdentityProvider`
- **THEN** возвращённый `VerifiedIdentity.roles` не `null` и содержит эффективные права, заново резолвленные на момент выдачи этого токена (см. требования выше)

#### Scenario: Реализация без собственных ролей делегирует резолвинг вызывающему коду
- **WHEN** гипотетическая другая реализация `IdentityProvider` возвращает `VerifiedIdentity` с `roles: null` для успешно проверенного токена
- **THEN** middleware авторизации не считает это ошибкой и не требует непустого `roles` от `IdentityProvider` — вместо этого RBAC-логика (`log-server-rbac`) резолвит права из `role_assignments`/`team_members` по идентификатору пользователя, как если бы `IdentityProvider` вообще не предоставлял ролей

### Requirement: Аутентификация приёма логов по секретному ключу проекта
Секретные ключи проектов SHALL храниться как криптографический хэш случайно сгенерированного токена (не пароль пользователя, не JWT); при аутентификации `POST /v1/logs` (см. `log-server-api`) сервер SHALL находить соответствующий `project_id` по хэшу присланного ключа, отклоняя запрос, если совпадение не найдено или найденный ключ отозван (`revoked_at` не `null`).

#### Scenario: Секретный ключ показывается только один раз
- **WHEN** владелец группы или администратор создаёт новый секретный ключ проекта
- **THEN** ответ API содержит ключ в открытом виде ровно один раз (в ответе на создание); последующие запросы (например, список ключей проекта) возвращают только метаданные (`label`, `created_at`, `revoked_at`), не сам ключ

#### Scenario: Несколько активных ключей позволяют ротацию без даунтайма
- **WHEN** у проекта есть два одновременно активных, не отозванных секретных ключа, и приложение продолжает слать логи со старым ключом, пока новый уже выдан
- **THEN** приём логов успешен с обоих ключей, пока старый явно не отозван
