## ADDED Requirements

### Requirement: Логин пользователя выдаёт JWT
Сервер SHALL предоставлять `POST /v1/auth/login`, принимающий email и пароль; при совпадении с сохранённым `password_hash` активного пользователя (`is_active = true`) SHALL возвращать подписанный JWT-токен, содержащий идентификатор пользователя (`sub`) и срок действия (`exp`), но не список его ролей.

#### Scenario: Успешный логин выдаёт валидный токен
- **WHEN** отправлен `POST /v1/auth/login` с email и паролем, совпадающими с активным пользователем
- **THEN** сервер отвечает 200 с JWT-токеном, который проходит проверку подписи и содержит `sub`, равный идентификатору этого пользователя

#### Scenario: Неверный пароль отклоняется
- **WHEN** отправлен `POST /v1/auth/login` с email существующего пользователя, но неверным паролем
- **THEN** сервер отвечает 401 и не выдаёт токен

#### Scenario: Неактивный пользователь не может войти
- **WHEN** отправлен `POST /v1/auth/login` с корректными кредами пользователя, у которого `is_active = false`
- **THEN** сервер отвечает 401 и не выдаёт токен

### Requirement: Пароли хранятся хэшированными
Сервер SHALL хранить `password_hash` пользователя через адаптивный алгоритм хэширования (`bcrypt`), никогда не сохраняя и не логируя пароль в открытом виде.

#### Scenario: В базе данных нет пароля в открытом виде
- **WHEN** создан пользователь с паролем через management API
- **THEN** значение, сохранённое в колонке `password_hash`, не совпадает с исходным паролем и не может быть тривиально обращено без подбора

### Requirement: Аутентификация management/query API по JWT с пересчётом прав из БД
Каждый запрос к management-эндпоинтам и `GET /v1/logs` SHALL требовать заголовок `Authorization: Bearer <jwt>` с действительным, не истёкшим токеном, выданным `POST /v1/auth/login`; сервер SHALL на каждом запросе заново резолвить текущие `RoleAssignment` пользователя из хранилища (`log-server-rbac`), не полагаясь на состояние ролей, которое могло быть верным в момент выдачи токена.

#### Scenario: Запрос без токена или с истёкшим токеном отклоняется
- **WHEN** запрос к management-эндпоинту или `GET /v1/logs` отправлен без заголовка `Authorization`, с неподписанным сервером токеном или с токеном, чей `exp` уже наступил
- **THEN** сервер отвечает 401 и не выполняет запрошенную операцию

#### Scenario: Отозванный после выдачи токена доступ действует немедленно
- **WHEN** пользователь получил валидный JWT, затем администратор/владелец отозвал все его `RoleAssignment`, после чего пользователь повторно обращается к `GET /v1/logs` с тем же (ещё не истёкшим) токеном
- **THEN** сервер отвечает 403, поскольку текущее состояние прав в БД не даёт доступа, несмотря на формально валидный токен

### Requirement: Аутентификация приёма логов по секретному ключу проекта
Секретные ключи проектов SHALL храниться как криптографический хэш случайно сгенерированного токена (не пароль пользователя, не JWT); при аутентификации `POST /v1/logs` (см. `log-server-api`) сервер SHALL находить соответствующий `project_id` по хэшу присланного ключа, отклоняя запрос, если совпадение не найдено или найденный ключ отозван (`revoked_at` не `null`).

#### Scenario: Секретный ключ показывается только один раз
- **WHEN** владелец группы или администратор создаёт новый секретный ключ проекта
- **THEN** ответ API содержит ключ в открытом виде ровно один раз (в ответе на создание); последующие запросы (например, список ключей проекта) возвращают только метаданные (`label`, `created_at`, `revoked_at`), не сам ключ

#### Scenario: Несколько активных ключей позволяют ротацию без даунтайма
- **WHEN** у проекта есть два одновременно активных, не отозванных секретных ключа, и приложение продолжает слать логи со старым ключом, пока новый уже выдан
- **THEN** приём логов успешен с обоих ключей, пока старый явно не отозван
