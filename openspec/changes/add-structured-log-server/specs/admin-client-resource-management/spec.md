## ADDED Requirements

### Requirement: Управление пользователями доступно только администратору
Приложение SHALL предоставлять экран списка и создания пользователей (`POST`/`GET /v1/users`), видимый и доступный только при наличии у текущего пользователя роли `admin`; для остальных пользователей этот экран SHALL быть скрыт из навигации.

#### Scenario: Экран пользователей скрыт для не-admin
- **WHEN** текущий пользователь не имеет `RoleAssignment(role: admin, scope: global)`
- **THEN** пункт навигации к управлению пользователями не отображается

#### Scenario: Сервер остаётся источником истины при попытке обхода UI
- **WHEN** не-admin пользователь каким-либо образом инициирует запрос `POST /v1/users`
- **THEN** сервер отклоняет запрос с 403 (см. `log-server-rbac`), и приложение показывает это как ошибку доступа, а не как успех

### Requirement: Управление группами доступно только администратору, команды и проекты — владельцу группы или администратору
Приложение SHALL предоставлять экраны списка и создания групп (`admin` only), списка и создания команд с управлением составом внутри группы, и списка/создания/редактирования проектов внутри группы (последние два — доступны `owner` этой группы или `admin`); элементы, требующие прав, которых нет у текущего пользователя, SHALL быть скрыты или неактивны в соответствующем экране.

#### Scenario: owner видит управление только своими группами
- **WHEN** пользователь имеет `RoleAssignment(role: owner, scope: group:G)` и не имеет ролей на другие группы
- **THEN** экраны управления командами/проектами доступны для `G`, но группы, на которые нет роли, не предлагаются для управления (могут быть видны в списке, если есть право на чтение — как исключительно для просмотра)

### Requirement: Экран проекта показывает квоту и текущее использование
Экран проекта SHALL отображать `retention_days`/`max_entries`/`max_bytes` вместе с текущим использованием (`entry_count`/`total_bytes`) из ответа `GET /v1/projects/:id` (`log-server-quotas`), и SHALL позволять `owner`/`admin` редактировать квоту через `PATCH /v1/projects/:id`.

#### Scenario: Использование отображается рядом с лимитом
- **WHEN** открыт экран проекта с заданным `max_entries`
- **THEN** приложение показывает текущее `entry_count` и `max_entries` вместе (например, «842 / 1000»), а не только один из этих показателей

#### Scenario: user не может редактировать квоту
- **WHEN** экран проекта открыт пользователем, чья роль на этот проект — `user`
- **THEN** поля квоты отображаются доступными только для чтения, без элементов управления для их изменения

### Requirement: Управление секретными ключами проекта с одноразовым показом значения
Приложение SHALL предоставлять на экране проекта список секретных ключей (только метаданные — `label`/`created_at`/`revoked_at`, без значения ключа), действие создания нового ключа и действие отзыва существующего; сразу после успешного создания приложение SHALL показать значение ключа в открытом виде ровно один раз, с явным предупреждением, что оно больше не будет показано, и действием копирования в буфer обмена.

#### Scenario: Значение ключа доступно один раз сразу после создания
- **WHEN** пользователь с правом на управление проектом создаёт новый секретный ключ
- **THEN** приложение показывает значение ключа в диалоге с предупреждением и кнопкой копирования; после закрытия диалога это значение больше не доступно нигде в приложении

#### Scenario: Список ключей не содержит значений
- **WHEN** открыт список секретных ключей проекта, содержащий ранее созданные ключи
- **THEN** для каждого ключа отображаются только `label`/`created_at`/`revoked_at`, само значение ключа не отображается и не хранится в памяти списка

### Requirement: Выдача и отзыв ролей пользователю или команде
Приложение SHALL предоставлять UI для создания и отзыва `RoleAssignment` (роль, область — группа или проект, получатель — пользователь или команда) в рамках прав, которые правила `log-server-rbac` разрешают текущему пользователю (`admin` — без ограничений; `owner` группы — только `owner`/`user` на свою группу/её проекты).

#### Scenario: Форма выдачи роли предлагает только допустимые значения
- **WHEN** форму выдачи роли открывает пользователь с ролью `owner` на группу `G` (без `admin`)
- **THEN** список доступных для выбора ролей в форме ограничен `owner`/`user` (без `admin`), а список доступных областей — группой `G` и её проектами

#### Scenario: Отзыв роли немедленно отражается в списке
- **WHEN** выполнен отзыв `RoleAssignment` через `DELETE /v1/role-assignments/:id`
- **THEN** этот грант исчезает из списка ролей в приложении сразу после успешного ответа сервера, без необходимости вручную обновлять экран
