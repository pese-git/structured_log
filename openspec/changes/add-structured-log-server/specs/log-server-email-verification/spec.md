## ADDED Requirements

### Requirement: Учётная запись с заданным email обязана подтвердить его перед входом
Сервер SHALL считать `email`, заданный у `User` (при самостоятельной регистрации — всегда обязателен, `log-server-auth`; при создании администратором через `POST /v1/users` — если указан), неподтверждённым до тех пор, пока `User.email_verified_at` не установлен; `grant_type=password` на `POST /v1/auth/token` SHALL отклоняться (`invalid_grant`) для такой учётной записи, независимо от корректности пароля. Учётные записи без `email` (`email IS NULL`) SHALL не подпадать под это ограничение.

#### Scenario: Вход отклоняется для неподтверждённого email
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=password` и верными `username`/`password` пользователя, у которого `email` задан, но `email_verified_at IS NULL`
- **THEN** сервер отвечает `{"error": "invalid_grant", ...}` и не выдаёт токены, независимо от корректности пароля

#### Scenario: Вход разрешён после подтверждения
- **WHEN** у пользователя из предыдущего сценария `email_verified_at` установлен, и повторно отправлен тот же `grant_type=password` запрос
- **THEN** сервер выдаёт обычную пару токенов

#### Scenario: Учётная запись без email не блокируется
- **WHEN** отправлен `POST /v1/auth/token` с `grant_type=password` для пользователя, у которого `email IS NULL`
- **THEN** отсутствие подтверждения email не влияет на результат — вход разрешён при верных кредах, как и до введения этого требования

#### Scenario: grant_type=refresh_token не проверяет email_verified_at повторно
- **WHEN** у пользователя уже есть действительный refresh-токен (полученный до того, как это требование стало актуальным для него, либо после подтверждения), и отправлен `grant_type=refresh_token`
- **THEN** сервер не отклоняет запрос по причине `email_verified_at` — эта проверка применяется только к `grant_type=password`

### Requirement: Ответ об ошибке различает неподтверждённый email и прочие причины отказа
Ответ `POST /v1/auth/token` с `grant_type=password`, отклонённый из-за неподтверждённого email, SHALL включать дополнительное поле `reason: "email_not_verified"` поверх стандартных полей RFC 6749 §5.2 (`error`, `error_description`) — расширение самого RFC-конверта, не отдельный формат.

#### Scenario: Поле reason присутствует только для этой конкретной причины
- **WHEN** `grant_type=password` отклонён из-за неподтверждённого email
- **THEN** тело ответа содержит `"reason": "email_not_verified"` в дополнение к `error`/`error_description`

#### Scenario: Поле reason отсутствует для прочих причин отказа
- **WHEN** `grant_type=password` отклонён по любой другой причине (неверный пароль, неактивный пользователь, неизвестный `username`)
- **THEN** тело ответа не содержит поле `reason`

### Requirement: Токен подтверждения выпускается при задании email и отправляется через EmailSender
При успешном создании пользователя с непустым `email` (самостоятельная регистрация или `POST /v1/users`) сервер SHALL создать одноразовый токен подтверждения (высокоэнтропийная случайная строка, хранится хэшем — не в открытом виде) в таблице `email_verification_tokens` и отправить его на указанный `email` через интерфейс `EmailSender` (`log-server-password-reset`), не вводя отдельный интерфейс отправки почты.

#### Scenario: Токен отправляется при самостоятельной регистрации
- **WHEN** успешно выполнен `POST /v1/auth/register` (email обязателен на этом пути)
- **THEN** создаётся токен подтверждения для этого пользователя, и `EmailSender.send` вызывается с адресом на этот `email`

#### Scenario: Токен отправляется при создании пользователя администратором с email
- **WHEN** `admin` выполняет `POST /v1/users` с непустым `email`
- **THEN** создаётся токен подтверждения, и `EmailSender.send` вызывается для этого `email`

#### Scenario: Токен не создаётся при создании пользователя без email
- **WHEN** `admin` выполняет `POST /v1/users` без поля `email`
- **THEN** токен подтверждения не создаётся, `EmailSender.send` не вызывается

### Requirement: POST /v1/auth/verify-email подтверждает email по токену
Сервер SHALL предоставлять `POST /v1/auth/verify-email` (JSON-тело `{"token": "..."}"`, не form-encoded — этот путь не часть контракта `/v1/auth/token`), находящий токен по хэшу и проверяющий `expires_at`/`used_at IS NULL`; при успехе SHALL устанавливать `User.email_verified_at = now()`, помечать токен использованным и инвалидировать остальные неиспользованные токены подтверждения этого пользователя.

#### Scenario: Валидный токен подтверждает email
- **WHEN** отправлен `POST /v1/auth/verify-email` с действительным, не истёкшим, не использованным токеном
- **THEN** сервер отвечает успехом, `User.email_verified_at` этого пользователя устанавливается, и последующий `grant_type=password` для него больше не отклоняется по причине `email_not_verified`

#### Scenario: Невалидный токен отклоняется
- **WHEN** отправлен `POST /v1/auth/verify-email` с неизвестным, истёкшим или уже использованным токеном
- **THEN** сервер отвечает 400 `invalid_token`, `email_verified_at` не изменяется

#### Scenario: Повторное использование одного и того же токена отклоняется
- **WHEN** токен подтверждения уже был успешно применён, и предъявлен повторно
- **THEN** сервер отвечает 400 `invalid_token`

### Requirement: POST /v1/auth/verify-email/resend переотправляет письмо без раскрытия состояния
Сервер SHALL предоставлять `POST /v1/auth/verify-email/resend` (JSON `{"email": "..."}"`), всегда отвечающий 202 с одинаковым телом независимо от того, существует ли пользователь с таким `email`, уже подтверждён ли он или email не задан ни у кого; если найден активный пользователь с этим `email` и `email_verified_at IS NULL`, SHALL инвалидировать его прежние неиспользованные токены подтверждения и создать новый, отправленный через `EmailSender`.

#### Scenario: Ответ одинаков независимо от состояния
- **WHEN** `POST /v1/auth/verify-email/resend` отправлен с `email`, который не зарегистрирован, уже подтверждён, или ещё не подтверждён
- **THEN** во всех трёх случаях сервер отвечает 202 с одинаковым телом

#### Scenario: Повторный запрос инвалидирует более ранний токен
- **WHEN** `POST /v1/auth/verify-email/resend` отправлен для пользователя с уже выпущенным, ещё не использованным токеном подтверждения
- **THEN** новый токен создаётся, а прежний токен подтверждения этого пользователя больше не принимается `POST /v1/auth/verify-email`
