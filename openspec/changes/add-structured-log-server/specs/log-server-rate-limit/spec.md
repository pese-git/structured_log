## ADDED Requirements

### Requirement: Ограничение частоты применяется к закрытому списку auth-эндпоинтов
Сервер SHALL ограничивать частоту запросов к `POST /v1/auth/token`, `POST /v1/auth/register`, `POST /v1/auth/password-reset`, `POST /v1/auth/password-reset/confirm`, `POST /v1/auth/verify-email`, `POST /v1/auth/verify-email/resend`, `POST /v1/auth/change-password` и `DELETE /v1/users/me`. Сервер SHALL не ограничивать частоту `POST /v1/logs`, `GET /v1/logs`, `GET /v1/logs/stream` и management-эндпоинтов — их регулируют квоты проекта (`log-server-quotas`) и RBAC (`log-server-rbac`).

#### Scenario: Приём логов не ограничивается частотой
- **WHEN** приложение отправляет `POST /v1/logs` с частотой, многократно превышающей любой лимит auth-эндпоинтов
- **THEN** сервер не отвечает `429` ни на один из батчей — ограничение объёма выражается только квотами проекта

#### Scenario: Management-запросы не ограничиваются частотой
- **WHEN** аутентифицированный `admin` выполняет подряд множество запросов `GET /v1/users`
- **THEN** сервер не отвечает `429`

### Requirement: Ограничение частоты не блокирует учётную запись
Ограничитель SHALL быть реализован исключительно как throttling: сервер SHALL не хранить в базе данных счётчик неудачных попыток, отметку блокировки или любое иное состояние, переживающее рестарт, и SHALL не требовать вмешательства администратора для восстановления доступа. Учётная запись SHALL становиться доступной для входа снова само́й по себе, по прошествии времени.

#### Scenario: Доступ восстанавливается без администратора
- **WHEN** запросы с некоторого ключа отклонены с `429`, и после этого запросы с этого ключа не отправлялись в течение времени, указанного в `Retry-After`
- **THEN** следующий запрос с этого ключа обрабатывается штатно, без каких-либо действий со стороны администратора

#### Scenario: Перебор пароля не запирает чужую учётную запись
- **WHEN** злоумышленник исчерпывает лимит неудачных попыток входа для `username` жертвы
- **THEN** учётная запись жертвы не помечается заблокированной, её действующие refresh-токены остаются действительными, и после истечения `Retry-After` она может войти обычным образом

### Requirement: Каждый запрос проверяется по двум независимым ключам
Сервер SHALL вести отдельные счётчики для клиентского IP и для субъекта попытки (`username` — для `POST /v1/auth/token` с `grant_type=password` и `POST /v1/auth/register`; отправленный `email` — для `password-reset`/`verify-email/resend`; идентификатор аутентифицированного пользователя — для `POST /v1/auth/change-password` и `DELETE /v1/users/me`). Счётчик IP SHALL расходоваться на каждом запросе к ограничиваемому пути, счётчик субъекта — только на неуспешной попытке, а успешная попытка SHALL полностью восстанавливать счётчик своего субъекта. Запрос SHALL отклоняться, если исчерпан любой из двух счётчиков.

#### Scenario: Частые успешные входы не ограничиваются по субъекту
- **WHEN** пользователь многократно и успешно выполняет `POST /v1/auth/token` с верным паролем
- **THEN** его счётчик субъекта не исчерпывается — каждый успех восстанавливает его — и запросы не отклоняются, пока не исчерпан счётчик IP

#### Scenario: Перебор пароля к одному аккаунту упирается в счётчик субъекта
- **WHEN** с некоторого адреса отправляется серия `POST /v1/auth/token` с верным `username` и неверными паролями
- **THEN** после исчерпания счётчика этого `username` сервер отвечает `429`, даже если счётчик IP ещё не исчерпан

#### Scenario: Распыление попыток по разным username упирается в счётчик IP
- **WHEN** с одного адреса отправляются неудачные попытки входа, каждая под своим `username`, так что ни один счётчик субъекта не исчерпан
- **THEN** после исчерпания счётчика IP сервер отвечает `429` на последующие запросы с этого адреса

### Requirement: Счётчик субъекта ведётся по отправленной строке, а не по найденной записи
Сервер SHALL заводить счётчик субъекта для `username`/`email` в том виде, в каком он получен в запросе, независимо от того, существует ли соответствующий пользователь. Ответ на ограничиваемый запрос SHALL быть неотличим для существующего и несуществующего субъекта, сохраняя анти-enumeration гарантии `log-server-password-reset`/`log-server-email-verification`.

#### Scenario: Несуществующий email ограничивается так же, как существующий
- **WHEN** отправляется серия `POST /v1/auth/password-reset` с адресом, которого нет ни у одного пользователя
- **THEN** сервер ограничивает их так же, как для существующего адреса, и до срабатывания ограничителя отвечает тем же `202`, что и для существующего — по ответам невозможно определить, существует ли адрес

#### Scenario: Объём памяти ограничителя ограничен сверху
- **WHEN** отправляется большое число запросов, каждый с уникальным, ранее не встречавшимся субъектом
- **THEN** число хранимых счётчиков не превышает настроенного предела — наименее недавно использованные вытесняются, сервер не исчерпывает память

### Requirement: Отклонённый запрос получает 429 с Retry-After
Отклонённый ограничителем запрос SHALL получать ответ `429` с заголовком `Retry-After` (целое число секунд до момента, когда запрос с тем же ключом будет принят) и телом в общем JSON-конверте ошибок с кодом `too_many_requests` — включая `POST`/`DELETE /v1/auth/token`, для которых это единственный ответ не в RFC 6749-конверте. Отклонённый запрос SHALL не выполнять запрошенное действие: не проверять пароль, не выпускать токены, не отправлять письма.

#### Scenario: Token-эндпоинт отвечает общим конвертом при 429
- **WHEN** запрос к `POST /v1/auth/token` отклонён ограничителем
- **THEN** ответ имеет статус `429`, заголовок `Retry-After` и тело вида `{"error": "too_many_requests", "message": "..."}` — не `{"error": ..., "error_description": ...}`

#### Scenario: Отклонённый запрос не отправляет письмо
- **WHEN** запрос к `POST /v1/auth/verify-email/resend` отклонён ограничителем
- **THEN** письмо не отправляется и новый токен подтверждения не создаётся

#### Scenario: Отклонённая попытка входа не проверяет пароль
- **WHEN** запрос к `POST /v1/auth/token` с `grant_type=password` отклонён ограничителем
- **THEN** сервер не выполняет проверку пароля и не выдаёт токены, даже если пароль верен

### Requirement: Клиентский IP определяется по сокету, если доверие прокси не настроено
Сервер SHALL по умолчанию использовать адрес сокета как клиентский IP и игнорировать заголовок `X-Forwarded-For`. Если конфигурация задаёт число доверенных прокси больше нуля, сервер SHALL брать соответствующий элемент `X-Forwarded-For`, отсчитывая с конца списка.

#### Scenario: Подделанный заголовок игнорируется по умолчанию
- **WHEN** клиент отправляет запросы с произвольными, каждый раз новыми значениями `X-Forwarded-For`, а доверие прокси не настроено
- **THEN** все запросы учитываются в одном счётчике — по адресу сокета — и ограничитель срабатывает так же, как без заголовка

#### Scenario: За доверенным прокси учитывается адрес клиента, а не прокси
- **WHEN** число доверенных прокси настроено равным 1, и запросы разных клиентов приходят через прокси с корректным `X-Forwarded-For`
- **THEN** счётчики ведутся по адресам клиентов из заголовка, а не по общему адресу прокси

### Requirement: Ограничитель отключается конфигурацией
Сервер SHALL предоставлять конфигурационный переключатель, полностью отключающий ограничение частоты (по умолчанию — включено).

#### Scenario: При отключённом ограничителе 429 не возвращается
- **WHEN** ограничитель отключён конфигурацией, и отправляется серия запросов, заведомо превышающая любые лимиты
- **THEN** сервер не отвечает `429` ни на один из них и не создаёт аудит-записей `auth.throttled`
