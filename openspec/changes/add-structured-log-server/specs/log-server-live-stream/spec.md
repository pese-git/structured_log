## ADDED Requirements

### Requirement: Живая доставка новых записей по SSE с той же областью видимости и RBAC, что запрос
Сервер SHALL предоставлять эндпоинт `GET /v1/logs/stream`, отвечающий `Content-Type: text/event-stream`, аутентифицируемый тем же JWT-токеном пользователя (`log-server-auth`), что и `GET /v1/logs`, требующий ровно один из параметров `project_id`/`group_id` и SHALL проверять через `log-server-rbac` то же право на эту область, что и `GET /v1/logs` — 403 при отсутствии права, 404 при несуществующей области, до открытия потокового тела ответа.

#### Scenario: Подписка в рамках проекта, на который есть доступ
- **WHEN** аутентифицированный пользователь с ролью на `project_id = P` (прямо или через команду) отправляет `GET /v1/logs/stream?project_id=P`
- **THEN** сервер открывает потоковое соединение и доставляет по нему записи, принятые сервером для проекта `P` после открытия соединения

#### Scenario: Подписка без прав на указанную область отклоняется до открытия потока
- **WHEN** аутентифицированный пользователь без `RoleAssignment`, покрывающего указанный `project_id`/`group_id`, отправляет `GET /v1/logs/stream`
- **THEN** сервер отвечает 403 обычным (не потоковым) ответом и не открывает `event-stream`-соединение

#### Scenario: Подписка по группе агрегирует все её проекты только при гранте на уровне группы
- **WHEN** пользователь с `RoleAssignment(role: user, scope: group:G)` отправляет `GET /v1/logs/stream?group_id=G`, где `G` содержит несколько проектов
- **THEN** поток доставляет записи, принятые для любого из проектов `G`

### Requirement: Живой поток фильтруется теми же параметрами, что исторический запрос
`GET /v1/logs/stream` SHALL принимать те же дополнительные параметры фильтрации, что `GET /v1/logs` (`level`/`category`/`logger`/поля корреляции/`q`/`context.*`), и SHALL доставлять только записи, удовлетворяющие им — той же предикатной логикой, что используется для построения `WHERE`-условия исторического запроса, не отдельной параллельной реализацией.

#### Scenario: Событие, не проходящее фильтр уровня, не доставляется
- **WHEN** открыта подписка `GET /v1/logs/stream?project_id=P&level=warning`, и сервер принимает для `P` запись с уровнем `debug`
- **THEN** эта запись не доставляется по этой подписке

#### Scenario: Событие, проходящее фильтр, доставляется немедленно
- **WHEN** открыта подписка `GET /v1/logs/stream?project_id=P&level=warning`, и сервер принимает для `P` запись с уровнем `error`
- **THEN** эта запись доставляется по подписке как SSE-событие

### Requirement: Блокировка проекта исключает его из живого потока так же, как из запроса
Пока `Project.is_blocked = true`, эта же блокировка (`log-server-rbac`) SHALL применяться к `GET /v1/logs/stream` симметрично `GET /v1/logs`: подписка напрямую на заблокированный `project_id` SHALL быть отклонена, подписка по `group_id` SHALL молча не доставлять события заблокированных проектов группы, и уже открытая подписка на `project_id`, заблокированный после открытия соединения, SHALL быть закрыта терминальным событием.

#### Scenario: Подписка напрямую на заблокированный проект отклоняется
- **WHEN** вызывающий с действительным `RoleAssignment`, покрывающим проект `P`, отправляет `GET /v1/logs/stream?project_id=P`, у которого `is_blocked = true`
- **THEN** сервер отвечает 403 с кодом `project_blocked`, не открывая потоковое соединение

#### Scenario: Подписка по группе молча исключает события заблокированного проекта
- **WHEN** открыта подписка `GET /v1/logs/stream?group_id=G`, где один из проектов `G` заблокирован, а остальные — нет
- **THEN** поток доставляет события только из незаблокированных проектов `G`, не отклоняя саму подписку

#### Scenario: Блокировка проекта во время активной подписки закрывает поток
- **WHEN** проект `P`, на который открыта подписка `GET /v1/logs/stream?project_id=P`, блокируется (`POST /v1/projects/:id/block`) во время активного соединения
- **THEN** сервер закрывает это соединение терминальным SSE-событием с причиной `project_blocked`, не оставляя его открытым молча

### Requirement: Catch-up по since_id без потери и без дублирования записей
`GET /v1/logs/stream` SHALL принимать необязательный параметр `since_id`; если он передан, сервер SHALL сначала доставить как обычные SSE-события все записи, удовлетворяющие текущим области/фильтрам, с `id > since_id`, принятые до момента открытия подписки, а затем непрерывно продолжить живой поток — без пропуска и без повторной доставки ни одной записи независимо от того, сколько заняла эта начальная выборка.

#### Scenario: Записи, принятые в зазоре между REST-страницей и подпиской, не теряются
- **WHEN** клиент получил `GET /v1/logs?project_id=P` с самой новой записью `id = N`, и до открытия `GET /v1/logs/stream?project_id=P&since_id=N` сервер успел принять для `P` ещё несколько записей
- **THEN** подписка доставляет эти записи (с `id > N`) как часть потока, прежде чем перейти к строго новым событиям, и ни одна из них не доставляется дважды

#### Scenario: Подписка без since_id начинается строго с текущего момента
- **WHEN** открыта подписка `GET /v1/logs/stream?project_id=P` без `since_id`
- **THEN** поток не доставляет ничего, что было принято для `P` до момента открытия соединения

### Requirement: Heartbeat и периодическая ревалидация авторизации долгоживущего соединения
Пока соединение `GET /v1/logs/stream` открыто, сервер SHALL периодически отправлять keep-alive (SSE-комментарий) и при каждом таком тике SHALL повторно проверять `token_version`/`is_active`/`deleted_at` аутентифицированного пользователя и текущий статус блокировки запрошенного проекта/проектов группы; при несовпадении/потере валидности сервер SHALL закрыть соединение терминальным SSE-событием, а не держать его открытым до истечения срока действия access-токена.

#### Scenario: Отзыв прав закрывает уже открытое соединение
- **WHEN** во время активной подписки `GET /v1/logs/stream` у аутентифицированного пользователя меняется `token_version` (например, `admin` отзывает его роль на эту область или блокирует его)
- **THEN** к следующему тику ревалидации сервер закрывает соединение терминальным событием, а не продолжает доставлять по нему записи

#### Scenario: Соединение не закрывается, пока авторизация остаётся действительной
- **WHEN** во время активной подписки `GET /v1/logs/stream` `token_version`/`is_active`/блокировка проекта не менялись
- **THEN** каждый тик ревалидации проходит без разрыва соединения
