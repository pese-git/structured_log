## ADDED Requirements

### Requirement: `email` — опциональное поле пользователя, не идентификатор для входа
`User.email` SHALL быть опциональным (`nullable`) и уникальным, если задано; задаётся при регистрации (`POST /v1/auth/register`) или администратором (`PATCH /v1/users/:id`). Аутентификация (`grant_type=password`) SHALL по-прежнему выполняться только по `username` — наличие или отсутствие `email` на неё не влияет.

#### Scenario: Пользователь без email продолжает входить по username/паролю
- **WHEN** пользователь без заданного `email` отправляет `grant_type=password` с верными `username`/паролем
- **THEN** сервер выдаёт токен как обычно — отсутствие `email` не блокирует аутентификацию

#### Scenario: Регистрация принимает email как необязательное поле
- **WHEN** `POST /v1/auth/register` отправлен с `username`/паролем и `email`
- **THEN** пользователь создаётся с сохранённым `email`; `POST /v1/auth/register` без поля `email` также создаёт пользователя (поле не обязательно)

### Requirement: Запрос восстановления пароля не раскрывает существование email
`POST /v1/auth/password-reset` (тело — JSON `{"email": "..."}`) SHALL всегда отвечать 202 с одинаковым телом ответа независимо от того, существует ли активный пользователь с указанным `email` — запрос не должен позволять определить перебором, какие email зарегистрированы в системе.

#### Scenario: Существующий активный email создаёт токен восстановления
- **WHEN** `POST /v1/auth/password-reset` отправлен с `email`, принадлежащим активному (`is_active = true`) пользователю
- **THEN** сервер создаёт одноразовый токен восстановления, отправляет его через `EmailSender` на этот `email` и отвечает 202

#### Scenario: Несуществующий или неактивный email отвечает так же
- **WHEN** `POST /v1/auth/password-reset` отправлен с `email`, не принадлежащим ни одному пользователю, либо принадлежащим деактивированному (`is_active = false`) пользователю
- **THEN** сервер не создаёт токен и не отправляет письмо, но отвечает тем же 202 с тем же телом, что и в сценарии выше

### Requirement: Токен восстановления одноразовый и с ограниченным сроком действия
Токен восстановления SHALL храниться на сервере как хэш (не plaintext), иметь срок действия (`expires_at`, конфигурируемый) и становиться непригодным для повторного использования после первого успешного применения (`used_at`).

#### Scenario: Истёкший токен отклоняется
- **WHEN** `POST /v1/auth/password-reset/confirm` отправлен с токеном, чей `expires_at` уже прошёл
- **THEN** сервер отвечает 400 (`invalid_token`) и не меняет пароль

#### Scenario: Уже использованный токен нельзя применить повторно
- **WHEN** `POST /v1/auth/password-reset/confirm` с одним и тем же токеном отправлен дважды подряд, и первый запрос завершился успехом
- **THEN** второй запрос отвечает 400 (`invalid_token`) и не меняет пароль повторно

#### Scenario: Несуществующий токен отклоняется
- **WHEN** `POST /v1/auth/password-reset/confirm` отправлен со строкой, не соответствующей ни одному созданному токену
- **THEN** сервер отвечает 400 (`invalid_token`)

### Requirement: Новый запрос восстановления инвалидирует предыдущие неиспользованные токены пользователя
Каждый успешный `POST /v1/auth/password-reset` (сценарий «существующий активный email») SHALL инвалидировать все ранее выданные и ещё не использованные токены восстановления этого пользователя — действителен только последний выданный токен.

#### Scenario: Более ранний токен перестаёт работать после повторного запроса
- **WHEN** пользователь дважды подряд запрашивает восстановление пароля через `POST /v1/auth/password-reset`, получая два токена, а затем предъявляет первый (более ранний) токен в `POST /v1/auth/password-reset/confirm`
- **THEN** сервер отвечает 400 (`invalid_token`) на первый токен; второй (последний выданный) токен остаётся действителен

### Requirement: Установка нового пароля инвалидирует текущие сессии пользователя
Успешный `POST /v1/auth/password-reset/confirm` SHALL обновить хэш пароля пользователя и инкрементировать его `User.token_version` — тем же механизмом немедленного отзыва, что применяется к любой смене пароля (`log-server-auth`), обесценивая все ранее выданные access-токены этого пользователя.

#### Scenario: Ранее выданный access-токен перестаёт быть валиден после сброса пароля
- **WHEN** у пользователя есть валидный access-токен, выданный до вызова `POST /v1/auth/password-reset/confirm`, и восстановление пароля завершается успехом
- **THEN** следующий запрос к management/query API с этим access-токеном отклоняется 401 (несовпадение `token_version`)

#### Scenario: Новый пароль действует немедленно
- **WHEN** `POST /v1/auth/password-reset/confirm` завершился успехом с новым паролем
- **THEN** `POST /v1/auth/token` с `grant_type=password` и этим новым паролем сразу выдаёт валидную пару токенов
