## Context

Сейчас в воркспейсе (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`, все в корне репозитория плоско) нет ни одного способа доставить лог за пределы процесса, кроме локального файла — `OutputFunction`/`LogSink` (`structured_log/lib/src/processors.dart:58`, `structured_log/lib/src/sink.dart`) уже задают чистый контракт «функция, принимающая запись», но ни одна встроенная реализация не отправляет данные по сети. Единственный существующий образец неблокирующего output — `AsyncFileOutput`/`_SerializedAsyncOutput` (`structured_log/lib/src/async_file_output.dart`): сериализованная через `Future` очередь, `catchError` на каждом шаге, публичный `Future<void> get flushed`. Этот паттерн — прямой прототип для будущего HTTP-sender'а. (Эти пути — до реструктуризации репозитория, см. decision 23: после неё пакет живёт в `emb/structured_log/`.)

Все 4 существующих пакета — плоская раскладка, без единого codegen-инструмента во всём монорепо. У проекта уже есть явно зафиксированный принцип «никакой магии» (`openspec/changes/add-structured-log-flutter/design.md`, decision №4). Хранилище `structured_log_server` — первый пакет воркспейса, сознательно вводящий codegen (`drift`/`build_runner`) — решение принято по прямому указанию пользователя, ограничено этим одним пакетом.

Требование пользователя расширило объём с одного доверенного приёмника логов до полноценного мультитенантного сервиса: несколько пользователей, объединённых в группы и команды, с разграничением доступа к проектам и лимитами на объём хранимой истории. Это меняет модель аутентификации приёма логов (больше не плоский список серверных API-ключей — теперь секретный ключ привязан к конкретному проекту) и добавляет management/query API, требующий аутентификации людей (JWT), а не приложений.

## Goals / Non-Goals

**Goals:**
- Дать способ централизованно собирать структурированные логи с нескольких проектов/команд в одном self-hosted сервисе, без стороннего SaaS.
- Разграничить доступ так, чтобы приложение, отправляющее логи, не имело доступа ни к чему, кроме приёма в свой проект, а человек, читающий логи, видел только то, что ему разрешено.
- Не дать одному проекту исчерпать общее хранилище — квота на историю обязательна для каждого проекта, а не опциональна.
- Сохранить нулевые runtime-зависимости `structured_log` — новый функционал живёт в отдельных пакетах, ядро не трогается.
- Дать программный и HTTP-контракт, по форме зеркалящий существующую запись лога (`event`/`level`/`timestamp`/`category`/`logger`/поля корреляции/произвольный `context`), не изобретая параллельную модель данных для самой записи.
- Дать пользователям возможность самостоятельно зарегистрироваться (username/пароль) без участия администратора, при этом оставив оператору сервера возможность полностью выключить самостоятельную регистрацию (env/CLI), если инструмент используется как закрытый корпоративный сервис.
- Отделить аутентификацию от RBAC интерфейсом `IdentityProvider`, чтобы встроенную (local) реализацию можно было в будущем заменить на Keycloak или другой OIDC-провайдер без переделки авторизации — по прямому требованию пользователя.
- Дать людям (не только приложениям через `structured_log_http`) полноценный UI над всем функционалом сервера — аутентификацией, управлением пользователями/группами/командами/проектами/квотами/секретными ключами/ролями и просмотром/поиском логов — одним Flutter-приложением `structured_log_admin_client`, а не голым JSON API.
- Реструктурировать воркспейс под появившиеся категории пакетов (frontend/backend/встраиваемые библиотеки), а не продолжать наращивать плоский список в корне репозитория, который был осмыслен, пока в воркспейсе были только встраиваемые библиотеки — по прямому требованию пользователя.
- Дать пользователю возможность самостоятельно восстановить доступ к своей учётной записи при утере пароля через email, не обращаясь к администратору или owner'у группы — по прямому требованию пользователя.
- Дать администратору возможность немедленно заблокировать любого пользователя и/или любой проект (независимо от того, в чьей они группе), как средство реагирования на инцидент — по прямому требованию пользователя.
- Дать администратору доступ к аудиту административных действий в системе (кто/что/над каким ресурсом/когда) — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («аудит-лог... только сам факт текущего состояния RoleAssignment»).
- Дать любому пользователю возможность безвозвратно удалить собственный аккаунт, с сохранением записи об этом в БД (soft-delete) и немедленным прекращением доступа удалённого аккаунта к системе — по прямому требованию пользователя.
- Дать администратору возможность безвозвратно удалить чужую учётную запись (не только заблокировать), тем же soft-delete механизмом, что самоудаление, с защитой от того, чтобы удаление не оставило группу без единственного владельца — по прямому (новому) требованию пользователя, снимающему более раннее ограничение этой же change (см. пересмотр decision 27 и Non-Goals).
- Защитить основную (первую) учётную запись администратора от удаления — ни самостоятельно, ни другим `admin` — по прямому требованию пользователя, отдельно от (и более узко, чем) любая защита «последнего администратора» по количеству (см. decision 28).
- Доставлять в `structured_log_admin_client` только что принятые сервером записи лога онлайн (SSE), без ручного обновления/опроса, и показывать их в виде ленты, ведущей себя как история чата — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («только просмотр по запросу/поиску, не потоковый tail»), см. decisions 29/30.
- Зафиксировать технологический стек и внутреннюю архитектуру кода `structured_log_server` (`feature-first` + слоистая архитектура, `fpdart`, `freezed`) и `structured_log_admin_client` (`feature-first` + Clean Architecture, `fpdart`, `freezed`, `cherrypick`, `flutter_bloc`, `dio`+`retrofit`, `fluent_ui`) — по прямому требованию пользователя, расширяющему объём этой change с одного лишь публичного контракта (HTTP API/поведение UI) на явные внутренние архитектурные решения обоих новых пакетов; см. decisions 32–38.
- Вынести не завязанные на бизнес-логику виджеты `structured_log_admin_client` в отдельный пакет, структурированный по Atomic Design (atoms/molecules/organisms) — по прямому требованию пользователя, обеспечивая проверяемую границу между presentation-виджетами и остальной архитектурой (decision 32); см. decision 39.
- Не давать войти в систему учётной записи с неподтверждённым `email` — по прямому требованию пользователя, обязательное требование; пересматривает более раннюю ревизию Non-Goals этой же change («верификация email... не реализуется»), см. decision 40.
- Дать администратору возможность редактировать существующую учётную запись (email/имя/пароль), не только блокировать/удалять её — по прямому требованию пользователя; см. decision 41.
- Пароль, заданный администратором (при создании или редактировании чужой учётной записи), SHALL всегда считаться временным — учётная запись обязана сменить его при следующем входе, прежде чем получить доступ к чему-либо ещё — по прямому требованию пользователя, обязательное требование, без возможности отключить; см. decision 42.
- Не дать перебирать пароли и злоупотреблять рассылкой писем через неаутентифицированные auth-эндпоинты: ограничить частоту попыток на уровне самого сервера, не полагаясь на то, что оператор поставит перед ним обратный прокси с собственным rate-limit'ом — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («rate-limiting... не реализуется»), см. decision 43.
- Дать администратору возможность увидеть в аудите, кто и когда входил в систему, какие попытки входа были неудачными и когда сервер начинал ограничивать частоту — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («аутентификационные события... вне объёма»), см. decision 44.
- Дать оператору возможность ограничить срок хранения аудита, раздельно для административных действий и для аутентификационных событий (последние несут IP-адреса и порождаются внешним трафиком) — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («retention/архивация... не реализуются»), см. decision 46.
- Дать оператору настраивать сервер при запуске аргументами командной строки и переменными окружения — с предсказуемым приоритетом источников, проверкой всех значений до открытия порта и без единой возможности передать секрет так, чтобы он попал в `ps` или историю shell — по прямому требованию пользователя; см. decision 47.
- Логировать собственную работу `structured_log_server` и `structured_log_admin_client` через `structured_log` — тот самый пакет, ради которого существует весь воркспейс, — вместо `print()` и разрозненных подходов; по прямому требованию пользователя, пересматривает часть decision 19 (запрет клиенту зависеть от `structured_log`), см. decision 48.
- Дать серверу возможность самому создать первого администратора при первом старте на пустой базе — с логином и паролем из переменных окружения либо со сгенерированным временным паролем — чтобы развёртывание «запустил и вошёл» не требовало отдельной команды; по прямому требованию пользователя, пересматривает decision 12, см. decision 49.

**Non-Goals:**
- Конкретная реализация `IdentityProvider` для Keycloak/внешнего OIDC-провайдера — эта change вводит только интерфейс и рефакторит под него уже спроектированную local-реализацию; сам внешний адаптер, JIT-provisioning внешних пользователей и CLI/env для выбора провайдера — будущая работа за пределами этой change (см. decision 17).
- Server-rendered HTML/веб-UI на самом сервере — эту роль для людей теперь выполняет `structured_log_admin_client`, а не HTML, отдаваемый сервером.
- Интеграция `structured_log_admin_client` с существующими viewer-пакетами (`structured_log_flutter`/`material`/`fluent`) или переиспользование их виджетов/`LogViewerController` — разные источники данных (удалённый query API vs. локальный `LogBuffer`), объединение — отдельная будущая работа.
- Офлайн-режим в `structured_log_admin_client` — просмотр всегда требует соединения с сервером; live-обновление через SSE теперь в объёме (см. decisions 29/30, пересматривает более раннюю ревизию этого Non-Goal).
- Кросс-isolate/pub-sub масштабирование живого потока (`log-server-live-stream`) — тот же non-goal много-isolate масштабирования сервера (см. ниже), распространённый на decision 29; переподключение по стандартному `Last-Event-ID`/протоколу `EventSource` — используется собственный параметр `since_id` (см. decision 29), не браузерный `EventSource` (не умеет произвольные заголовки для Bearer-аутентификации).
- Воспроизведение живого потока с произвольной глубины в прошлом («перемотка» истории через SSE) — только ограниченный «догон» между последней полученной REST-страницей и моментом подписки (decision 29); более глубокая история — обычная пагинация `GET /v1/logs`, не через `/v1/logs/stream`.
- FTS5-поиск — на MVP `LIKE`.
- Многопоточное/много-isolate масштабирование сервера; Windows в CI на старте.
- SSO/MFA — вне объёма MVP; создание пользователя администратором (`POST /v1/users`) остаётся доступно наравне с самостоятельной регистрацией и восстановлением пароля по email (см. decision 24).
- Самостоятельное изменение пользователем уже сохранённого `email` (`PATCH /v1/users/me`) — `email` задаётся только при регистрации или администратором (см. decision 24) и, будучи задан, теперь обязан быть подтверждён (decision 40), но сменить его самостоятельно на новый нельзя; потребовало бы либо повторного ввода пароля, либо верификации нового адреса тем же механизмом, что уже спроектирован decision 40 — future work, если понадобится. Верификация `email` при его первом задании (в отличие от смены) больше не Non-Goal — см. decision 40, пересматривающую более раннюю ревизию этого пункта.
- Нативные deep link'и (кастомные URI-схемы/App Links/Universal Links) на восстановление пароля или подтверждение email в мобильных/desktop сборках `structured_log_admin_client` — оба токена всегда можно ввести вручную; удобство через URL с query-параметром `token` работает только в web-сборке (см. decision 24/40).
- Блокировка учётной записи после серии неудачных попыток входа (account lockout — `locked_until`/счётчик неудач на `User`, административный `unlock`) — по прямому выбору пользователя из предложенных вариантов: ограничение частоты SHALL быть только throttling'ом без состояния в БД, см. decision 43. Rate-limiting сам по себе больше не Non-Goal (пересматривает более раннюю ревизию этого пункта, где не реализовывался вовсе).
- Разделяемое между процессами/isolate хранилище счётчиков rate-limit'а (Redis и т.п.) — тот же non-goal много-isolate масштабирования сервера (decision 4), распространённый на decision 43: счётчики живут в памяти одного isolate и обнуляются при рестарте.
- Rate-limiting `POST /v1/logs`, `GET /v1/logs` и `GET /v1/logs/stream` — приём и чтение логов ограничиваются квотами проекта (`log-server-quotas`) и его секретным ключом, не частотным лимитом auth-эндпоинтов (decision 43); их профиль нагрузки — нормальный трафик приложения, а не подбор кредов.
- CAPTCHA, proof-of-work, MFA и любое другое «докажи, что ты человек» на auth-эндпоинтах — вне объёма; throttling (decision 43) не заменяет их, а лишь делает перебор дорогим по времени.
- Блокировка целой `Group` одним действием, временная блокировка с автоматическим истечением/снятием по таймеру, блокировка проекта `owner`-ом (только `admin`, см. decision 25) — пользователь явно ограничил требование пользователем и/или проектом, не группой; блокировка группы достижима вручную — заблокировать каждый её проект по отдельности, если понадобится.
- Полная протокольная поверхность OIDC/Keycloak сверх token-эндпоинта: понятие OAuth2 `client`/`client_id`/`client_secret` и их регистрация, token introspection endpoint (RFC 7662), OIDC UserInfo endpoint, discovery-документ `.well-known/openid-configuration`, ID-токены (в терминах OIDC) — уникально для нашего единственного «клиента» (сам API) не нужны; см. decision 10.
- Аудит бизнес-данных: приём (`POST /v1/logs`) и запрос (`GET /v1/logs`) самих записей лога SHALL не попадать в аудит-лог — это высокочастотный поток данных, а не административное действие; аудит охватывает только мутирующие management-операции (см. decision 26).
- Аудит `grant_type=refresh_token` (продление сессии) — единственное аутентификационное событие, остающееся вне аудита по прямому выбору пользователя: это не новое решение о доступе, а продолжение уже принятого, и самое частотное из всех (каждые ~15 минут на активную сессию). Успешный/неуспешный вход, явный logout и срабатывание ограничителя частоты — теперь в объёме, см. decision 44 (пересматривает более раннюю ревизию этого пункта, выводившую все аутентификационные события целиком).
- Отдельный эндпоинт/таблица для аутентификационных событий (`GET /v1/auth-events`, `auth_events`) — они пишутся в уже существующие `audit_log_entries`/`GET /v1/audit-log`, см. decision 44.
- Архивация/экспорт аудита перед удалением (выгрузка в файл, S3, внешний SIEM) — retention (decision 46) только удаляет; кому нужна долгая история, тот задаёт больший срок или снимает его вовсе. Сам retention больше не Non-Goal (пересматривает более раннюю ревизию этого пункта).
- Настройка срока хранения аудита через API (`PATCH` какой-либо конфигурации) — только через конфигурацию сервера при старте (decision 46); политика удаления собственного журнала действий администраторов не должна меняться теми, чьи действия он фиксирует.
- Удаление отдельных записей аудита или очистка «по кнопке» из UI — не существует ни эндпоинта, ни роли, способной это сделать (decision 46).
- Потолок по числу строк аудита (`maxAuditEntries`) как второй, независимый от времени механизм вытеснения — рассматривался и отклонён: два пути потери записей, из которых второй срабатывает непредсказуемо для администратора; ограничитель частоты (decision 43) и так задаёт потолок темпу порождения `auth.*`.
- Фиксированный пароль по умолчанию (`admin`/`admin`) у автоматически созданного администратора — пароль либо задан оператором через окружение, либо генерируется случайным при каждом создании (decision 49); предсказуемых кредов у сервера не бывает ни в одном режиме.
- Автоматическое восстановление доступа на непустой базе — автосоздание срабатывает только когда в таблице `users` нет ни одной записи (decision 49); система, из которой удалили или заблокировали всех администраторов, восстанавливается командой `create-admin`, а не рестартом.
- Отправка собственных логов `structured_log_admin_client` на сервер через `structured_log_http` — admin-клиент не рапортует о себе в тот же сервис, которым управляет (decision 48): сетевая ошибка породила бы лог, отправка которого снова упирается в ту же ошибку.
- Замена аудита (`log-server-audit`) собственными логами сервера или наоборот — это два разных журнала с разными гарантиями (decision 48).
- Запись собственной диагностики сервера в таблицу `log_entries` — она принадлежит проектам-тенантам, а не серверу (decision 48).
- Конфигурационный файл (YAML/TOML/JSON/`.env`) как источник настроек — только CLI-аргументы и переменные окружения (decision 47); `*_FILE`-переменные для секретов не являются исключением из этого правила: они доставляют одно значение, а не структуру настроек.
- Перечитывание конфигурации на лету (SIGHUP, watch файла, admin-эндпоинт «изменить настройки») — конфигурация читается один раз при старте и неизменна в течение жизни процесса (decision 47); смена любого параметра — рестарт.
- Флаги командной строки для секретов (JWT-секрет, SMTP-пароль) — их не существует вовсе, а не «существуют, но не рекомендуются» (decision 47, по прямому выбору пользователя).
- Автогенерация JWT-секрета при первом запуске — сервер отказывается стартовать без него (decision 47).
- Retention/квота на сам аудит-лог, экспорт, свободный полнотекстовый поиск по нему, видимость аудита для `owner` (только `admin`, см. decision 26) — не реализуются в этой доработке (см. Risks/Open Questions).
- Алерты/уведомления о приближении к квоте — только жёсткий отказ при превышении.
- Кросс-групповые команды — `Team` принадлежит ровно одной `Group`; пользователь может состоять в нескольких командах разных групп по отдельности.
- Ротация серверного JWT-signing-secret без даунтайма (один текущий секрет из конфигурации; см. Risks).
- Публикация `structured_log_server`/`structured_log_http` на pub.dev в рамках этой change.
- Восстановление удалённого аккаунта (undelete) через API — удаление необратимо с точки зрения любого клиента этого API (см. decision 27).
- Автоматическое переназначение владения группой как часть процесса удаления — сервер только обнаруживает и блокирует удаление единственного владельца (`sole_group_owner`, decision 27), не выбирает и не назначает нового владельца сам; передача роли `owner` кому-то другому выполняется вручную, тем же уже существующим `POST /v1/role-assignments`, до повторной попытки удаления.
- Массовое/пакетное удаление нескольких учётных записей одним вызовом — только по одному пользователю за раз (`DELETE /v1/users/:id`).
- Защита «последнего администратора» **по количеству** (запрет удалять единственного оставшегося активного `admin`, кем бы он ни был) — не вводится; вместо этого CLI-bootstrap (`create-admin`, decision 12) явно пересматривается так, чтобы засчитывать только активных, неудалённых `admin` при проверке «уже есть ли admin» (см. decision 27), сохраняя путь восстановления. Это отдельно и уже, чем защита основного администратора **по идентичности** (decision 28, введена по новому требованию пользователя) — можно иметь пять `admin`, удалить любые четыре из них (включая единственного оставшегося, если он не основной), но конкретно основного администратора нельзя удалить никогда, независимо от того, сколько других `admin` есть в системе. В отличие от единственного владельца группы (теперь блокирует удаление), защита по количеству для `admin` не вводится — это осознанная асимметрия, см. Risks.
- Физическая очистка (hard-delete/purge) удалённых строк `users` из БД — soft-delete в этой доработке навсегда сохраняет строку (и, соответственно, занятость её `username`/`email`), пока такой механизм не появится отдельно; см. decision 27/Risks.
- Детальная визуальная раскладка экранов `structured_log_admin_client` (конкретная вёрстка/spacing/иконки) — экраны уже отрисованы отдельно (Claude Design, вне этого репозитория и вне артефактов OpenSpec); эта change фиксирует только поведение (specs/admin-client-*) и технологический стек/архитектуру кода (decisions 32–38), не пиксельный дизайн.
- Изменение `username` через `PATCH /v1/users/:id` или любой другой эндпоинт — остаётся неизменным идентификатором после создания (decision 16 не пересматривается); `PATCH /v1/users/:id` (decision 41) редактирует только `email`/`display_name`/`password`.
- Политика сложности/минимальной длины пароля — ни для обычного, ни для временного пароля; валидация формата пароля (кроме непустоты) не входит в объём этой доработки.
- Срок действия/автоматическое снятие `User.must_change_password` по таймеру (decision 42) — флаг снимается исключительно явной сменой пароля через `POST /v1/auth/change-password`, бессрочно висит до этого момента, как и незавершённая верификация email (decision 40).

## Decisions

1. **HTTP-фреймворк: `shelf` + `shelf_router`, не `dart_frog`.**
   Альтернатива — `dart_frog`. Отклонено: `dart_frog create` навязывает собственный скелет и CLI как основной воркфлоу — расходится с плоской раскладкой и отсутствием codegen во всех остальных пакетах монорепо. shelf соответствует принципу «никакой магии»; dart_frog внутри и так построен на shelf.

2. **Хранилище: `drift` поверх SQLite (`NativeDatabase`, embedded, файл на диске).** (позже расширено decision 34: `freezed`/`json_serializable`, и в клиенте — `retrofit_generator`, decision 37 — тот же принцип «codegen как явное исключение», распространённый на два новых пакета)
   Решение принято по прямому указанию пользователя, пересматривая изначальный вариант raw `package:sqlite3` (отклонён именно чтобы не заводить в монорепо первый codegen-инструмент). `drift` даёт типобезопасные, проверяемые на этапе компиляции запросы и миграции схемы «из коробки» (`Migrator`, `onUpgrade`), что для сервиса с растущей мультитенантной схемой (7 таблиц, см. decision 6) перевешивает цену `build_runner`. Trade-off явно принимается (см. Risks): `build_runner` — dev-зависимость только `structured_log_server`, `*.g.dart` не коммитится.

3. **Полнотекстовый поиск на MVP — `LIKE '%term%'` через `customSelect`, не FTS5.**
   Отклонено заводить FTS5 сейчас: усложняет схему и путь миграции ради функциональности вне согласованного MVP. `LIKE`/`json_extract`-условия, не выразимые типизированным query-builder'ом drift, пишутся как сырые SQL-фрагменты через `customSelect`/`customStatement`.

4. **Параллелизм: один `QueryExecutor` drift (`NativeDatabase`), `PRAGMA journal_mode=WAL`, без явного шардирования по isolate.**
   shelf по умолчанию обслуживает запросы в одном isolate — единственный хэндл к базе безопасен без дополнительной синхронизации. Явный non-goal — пул воркеров/шардирование, пересмотреть при упоре в throughput.

5. **Клиентский sender — отдельный пакет `structured_log_http`, не расширение core `structured_log` и не часть `structured_log_server`.**
   Wire-контракт (эндпоинт, форма батча, auth) эволюционирует вместе с сервером, а не с ядром логирования — привязывать к этому независимо версионируемый, уже опубликованный core-пакет не стоит. Класть в `structured_log_server` тоже нельзя: клиентскому приложению не нужны серверные зависимости (`shelf`, `drift`, `dart_jsonwebtoken` и т.п.). `structured_log_http` — чистый Dart, единственная зависимость `structured_log`; `HttpLogOutput` по паттерну `_SerializedAsyncOutput`/`AsyncFileOutput`, плюс батчинг и retry с backoff на сетевых ошибках/5xx (не на 4xx).

6. **Модель мультитенантности: `User` / `Group` / `Team` / `Project` / `ProjectSecretKey` / `RoleAssignment`.**
   - `Group` владеет `Project`-ами (`group_id` на `Project`, NOT NULL — проект не может существовать вне группы).
   - `Team` — набор `User` внутри ровно одной `Group` (`team_id`/`group_id`), только для массовой выдачи прав нескольким пользователям сразу; создаётся `owner`-ом группы или `admin`. Отдельная сущность от `Group`, по прямому уточнению пользователя, а не переиспользование `Group` как «группы пользователей» — иначе одна и та же сущность одновременно и владела бы проектами, и была бы получателем прав, что смешивает два разных понятия и не позволило бы владельцу группы держать несколько независимых команд с разным набором прав внутри одной группы.
   - `RoleAssignment(subject_type: user|team, subject_id, role: admin|owner|user, scope_type: global|group|project, scope_id)` — единая таблица выдачи прав; `subject_type: team` разворачивается в проверке доступа через текущее членство пользователя в команде (см. decision 7), а не копируется в отдельные записи на каждого участника — так добавление/удаление участника команды меняет его эффективные права немедленно, без синхронизации дублирующихся `RoleAssignment`.
   - Альтернатива — хранить роль как одно enum-поле прямо на `User`/на паре `(user, group)`. Отклонено: не выражает произвольную комбинацию «эта команда — `user` на этом проекте, этот человек лично — `owner` той же группы», которая явно требуется постановкой.

7. **Правила выдачи ролей: кто кому какую роль может назначить.**
   - `admin` — может создать `RoleAssignment` с любой ролью на любой области видимости, для любого `User`/`Team`. Только `admin` создаёт новые `Group` и новых `User`.
   - `owner` (на группу `G`, т.е. есть `RoleAssignment(role: owner, scope: group:G)`, прямой или через команду) — может создавать/удалять `Project`/`Team` внутри `G`, менять квоты и ротировать секретные ключи проектов `G`, и создавать `RoleAssignment` с ролью `owner` или `user` на область `group:G` или `project:P` (где `P ∈ G`), для любого `User` или `Team` внутри `G`. Не может выдать роль `admin` — это зарезервированная за существующими `admin` роль, не привязанная ни к одной группе.
   - `user` — не может создавать `RoleAssignment` ни для кого (нет делегирования); имеет только доступ на чтение/поиск логов в рамках выданной ему области видимости.
   - Альтернатива — дать `owner` право выдавать `admin`. Отклонено: `admin` — глобальная суперпользовательская роль вне какой-либо группы, выдача её из контекста «владения одной группой» ломает изоляцию тенантов, которую вся эта модель призвана обеспечить.

8. **Проверка доступа при запросе (`GET /v1/logs`, management-эндпоинты): область видимости обязательна и явна в запросе, без «слияния» нескольких проектов по умолчанию.**
   `GET /v1/logs` обязан указывать ровно одну область — `project_id` или `group_id` — и сервер проверяет, что у вызывающего (напрямую или через членство в команде) есть `RoleAssignment` (`admin` глобально, либо `owner`/`user` с областью, покрывающей запрошенную: `global` покрывает всё, `group:G` покрывает `G` и все её проекты, `project:P` покрывает только `P`) для именно этой области; иначе 403. Запрос по `group_id` агрегирует логи всех проектов группы только если сам грант — на уровне `group`, а не является объединением нескольких отдельных `project`-грантов у вызывающего.
   Альтернатива — возвращать объединение логов всех доступных вызывающему проектов без явного `project_id`/`group_id`. Отклонено: неоднозначная семантика пагинации/курсора при слиянии нескольких таблиц-разделов, и молчаливое расширение того, что видит клиент, при выдаче ему новых прав — хуже для предсказуемости и аудита, чем явный параметр.

9. **Аутентификация приёма логов: секретный ключ, привязанный к проекту (не к серверу целиком).**
   `POST /v1/logs` аутентифицируется `Authorization: Bearer <project-secret-key>`; ключ однозначно резолвится в `project_id` через таблицу `ProjectSecretKey` (хранится как хэш, не plaintext — см. decision 11) — это заменяет более раннюю версию решения (плоский список серверных API-ключей, общий на весь сервер), которая была уместна только для однопроектного MVP до появления мультитенантности. У проекта может быть несколько одновременно активных ключей (ротация без даунтайма), каждый — с `label` и возможностью отзыва (`revoked_at`).

10. **Аутентификация management/query API: единый OAuth2/OIDC-совместимый token-эндпоинт (по образцу Keycloak `/protocol/openid-connect/token`), а не набор специальных путей; эффективные роли зашиты в claims access-токена, немедленный отзыв — через `token_version`.**
    По прямому указанию пользователя контракт auth API приведён к стандарту OAuth2 (RFC 6749) / OIDC, взяв Keycloak как эталон «общепринятого» API, вместо собственных придуманных путей и форматов из более ранней ревизии этого решения (`POST /v1/auth/tokens` + `POST /v1/auth/tokens/refresh` с JSON-телом). Конкретно принято:
    - **Один эндпоинт `POST /v1/auth/token`**, тело — `application/x-www-form-urlencoded` (как того требует RFC 6749 §4.3.2/§6 для token-эндпоинта; JSON-тело было бы нестандартным), различающий сценарий по полю `grant_type`:
      - `grant_type=password` (Resource Owner Password Credentials, RFC 6749 §4.3) — поля `username`/`password`, ровно та же семантика, что раньше называлась «создание токена».
      - `grant_type=refresh_token` (RFC 6749 §6) — поле `refresh_token`, та же семантика, что раньше была отдельным путём `/tokens/refresh`.
    - **Тело ответа** — JSON со стандартными полями RFC 6749 §5.1 и принятыми в Keycloak именами: `access_token`, `token_type` (`"Bearer"`), `expires_in` (секунды до истечения access-токена), `refresh_token`, `refresh_expires_in`.
    - **Формат ошибок именно этого эндпоинта** — RFC 6749 §5.2 (`{"error": "invalid_grant" | "invalid_request" | "unsupported_grant_type", "error_description": "..."}`), а не общий JSON-конверт ошибок остального API (`log-server-api`) — это осознанное, точечное исключение ради совместимости с готовыми OAuth2-клиентами, которые ожидают именно эту форму на token-эндпоинте.
    - **Отзыв токена — `DELETE /v1/auth/token`** (тот же путь, что и создание, но методом, выражающим удаление ресурса — по прямому уточнению пользователя, вместо отдельного пути `/logout`), тело — `application/x-www-form-urlencoded` с полем `refresh_token`. Вслед за RFC 7009 §2.2 (OAuth 2.0 Token Revocation) сервер отвечает 200 с пустым телом независимо от того, был ли токен валиден/уже отозван/не существовал — чтобы ответ не позволял проверять валидность чужого токена; единственная ошибка — отсутствие поля `refresh_token` в запросе (400, формат RFC 6749 §5.2).
    - Access-токен — JWT (`dart_jsonwebtoken`, HS256, подписывающий секрет из конфигурации сервера), короткоживущий (например, 15 минут), с claims `iss` (издатель — настраиваемый идентификатор сервера), `sub` (идентификатор пользователя), `iat`, `exp`, `jti` (уникальный id токена), `preferred_username`, **`tv`** (значение `User.token_version` на момент выдачи — см. ниже) и **`roles`** — плоский снапшот эффективных прав пользователя на момент выдачи (прямых `RoleAssignment` и унаследованных через членство в командах), в форме массива `{role, scope_type, scope_id}`, по духу ролевых claims Keycloak (`realm_access`/`resource_access`), но без деления на realm/client roles — этого деления у нас нет. Middleware авторизации на management/query-эндпоинтах читает права прямо из `roles`, не запрашивая `role_assignments`/`team_members`/`teams` на каждый запрос — в этом и есть операционный выигрыш решения относительно более ранней версии.
    - Refresh-токен — непрозрачная высокоэнтропийная строка (не JWT), хранится на сервере как хэш (та же логика, что для секретных ключей проектов — decision 11) в таблице `refresh_tokens (id, user_id, token_hash, created_at, expires_at, revoked_at)`; ротируется при каждом использовании (`grant_type=refresh_token` отзывает предъявленный и выдаёт новую пару) — типовая защита от повторного использования украденного refresh-токена. Предъявление уже отозванного refresh-токена трактуется как сигнал компрометации: сервер отзывает все refresh-токены этого пользователя, а не только предъявленный.
    - Явно НЕ повторяется вслед за Keycloak: понятие OAuth2 `client`/`client_id`/`client_secret` (у нас один неявный «клиент» — сам API, нет отдельной регистрации приложений), token introspection endpoint (RFC 7662), OIDC UserInfo endpoint, discovery-документ `.well-known/openid-configuration` — всё это добавляет протокольную полноту, не нужную ни одному текущему потребителю API этой change (см. Non-Goals).
    - **Немедленный отзыв при снапшоте ролей в токене — через `User.token_version`.** `token_version` — целочисленный счётчик на пользователе; при каждом запросе к management/query API сервер делает один дешёвый point-lookup `SELECT token_version FROM users WHERE id = sub` (индексированный PK) и сравнивает с claim `tv` — несовпадение немедленно даёт 401 («токен инвалидирован»), не читая `roles` из него. `token_version` инкрементируется атомарно при любом событии, которое должно обесценить уже выданные токены: создание/отзыв `RoleAssignment`, где subject — сам пользователь; изменение членства пользователя в команде; создание/отзыв `RoleAssignment`, где subject — команда (каскадный bulk-`UPDATE` по всем текущим участникам этой команды одним запросом); деактивация пользователя (`is_active = false`); смена пароля. Все эти события — редкие административные действия (owner/admin меняют права, пользователь меняет пароль), а не типовой запрос логов, поэтому цена каскадного обновления в разы меньше цены джойна `role_assignments`↔`team_members`↔`teams`, которую этот подход убирает с горячего пути `GET /v1/logs`.
    - И `grant_type=password`, и `grant_type=refresh_token` SHALL каждый раз заново резолвить `roles` и брать текущее значение `token_version` в `tv` — не копировать claims из предыдущего токена: иначе `roles` в новом токене оставался бы таким же устаревшим, каким был в старом, и весь смысл `token_version`-проверки терялся бы. Именно это делает связку «401 при устаревшем `tv`» + «клиент делает refresh» + «refresh пересчитывает roles/tv заново» эквивалентной немедленному отзыву: следующий же запрос клиента (после обязательного refresh) видит актуальные права.
    Альтернатива (прежняя версия этого решения) — не класть роли в claims вовсе, полностью резолвить `RoleAssignment`/членство в командах из БД на каждый запрос напрямую, без `roles`-claim и без `token_version`. Отклонена по прямому решению пользователя, пересматривающему более раннюю ревизию этого decision: тот вариант тоже даёт немедленный отзыв, но ценой джойна нескольких таблиц на каждый запрос вместо одного PK-lookup; цена оправдана только если это единственный способ получить немедленный отзыв — `token_version` даёт то же свойство дешевле.

11. **Хранение секретов: `bcrypt` для паролей пользователей, SHA-256 случайного токена для секретных ключей проектов — разные механизмы для разных угроз.**
    Пароль — низкоэнтропийный, выбираемый человеком секрет, для которого важна защита от офлайн-перебора по словарю — для этого нужен медленный, адаптивный алгоритм (`bcrypt`). Секретный ключ проекта — высокоэнтропийная случайная строка (генерируется сервером через `Random.secure()`, не запоминается человеком), для которой не требуется устойчивость к словарному перебору — медленный `bcrypt` был бы просто накладными расходами на каждый вызов `POST /v1/logs` (в отличие от логина, происходящего часто), а быстрый криптографический хэш (SHA-256) даёт то же свойство «в БД не хранится plaintext» без этой цены. Оба секрета показываются вызывающему только один раз, в момент создания.

12. **Bootstrap первого `admin`: явная CLI-команда, не автоматическое создание при первом запуске.**
    `bin/server.dart create-admin --username ... --password ...` (или аналогичный флаг), выполняемая оператором сервера отдельно от обычного `dart run bin/server.dart`; работает только если в БД ещё нет ни одного `admin` (защита от повторного использования как лазейки для повышения прав). Альтернатива — создавать admin автоматически при пустой БД по данным из переменных окружения при обычном старте сервера. Отклонено: неявное поведение при старте (риск случайно оставить сервер с дефолтными кредами, если оператор не подставил свои через env) хуже одной осознанной команды, которую оператор запускает сам. **Пересмотрено decision 49** по прямому требованию пользователя: автосоздание при пустой базе введено. Исходный мотив при этом не отброшен, а закрыт иначе — дефолтных кредов не существует (пароль либо из окружения, либо сгенерированный случайно), созданный так пароль помечен временным и до смены не открывает ничего, кроме собственной смены, а само автосоздание выключается одним флагом. Сама команда `create-admin` остаётся и продолжает работать по прежним правилам — она нужна для повторного bootstrap на непустой базе и для установок с выключенным автосозданием.

16. **Аутентификация по `username` (не `email`); самостоятельная регистрация, переключаемая конфигурацией сервера.**
    `User.username` — обязательное уникальное поле, единственный идентификатор для логина. `User.email` — уникальное (если задано) поле, добавленное decision 24 исключительно для восстановления пароля; логин по нему не выполняется, идентификатором для входа остаётся только `username`. `POST /v1/auth/register` (username + пароль + **обязательный `email`**, опционально `display_name`) создаёт нового `User` без единого `RoleAssignment` — то есть без доступа ни к одному ресурсу, пока `owner`/`admin` явно не выдаст права; регистрация создаёт только учётную запись, не привилегии. Доступность этого эндпоинта управляется полем `ServerConfig.registrationEnabled` (`bool`), задаваемым CLI-флагом (например, `--enable-registration`/`--disable-registration`) или переменной окружения при старте сервера; по умолчанию — `false` (выключено), так как для self-hosted внутреннего инструмента более безопасно начинать с закрытой регистрации, включаемой оператором осознанно. `POST /v1/users` (создание пользователя `admin`-ом) остаётся доступным независимо от этого флага — два независимых пути создания учётной записи.
    Альтернатива — регистрация всегда включена, без флага. Отклонено: сервис может использоваться как закрытый корпоративный инструмент, где открытая регистрация недопустима; явный флаг даёт оператору выбор без необходимости патчить код.

17. **Аутентификация абстрагирована интерфейсом `IdentityProvider`, чтобы local-реализацию (decisions 10/16) можно было подменить на Keycloak/другой OIDC-провайдер, не переделывая RBAC.**
    По прямому требованию пользователя весь код, зависящий от «как проверен токен и откуда взялись роли», обращается не к конкретной local-реализации напрямую, а к интерфейсу:
    ```
    abstract class IdentityProvider {
      Future<VerifiedIdentity?> verifyAccessToken(String bearerToken);
    }
    class VerifiedIdentity {
      final String subject;       // провайдеро-специфичный id пользователя (у local — наш User.id)
      final String? username;     // preferred_username-эквивалент, для JIT-провижининга/отображения
      final List<EffectiveRole>? roles; // null = провайдер не поставляет роли — резолвить из role_assignments; non-null = доверять этому списку как есть
    }
    ```
    - **`roles == null`** — точка расширения для внешнего провайдера, который НЕ поставляет собственные роли (например, Keycloak используется только для идентификации, а права на `Group`/`Project` всё равно выдаются через наш `POST /v1/role-assignments` и хранятся в `role_assignments`, привязанные к JIT-провижненному локальному `User`). Тогда авторизация резолвит `roles` из БД — тем же кодом, что уже существовал как более ранняя (до decision 10) версия этого решения.
    - **`roles != null`** — точка расширения для внешнего провайдера, который сам поставляет права (например, маппинг ролей/групп Keycloak через protocol mappers/custom claims в `{role, scope_type, scope_id}` — конкретный маппинг специфичен для настройки конкретного Keycloak realm и не часть этого интерфейса). В этом режиме `role_assignments` в нашей БД может не использоваться вовсе для таких пользователей, либо использоваться как дополнение — это решает конкретная реализация внешнего провайдера, не эта change.
    - **Терминологическая ловушка, которую обязан помнить будущий адаптер: `group` у Keycloak и `Group` у нас — разные сущности.** В Keycloak, LDAP и OIDC «группа» — это набор пользователей; в этой системе набор пользователей называется `Team`, а `Group` — контейнер проектов и команд, на который выдаются роли и к которому привязано владение. Соответствие при маппинге: членство в Keycloak-группе отображается в `TeamMember` (или напрямую в `RoleAssignment`, если адаптер поставляет права сам, `roles != null`), но **никогда** в `Group` — совпадение слов здесь ложное. Имя `Group` сохранено осознанно (тот же смысл, что у `Group` в GitLab, который тоже владеет проектами), а не по недосмотру; переименование рассматривалось и отклонено, поэтому правило маппинга фиксируется здесь, а не оставляется на догадку того, кто будет писать адаптер.
    - **`token_version`-проверка (decision 10) остаётся полностью внутренней деталью local-реализации** `IdentityProvider.verifyAccessToken` — она не часть интерфейса и не видна вызывающему коду; для local-провайдера несовпадение `tv` просто возвращает `null` (как любой другой невалидный токен), давая 401. Немедленный отзыв для внешнего провайдера, поставляющего собственные `roles`, зависит от его собственной модели ревокации (например, короткого TTL Keycloak-токенов) — эта change не даёт такой гарантии для чужих провайдеров, только для local.
    - Интерфейс экспортируется из публичного API `structured_log_server` (по аналогии с `OutputFunction`/`LogSink` в `structured_log`), чтобы будущий пакет вроде `structured_log_server_keycloak` мог реализовать его отдельно и быть передан при старте сервера (`startServer(identityProvider: ...)`), без форка или изменения `structured_log_server`.
    - Явно НЕ входит в эту change: сама реализация `IdentityProvider` под Keycloak (JWKS-верификация RS256, `iss`/`aud`-валидация, JIT-provisioning, маппинг ролей), схема `User.external_subject` под неё, CLI/env для выбора провайдера (сейчас единственная реализация — local, выбор не требуется). Эти поля/пакеты добавляются вместе с первой реальной внешней реализацией, не спекулятивно сейчас.
    Альтернатива — не вводить интерфейс, оставить local-реализацию единственной и жёстко зашитой. Отклонено по прямому требованию пользователя: тогда подмена на Keycloak в будущем означала бы переписывать код авторизации, а не подставлять новую реализацию одного интерфейса.

13. **Квоты проекта: `retention_days` (обязательное поле) + опциональные `max_entries`/`max_bytes`, с отдельным счётчиком использования.**
    Каждый `Project` обязан иметь `retention_days`. `max_entries`/`max_bytes` — опциональны (`null` = без лимита по этому измерению), задаются владельцем/админом при создании/редактировании проекта. Текущее использование хранится не как `COUNT(*)`/`SUM(size)` по требованию (дорого на большой таблице), а как отдельная строка `ProjectUsage(project_id, entry_count, total_bytes)`, обновляемая атомарно в той же транзакции, что вставка батча и что периодическая очистка по retention — так проверка квоты на приёме — это дешёвый point-lookup, а не агрегирующий запрос по всей таблице записей проекта.

14. **Enforcement квоты: retention — периodic purge job; entries/bytes — отказ конкретным записям батча при приёме.**
    Отдельный периодический таймер (например, раз в час) внутри процесса сервера удаляет записи `log_entries` старше `retention_days` каждого проекта и уменьшает соответствующий `ProjectUsage`. Проверка `max_entries`/`max_bytes` происходит на приёме (`POST /v1/logs`): если добавление записи из батча превысило бы лимит проекта, эта конкретная запись отклоняется (той же схемой частичного приёма батча, что и валидационные ошибки, — не весь батч целиком), с кодом ошибки `quota_exceeded` и HTTP `507 Insufficient Storage` (единственный статус из стандарта, чья семантика буквально «сервер не может сохранить представление [из-за нехватки места]» — точнее подходит, чем `413`, зарезервированный в этом API за превышением размера самого HTTP-тела).

15. **CI: отдельный новый job в существующем [.github/workflows/ci.yml](.github/workflows/ci.yml), не расширение текущего `test`-job.**
    Текущий `test`-job жёстко привязан к `working-directory: structured_log` (не матрица), в отличие от `flutter`-job'а. Новый job матрицей по пакету (`structured_log_server`, `structured_log_http`) через `dart-lang/setup-dart`, стартуя с `ubuntu-latest`, с шагом `dart run build_runner build` перед `analyze`/`test` для `structured_log_server`.

18. **`structured_log_admin_client` — самостоятельное Flutter-приложение под конкретный бэкенд этой change, не headless-ядро + скин по образцу `structured_log_flutter`/`structured_log_material`/`fluent`.**
    Три существующих Flutter-пакета устроены как headless `LogViewerController`/`LogBuffer` (не привязаны к конкретному бэкенду — источник данных всегда локальный `LogSink.output`) + отдельные пакеты-скины поверх них. Для admin-клиента это разделение неуместно: весь смысл приложения — быть UI именно над HTTP-контрактом `structured_log_server` (аутентификация, RBAC, квоты — понятия, которых не существует в headless-ядре просмотра логов), нет и не предвидится второго backend-контракта, под который стоило бы абстрагироваться. Поэтому — один пакет, без разделения на core/skin (конкретный UI-кит — `fluent_ui`, не Material 3, см. decision 38, пересматривающую именно эту часть выбора).
    Альтернатива — вынести headless-слой (API-клиент, модели, состояние) в отдельный `structured_log_admin_core` и UI поверх него, по аналогии с viewer-пакетами. Отклонено сейчас: преждевременная абстракция при единственном потребителе (headless/skin-разделение оправдано, когда есть более одного скина, использующего одно ядро — см. `openspec/changes/add-structured-log-flutter/design.md`, decision 2, тот же принцип «не абстрагировать раньше второго потребителя»); пересмотреть, если понадобится второй UI-кит (Cupertino/Fluent) для этого же клиента.

19. **HTTP-клиент admin-клиента: `dio`, не `http` и не `dart:io` напрямую.** (дополнено decision 37: поверх этого же `dio`-инстанса типизированные эндпоинты идут через `retrofit`, `GET /v1/logs/stream` — вручную; interceptor'ы ниже не пересматриваются)
    Нужны interceptor'ы: автоматическая подстановка `Authorization: Bearer <access-token>` в каждый запрос и единая точка перехвата 401 → `grant_type=refresh_token` → повтор исходного запроса. `package:http` не даёт interceptor-цепочки из коробки, это писалось бы вручную поверх него; `dio` даёт то же самое как штатный примитив (`Interceptor`/`InterceptorsWrapper`), не более тяжёлый по сути, чем `http`, но избавляющий от собственной обёртки с тем же результатом. Zero-dependency принцип `structured_log` (см. `AGENTS.md`) на Flutter-приложения не распространяется — это не библиотека, которую кто-то подключает транзитивно, а конечное приложение.
    `structured_log_admin_client` НЕ зависит от `structured_log_server`/`structured_log_http` — общается с сервером только по документированному HTTP/JSON контракту (`specs/log-server-api`, `specs/log-server-auth`, ...), без единой строчки общего Dart-кода с бэкендом. Отклонённая альтернатива — общий пакет типов запроса/ответа между сервером и клиентом (снизил бы риск рассинхрона контракта, см. Risks) — отклонено сейчас: добавляет пакет ради типобезопасности одного клиента, а рассинхрон и так ловится интеграционными тестами, гоняющими клиентский код (или его логику) против реального сервера (задача в `tasks.md`), а не общим пакетом типов. **Пересмотрено decision 48** в одной части: зависимость на `structured_log` клиенту разрешена — но исключительно как на библиотеку логирования общего назначения для собственной диагностики, а не как на код бэкенда; запрет общего пакета типов контракта и зависимостей на `structured_log_server`/`structured_log_http` не пересматривается.

20. **Хранение токенов: `flutter_secure_storage`, не `shared_preferences`.**
    Access- и refresh-токены — секреты (особенно refresh-токен, долгоживущий и напрямую дающий переоформить сессию); `shared_preferences` на большинстве платформ хранит данные в незашифрованном виде (plist/XML/localStorage), `flutter_secure_storage` — обёртка над Keychain (iOS/macOS)/Keystore (Android)/Credential Manager (Windows)/аналогами на остальных платформах. Одноразовые секретные ключи проектов, которые оператор видит при создании через этот же клиент, в постоянное хранилище клиента не попадают вовсе (показываются один раз, копируются оператором вручную — см. `specs/admin-client-resource-management`), так что этот выбор касается только пользовательской auth-сессии.

21. **Логи проекта в admin-клиенте не переиспользуют `LogViewerController`/виджеты material/fluent — собственная простая реализация поверх `GET /v1/logs`.** (конкретный механизм этого «собственного слоя состояния» — `flutter_bloc`, decision 36)
    `LogViewerController` (`structured_log_flutter`) фильтрует уже находящийся в памяти `List<Map<String, dynamic>>` из локального `LogBuffer` — синхронно, без пагинации, без сетевых вызовов. Источник данных admin-клиента принципиально другой: удалённый, постранично загружаемый, с серверной (не клиентской) фильтрацией через query-параметры. Подгонять `LogViewerController` под оба источника сразу — усложнение существующего, стабильного, уже опубликованного на pub.dev API `structured_log_flutter` ради одного нового потребителя. Проще и безопаснее — собственный, маленький state-слой в `structured_log_admin_client` (выбранная область видимости + текущие фильтры + список записей + курсор пагинации), не претендующий на переиспользование виджетов `structured_log_material`/`fluent`. Унификация (например, `LogViewerController` с pluggable источником данных) — явный Non-Goal, возможная будущая работа, если у `LogViewerController` появится более одного варианта загрузки данных.

22. **`GET /v1/projects/:id` дополнительно возвращает текущее использование квоты (`entry_count`/`total_bytes` из `ProjectUsage`).**
    Небольшое расширение уже спроектированного `log-server-quotas`/`log-server-api`, понадобившееся именно для admin-клиента: отображение «сколько уже использовано из лимита» требует, чтобы это было доступно через API, а не только использовалось сервером внутренне для enforcement на приёме. Не breaking — совместимое добавление полей в существующий ответ.

23. **Реструктуризация репозитория: категории верхнего уровня `emb/`/`backend/`/`frontend/`/`packages/` вместо единого плоского списка пакетов в корне.**
    До этой change все пакеты воркспейса были одного рода — библиотеки, встраиваемые в чужое приложение (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) — и жили плоско в корне репозитория явным списком в `melos.yaml`, по образцу [cherrypick](https://github.com/pese-git/cherrypick) (см. `openspec/changes/add-structured-log-flutter/design.md`, decision 1). С появлением `structured_log_server` (самостоятельный сервис, не встраиваемая библиотека) и `structured_log_admin_client` (самостоятельное приложение, тоже не встраиваемая библиотека) плоский список перестал отражать реальную структуру воркспейса — в нём появились категориально разные виды пакетов, а не только один. По прямому требованию пользователя вводится 4 категории верхнего уровня:
    - `emb/` — встраиваемые в приложения библиотеки: `structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`, `structured_log_http` (все существующие пакеты + новый клиентский sender — он такая же встраиваемая библиотека, как и остальные четыре).
    - `backend/` — серверные приложения: `structured_log_server`.
    - `frontend/` — клиентские приложения с UI: `structured_log_admin_client`.
    - `packages/` — зарезервировано под будущие пакеты, не подпадающие однозначно ни под одну из трёх категорий выше; пустая в рамках этой change (не создаётся как пакет — просто директория-заглушка, без записи в `packages:` `melos.yaml`, пока в ней ничего нет).
    Это явный пересмотр более раннего решения (плоская раскладка без вложенности, выбранная ради единообразия с `cherrypick`) — тогда «плоско» было оправдано однородностью пакетов; сейчас неоднородность (библиотека vs сервис vs приложение) стала реальной, а не гипотетической, и категоризация уже не «вложенность ради вложенности», отклонённая в той более ранней ревизии, а разделение по факту различной природы пакетов.
    Альтернатива — оставить плоскую раскладку, просто продолжив перечислять новые пакеты в корне рядом со старыми. Отклонено по прямому указанию пользователя: с ростом числа пакетов разных категорий плоский список в корне репозитория (и в `melos.yaml`) перестаёт сам по себе сообщать, что чем является, — категории делают это явным без необходимости запоминать/документировать отдельно.

24. **Восстановление пароля по email: отдельный pre-auth flow (`POST /v1/auth/password-reset` + `POST /v1/auth/password-reset/confirm`), не расширение `/v1/auth/token`; `User.email` — новое поле, обязательное при самостоятельной регистрации; отправка письма — через интерфейс `EmailSender`.**
    По прямому требованию пользователя добавлена возможность самостоятельно восстановить доступ к аккаунту при утере пароля, не обращаясь к администратору/owner'у группы — до этой доработки единственный способ сменить пароль пользователю был недоступен вовсе (Non-Goal более ранней ревизии). Конкретно принято:
    - **`User.email`** — новое уникальное (если задано) поле; не идентификатор для входа (им остаётся `username` — decision 16 не пересматривается), только контактный адрес для восстановления пароля. **Обязательно при самостоятельной регистрации** (`POST /v1/auth/register` SHALL требовать `email` наравне с `username`/паролем — 400 при отсутствии, 409 при уже занятом): пользователь, зарегистрировавшийся сам, — единственный, кто отвечает за восстановление собственного доступа, и без email эта возможность была бы для него недостижима с первого дня. При создании пользователя администратором (`POST /v1/users`) `email` остаётся опциональным — админ создаёт учётную запись осознанно и может сообщить пароль вне этого flow; поэтому колонка `User.email` в схеме хранения — `nullable`, а не `NOT NULL` (обязательность — валидация конкретно на `POST /v1/auth/register`, не ограничение на уровне таблицы). Самостоятельное изменение уже сохранённого `email` (`PATCH /v1/users/me`) — явный Non-Goal (см. выше): потребовало бы либо повторного ввода текущего пароля, либо верификации нового адреса подтверждающим письмом — отдельная будущая работа.
    - Альтернатива — оставить `email` опциональным и при самостоятельной регистрации (более ранняя ревизия этого decision). Отклонена по прямому требованию пользователя: опциональность означала бы, что часть самостоятельно зарегистрированных пользователей не смогут воспользоваться восстановлением пароля вовсе — ровно тот случай, который эта доработка призвана закрыть; обязательность на этом единственном пути устраняет пробел, не усложняя путь создания администратором, где email по-прежнему не нужен.
    - **`POST /v1/auth/password-reset`** (JSON-тело `{"email": "..."}"`, не form-encoded — этот эндпоинт не часть контракта `/v1/auth/token` и RFC 6749 на него не распространяется) SHALL всегда отвечать 202 с одинаковым телом независимо от того, существует ли пользователь с указанным `email` — по аналогии с `DELETE /v1/auth/token` (decision 10), чтобы ответ не позволял перебором `email` определять зарегистрированные адреса (user enumeration). Если активный пользователь с таким `email` найден — сервер инвалидирует все его ранее выданные неиспользованные токены восстановления и создаёт новый: высокоэнтропийная случайная строка (`Random.secure()`, тот же генератор, что и для секретных ключей проектов), хранится хэшем (SHA-256 — тот же выбор и по той же причине, что decision 11: токен не запоминается человеком, устойчивость к словарному перебору не нужна) в новой таблице `password_reset_tokens (id, user_id, token_hash, created_at, expires_at, used_at)`, с коротким сроком действия (например, 30 минут, настраивается). Письмо отправляется через `EmailSender`.
    - **`POST /v1/auth/password-reset/confirm`** (JSON-тело `{"token": "...", "new_password": "..."}"`) находит токен по хэшу и проверяет `expires_at`/`used_at IS NULL`; невалиден (не найден/истёк/уже использован) → 400 `invalid_token`, в общем JSON-конверте ошибок `log-server-api` (не в формате RFC 6749 — этот эндпоинт вне контракта `/v1/auth/token`); валиден → обновляет хэш пароля, помечает токен использованным (`used_at`), инвалидирует остальные неиспользованные токены восстановления этого пользователя и — как любая смена пароля — инкрементирует `User.token_version`. Это уже существующее правило (decision 10 перечисляет «смена пароля» среди инвалидирующих событий) — восстановление пароля не вводит новый механизм отзыва, а лишь использует уже спроектированный.
    - **Интерфейс `EmailSender`** (по образцу `IdentityProvider`, decision 17): `abstract class EmailSender { Future<void> send({required String to, required String subject, required String body}); }`, публично экспортирован из barrel-файла `structured_log_server`. Референс-реализация — `SmtpEmailSender` поверх `package:mailer` (SMTP host/port/username/password/from-адрес — новые поля `ServerConfig`, из CLI-флагов/переменных окружения, по аналогии с `registrationEnabled`). Абстракция введена по той же причине, что `IdentityProvider`: оператор может подставить другую реализацию (например, вызов API транзакционного email-провайдера) при старте сервера, не трогая код flow восстановления.
    - **Тело письма — сырой токен для ручного ввода, плюс необязательная ссылка.** Письмо содержит код восстановления как текст (для ввода в `structured_log_admin_client` вручную) и дополнительно URL вида `<passwordResetBaseUrl>?token=...` (адрес настраивается оператором — актуален только для web-сборки admin-клиента, которая может прочитать `token` из query-параметра при загрузке страницы и подставить его в форму). Нативные deep link'и (кастомные URI-схемы/App Links/Universal Links на mobile/desktop) — явный Non-Goal: платформенно-специфичная настройка ради удобства, не необходимость, раз токен всегда можно ввести вручную.
    Альтернатива — не вводить `email` вовсе, оставить сброс пароля обязанностью администратора (более ранняя ревизия Non-Goals). Отклонена по прямому требованию пользователя: самостоятельное восстановление — стандартное ожидание от системы аутентификации, а стоимость (одно опциональное поле + два pre-auth эндпоинта + интерфейс отправки почты) оправдана — тем более что механизм немедленного отзыва при смене пароля (`token_version`) уже существовал и не требует изменений.

25. **Блокировка пользователя/проекта — исключительно роль `admin`, отдельные action-эндпоинты (`block`/`unblock`), а не расширение `PATCH`.**
    По прямому требованию пользователя: `admin` (и только `admin` — не `owner`, даже в своей группе) может немедленно заблокировать любого пользователя или любой проект как средство реагирования на инцидент (скомпрометированный аккаунт/секретный ключ, злоупотребление квотой и т.п.), независимо от того, в чьей группе они находятся.
    - **Блокировка пользователя** — `POST /v1/users/:id/block` / `POST /v1/users/:id/unblock` (оба — `admin` only). `block` устанавливает `User.is_active = false` (уже существующее поле — decision 10 перечисляет деактивацию среди событий, инкрементирующих `token_version`; блокировка использует тот же переключатель, не вводит второе, параллельное поле состояния), **и дополнительно явно отзывает все refresh-токены этого пользователя** (`revoked_at` на всех непросроченных записях `refresh_tokens` этого `user_id`) — это заполняет пробел более ранней ревизии decision 10: там `token_version` инвалидирует только access-токены, но не рассматривался сценарий, где заблокированный пользователь предъявляет ещё не истёкший refresh-токен и получает новый access-токен с уже неактуальным (но формально корректным на момент выдачи) состоянием. Поэтому решение здесь дополнительно требует: `grant_type=refresh_token` SHALL проверять `is_active` пользователя, к которому привязан refresh-токен, и отклонять выдачу новой пары, если пользователь неактивен, — той же ошибкой `invalid_grant`, что и для отозванного/истёкшего токена, независимо от отзыва самих refresh-токенов (защита в глубину: даже если по какой-то причине конкретный refresh-токен не был отозван, неактивный пользователь всё равно не получит новый access-токен). `unblock` возвращает `User.is_active = true`; заблокированный пользователь при этом не теряет свои `RoleAssignment` — они восстанавливаются автоматически вместе с возможностью снова аутентифицироваться.
    - **Блокировка проекта** — новое поле `Project.is_blocked` (bool, по умолчанию `false`) + `POST /v1/projects/:id/block` / `POST /v1/projects/:id/unblock` (оба — `admin` only, в отличие от остального управления проектом, доступного `owner`/`admin` — decision 7/`log-server-rbac`: блокировка — единственное действие над проектом, которое `owner` совершить не может даже над своим собственным проектом, потому что это инструмент реагирования на инцидент поверх иерархии обычных прав, а не рутинное управление). Пока `is_blocked = true`: `POST /v1/logs` (приём по секретному ключу этого проекта) SHALL отклоняться с кодом `project_blocked` (403), не проверяя и не сохраняя ни одной записи батча; `GET /v1/logs?project_id=<заблокированный>` SHALL отклоняться тем же кодом, даже для вызывающего с действительным доступом по RBAC — блокировка перекрывает обычную авторизацию, а не дополняет её. `GET /v1/logs?group_id=G`, где `G` содержит заблокированный проект среди прочих, SHALL молча исключать записи заблокированного проекта из агрегированного результата, не отклоняя запрос целиком — иначе один заблокированный проект в группе останавливал бы просмотр логов всех остальных, ничем не провинившихся проектов той же группы.
    - Секретный ключ заблокированного проекта не отзывается и не удаляется — блокировка обратима (`unblock` немедленно возвращает приём и запрос к норме без необходимости пересоздавать ключи), в отличие от отзыва конкретного ключа (`revoked_at`), который необратим по конструкции (decision 11).
    Альтернатива — не выделять блокировку в отдельное действие, а разрешить `PATCH /v1/users/:id`/`PATCH /v1/projects/:id` с полем `is_active`/`is_blocked` наравне с остальными редактируемыми полями. Отклонено: блокировка — операция другого характера, чем обычное редактирование (у пользователя явно другие права её совершать — только `admin`, тогда как `PATCH /v1/projects/:id` в остальном доступен и `owner`), смешение полей с разной авторизацией в одном универсальном `PATCH` создало бы почву для ошибки (например, per-field авторизацию внутри одного эндпоинта проще упустить в реализации, чем при физически разных путях).

26. **Аудит: отдельная таблица `audit_log_entries`, фиксированный (закрытый) набор типов действий, запись в той же транзакции, что и само действие; чтение — только `admin`, без квоты/retention на сам аудит-лог в этой доработке.**
    По прямому требованию пользователя — пересматривает более раннюю ревизию Non-Goals этой же change («аудит-лог изменений прав доступа... только сам факт текущего состояния `RoleAssignment`»): теперь это полноценная возможность, а не «состояние без истории».
    - **Схема**: `audit_log_entries(id, actor_user_id — nullable, action, target_type, target_id — nullable, metadata — JSON-текст, created_at)`. `actor_user_id` — `nullable`, потому что не для каждого события есть аутентифицированный админ/owner в контексте вызова (см. ниже про self-registration); `target_type`/`target_id` — полиморфная ссылка (на `users`/`groups`/`teams`/`projects`/`project_secret_keys`/`role_assignments`), так как единая таблица должна охватывать разнородные ресурсы; `metadata` — JSON-текст, а не типизированные колонки на каждое действие: набор релевантных деталей разный для каждого `action` (например, для `role_assignment.created` — `{role, scope_type, scope_id, subject_type, subject_id}`, для `project.quota_updated` — `{before: {...}, after: {...}}`), заводить отдельную таблицу/набор колонок под каждый тип действия было бы избыточно ради типобезопасности, которая здесь не incrementally полезна (аудит-запись не участвует в бизнес-логике, только читается человеком/UI).
    - **Закрытый набор `action`**: `user.created`, `user.blocked`, `user.unblocked`, `user.deleted`, `group.created`, `team.created`, `team.member_added`, `team.member_removed`, `project.created`, `project.quota_updated`, `project.blocked`, `project.unblocked`, `secret_key.created`, `secret_key.revoked`, `role_assignment.created`, `role_assignment.revoked`, `password.reset_confirmed` — то есть каждая мутирующая management-операция, спроектированная в этой change (decisions 6, 7, 13, 14, 24, 25, 27). Явно не входят: сам приём/запрос логов (`POST`/`GET /v1/logs` — бизнес-данные, не административное действие, и на порядки более частые), события аутентификации (успешный/неуспешный логин, `logout`, `refresh`) — другая категория событий с другим профилем частоты, не входящая в эту доработку (см. Non-Goals).
    - **Запись в той же транзакции, что мутация** — если сама операция (например, отзыв `RoleAssignment`) откатывается, аудит-запись не должна была создаться отдельно от неё; drift-транзакция вокруг каждой мутирующей операции покрывает и её собственное изменение, и вставку в `audit_log_entries`.
    - **`actor_user_id` для самостоятельной регистрации** — сама создаваемая учётная запись (пользователь буквально совершил действие над собой), а не `null`; для действий администратора/owner — их `user_id` из аутентифицированного access-токена.
    - **`GET /v1/audit-log`** — `admin` only (глобально, не привязано к конкретной группе/проекту — не у всех типов действий есть проект/группа как область), с фильтрами `actor_user_id`/`action`/`target_type`/`target_id`/`from`/`to` и keyset-пагинацией по `id`, тем же паттерном, что `GET /v1/logs`.
    - **Без quota/retention на сам аудит-лог** в этой доработке — он растёт неограниченно (см. Risks); в отличие от `log_entries`, где квота обязательна с самого начала (decision 13), административных мутаций на порядки меньше, чем записей лога, так что немедленная необходимость в retention для аудита менее очевидна — явный Non-Goal, а не забытая деталь. **Пересмотрено decision 46**: retention для аудита введён (двумя раздельными сроками, по умолчанию отключёнными) после того, как decision 44 добавила в аудит аутентификационные события, порождаемые внешним трафиком, — то есть исходная посылка «административных мутаций мало» перестала описывать всё содержимое таблицы.
    Альтернатива — переиспользовать `log_entries` (записывать аудит-события как обычные лог-записи в какой-то служебный проект). Отклонено: `log_entries` спроектирована под пользовательские структурированные логи приложений (с `project_id`, квотами, произвольным `context`) — административные события этой семантике не соответствуют (нет владеющего проекта, не должны подчиняться пользовательским квотам/retention проекта), а смешение доменов усложнило бы обе модели ради экономии одной таблицы.

27. **Удаление аккаунта (`DELETE /v1/users/me` для себя, `DELETE /v1/users/:id` для admin над кем угодно): переиспользует переключатель `is_active` block/unblock (decision 25), необратимо через API, блокируется при единственном владении группой, каскадно отзывает роли/членство.**
    По прямому требованию пользователя: любой аутентифицированный пользователь может безвозвратно удалить свой собственный аккаунт, а администратор — безвозвратно удалить любую чужую учётную запись; удалённые аккаунты помечаются в БД (soft-delete), не удаляются физически, и немедленно теряют доступ к системе. Это пересмотр более ранней ревизии этого же decision в рамках этой change, которая ограничивала удаление только самим собой (см. Non-Goals той ревизии, снятый ниже) — исходно принудительное удаление чужого аккаунта было явным Non-Goal/Open Question, теперь отдельным требованием пользователя переведено в объём.
    - **Новое поле `User.deleted_at`** (nullable timestamp), отдельно от `is_active`: `is_active` описывает «может ли учётная запись сейчас аутентифицироваться» (общий переключатель для блокировки admin'ом и удаления), `deleted_at` — «была ли эта учётная запись когда-либо удалена — самостоятельно или администратором» (более сильное, постоянное состояние, не различающее, кто именно удалил). Оба эндпоинта удаления устанавливают одинаковый набор атомарно: `deleted_at = now()`, `is_active = false`, отзыв всех refresh-токенов, инкремент `token_version`, плюс (новое в этом пересмотре) удаление прямых `role_assignments` пользователя и его записей в `team_members` — тот же самый набор действий, что и `POST /v1/users/:id/block` (decision 25), с добавлением `deleted_at` и каскадного отзыва ролей/членства. Это осознанное переиспользование: удалённый аккаунт должен быть недоступен для входа точно так же, как заблокированный, а весь механизм немедленного отзыва уже спроектирован под это.
    - **Два эндпоинта, один и тот же внутренний путь**: `DELETE /v1/users/me` (доступен любой роли, только над собой, требует пароль) и `DELETE /v1/users/:id` (только `admin` — `log-server-rbac`, над любым другим пользователем, пароль цели не требуется — вызывающий уже аутентифицирован собственной admin-сессией). `DELETE /v1/users/:id` с `:id`, равным самому вызывающему, отклоняется 400 — самоудаление всегда идёт через `/me`, чтобы не обходить требование пароля для собственного аккаунта, назвав себя «целью» административного эндпоинта.
    - **Подтверждение паролем — только для самоудаления**: `DELETE /v1/users/me` принимает текущий пароль в теле запроса и не выполняет удаление при его несовпадении — короткоживущий access-токен сам по себе (например, украденный или оставленный в открытой сессии) недостаточен для необратимого действия над собственным аккаунтом. `DELETE /v1/users/:id` пароль не запрашивает вовсе (ни свой, ни чужой) — по той же логике, что `block`/`unblock` (decision 25): это административное действие, авторизованное ролью `admin`, а не действие пользователя над собой.
    - **Защита единственного владельца группы (новое в этом пересмотре)**: перед применением изменений оба эндпоинта проверяют, не является ли целевой пользователь единственным `owner` (прямо или через команду) хотя бы одной группы. Если да — 409 с кодом `sole_group_owner` и списком блокирующих групп, без каких-либо изменений в БД. Владение нужно сначала передать вручную (`POST /v1/role-assignments` на нового `owner` этой группы), затем повторить удаление. Это ровно та защита, которую предыдущая ревизия этого decision сознательно не вводила («каскадная очистка/переназначение... не автоматизируется») — теперь недостающая часть добавлена не автоматическим переназначением (кому передать — решение человека, не сервера), а блокировкой, пока человек не примет это решение сам.
    - **Каскадный отзыв ролей и членства (новое в этом пересмотре)**: раньше `role_assignments`/`team_members` удалённого пользователя намеренно оставались как есть («висящие» ссылки на неактивную строку). Теперь, поскольку защита единственного владельца гарантирует, что среди оставшихся прямых `role_assignments` нет ни одного «владения без дублирования», удаление может безопасно снести их все, не оставляя недоступного, но формально существующего доступа, привязанного к неактивному пользователю. Роли, выданные команде (`subject_type: team`), не затрагиваются — они принадлежат команде, не конкретному её участнику.
    - **Необратимо через API**: сервер не предоставляет способ снять `deleted_at`. `POST /v1/users/:id/unblock` (decision 25) SHALL явно отказывать (400), если у пользователя установлен `deleted_at`, независимо от того, кем он был удалён — иначе block/unblock, задуманный как обратимый инструмент, стал бы лазейкой, отменяющей необратимость удаления.
    - **`username`/`email` удалённого аккаунта остаются занятыми, пока запись физически не вычищена из БД** — не пересматривается этим пересмотром: уникальность в схеме (decision 16/24) остаётся глобальной, без исключения по `deleted_at`; строка `users` продолжает существовать (и занимать `username`/`email`) до тех пор, пока её кто-то явно не удалит физически. Физическая очистка (hard-delete/purge) — по-прежнему явный Non-Goal.
    - **Восстановление bootstrap-пути**: проверка «уже существует ли admin» в `create-admin` (decision 12) — «существует ли **активный, неудалённый** admin» — не пересматривается; продолжает работать одинаково независимо от того, удалил ли последний admin себя сам или его удалил другой admin.
    Альтернатива (сделать удаление отдельным от блокировки переключателем) — отклонена по той же причине, что и в исходной ревизии этого decision. Альтернатива именно для этого пересмотра — автоматически переназначать владение группой на самого удаляющего admin'а вместо блокировки с 409. Отклонено: делает admin неявным владельцем групп, которыми он не просил управлять, только потому, что оказался тем, кто нажал «удалить» — явная блокировка с понятным кодом ошибки дешевле для реализации и оставляет решение «кому передать» человеку, а не эвристике.

28. **Основной (первый) администратор защищён от удаления по идентичности (`User.is_primary_admin`), а не по количеству оставшихся `admin`.**
    По прямому требованию пользователя, отдельно от и уже, чем любая защита «последнего администратора» (которую предыдущая ревизия decision 27 сознательно не вводила, см. Non-Goals) — тот пересмотр оставлял асимметрию, где `owner` группы защищён (нельзя удалить единственного), а `admin` — нет вовсе. Это новое требование не вводит защиту «по количеству» (можно по-прежнему удалить всех `admin`, кроме одного конкретного), а вводит защиту «по идентичности»: один конкретный, распознаваемый пользователь — тот, кто был создан самым первым вызовом bootstrap-команды `create-admin` — не может быть удалён никогда, независимо от того, сколько ещё активных `admin` есть в системе.
    - **`User.is_primary_admin`** (bool, по умолчанию `false`) — новое поле, устанавливаемое в `true` ровно один раз, первым bootstrap — автоматическим при пустой базе (decision 49) либо командой `create-admin`, смотря каким путём в системе появился первый администратор (когда ни у одного пользователя в таблице ещё не установлен этот флаг — независимо от того, активен ли, заблокирован ли или уже пройден флаг «нет admin», разрешающий повторный запуск `create-admin`, decision 12/27). Если `create-admin` выполняется повторно (например, потому что единственный активный admin был заблокирован, а не основной администратор — legitimate по проверке decision 12/27), новый созданный `admin` НЕ получает `is_primary_admin = true` — флаг остаётся установленным ровно на одном пользователе за всю историю сервера. Никакой API-путь не может установить или снять этот флаг — только сам bootstrap.
    - **Проверка на удаление**: `DELETE /v1/users/me` и `DELETE /v1/users/:id` (decision 27) SHALL отклоняться (403, код `cannot_delete_primary_admin`), если у целевого пользователя `is_primary_admin = true` — эта проверка не зависит от проверки единственного владельца группы (decision 27) и не заменяет её: обе проверки применяются независимо, и любая из них, сработав, блокирует удаление.
    - **Блокировка не распространяется на другие действия**: `POST /v1/users/:id/block` по-прежнему может быть применён к основному администратору (заблокировать, но не удалить) — это осознанно вне рамок этого требования (пользователь просил именно «нельзя удалить», не «нельзя заблокировать»); см. Risks про то, почему это не создаёт лазейку.
    - **UI**: экран пользователя в `structured_log_admin_client` скрывает/деактивирует действие удаления для пользователя с `is_primary_admin = true`, а не полагается только на отказ сервера постфактум (тот же принцип, что уже применяется к остальным недоступным по правам элементам UI).
    Альтернатива — защита «по количеству» (нельзя удалить последнего активного `admin`, кем бы он ни был). Отклонена по прямому указанию пользователя, специфично называвшего «основного (первого)» администратора — идентичность, а не счётчик; защита по количеству также сложнее корректно реализовать при параллельных удалениях (гонка «остался ли ещё один admin» в момент проверки), тогда как проверка одного фиксированного флага на конкретной строке не имеет такой гонки.

29. **Живая доставка новых записей лога: `GET /v1/logs/stream` (SSE), а не WebSocket; in-process broadcast в рамках одного isolate, а не отдельная pub/sub-подсистема; аутентификация Bearer-заголовком через собственный потоковый HTTP-клиент, а не браузерным `EventSource`.**
    По прямому требованию пользователя: самые свежие записи, принятые сервером, должны доставляться подписанным клиентам онлайн, не дожидаясь их следующего опроса.
    - **SSE, не WebSocket.** Канал строго однонаправленный (сервер → клиент, клиент только выбирает область/фильтры один раз при подписке через query-параметры запроса) — WebSocket добавил бы протокольную сложность (отдельное рукопожатие, кадрирование, необходимость самостоятельно реализовать keep-alive) ради дуплекса, которым эта возможность не пользуется. SSE — обычный HTTP-запрос с потоковым телом ответа (`Content-Type: text/event-stream`), проходит через ту же инфраструктуру (прокси/балансировщики/тот же `shelf`-`Pipeline`), что и остальной API, и на `shelf` реализуется штатно — `Response(200, body: <Stream<List<int>>>, headers: {...})`.
    - **`GET /v1/logs/stream`** — те же обязательные `project_id`/`group_id` (ровно один) и та же проверка RBAC/блокировки проекта, что `GET /v1/logs` (decision 8/25), плюс те же дополнительные фильтры (`level`/`category`/`logger`/поля корреляции/`q`/`context.*`) — событие транслируется подписчику, только если проходит те же условия, что использовались бы для его выборки обычным запросом. Ради этого предикатная логика фильтра (`lib/src/storage/query.dart`) рефакторится в форму, пригодную и для построения SQL `WHERE` (исторический запрос), и для проверки одной уже загруженной записи в памяти (живой поток) — одна и та же модель `LogFilter`, два потребителя, вместо двух параллельных реализаций фильтрации, которые могли бы разойтись.
    - **Транспорт события**: `id: <id записи>\nevent: log\ndata: <запись как JSON, одна строка>\n\n`; периодический heartbeat — комментарий SSE (`: ping\n\n`) каждые ~20–30 секунд (см. Open Questions про точное значение), чтобы прокси/балансировщики не закрывали простаивающее соединение по таймауту неактивности.
    - **In-process broadcast, без внешнего pub/sub.** Один процесс сервера (decision 4 — один `QueryExecutor`/один isolate, без шардирования) уже видит все вставки; после `POST /v1/logs` успешно сохраняет принятые батчем записи (прошедшие валидацию и квоту, см. разделы 6/7 `tasks.md`), каждая публикуется в единственный глобальный `StreamController<LogEntry>.broadcast()` процесса. Каждое открытое SSE-соединение подписывается на этот же broadcast-стрим и применяет к каждому событию: (а) принадлежит ли `project_id` события разрешённой области (сам `project_id` или один из проектов запрошенной `group_id`), (б) не заблокирован ли сейчас этот проект (point-lookup `is_blocked`, тот же принцип, что уже используется для `GET /v1/logs?group_id=...` — decision 25, но проверяемый на момент каждого события, а не один раз при подписке), (в) `LogFilter.matches(entry)` — тот же предикат, что и в SQL. Внешний pub/sub (Redis и подобное) не нужен, пока сервер работает в одном isolate/процессе — если много-isolate масштабирование когда-либо перестанет быть Non-Goal (decision 4), broadcast потребует такой замены; сейчас это не требуется.
    - **Аутентификация — тем же access-JWT, что management/query API, заголовком `Authorization: Bearer`, не query-параметром.** Секрет (токен) в URL остаётся в логах прокси/сервера и истории браузера — та же причина, по которой decision 10 уже отклонил токен в query-параметре для `/v1/auth/token`. Следствие этого выбора — браузерный `EventSource` (не поддерживающий собственные заголовки) не может потребить этот эндпоинт напрямую; это осознанно принято, потому что единственный предусмотренный потребитель — `structured_log_admin_client` — уже не браузерный `EventSource`, а `dio` (decision 19) с потоковым `ResponseType.stream`, куда `Authorization`-заголовок подставляется тем же interceptor'ом, что и на остальные запросы; клиент сам построчно разбирает `data:`/`: ping`-кадры (небольшой парсер, не отдельная зависимость).
    - **Ревалидация авторизации на долгоживущем соединении.** Access-токен короткоживущий (decision 10, единицы-десятки минут), но SSE-соединение может жить дольше его срока действия. Держать его открытым до истечения токена без повторной проверки означало бы дыру в уже спроектированной гарантии мгновенного отзыва (`token_version`, decision 10; блокировка, decision 25; удаление, decision 27/28) — единственное место в системе, где отозванные права могли бы молча продолжать действовать до следующего запроса. Поэтому сервер при каждом тике heartbeat дополнительно делает тот же дешёвый point-lookup, что и обычный запрос (`token_version`/`is_active`/`deleted_at` пользователя, `is_blocked` текущего проекта/группы), и, если что-то из этого больше не проходит, закрывает поток терминальным событием (`event: end\ndata: {"reason": "token_revoked" | "project_blocked"}\n\n`) вместо того, чтобы держать соединение открытым молча — HTTP-статус к этому моменту уже отправлен (200) и не может быть переигран на 401/403, поэтому сигнал передаётся содержимым потока, а не кодом ответа; клиент трактует это как обычный 401/403 (переподключение через `admin-client-auth`, decision 12.4/12.5-эквивалент для стрима).
    - **Catch-up через `since_id`, без гонки и без дублей.** Между обычным `GET /v1/logs` (начальная страница) и открытием `/v1/logs/stream` неизбежен зазор, в который могли прийти новые записи. Клиент передаёт `since_id` — `id` последней уже отображённой записи; сервер сначала подписывается на broadcast (буферизуя всё, что приходит, пока не готов первый ответ), затем одним запросом выбирает из хранилища записи с `id > since_id` (тем же фильтром/областью), отдаёт их как обычные SSE-события, затем сбрасывает то, что накопилось в буфере подписки за это время, отбрасывая уже отданные `id` — так клиент не теряет и не дублирует ни одной записи независимо от того, сколько заняла начальная выборка. `since_id` не обязателен — без него поток начинается строго с этого момента вперёд (типичный случай первой подписки сразу после первой страницы).
    Альтернатива — WebSocket вместо SSE. Отклонена: не нужен дуплекс, а операционная сложность (отдельный протокол, свой keep-alive, не такая прозрачная работа через часть HTTP-прокси) не окупается для однонаправленной трансляции. Альтернатива — polling (клиент сам периодически перезапрашивает `GET /v1/logs`) вместо push. Отклонена по прямому требованию пользователя («доставляться по sse») — а также потому, что polling либо тратит ресурсы на пустые ответы при частом опросе, либо даёт задержку при редком.

30. **Admin-клиент: лента логов ведёт себя как история чата — автослежение только у нижнего края, отдельная явная пауза/возобновление, по аналогии с `LogViewerController.paused` (decision 21), но поверх удалённого `GET /v1/logs`+`GET /v1/logs/stream`, а не локального `LogBuffer`.**
    По прямому требованию пользователя: «всегда показываем самые свежие события, и только по скроллу отображаем предыдущие»; «динамическое отображение можно приостановить и заново запустить».
    - **Начальная загрузка** — обычная первая страница `GET /v1/logs` (decision 31 — по убыванию `id`, то есть самые новые записи), список рендерится в хронологическом порядке (старые сверху/новые снизу, как переписка), прокрученным к нижнему краю; сразу вслед за этим открывается `/v1/logs/stream?since_id=<id самой новой полученной записи>` (decision 29) с теми же `project_id`/`group_id`/фильтрами.
    - **Автослежение** — пока пользователь прокручен к нижнему краю (или ещё не прокручивал), каждая новая запись из SSE-потока дописывается в конец и список автопрокручивается за ней, как типичная лента чата. Если пользователь прокрутил выше нижнего края (читает историю), новые записи **не** выталкивают его вниз принудительно — вместо этого они копятся, и показывается индикатор («N новых событий ↓»), по нажатию на который список прокручивается к концу и автослежение возобновляется. Это не то же самое, что явная пауза ниже — это неявное следствие текущей позиции прокрутки, снимается самим возвратом к низу.
    - **Подгрузка истории по прокрутке вверх** — при приближении к верхнему краю уже загруженного списка приложение подгружает более раннюю страницу через уже существующий курсор `GET /v1/logs` (`admin-client-log-browser`, «Постраничная подгрузка...») и добавляет её сверху, не трогая уже показанное внизу — то есть тот же механизм пагинации, что уже специфицирован, но её триггер — не отдельная кнопка «ещё», а сама прокрутка к верхней границе.
    - **Явная пауза/возобновление** — отдельное действие (кнопка), не зависящее от текущей прокрутки: при паузе видимый список замораживается целиком (как `LogViewerController.paused` замораживает `visibleEntries`, decision 21) — SSE-соединение при этом остаётся открытым и продолжает получать события в фоне (не переподключается), они лишь не попадают в видимый список, а копятся в ограниченном по размеру буфере (см. Risks — не безграничный, по аналогии с decision про верхний предел буфера `structured_log_http`). Возобновление сбрасывает буфер в список и прокручивает к концу, как будто паузы не было — если буфер был усечён переполнением (пауза держалась необычно долго), вместо частичного «рваного» списка приложение вместо накопленного буфера просто перезагружает свежую первую страницу через `GET /v1/logs` и открывает новую подписку с этого места, не пытаясь честно доиграть пропущенный кусок.
    - Ни автослежение, ни пауза не относятся к самой подписке SSE — она остаётся открытой (кроме случая переполнения буфера паузы выше) на всё время, пока экран логов открыт с данной областью/фильтрами; закрывается и переоткрывается заново только при смене области/фильтров (сброс пагинации — уже специфицированное поведение, `admin-client-log-browser`) или явном обрыве соединения (переподключение с `since_id` последней отображённой записи).
    Альтернатива — при паузе закрывать SSE-соединение и переподключаться с `since_id` при возобновлении. Отклонена: усложняет клиент (логика переподключения нужна на каждую паузу, не только на реальный сетевой обрыв) без явной выгоды при типичных объёмах событий одного проекта/группы; открытое-но-не-рендерящееся соединение — тот же принцип, что уже применяется в `LogBuffer.capture()` (продолжает захват независимо от `LogViewerController.paused`, decision 21) — сохранение уже проверенного паттерна, не изобретение нового для этого экрана.

31. **`GET /v1/logs` без явного указания направления возвращает записи по убыванию `id` (сначала самые новые); курсор пагинации продвигается к более ранним записям.**
    Уточнение уже спроектированного, но явно не зафиксированного направления курсорной пагинации (decision 8/`log-server-api`) — понадобившееся именно сейчас, потому что лента в стиле истории чата (decision 30) требует, чтобы «первая страница без курсора» детерминированно означала «самые свежие N записей», а не какую-то неопределённую начальную точку. Это не новый параметр и не breaking-изменение контракта — тот же эндпоинт, то же поле `limit`/курсор, только явно задокументированное направление по умолчанию; конкретный `order`-параметр для переключения направления не вводится, так как ни один сценарий этой change в нём не нуждается.
    Альтернатива — оставить направление неопределённым, документировав явную загрузку «последней страницы» отдельным способом (например, специальным значением курсора вроде `latest`). Отклонена как более сложный контракт ради явности там, где сначала-новые-записи — единственное осмысленное поведение по умолчанию для UI логов (и уже фактическое ожидание большинства подобных систем — просмотрщиков логов/чатов).

32. **Организация кода: `feature-first` в обоих новых пакетах; внутри фичи — слоистая архитектура в `structured_log_server`, полная Clean Architecture в `structured_log_admin_client`.**
    По прямому требованию пользователя. `lib/src/` (сервер) и `lib/src`/`lib/features` (клиент) организуются в первую очередь по фиче предметной области (`auth`, `users`, `projects`, `logs`, `live_stream`, `audit`, `teams`, ...), а не по техническому типу файла (`routes/`, `services/`, `models/` сквозным списком на весь пакет) — тот же принцип `feature-first`, что уже зафиксирован для `structured_log_admin_client` в исходной формулировке этой же change (см. «Структура пакетов» плана этой change) и независимо являющийся общей практикой для приложений такого масштаба.
    - **Сервер — слоистая архитектура, не полный Clean Architecture.** Внутри фичи — деление на слои (например, `domain`/`data`/`http` или эквивалентное), но без выделенного presentation-слоя, которому Clean Architecture в первую очередь адресована (`structured_log_server` — headless HTTP API, а не приложение с UI) — полный четырёхслойный Clean Architecture здесь был бы избыточной структурой ради структуры.
    - **Клиент — полная Clean Architecture** (`domain`/`application`/`infrastructure`/`presentation` внутри каждой фичи) — у клиента, в отличие от сервера, есть настоящий UI-слой (Flutter-виджеты, `flutter_bloc`), для которого разделение domain/presentation несёт реальную пользу (тестируемость бизнес-логики без Flutter-виджетов, замена infrastructure на моки в тестах).
    - Общие сквозные таблицы хранения (`log-server-storage`, decision 6) и общая HTTP-инфраструктура (error envelope, middleware) сервера остаются в отдельном `shared`/`common`-слое вне фич — они используются несколькими фичами одновременно, помещение их в одну конкретную фичу создало бы произвольную, ничем не обоснованную привязку.
    - Точная файловая раскладка (конкретные имена директорий/файлов) — не часть этой change; `tasks.md` описывает задачи по capability, а не по итоговому дереву файлов, чтобы не фиксировать преждевременно детали, уточняемые в процессе самой реализации. См. Risks.
    Альтернатива — организация по техническому типу файла на весь пакет (как это по умолчанию описано путями в более ранних задачах `tasks.md`, например `lib/src/storage/database.dart`, `lib/src/auth/...`). Отклонена по прямому требованию пользователя: при росте числа фич технический список файлов не показывает, какие файлы относятся к одной и той же предметной возможности, тогда как `feature-first` делает это явным без необходимости отдельно документировать.

33. **`fpdart` (`Either`/`Option`) — для ожидаемых, часть потока управления составляющих исходов, в обоих новых пакетах; не для программных ошибок.**
    По прямому требованию пользователя. Различие, которое эта доработка проводит явно (иначе легко скатиться к «оборачивать всё в `Either`», что не является целью):
    - **Ожидаемый исход, часть контракта** (`Either<Failure, T>`/`Option<T>`): ошибка валидации входных данных, отказ RBAC, превышение квоты, `invalid_grant`/`invalid_token`, сетевая ошибка на клиенте, `401`/`403`/`404`/`409` от сервера — вызывающий код обязан явно обработать оба исхода на этапе компиляции, а не полагаться на то, что не забудет `catch`. Доменные/application-слои возвращают `Either`, презентационный слой клиента (`flutter_bloc`) или HTTP-слой сервера (`shelf`-хендлер) на границе превращает `Left`/`Right` в конкретный ответ (HTTP-статус + JSON-конверт ошибок — уже спроектированный контракт, decisions 10 и др. — не меняется; `fpdart` — деталь внутренней реализации, не часть wire-контракта).
    - **Программная ошибка** (нарушенный инвариант, баг) — остаётся исключением (`throw`), не `Either`; `fpdart` не заменяет исключения полностью, только там, где ошибка — ожидаемая альтернатива успеху, а не признак дефекта.
    Альтернатива — исключения везде (текущий стиль остальных пакетов воркспейса, например `structured_log`). Отклонена по прямому требованию пользователя для этих двух конкретных пакетов — `structured_log` сам не пересматривается, остаётся без сторонних зависимостей (Non-Goals/`AGENTS.md`).

34. **`freezed` (+ `json_serializable`) для неизменяемых моделей и sealed-объединений в обоих новых пакетах — расширяет codegen-исключение decision 2 с `drift` на ещё два инструмента, по-прежнему ограниченное этими двумя новыми пакетами.**
    По прямому требованию пользователя. `freezed` генерирует неизменяемые data-классы (`==`/`hashCode`/`copyWith`/`toString` из коробки) и sealed-объединения (например, `LogFeedState` клиента — `Loading`/`Following`/`ScrolledUp`/`Paused`, или доменная ошибка сервера как объединение конкретных причин отказа) — естественная пара для `fpdart`'s `Either<Failure, T>`, где и `Failure`, и `T` обычно — `freezed`-классы. `json_serializable` (через `@JsonSerializable`/`freezed`'s `.fromJson`/`.toJson` фабрики) сериализует их на границе HTTP.
    - **`structured_log_server`**: тот же `build_runner`, что уже требуется `drift` (decision 2), покрывает и генерацию `freezed`/`json_serializable` в одном прогоне — не отдельный шаг codegen, не отдельный риск сверх уже принятого decision 2.
    - **`structured_log_admin_client`**: до этой доработки ни один Flutter-пакет воркспейса (`structured_log_flutter`/`material`/`fluent`) не использовал codegen — этот выбор впервые вводит `build_runner` во Flutter-пакет. Явно ограничено `structured_log_admin_client` — три существующих viewer-пакета этим решением не затрагиваются и не обязаны когда-либо его перенимать.
    - Это explicitly пересматривает формулировку принципа «никакой магии»/«codegen — единственное исключение, `drift`, не прецедент для остального воркспейса» из более ранней ревизии этой же change (и из `docs/architecture/README.md`, обновляется вместе с этой правкой) — точнее теперь: codegen остаётся исключением для `emb/`-пакетов (`structured_log`/`structured_log_flutter`/`structured_log_material`/`structured_log_fluent`/`structured_log_http`), но для новых `backend/`/`frontend`-пакетов этой change теперь три санкционированных инструмента (`drift`, `freezed`, и — только в клиенте — `retrofit_generator`, decision 37), а не один.
    Альтернатива — писать неизменяемые классы вручную (`const` конструкторы, ручные `==`/`copyWith`). Отклонена по прямому требованию пользователя: с ростом числа моделей (пользователи/группы/команды/проекты/роли/аудит-записи и их DTO) ручное сопровождение `==`/`hashCode`/`copyWith` для каждой — источник трудноуловимых багов (забытое поле в `==`), которого генерация избегает по конструкции.

35. **Dependency injection в `structured_log_admin_client`: `cherrypick`.**
    По прямому требованию пользователя. `cherrypick` — DI-библиотека того же автора, уже давшая название конвенции плоской раскладки пакетов этого воркспейса (`AGENTS.md`: «по образцу [cherrypick]... того же автора»); здесь она используется впервые непосредственно как зависимость, не только как источник конвенции именования. Даёт компонентную (scope-based) регистрацию зависимостей для Clean-Architecture-слоёв каждой фичи (decision 32) — конкретные `infrastructure`-реализации (репозитории поверх `retrofit`-клиентов) внедряются в `application`-слой через DI-контейнер, а не создаются напрямую внутри presentation-кода.
    Альтернатива — `get_it`/`provider`/ручная передача зависимостей через конструкторы без DI-фреймворка. Отклонена по прямому требованию пользователя — `cherrypick`, а не альтернативы, экосистемно более familiar автору и уже задаёт прецедент именования в этом же воркспейсе.

36. **Управление состоянием в `structured_log_admin_client`: `flutter_bloc` (`Bloc`/`Cubit`) — конкретизирует «собственный маленький state-слой» из decision 21/30, не абстрактный `ChangeNotifier`.**
    По прямому требованию пользователя. Decision 21 уже отклонил переиспользование `LogViewerController` (`ChangeNotifier`-based) ради собственного, маленького слоя состояния для просмотрщика логов; decision 30 описал этот слой через состояния (следование/прокручено-вверх/пауза) и переходы между ними, не называя конкретный механизм. `flutter_bloc` — этот механизм: `LogFeedBloc`/`LogFeedCubit` с явными состояниями (`Following`/`ScrolledUp`/`Paused`, как `freezed`-объединение — decision 34) и событиями (`_NewEntryArrived`/`_ScrolledToTop`/`_PausePressed`/`_ResumePressed`/`_FiltersChanged`, ...), которые ровно реализуют диаграмму состояний decision 30 как `Bloc`-автомат. Тот же подход — для остальных экранов (аутентификация, управление ресурсами, аудит): каждый экран/фича — свой `Bloc`/`Cubit` в presentation-слое (decision 32), получающий зависимости (repositories/use-cases) через `cherrypick` (decision 35).
    Альтернатива — `riverpod`/`provider`/остаться на неспецифицированном `ChangeNotifier`-подобном контроллере. Отклонена по прямому требованию пользователя — `flutter_bloc`, а не альтернативы.

37. **HTTP-клиент в `structured_log_admin_client`: `dio` + `retrofit` для типизированных request/response-эндпоинтов; `GET /v1/logs/stream` остаётся вручную написанным поверх того же `dio`, не через `retrofit`.**
    По прямому требованию пользователя, расширяет decision 19 (`dio`, не `package:http`) добавлением `retrofit` — кодогенерируемых типизированных интерфейсов клиента (`@RestApi()`/`@GET`/`@POST`-аннотации → сгенерированная реализация, вызывающая тот же `dio`-инстанс) поверх уже спроектированных interceptor'ов (подстановка `Authorization`, перехват 401 → refresh → повтор, decision 19 не пересматривается в этой части). Модели запроса/ответа — `freezed`+`json_serializable` (decision 34), `retrofit_generator` — тот же `build_runner`-прогон.
    - **`GET /v1/logs/stream` — осознанное исключение из `retrofit`.** SSE — долгоживущее потоковое тело с построчным разбором кадров (`id:`/`event:`/`data:`, см. `live-streaming.md`), а не одно типизированное JSON-тело ответа на один запрос — модель `retrofit` (один аннотированный метод → один десериализованный объект/список) этому не соответствует. `log_stream_client.dart` (архитектура клиента, `docs/architecture/admin-client.md`) остаётся написанным вручную поверх `dio`'s `ResponseType.stream`, используя тот же `Authorization`-interceptor, что и `retrofit`-клиенты — единственная граница, где в приложении сосуществуют два стиля обращения к HTTP.
    - **Уточнено реализацией (15.09.2026): «тот же `dio`» оказалось «тот же перехватчик, второй инстанс».** На web `dio` не умеет стримить ответ, и это не настраивается — браузерный адаптер ставит `xhr.responseType = 'arraybuffer'` и отдаёт тело целиком в `onLoad`, так что подписка, доставляемая по мере поступления, через него не проходит вовсе. Живой поток читается через `fetch`/`ReadableStream` (`shared/api/streaming/`, условный импорт; вне web возвращается `null` и остаётся платформенный адаптер `dio`). Адаптер стоит на отдельном инстансе `ApiClient.streamDio`, и тот несёт **тот же объект** `AuthInterceptor`, что основной: гарантия, ради которой это решение и писалось — один `Authorization` и одно обновление токена в полёте — живёт в экземпляре перехватчика, а не в экземпляре `Dio`, и сохранена. Расходится с первоначальной формулировкой только число инстансов. Юнит-тесты этого не ловят — они идут на Dart VM с подставным адаптером; ловится браузером.
    Альтернатива — реализовать все эндпоинты, включая `/v1/logs/stream`, вручную на `dio`, без `retrofit` вовсе. Отклонена по прямому требованию пользователя для «обычных» эндпоинтов — `retrofit` снимает ручное написание однотипного кода сериализации/десериализации на каждый из полутора десятков JSON-эндпоинтов контракта (`api/http-api.md`); ручной путь оставлен только там, где `retrofit` объективно не подходит (потоковый SSE), а не выбран как основной стиль.

38. **UI-кит `structured_log_admin_client`: `fluent_ui`, не Material 3 — пересматривает выбор UI-кита в decision 18 (часть про «один пакет, без core/skin» decision 18 не пересматривается).**
    По прямому требованию пользователя. Более ранняя ревизия decision 18 выбирала Material 3 без отдельного обоснования (по умолчанию для Flutter-приложений); теперь явно заменено на `fluent_ui` — `FluentApp`/Fluent-виджеты вместо `MaterialApp`/Material-виджетов. Экраны уже отрисованы отдельно (Claude Design, вне репозитория и вне OpenSpec) — реализация следует этим макетам, когда они существуют; сама визуальная раскладка — явный Non-Goal этой change (см. выше).
    - **Не переиспользование `structured_log_fluent`.** В воркспейсе уже есть `structured_log_fluent` — Fluent-скин просмотрщика логов поверх `structured_log_flutter`. Выбор `fluent_ui` для `structured_log_admin_client` — совпадение дизайн-системы, не переиспользование кода: decision 21 (не переиспользовать `LogViewerController`/виджеты `material`/`fluent` — разные источники данных) не пересматривается этим decision. Оба приложения могут выглядеть стилистически похоже (одна дизайн-система), не деля ни строчки кода.
    - Часть decision 18 про «один пакет, без разделения core/skin» (обоснование — единственный потребитель, единственный backend-контракт) не зависит от выбора конкретного UI-кита и остаётся в силе без изменений.
    Альтернатива — оставить Material 3 (более ранняя ревизия decision 18). Отклонена по прямому требованию пользователя.

39. **Общие, не завязанные на бизнес-логику виджеты `structured_log_admin_client` выносятся в отдельный пакет `frontend/structured_log_admin_ui/`, структурированный по Atomic Design (atoms/molecules/organisms).**
    По прямому требованию пользователя.
    - **Расположение — `frontend/`, не `emb/`.** `emb/` (decision 23) — категория библиотек, встраиваемых в *произвольное стороннее* приложение (`structured_log`/`structured_log_flutter`/`structured_log_material`/`structured_log_fluent`/`structured_log_http`) — ни одна из них не привязана к конкретному продукту. `structured_log_admin_ui`, напротив, — компонентная библиотека конкретно для эстетики и словаря `structured_log_admin_client` (её атомы естественно включают предметно-специфичные вещи вроде бейджа уровня лога), не пакет общего назначения, который имело бы смысл подключать в произвольный сторонний Flutter-проект. Поэтому — рядом с `structured_log_admin_client` в `frontend/`, не в `emb/`.
    - **Направление зависимости — одностороннее.** `structured_log_admin_client` зависит от `structured_log_admin_ui` (path-зависимость внутри workspace), никогда наоборот; `structured_log_admin_ui` НЕ зависит от `fpdart`/`freezed`/`cherrypick`/`flutter_bloc`/`dio`/`retrofit` (decisions 33–37) и не импортирует ничего из `structured_log_admin_client` — только `flutter` sdk и `fluent_ui` (decision 38, компонует/оборачивает Fluent-примитивы в темизированные атомы, не переизобретает их). Это делает границу «эти виджеты не могут дотянуться до Bloc/repository-кода» проверяемой на этапе `pub get`/анализа (циклическая или обратная зависимость — ошибка сборки), а не только соглашением, которое легко случайно нарушить внутри одного пакета.
    - **Три уровня — ровно те, что назвал пользователь, не классические пять.** Классический Atomic Design (Brad Frost) добавляет ещё `templates` и `pages` — но они по определению собирают organisms в целый экран с реальными данными, то есть уже завязаны на бизнес-логику/данные конкретной фичи. Это прямо противоречит самой формулировке требования («не завязаны на бизнес-логику»), поэтому `templates`/`pages` сюда не переносятся — они остаются экранами (`presentation`-слой каждой фичи, decision 32) внутри `structured_log_admin_client`, которые *используют* atoms/molecules/organisms из этого пакета, оборачивая их в конкретные данные и колбэки, привязанные к своему `Bloc` (decision 36). В `structured_log_admin_ui` — только:
      - **atoms** — наименьшие неделимые элементы (бейдж уровня лога, кнопка/текстовый стиль, иконка, токены отступов/типографики/цвета);
      - **molecules** — небольшие сочетания атомов (поле поиска с иконкой и кнопкой очистки, чип фильтра, строка «ключ: значение» для отображения квоты, переключатель с подписью);
      - **organisms** — более сложные, самодостаточные секции UI (строка списка ресурса с действиями, панель фильтров, каркас диалога подтверждения, каркас навигации) — каждая из них принимает только примитивные/enum-параметры и колбэки (`onTap`/`onChanged` и т.п.), не доменные модели этого API и не `Bloc`-состояния напрямую; допустимо эфемерное, чисто презентационное локальное состояние (hover/фокус/раскрыт-свёрнут) через обычный `StatefulWidget`/`ValueNotifier` — не через `flutter_bloc`.
    - **Дублирование палитры уровня лога, не переиспользование.** `LogLevelBadge` (атом) владеет собственным маленьким мэппингом цвета уровня, не импортирует его из `structured_log_material`/`structured_log_fluent` (decision 21 — admin-клиент в принципе не делит код с viewer-пакетами) — тот же принцип, что уже применён между `structured_log_material` и `structured_log_fluent` (`logLevelColor()` осознанно продублирована между ними, см. их собственный `design.md`), а не исключение из него.
    - **`example/`** — приложение-галерея компонентов (по аналогии с `structured_log_material_example`/`structured_log_fluent_example`), демонстрирующее каждый atom/molecule/organism — живая документация вместо статичных скриншотов; удобно и для ручной визуальной проверки соответствия макетам Claude Design (decision 38).
    - **`publish_to: none`**, как и сам `structured_log_admin_client` (Open Questions) — тесно привязан к его конкретной эстетике и словарю компонентов, не библиотека общего назначения.
    - **Это не противоречит принципу «не абстрагировать раньше второго потребителя» (decisions 18/21).** Тот принцип — про преждевременное обобщение ради гипотетического *второго* потребителя/backend'а/UI-кита. Здесь мотивация другая и не гипотетическая: разделение presentation-виджетов и бизнес-логики *внутри одного и того же* приложения, продиктованное прямым требованием пользователя, а не ставкой на будущее переиспользование — единственный потребитель `structured_log_admin_ui` как был, так и остаётся `structured_log_admin_client`.
    Альтернатива — держать эти виджеты в `structured_log_admin_client` (например, `lib/shared/widgets/`), без отдельного пакета. Отклонена по прямому требованию пользователя: директория внутри того же пакета ничем технически не мешает импортировать Bloc/repository-код из презентационного виджета — только отдельный пакет даёт проверяемую компилятором границу, независимое тестирование и явную видимость этой границы для будущих контрибьюторов/AI-агентов.

40. **Подтверждение email обязательно перед входом: `User.email_verified_at`, единообразно для любой учётной записи с заданным `email`, независимо от того, как она создана — не расширение `/v1/auth/token`, а отдельный pre-auth flow, переиспользующий интерфейс `EmailSender` (decision 24).**
    По прямому требованию пользователя, обязательное требование — пересматривает более раннюю ревизию Non-Goals этой же change («верификация email при задании... не реализуется»).
    - **Единое правило, без привязки к способу создания аккаунта.** Любая учётная запись, у которой `email` задан (сейчас это происходит либо всегда — при самостоятельной регистрации, decision 24, либо опционально — при создании администратором через `POST /v1/users`), обязана подтвердить его, прежде чем `grant_type=password` начнёт выдавать токены для неё. Учётные записи без `email` (включая `create-admin`-bootstrap, decision 12, который email вообще не запрашивает) под это правило не подпадают — подтверждать нечего. Рассматривалась альтернатива ограничить проверку только самостоятельной регистрацией (раз именно там `email` обязателен) — отклонена: пришлось бы вводить и хранить дополнительный признак «как создан этот пользователь» ради единственной цели различить два пути, тогда как единое правило «email задан → должен быть подтверждён» не требует такого признака вовсе и проще специфицируется и реализуется. Практическое следствие: администратор, указавший `email` при создании пользователя через `POST /v1/users`, должен предупредить его о необходимости подтвердить адрес до первого входа — небольшое трение, принятое ради единообразия (см. Risks).
    - **Новая таблица `email_verification_tokens`** (`id`, `user_id`, `token_hash`, `created_at`, `expires_at`, `used_at`) — структурно идентична `password_reset_tokens` (decision 24): `token_hash` — SHA-256 случайной строки от `Random.secure()` (тот же выбор и по той же причине, что decision 11/24 — токен не запоминается человеком), сама строка никогда не хранится. Токен создаётся сразу после того, как `email` становится заданным (успешная самостоятельная регистрация, либо `POST /v1/users` с непустым `email`) и отправляется через уже существующий интерфейс `EmailSender` — новый интерфейс не вводится.
    - **`POST /v1/auth/verify-email`** (JSON `{"token": "..."}"`, не форм-encoded — этот путь не часть контракта `/v1/auth/token`, RFC 6749 на него не распространяется, тот же выбор, что уже сделан для `password-reset/confirm`, decision 24) находит токен по хэшу, проверяет `expires_at`/`used_at IS NULL`; невалиден → 400 `invalid_token` (тот же код, что уже используется `password-reset/confirm` — семантически то же самое «токен восстановления/подтверждения недействителен», различается только эндпоинтом, в котором встречается); валиден → устанавливает `User.email_verified_at = now()`, помечает токен использованным, инвалидирует остальные неиспользованные токены подтверждения этого пользователя.
    - **`POST /v1/auth/verify-email/resend`** (JSON `{"email": "..."}"`) — всегда 202 с одинаковым телом, независимо от того, существует ли такой email, уже подтверждён он или нет (тот же анти-enumeration паттерн, что `password-reset`, decision 24) — инвалидирует прежние неиспользованные токены подтверждения этого пользователя и создаёт новый, если email существует и ещё не подтверждён; иначе молча ничего не делает.
    - **`grant_type=password` для email, заданного, но не подтверждённого** — отклоняется как `invalid_grant`, тем же путём, что уже отклоняются неверный пароль и неактивный пользователь (decision 10/25) — с одним дополнением: тело ответа несёт дополнительное, не входящее в RFC 6749 поле `reason: "email_not_verified"` поверх стандартных `error`/`error_description`. Это аддитивное расширение RFC-конверта (не входящее в него поле игнорируется любым конформным OAuth2-клиентом) — тот же принцип, что уже применён к общему JSON-конверту ошибок (`sole_group_owner`'s `details`), распространённый здесь на RFC-конверт впервые. Без этого поля `structured_log_admin_client` не мог бы отличить «неверный пароль» от «email не подтверждён» и показать разные, осмысленные сообщения (decision 33's fpdart-обработка ошибок клиента полагается на этот сигнал). `grant_type=refresh_token` дополнительную проверку не получает — раз первичный `grant_type=password`-вход в принципе недостижим для неподтверждённого email, ни один refresh-токен для такой учётной записи не мог быть выдан, повторная проверка на каждый refresh была бы избыточна (в отличие от `is_active`, decision 25, которое может измениться уже *после* выдачи токенов).
    - **Аудит**: успешное подтверждение — новое действие `email.verified` в закрытом наборе (decision 26), `actor_user_id` — сам подтвердившийся пользователь (та же логика, что `user.created` для самостоятельной регистрации и `password.reset_confirmed`).
    - **Доставка ссылки** — тот же паттерн, что decision 24: письмо содержит сырой токен для ручного ввода плюс необязательный URL `<emailVerificationBaseUrl>?token=...` (новое поле `ServerConfig`, по аналогии с `passwordResetBaseUrl`), актуальный только для web-сборки. Рассматривался вариант с прямой GET-ссылкой, подтверждающей email одним кликом без какого-либо экрана приложения (типовой паттерн «click to verify» у многих сервисов) — отклонён: GET — небезопасный (не read-only) метод для действия, меняющего состояние, и превращает случайное открытие письма почтовым сканером/preview-ботом в непреднамеренное сжигание токена; вместо этого web-сборка сама выполняет `POST /v1/auth/verify-email` при обнаружении `?token=` в URL — то есть ссылка ведёт на страницу приложения, а не напрямую на API-эндпоинт, тем же способом, что уже принят для `password-reset` (страница читает `token` из query-параметра и подставляет в форму/шлёт запрос сама, не сама ссылка меняет состояние).
    Альтернатива — не блокировать вход, а лишь показывать в UI предупреждение о неподтверждённом email (email работает для приёма писем, но вход не запрещён). Отклонена по прямому требованию пользователя: это обязательное требование, а не рекомендация — единственный способ действительно гарантировать, что сервер не полагается на адрес, которым никто не подтвердил владение (что в первую очередь и было названо пробелом, приведшим к этому требованию).

41. **`PATCH /v1/users/:id` (admin only) — редактирование `email`/`display_name`/`password` существующего пользователя; не трогает поля, у которых уже есть собственные эндпоинты.**
    По прямому требованию пользователя, закрывает пробел: до этого decision у `admin` был способ создать (`POST /v1/users`), заблокировать/разблокировать, удалить пользователя — но не отредактировать уже существующего (например, поправить опечатку в `email`, или задать/сбросить пароль, если пользователь его забыл, а `email` не задан, значит `password-reset` ему недоступен).
    - **Ровно три редактируемых поля**: `email`, `display_name`, `password` — частичное обновление (PATCH-семантика, любое подмножество полей в теле запроса). `username` не редактируется никогда (decision 16, идентификатор неизменен после создания); `is_active`/`deleted_at`/`is_primary_admin`/роли не трогаются этим эндпоинтом — у каждого уже есть отдельный путь (`block`/`unblock`, `DELETE /v1/users/:id`, `create-admin`, `POST`/`DELETE /v1/role-assignments`) с собственной, более узкой авторизацией, и decision 25 уже explicitly отклонял смешение разноавторизованных полей в одном универсальном `PATCH` — этот эндпоинт продолжает то же разделение, не вводит для него исключение.
    - **Смена `email` на новое значение сбрасывает подтверждение.** Если новое значение `email` отличается от предыдущего (включая переход от `null` к непустому или наоборот), сервер SHALL установить `email_verified_at = null` и — если новое значение непустое — выпустить новый токен подтверждения той же общей функцией, что уже вызывается при `POST /v1/auth/register`/`POST /v1/users` (decision 40) — новый адрес ещё не доказал, что им владеет тот же человек, что и старым (или что вообще существует), даже если старый уже был подтверждён. Уникальность (`409 email_taken`) проверяется, как и везде.
    - **Смена `password` всегда помечает её временной** — это не решение этого decision самого по себе, а прямое применение decision 42 к ещё одному месту, где пароль пользователю назначает не он сам, а `admin`; подробности (флаг, отзыв refresh-токенов, дальнейшее ограничение доступа) — там.
    - **Аудит**: `user.updated`, `metadata` перечисляет изменённые поля (`{"fields_changed": ["email", "password"]}`) — значение пароля (ни хэш, ни тем более plaintext) в `metadata` не попадает никогда; значения `email`/`display_name` — `{before, after}`, тем же паттерном, что `project.quota_updated` (decision 26).
    Альтернатива — не вводить `PATCH`, оставить редактирование недостижимым (пользователь с опечаткой в email или забытым паролем без email навсегда полагается на удаление+пересоздание — которое либо невозможно из-за занятости `username`/`email` удалённым аккаунтом, decision 27, либо требует физической очистки, которой нет). Отклонена по прямому требованию пользователя — это и был обозначенный пробел.

42. **Пароль, заданный администратором (`POST /v1/users` или `PATCH /v1/users/:id`, decision 41), всегда временный — `User.must_change_password`, без возможности отключить; принудительная смена через новый `POST /v1/auth/change-password`, блокирующий всё остальное до этого момента.**
    По прямому требованию пользователя, обязательное требование.
    - **Третий путь, ставящий флаг** (добавлен decision 49): автоматическое создание первого администратора при старте на пустой базе. Логика та же — пароль пользователю назначил не он сам, значит он временный. `create-admin` при этом флаг по-прежнему НЕ ставит: там пароль набрал сам оператор, симметрично самостоятельной регистрации.
    - **Флаг устанавливается всегда, не по выбору администратора.** Формулировка требования — «всегда флаг включён»: нет параметра запроса, отключающего это поведение. Причина единообразия та же, что уже применена в decision 40 — не вводить признак-исключение ради частного случая, когда правило можно сформулировать без него. Самостоятельная регистрация (`POST /v1/auth/register`) флаг никогда не устанавливает — пользователь выбрал пароль сам, форсировать его смену не для чего.
    - **Установка флага не блокирует сам вход** (в отличие от decision 40's `email_verified_at`) — `grant_type=password` с новым (временным) паролем SHALL выдавать токены штатно, потому что пользователь обязан его знать (администратор сообщил вне этого API), а отказ в выдаче токена вообще не дал бы способа сменить пароль через API. Вместо этого блокируется **всё остальное**.
    - **Блокировка через middleware, не через каждый хендлер по отдельности.** Пока `User.must_change_password = true`, любой JWT-аутентифицированный запрос, кроме закрытого списка (`POST /v1/auth/change-password`, `DELETE /v1/users/me`, `POST /v1/auth/token` с `grant_type=refresh_token`, `DELETE /v1/auth/token`), SHALL отклоняться `403` с кодом `must_change_password`, в общем JSON-конверте ошибок (это не эндпоинт токена — RFC-конверт decision 10 сюда не относится). Реализационно — один дешёвый point-lookup рядом с уже существующим point-lookup'ом `token_version` (decision 10) в middleware после `IdentityProvider.verifyAccessToken`, до авторизации по ролям — не часть самого интерфейса `IdentityProvider` (та же граница, что уже проведена для `token_version`-проверки, decision 17), и не требует отдельного сетевого/БД-похода, если реализация объединит оба point-lookup'а в один запрос (деталь реализации, не фиксируется здесь).
    - **Список исключений — минимальный, не «всё безопасное».** `change-password` — очевидно (без него флаг снять невозможно). `DELETE /v1/users/me` — пользователь с временным паролем, который решил, что не хочет продолжать (а не менять пароль), не должен быть заперт без возможности уйти — тем более что этот эндпоинт и так требует пароль, то есть уже доказывает, что временный пароль ему известен. `POST /v1/auth/token` (`refresh_token`) и `DELETE /v1/auth/token` — поддержание/явное завершение сессии не должно требовать сначала сменить пароль. Всё остальное — управление ресурсами, чтение логов, что угодно ещё — блокируется без исключений.
    - **`POST /v1/auth/change-password`** (JSON `{"current_password": "...", "new_password": "..."}"`, доступен любой аутентифицированной роли только над собой — не form-encoded, вне контракта `/v1/auth/token`) — проверяет `current_password` (401 `invalid_grant` при неверном, тот же код, что уже используется у `DELETE /v1/users/me` для той же ситуации), при успехе обновляет `password_hash`, инкрементирует `token_version` (уже существующее правило — «смена пароля» в списке инвалидирующих событий, decision 10) и устанавливает `User.must_change_password = false`. Это заодно закрывает отдельно обнаруженный пробел — раньше в системе не было ни одного способа сменить свой пароль, находясь уже залогиненным (единственный путь смены пароля был `password-reset/confirm`, не требующий аутентификации, но требующий `email`) — теперь `change-password` доступен всегда, не только пока `must_change_password = true`.
    - **Инкремент `token_version` при установке флага, плюс явный отзыв refresh-токенов.** `PATCH /v1/users/:id` (decision 41) и `POST /v1/users`, задавая пароль, SHALL отзывать все текущие refresh-токены цели — тем же вызовом, что уже используется для блокировки (decision 25) — а не полагаться на один только `token_version`. Без явного отзыва предъявление ещё не истёкшего refresh-токена всё равно выдало бы новый access-токен (тот же самый механизм, которым обычно продлевается сессия) — пользователь с активной сессией продолжил бы работать под старым паролем, даже не зная, что он сброшен, а требование принудительной смены не сработало бы, пока он сам не выйдет и не войдёт заново. Явный отзыв гарантирует, что следующий запрос идёт через `grant_type=password` с новым паролем.
    - **Ревалидация SSE не требует отдельного изменения.** Если у пользователя открыт `GET /v1/logs/stream` в момент, когда администратор через `PATCH /v1/users/:id` сбрасывает его пароль, heartbeat живого потока (decision 29) уже периодически перепроверяет `token_version` — инкремент, который это decision и так вызывает, закрывает соединение терминальным событием тем же уже существующим механизмом, без нового кода специально под этот случай.
    - **Пересечение с decision 40.** Учётная запись может одновременно иметь неподтверждённый `email` и временный пароль (например, `admin` создал пользователя сразу с обоими) — decision 40 блокирует сам `grant_type=password` (токен не выдаётся вовсе), значит до подтверждения email пользователь не доходит даже до состояния «залогинен, но должен сменить пароль»; после подтверждения email — обычный вход выдаёт токены, и уже decision 42 блокирует всё, кроме смены пароля. Порядок естественный, конфликта между двумя правилами нет.
    Альтернатива — необязательный флаг, который администратор явно включает при желании («отметить пароль как временный» отдельным чекбоксом/параметром). Отклонена по прямому требованию пользователя — сформулировано как «всегда», не «по умолчанию» или «опционально».

43. **Ограничение частоты auth-эндпоинтов — только throttling (token bucket в памяти), без блокировки учётной записи; два независимых ключа на запрос (клиентский IP и субъект попытки), `429` + `Retry-After`.**
    По прямому выбору пользователя из предложенных вариантов: рассматривались временная блокировка аккаунта (счётчик неудач и `locked_until` на `User`, переживающие рестарт, плюс административный `unlock`) и её вариант с экспоненциальным ростом длительности — оба отклонены в пользу чистого throttling'а. Обоснование выбора: блокировка вводит новое состояние в БД, новый эндпоинт (`POST /v1/users/:id/unlock`) и, главное, новый вектор отказа в обслуживании — зная чужой `username` (а он в этой системе не секрет: `POST /v1/auth/register` отвечает `409 username_taken`, decision 16, то есть перечисление имён и так возможно), любой желающий может целенаправленно запереть чужую учётную запись, и жертве понадобится администратор. Throttling такой возможности не даёт: он замедляет злоумышленника ровно настолько же, насколько и легитимного пользователя с того же ключа, и сам собой рассасывается со временем без чьего-либо вмешательства.
    - **Состояние — только в памяти, ничего в БД.** Один `Map<key, _Bucket>` в рамках единственного isolate (decision 4 — сервер и так однопоточный, разделяемое хранилище счётчиков не нужно и явный Non-Goal). Рестарт обнуляет все счётчики — принято сознательно (см. Risks): таблицы, миграции и I/O ради счётчика, живущего минуты, не окупаются, а рестарт сервера не является частью управляемого злоумышленником сценария.
    - **Алгоритм — token bucket с непрерывным пополнением, не fixed window.** Fixed window (N запросов в календарную минуту) допускает всплеск в 2N на границе окон; token bucket задаёт и устойчивую скорость (`refill`), и допустимый всплеск (`capacity`) двумя независимыми числами. Пополнение вычисляется лениво, при обращении к ключу (`now - lastRefill`), — никакого фонового таймера на каждый ключ.
    - **Два ключа, оба должны пропустить запрос.** (1) **Клиентский IP** — расходует токен на *каждый* запрос к ограничиваемому пути; закрывает распыление попыток по многим `username` с одного хоста. (2) **Субъект попытки** — `username` для `POST /v1/auth/token` (`grant_type=password`) и `POST /v1/auth/register`, отправленный `email` для `password-reset`/`verify-email/resend`, `sub` из access-токена для `POST /v1/auth/change-password` и `DELETE /v1/users/me`; расходует токен только на **неуспешную** попытку, а успешная — полностью восстанавливает ведро этого ключа. Благодаря этому легитимный пользователь, который просто часто логинится (или переустанавливает приложение), ограничителя не видит вовсе, а подбор пароля к конкретному аккаунту упирается в него с первых же неудач. Если сработал любой из двух — ответ `429`, `Retry-After` считается по тому ведру, которое освободится позже.
    - **Ключ субъекта — это отправленная строка, а не найденная запись.** Ведро заводится на `username`/`email` ровно в том виде, в каком он пришёл в запросе (после нормализации регистра), независимо от того, существует ли такой пользователь. Иначе ограничитель сам стал бы оракулом существования: несуществующие адреса не ограничивались бы и отвечали быстрее — ровно та утечка, которую decision 24/40 закрывают одинаковым `202` для любого адреса. Оборотная сторона — злоумышленник может насоздавать произвольное число ключей: поэтому размер карты ограничен сверху конфигурацией, при переполнении вытесняется наименее недавно использованный ключ (LRU), и отдельный периодический проход выбрасывает полные (не ограничивающие ничего) вёдра. Вытеснение ключа равносильно его сбросу — это ослабление, но ограниченное: чтобы вытеснить свой собственный ключ, злоумышленнику нужно сгенерировать больше уникальных ключей, чем вмещает карта, *быстрее*, чем его же IP-ведро (которое вытеснить сложнее — оно постоянно используется и потому всегда «недавнее») позволит ему делать запросы.
    - **Ограничиваемые пути — только те, где цена попытки асимметрична:** `POST /v1/auth/token` (оба `grant_type`), `POST /v1/auth/register`, `POST /v1/auth/password-reset`, `POST /v1/auth/password-reset/confirm`, `POST /v1/auth/verify-email`, `POST /v1/auth/verify-email/resend`, `POST /v1/auth/change-password`, `DELETE /v1/users/me`. Первые шесть — неаутентифицированные (подбор пароля, подбор одноразового токена, рассылка писем за чужой счёт); последние два аутентифицированы, но принимают `current_password`/`password` и потому остаются поверхностью для подбора пароля тем, кто уже завладел одним лишь access-токеном. Всё остальное (management API, чтение логов) не ограничивается: там уже есть RBAC, а злоупотребление частотой не даёт злоумышленнику ничего, чего не даёт сам факт наличия прав. `POST /v1/logs` не ограничивается принципиально — его регулируют квоты проекта (`log-server-quotas`), см. Non-Goals.
    - **Ответ — `429` с общим JSON-конвертом ошибок, включая token-эндпоинт, плюс заголовок `Retry-After` (целые секунды).** Это единственное место, где `POST`/`DELETE /v1/auth/token` отвечает не RFC-конвертом (decision 10). Обоснование: RFC 6749 §5.2 описывает ошибки *обработки запроса на выдачу токена* и её закрытый набор кодов; запрос, отклонённый ограничителем частоты, до обработки гранта не доходит вовсе — его отклоняет middleware перед хендлером, ровно так же, как это сделал бы обратный прокси, если бы оператор поставил его перед сервером. Рассматривалась альтернатива — втиснуть ответ в RFC-конверт с `error: "invalid_request"` (единственный отдалённо подходящий код) — отклонена: она соврала бы клиенту о причине («запрос неправильный», хотя он совершенно правильный) ради формальной однородности, а `Retry-After` всё равно передаётся заголовком, не телом. Клиент отличает этот случай от всех прочих по HTTP-статусу, а не по форме тела.
    - **Клиентский IP берётся из сокета, а `X-Forwarded-For` учитывается только по явной конфигурации** (`trustedProxyHops`, по умолчанию `0` — заголовок игнорируется полностью; при `N > 0` берётся `N`-й с конца элемент списка). Без этого различения ограничитель либо бесполезен (сервер за прокси видит один и тот же адрес прокси у всех), либо обходится тривиально (сервер без прокси доверяет подделанному клиентом заголовку). Значение по умолчанию выбрано безопасным: не доверять заголовку вовсе.
    - **Целиком отключается конфигурацией** (`rateLimitEnabled`, по умолчанию включён) — для разработки, для тестов, которым иначе пришлось бы считать попытки, и для развёртываний, где ограничение уже делает внешний шлюз и второй слой только мешает.
    - **`structured_log_http` не затрагивается** — клиентский sender ходит только в `POST /v1/logs`, который не ограничивается; ни retry/backoff (задача 9.3), ни его контракт менять не нужно.
    Альтернатива — вообще ничего не делать на сервере, оставив rate-limiting оператору (nginx/Cloudflare перед сервисом). Отклонена по прямому требованию пользователя: сервис позиционируется как self-hosted «поставил и работает», и его безопасность не должна зависеть от инфраструктурной обвязки, которую конкретный оператор может и не поставить.

44. **Аутентификационные события в аудите: `auth.login_succeeded`, `auth.login_failed`, `auth.logged_out`, `auth.throttled` — в уже существующую таблицу `audit_log_entries`, без `grant_type=refresh_token`.**
    По прямому выбору пользователя (вариант «вход/неудача/логаут/срабатывание ограничителя, без refresh»), пересматривает более раннюю ревизию Non-Goals этой же change.
    - **Четыре новых значения в уже закрытом наборе `action` (decision 26), не новая таблица и не новый эндпоинт.** Вопрос, на который отвечает аудит («кто и что сделал в системе»), не меняется от того, что часть событий — аутентификационные; заводить параллельную `auth_events` с собственной пагинацией, фильтрами и правами означало бы дублировать `GET /v1/audit-log` целиком ради одного различия в природе события. Существующий фильтр по `action` и так позволяет смотреть только аутентификацию (`action=auth.login_failed`) или только администрирование.
    - **`grant_type=refresh_token` не аудируется** — по прямому выбору пользователя. Обоснование: refresh не является новым решением о доступе (оно принято при `grant_type=password` и уже записано), при этом он самый частотный из всех событий — по одному на сессию каждые ~15 минут, то есть на порядок-два больше записей, чем все остальные вместе. Отзыв refresh-токена (`DELETE /v1/auth/token`) при этом аудируется (`auth.logged_out`) — он редок и является явным действием пользователя.
    - **`auth.login_failed` не хранит ни пароль, ни неизвестный `username`.** `metadata` несёт `reason` (`invalid_password` / `unknown_user` / `email_not_verified` / `blocked` / `deleted`), `client_ip` и `user_agent`. Если `username` не соответствует ни одной записи, `actor_user_id` — `null` (для этого колонка и была оставлена nullable, decision 26), а сама отправленная строка **не сохраняется**: `metadata` несёт только `{"unknown_user": true}`. Причина не в объёме, а в том, что в поле `username` регулярно попадает пароль (человек промахнулся полем или полем сдвинулась вставка из менеджера паролей) — сохранённый «неизвестный username» превратил бы админский аудит в коллекцию чужих паролей в открытом виде. Для существующего пользователя ничего сохранять и не нужно: `actor_user_id` уже указывает на него.
    - **`auth.throttled` пишется один раз на эпизод, а не на каждый отклонённый запрос.** Запись создаётся в момент перехода ведра (decision 43) в состояние «пусто» — последующие `429` по тому же ключу, пока он не восстановится, новых записей не создают. Иначе аудит стал бы усилителем самой атаки: тысяча отклонённых запросов означала бы тысячу записей в БД — то есть отклонённый запрос обходился бы серверу дороже, чем обработанный, ровно наоборот к цели ограничителя. `metadata` несёт, какой ключ сработал (`"key_kind": "ip" | "subject"`), путь и `client_ip`; для subject-ключа неизвестного пользователя действует то же правило, что выше — сама строка не сохраняется.
    - **Аудит-запись не в одной транзакции с «действием»** — в отличие от общего правила decision 26. Для мутирующих management-операций транзакционность нужна, чтобы не осталось записи о том, чего не произошло; у аутентификационных событий «действие» — это либо выдача токена (успех фиксируется после неё), либо *отказ*, у которого нет мутации, с которой можно было бы разделить транзакцию. Правило decision 26 остаётся в силе для всего остального и просто не применимо здесь.
    - **`auth.login_succeeded` — только для `grant_type=password`**, `actor_user_id` и `target_id` — сам вошедший пользователь, `metadata` — `client_ip`/`user_agent`. Это же поле `client_ip` делает возможным ответ на вопрос «с какого адреса вошли под этой учётной записью», который обычно и задают при разборе инцидента, — и одновременно превращает аудит в хранилище персональных данных (см. Risks).
    Альтернатива — писать аутентификационные события в обычный лог сервера (`structured_log`, которым сервер и так логирует сам себя), а не в аудит. Отклонена: серверный лог не гарантирует сохранности (может быть отключён, отфильтрован по уровню, ротирован), не доступен администратору через API и не имеет фильтров/пагинации — а требование было именно «администратор видит, кто и когда входил».

45. **`429` обрабатывается в `structured_log_admin_client` тем же централизованным перехватчиком `dio`, что и `401`, а не каждым экраном по отдельности.**
    Продолжение decision 33/37 (слой данных клиента — `dio` + `retrofit`, ошибки — как `Either`-левая сторона через `fpdart`), не новая архитектура: перехватчик, который уже умеет распознавать `401` и запускать обновление токена, распознаёт и `429`, читает `Retry-After` и отдаёт типизированную ошибку `RateLimited(retryAfter)` наверх. В отличие от `401`, автоматический повтор запроса перехватчиком **не** делается — ждать десятки секунд, не сказав пользователю ни слова, хуже, чем показать ему, сколько ждать; решение о повторе принимает экран (или сам пользователь). Экран логина показывает обратный отсчёт и блокирует кнопку до его конца; экраны восстановления пароля и повторной отправки письма — то же сообщение, не раскрывающее, существует ли адрес (одинаковое и для существующего, и для несуществующего email — иначе клиент свёл бы на нет анти-enumeration decision 24/40 на стороне сервера).

46. **Retention аудита — два независимых срока (административные действия и `auth.*`), оба по умолчанию отключены; удаление выполняет уже существующий periodic purge job, а не новый механизм; ручного удаления записей аудита не существует.**
    По прямому выбору пользователя из предложенных вариантов (раздельные сроки; по умолчанию выключено), закрывает риск, записанный decision 44.
    - **Два срока, потому что это два разных класса данных.** `auditRetentionDays` (административные действия) и `authEventRetentionDays` (`auth.login_succeeded`/`auth.login_failed`/`auth.logged_out`/`auth.throttled`) задаются независимо. Одно общее число не может угодить обоим: административных мутаций мало, они ценны годами и не содержат ничего, кроме идентификаторов ресурсов; аутентификационных событий на порядки больше, порождает их внешний неаутентифицированный трафик, и они несут `client_ip`/`user_agent` — персональные данные, для которых долгое хранение не преимущество, а обязательство (decision 44's Risks). Рассматривался вариант с одним общим сроком — отклонён именно поэтому.
    - **Оба по умолчанию `null` — «хранить вечно», то есть текущее поведение.** Обновление сервера само по себе SHALL не удалять ничего: оператор, который годом раньше развернул сервис, не должен обнаружить, что апгрейд тихо вычистил ему историю. Включение retention — явное, осознанное действие оператора. Плата — по умолчанию таблица по-прежнему растёт неограниченно (см. Risks); это принято как меньшее зло по сравнению с молчаливым удалением чужих данных при апгрейде.
    - **Классификация — по явному списку `action`, не по префиксу `LIKE 'auth.%'`.** Набор `action` закрыт (decision 26), поэтому запрос очистки перечисляет четыре аутентификационных значения через `IN (...)`, а административная очистка — `NOT IN (...)`: это использует уже существующий индекс по `action` (задача 2.2), тогда как `LIKE 'auth.%'` заставил бы сканировать. Цена — добавление нового `auth.*`-действия в будущем требует внести его в этот список; ровно та же ручная дисциплина, что уже зафиксирована как риск для самого закрытого набора, и проверяемая тем же способом (тест, перечисляющий все значения набора и требующий, чтобы каждое было отнесено ровно к одному классу).
    - **Удаление выполняет тот же периодический таймер, что чистит `log_entries` по `retention_days` проекта (decision 14)** — новый фоновый механизм не вводится; добавляется два шага в уже существующий проход. Удаление идёт **порциями** (`DELETE ... LIMIT N` в цикле, пока не кончатся подходящие строки), а не одним запросом на всю таблицу: SQLite в режиме WAL допускает одновременное чтение при записи, но не вторую запись, и единственный `DELETE` на миллионы строк заблокировал бы приём логов на всё время своего выполнения. Индекс по `audit_log_entries.created_at` для этого уже есть (задача 2.2) — новых индексов не требуется.
    - **Каждый проход, что-то удаливший, оставляет запись `audit.purged`** (`actor_user_id: null` — действие сервера, а не человека; `metadata` — `{"scope": "auth" | "admin", "deleted_count": N, "older_than": "<ISO 8601>"}`). Без неё администратор, обнаруживший, что истории за прошлый год нет, не может отличить «сервер удалил по политике» от «кто-то вычистил следы» — а это ровно тот вопрос, ради которого аудит и существует. Записей не больше одной на класс за проход, то есть их объём ограничен интервалом таймера, а не трафиком. Само `audit.purged` относится к административному классу (его срок — `auditRetentionDays`), иначе объяснение исчезновения `auth.*`-записей исчезало бы вместе с ними.
    - **Ручного удаления записей аудита нет ни в каком виде** — ни `DELETE /v1/audit-log`, ни удаления отдельной записи, ни «очистить» в UI, ни роли, которой это доступно. Единственный путь исчезновения записи — настроенная оператором политика, применяемая единообразно ко всем записям своего класса. Это осознанное свойство: администратор — субъект аудита, а не его владелец, и возможность выборочно удалить собственный след обесценила бы журнал целиком. Оператор, у которого есть доступ к файлу БД, разумеется, может сделать что угодно — но это уже уровень доступа, на котором его останавливает не API.
    - **Действующая политика видна в ответе `GET /v1/audit-log`** (поля `audit_retention_days`/`auth_event_retention_days` рядом с `items`/`next_cursor`), а не отдельным эндпоинтом конфигурации. Администратор, ищущий событие двухлетней давности и не находящий его, должен видеть причину там же, где ищет. Утечки конфигурации это не создаёт: сам `GET /v1/audit-log` доступен только `admin` (decision 26).
    - **Срок хранения не настраивается через API** — только конфигурацией сервера при старте. Политика удаления журнала действий администраторов не должна меняться теми, чьи действия он фиксирует; это то же рассуждение, что и про отсутствие ручного удаления, применённое к параметру вместо записи.
    Альтернатива — дополнительно ограничивать аудит по числу строк (`maxAuditEntries` с вытеснением самых старых), как `max_entries` у проекта (decision 13). Отклонена: это второй, независимый путь потери записей, срабатывающий в момент, который администратор не выбирал и не может предсказать («почему пропала запись недельной давности, если срок — год?»), тогда как темп порождения `auth.*` и так ограничен сверху decision 43.

47. **Конфигурация при старте: CLI-аргументы поверх переменных окружения поверх дефолтов; имена соответствуют друг другу механически; секреты — только через окружение или `*_FILE`; всё проверяется до открытия порта.**
    По прямому требованию пользователя (сервер должен учитывать CLI-аргументы и env при запуске) и по его же выбору из предложенных вариантов — префикс `STRUCTURED_LOG_` и запрет секретов в аргументах. До этого decision конфигурация существовала только как перечисление полей `ServerConfig` в задаче 8.1 с припиской «из аргументов/переменных окружения» — без правил приоритета, проверки и именования.
    - **Три источника, один порядок: CLI → env → значение по умолчанию.** Аргумент командной строки всегда выигрывает у переменной окружения, переменная — у дефолта. Обратный порядок (env поверх CLI) сделал бы невозможным разовый запуск с другим портом на машине, где окружение уже настроено; отсутствие приоритета вообще (ошибка при конфликте) наказывало бы ровно за тот сценарий, ради которого CLI-аргументы и нужны — «запустить как обычно, но вот это иначе».
    - **Имя параметра выводится механически, а не придумывается для каждого.** `--http-port` ↔ `STRUCTURED_LOG_HTTP_PORT`, `--db-path` ↔ `STRUCTURED_LOG_DB_PATH`, `--audit-retention-days` ↔ `STRUCTURED_LOG_AUDIT_RETENTION_DAYS`: kebab-case во флаге, тот же набор слов в SCREAMING_SNAKE с префиксом в окружении. Благодаря этому справочник настроек — одна таблица, а не две, и оператор, увидевший флаг в документации, знает переменную, не заглядывая никуда. Префикс `STRUCTURED_LOG_` выбран пользователем из вариантов: он длиннее `SLOG_`, но совпадает с именем пакета и не рискует столкнуться с чужой переменной в общем окружении контейнера — важно для сервиса, который по своей природе разворачивают рядом с чем-то ещё.
    - **Секретов в командной строке нет физически.** `STRUCTURED_LOG_JWT_SECRET` и `STRUCTURED_LOG_SMTP_PASSWORD` (и любой будущий секрет) принимаются только из окружения либо из файла по пути из `STRUCTURED_LOG_JWT_SECRET_FILE`/`STRUCTURED_LOG_SMTP_PASSWORD_FILE` — той же конвенцией, что используют Docker и Kubernetes для монтируемых секретов. Соответствующего флага не существует вовсе: флаг, помеченный «не используйте в проде», всё равно используют, а аргументы процесса видны в `ps` любому пользователю машины, оседают в истории shell и в логах супервизора. **Если заданы обе формы одновременно** (и `..._SECRET`, и `..._SECRET_FILE`) — это ошибка конфигурации, а не молчаливый приоритет одной над другой: в реальных развёртываниях такое сочетание почти всегда означает недописанную миграцию с одного способа на другой, и тихий выбор победителя прячет её до первой странности с токенами. Файл читается один раз при старте, с обрезкой завершающего перевода строки (иначе `echo secret > file` даёт секрет, отличающийся от набранного глазами).
    - **JWT-секрет обязателен, дефолта у него нет, и сервер его не генерирует.** Без `STRUCTURED_LOG_JWT_SECRET`(`_FILE`) запуск сервера отклоняется. Рассматривалась генерация случайного секрета при первом старте (удобно для «просто попробовать») — отклонена: такой секрет живёт в памяти процесса, и каждый рестарт молча инвалидирует все выданные токены; оператор видит не понятный отказ на старте, а необъяснимые разлогинивания в продакшене. Явный отказ с подсказкой, как сгенерировать секрет, честнее.
    - **Вся проверка — до того, как открыт порт и создан файл БД.** Конфигурация разбирается, проверяется и только потом передаётся в `startServer(config)`. Ошибки собираются **все сразу** и печатаются списком, а не по одной за запуск: оператор, у которого неверны три значения, узнаёт об этом за один прогон, а не за три. Код выхода — `78` (`EX_CONFIG` из `sysexits.h`), отличный от кода рантайм-сбоя: супервизор (systemd, Docker-restart-policy, Kubernetes) по нему отличает «перезапуск не поможет, конфигурация плохая» от «упало, стоит попробовать ещё раз». Альтернатива — обычный `1` на всё; отклонена как теряющая ровно это различие, при том что стоит она одной константы.
    - **Требования зависят от подкоманды.** `create-admin` (decision 12) резолвит конфигурацию тем же кодом, но обязателен для неё только путь к БД: требовать JWT-секрет и SMTP-настройки от команды, которая всего лишь пишет строку в таблицу, — искусственное препятствие при первичной настройке (администратора обычно заводят до того, как настроена почта).
    - **Неизвестный флаг — ошибка; неизвестная переменная с нашим префиксом — предупреждение.** Опечатка `--htp-port` обязана останавливать запуск (этого и ждут от CLI). А вот `STRUCTURED_LOG_PROT=9000` остановить нельзя — окружение контейнера принадлежит не только нам, и падать из-за чужой переменной недопустимо; но и молчать нельзя, иначе оператор ищет причину «сервер игнорирует порт» часами. Отсюда асимметрия: ошибка для аргументов, предупреждение в лог для переменных с префиксом `STRUCTURED_LOG_`, которые парсер не знает.
    - **Значения разбираются строго.** Булев параметр в окружении принимает `true/false/1/0/yes/no` без учёта регистра, всё остальное — ошибка (а не «непонятное считаем `false`», из-за чего `STRUCTURED_LOG_RATE_LIMIT_ENABLED=off` тихо выключил бы защиту вопреки ожиданию, что она включена). В CLI булевы — обычные negatable-флаги `package:args` (`--registration-enabled` / `--no-registration-enabled`). Пустая строка в переменной означает «не задано» и равносильна её отсутствию — в `docker-compose` пустое значение получается слишком легко, чтобы трактовать его как осмысленное. Длительности и размеры выражаются целыми числами с единицей **в имени** (`--access-token-ttl-seconds`, `--audit-retention-days`, `--max-batch-bytes`), а не строками вида `30m`/`10MB`: разбор таких строк — ещё один маленький язык с собственными неоднозначностями (`m` — минуты или месяцы?), тогда как единица в имени читается в документации и в `--help` одинаково.
    - **`--print-config` печатает эффективную конфигурацию с источником каждого значения** (`cli` / `env` / `default`) и выходит с кодом 0, не запуская сервер. Секреты при этом **никогда** не печатаются — вместо значения выводится `***` и источник, чтобы можно было убедиться, что секрет вообще подхвачен и именно оттуда, откуда ожидалось. Это прямой ответ на самый частый вопрос эксплуатации — «почему сервер работает не с теми настройками, которые я задал».
    - **`--help` генерируется из того же описания параметров, что и парсер** — не пишется отдельным текстом, который расходится с реальностью на второй итерации. Тест проверяет, что у каждого параметра есть описание и что каждый параметр `ServerConfig` действительно резолвится (новое поле, забытое в парсере, роняет тест, а не тихо остаётся дефолтным).
    - **`ServerConfig` — иммутабельный value-объект, а не глобальный синглтон.** Он создаётся один раз в `bin/server.dart` и передаётся дальше явно; тесты конструируют его напрямую, не трогая окружение процесса. Это сознательный контраст с `StructlogConfiguration` в `structured_log` (глобальное изменяемое состояние, из-за которого тесты обязаны вызывать `reset()` в `tearDown`) — повторять это решение в сервере незачем.
    Альтернатива — поддержать ещё и конфигурационный файл (YAML/TOML). Отклонена: третий источник требует правил слияния с двумя существующими, формата, схемы и валидации пути к нему, а для self-hosted сервиса, который запускают из `docker run`/`systemd`/compose, env-переменных и флагов достаточно; файл всегда можно добавить позже как ещё один слой между env и дефолтами, не ломая уже описанный порядок.

48. **`structured_log_server` и `structured_log_admin_client` логируют собственную работу через `structured_log` — тот же пакет, который воркспейс публикует; `print()`/`debugPrint` в них не используются.**
    По прямому требованию пользователя. Для сервера это формализует уже имевшуюся зависимость (задача 1.4 включала `structured_log` в его `pubspec.yaml`, но нигде не было сказано, как именно он применяется); для клиента это **пересмотр decision 19**, который прямо запрещал `structured_log_admin_client` зависеть от `structured_log`.
    - **Что именно пересматривается в decision 19, а что — нет.** Запрет там существовал ради одной цели: между сервером и клиентом не должно быть общего Dart-кода, несущего контракт API, чтобы контракт оставался HTTP/JSON, а не разделяемым пакетом типов. Эта часть **остаётся в силе**: общего пакета DTO по-прежнему нет, клиент по-прежнему не зависит ни от `structured_log_server`, ни от `structured_log_http`. Меняется только то, что `structured_log` перестаёт считаться «кодом бэкенда»: это библиотека логирования общего назначения, одинаково уместная в любом Dart/Flutter-приложении, и её присутствие в клиенте ничего не говорит о контракте. Отдельно не пересматривается и запрет на `structured_log_flutter`/`material`/`fluent` в клиенте (Non-Goals): просмотрщик чужих логов клиенту по-прежнему не нужен — у него собственный удалённый источник данных.
    - **Две вещи, которые нельзя смешивать.** У сервера теперь три разных журнала, и граница между ними — это правило, а не вкус: `log_entries` — бизнес-данные проектов-тенантов, пришедшие по `POST /v1/logs`; `audit_log_entries` — административные и аутентификационные факты, источник правды для разбора инцидента (decisions 26/44); **собственный лог сервера** — диагностика процесса (старт, конфигурация, ошибки запросов, работа purge job). Диагностика SHALL не писаться в `log_entries` (она не принадлежит ни одному проекту и исказила бы чужие квоты) и SHALL не подменять аудит (лог можно отключить уровнем, а аудит — нет).
    - **Структурные поля вместо интерполяции.** Сервер логирует `logger.bind(request_id: ..., method: ..., path: ...).info('request.completed', context: {'status': 404, 'duration_ms': 12})`, а не `print('GET $path -> 404 in 12ms')`. Это ровно то, ради чего `structured_log` написан, и делает собственный лог сервера пригодным для той же машинной обработки, что он предлагает своим пользователям. Поля корреляции берутся из уже существующего `LogCorrelation` (`request_id`/`session_id`), а не изобретаются заново.
    - **Выводы разные у сервера и клиента.** Сервер: консоль в разработке, `AsyncRotatingFileOutput` при заданном файле — именно асинхронный, потому что синхронная запись в файл на каждый запрос блокировала бы единственный isolate, обслуживающий все соединения (decision 4). Клиент: консоль в debug-сборке, в release — по умолчанию только `warning` и выше, чтобы на устройстве пользователя не оседала лишняя диагностика.
    - **Секреты и персональные данные не попадают в собственный лог.** Пароли (ни в каком виде), токены, секретные ключи проектов, содержимое писем — никогда; `client_ip`/`user_agent` допустимы только там, где они уже допущены аудитом (decision 44). То же правило, что для аудита, распространённое на диагностику, — с той разницей, что лог легче случайно наполнить: логирование целого объекта запроса или ответа `/v1/auth/token` — типичная ошибка, которую этот пункт закрывает явно.
    - **Единственное исключение** (введено decision 49): пароль, **сгенерированный** сервером при автосоздании первого администратора, печатается в лог ровно один раз — в момент создания, уровнем `warning`, с явной пометкой, что он временный и подлежит смене при первом входе. Границы исключения узкие: пароль, **заданный** оператором через окружение, не печатается никогда (он и так известен тому, кто его задал); печать происходит только при фактическом создании записи, а не при каждом старте; в `--print-config` этот параметр маскируется как любой другой секрет. Обоснование: другого канала доставки сгенерированного пароля не существует — без него автосоздание бессмысленно, потому что войти было бы нечем.
    - **`print()`/`debugPrint`/`dart:developer.log` запрещены** в обоих пакетах и проверяются тестом-стражем, а не договорённостью: иначе диагностика расползается по двум механизмам, из которых один не настраивается, не фильтруется по уровню и не пишется в файл.
    - **Уровень и назначение — через конфигурацию (decision 47)**: `--log-level`, `--log-file`, `--log-format` (`console`/`json`) и параметры ротации резолвятся тем же механизмом, что остальные настройки, и попадают в `--print-config`. У клиента рантайм-конфигурации логирования нет — уровень определяется режимом сборки.
    - **Зачем вообще.** Помимо прямого требования: сервер и клиент становятся первыми нетривиальными потребителями собственной библиотеки воркспейса. Неудобство `BoundLogger` или дыра в `AsyncRotatingFileOutput` обнаружатся на своём же коде раньше, чем на чужом — это и есть та проверка, которую невозможно получить, публикуя библиотеку и не используя её.
    Альтернатива — `package:logging` (стандартная библиотека логирования Dart) в обоих пакетах. Отклонена: воркспейс существует ради `structured_log`, и выбор чужой библиотеки для собственных сервисов означал бы либо что своя не готова к реальному применению, либо что автор ей не пользуется — оба вывода нежелательны и оба проверяемы только применением.

49. **Первый администратор создаётся автоматически при старте, если таблица `users` пуста: логин и пароль из окружения, иначе логин `admin` и случайно сгенерированный пароль, всегда временный — пересматривает decision 12.**
    По прямому требованию пользователя и по его же выбору из предложенных вариантов (условие «таблица пуста», сгенерированный пароль вместо фиксированного, выключатель по умолчанию включён).
    - **Условие — пустая таблица `users` целиком, а не «нет активного `admin`».** Второе условие (то, которым пользуется `create-admin`, decision 12/27) означало бы, что в работающей системе, где администраторов удалили или заблокировали, очередной рестарт молча создаёт учётную запись с предсказуемым именем `admin` — рядом с живыми пользователями, чужими проектами и логами. Пустая таблица бывает ровно один раз за жизнь базы, и это единственный момент, когда автосоздание никому не может помешать. Восстановление доступа на непустой базе остаётся за `create-admin` — осознанным действием оператора, а не побочным эффектом перезапуска.
    - **Чем закрыт исходный мотив decision 12** («риск случайно оставить сервер с дефолтными кредами»): (1) предсказуемого пароля не существует ни в одном режиме — либо оператор задал свой через окружение, либо сервер сгенерировал случайный; (2) любой созданный так пароль временный (decision 42), то есть до его смены учётная запись не может ничего, кроме как сменить пароль, разлогиниться и удалиться; (3) автосоздание целиком выключается одним параметром. Отклонённая в decision 12 альтернатива возвращается, но уже без того свойства, за которое была отклонена.
    - **Параметры** (по правилам decision 47): `--bootstrap-admin-enabled` / `STRUCTURED_LOG_BOOTSTRAP_ADMIN_ENABLED` (по умолчанию `true`); `--bootstrap-admin-username` / `STRUCTURED_LOG_BOOTSTRAP_ADMIN_USERNAME` (по умолчанию `admin`); пароль — `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD` или `..._FILE`, **без CLI-флага**, поскольку это секрет.
    - **Сгенерированный пароль печатается ровно один раз** — см. оговорку в decision 48 и Risks ниже. Заданный через окружение не печатается никогда.
    - **Созданная запись: `is_primary_admin = true` и `must_change_password = true`.** Первый — потому что это буквально первый администратор за историю системы, то есть ровно тот случай, ради которого decision 28 вводил флаг; формулировка «устанавливается самим `create-admin`» там и в спеках заменена на «первым bootstrap, каким бы путём он ни произошёл», гарантия уникальности флага не меняется (она держится частичным уникальным индексом, а не тем, какой код его поставил). Второй — прямое применение decision 42: пароль назначен не самим пользователем.
    - **`create-admin` флаг `must_change_password` по-прежнему не ставит.** Асимметрия намеренная и стоит того, чтобы быть названной: при автосоздании пароль придумал сервер, при `create-admin` — оператор набрал его сам, то есть ситуация симметрична самостоятельной регистрации (decision 42 уже освобождает её от флага).
    - **Email не собирается.** Автоматически созданная учётная запись создаётся без `email` и потому освобождена от обязательного подтверждения (decision 40 — освобождены все записи без адреса). Иначе первый старт был бы тупиком: подтверждать некому, SMTP на этом этапе может быть вообще не настроен, а вход без подтверждения запрещён.
    - **Момент выполнения и транзакция.** Проверка «таблица пуста» и вставка происходят в одной транзакции — тем же приёмом, который Risks уже предписывают `create-admin`, — после применения миграций и **до** открытия порта: сервер не должен принять ни одного запроса в состоянии «пользователей нет». При параллельном старте двух процессов на одной базе выиграет один, второй увидит непустую таблицу и ничего не создаст; уникальный частичный индекс на `is_primary_admin` страхует это на уровне схемы. Проигрыш гонки — **штатный исход, а не ошибка**: процесс пишет то же предупреждение о пропуске и продолжает старт. Отличать от него надо ошибку самих bootstrap-параметров (нечитаемый `*_FILE`, пустой логин) — это ошибка конфигурации, то есть код выхода 78 до открытия порта по decision 47.
    - **Параметры заданы, но база не пуста — пропуск с предупреждением, а не молча.** Оператор, выставивший `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD` в расчёте «поменяю администратору пароль», обязан узнать, что переменная не сработала, — иначе он будет искать причину, по которой «пароль не меняется», в совершенно другом месте. Это тот же принцип, по которому decision 47 предупреждает о неизвестных переменных с нашим префиксом.
    - **Пароль существующего администратора не обновляется никогда.** Если таблица не пуста, `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD` не применяется ни к кому — иначе переменная окружения превратилась бы в вечный backdoor «сбросить пароль администратора рестартом», доступный всякому, кто может отредактировать манифест оркестратора. Симметричный случай — база пуста, а автосоздание выключено — тоже сопровождается предупреждением с подсказкой запустить `create-admin`.
    - **Аудит.** Факт автосоздания фиксируется действием `user.created` с `actor_user_id: null` — третий законный случай `null` в этой колонке после `auth.login_failed` под несуществующим именем и `audit.purged` (decision 44/46), и ровно тот случай, ради которого она оставлена nullable: действие совершил сервер, а не человек. `metadata` несёт `{"bootstrap": true, "password_source": "env" | "generated"}`; сам пароль не попадает туда ни в каком виде.
    - **Клиент не меняется.** Требование «после первого входа принудительно затребовать смену» закрыто уже спроектированным механизмом: `403 must_change_password` перехватывается на уровне слоя данных и переводит на блокирующий экран смены пароля (decision 42, `specs/admin-client-auth`). Единственное, что стоит поправить, — формулировку на этом экране («пароль задал администратор»), чтобы она подходила и к паролю, сгенерированному сервером.
    - **Побочно обнаруженное противоречие.** `create-admin --password ...` (decision 12, задача 8.3) кладёт секрет в аргументы процесса — ровно то, что decision 47 запрещает словами «и любой будущий секрет». Эта доработка его не исправляет, чтобы не расширять объём, но и не оставляет молчаливым: см. Open Questions.
    Альтернатива — фиксированный пароль по умолчанию (`admin`/`admin`), как делают многие self-hosted сервисы. Отклонена: это ровно те «дефолтные креды», из-за которых decision 12 отклонял автосоздание целиком, и временность пароля спасает лишь до первого входа — кто угодно, дотянувшийся до порта раньше оператора, входит первым и меняет пароль на свой. Альтернатива — не печатать сгенерированный пароль вовсе, а требовать его задания через окружение. Отклонена: тогда «просто запустить и войти» не работает, то есть требование не выполнено, — а печать в лог, доступный тому же, кто запустил процесс, не расширяет круг посвящённых.

50. **Поэтапная разработка: Этап 0 (реструктуризация монорепо) → Этап 1 (минимальная инфраструктура + единственный root-администратор: проекты, ключи, просмотр логов — по запросу и живым потоком по SSE, через `structured_log_admin_client`, с ограничением частоты auth-эндпоинтов) → последующие этапы, определяемые по мере старта каждого из них.**
    По прямому требованию пользователя. Эта change специфицирована целиком (49 decisions, все capability-спеки), но заявленный объём — это далеко не то, что нужно реализовать одним куском; пользователь явно запросил деление на этапы с конкретным критерием готовности Этапа 1. Полная точная граница — в новом разделе «Delivery Phases» ниже (по задачам `tasks.md`); здесь — сам принцип и его обоснование.
    **Пересмотрено** сразу вслед за первой формулировкой, тем же прямым требованием пользователя: `structured_log_admin_client` (вместе с обязательным для него `structured_log_admin_ui`, decision 39) и ограничение частоты (decision 43) перенесены из «последующих этапов» в Этап 1. Обоснование каждого — в соответствующем пункте ниже; принцип границы (буквальная формулировка «единственный root-администратор... проекты, ключи, логи») не меняется — расширяется набор *путей*, которыми эта формулировка выполняется (GUI в дополнение к HTTP API напрямую), а не сам функциональный охват (по-прежнему один пользователь, без делегирования, без email-флоу, без аудита).
    **Пересмотрено ещё раз**, тем же прямым требованием пользователя: живой поток логов (SSE, decisions 29–31, разделы 21/22 `tasks.md`) тоже перенесён в Этап 1. Первая формулировка откладывала его именно потому, что без GUI-клиента он не имел потребителя — предыдущая правка это условие сняла, добавив `structured_log_admin_client`, и раздел 22 (лента-как-история-чата) как раз то место, где живой поток используется. Обоснование — в соответствующих пунктах ниже.
    - **Критерий Этапа 1 — буквально формулировка пользователя, не переинтерпретация.** «Единственный пользователь (root-администратор) может создавать проекты, выпускать ключи, наблюдать за логами» — это одна учётная запись, без делегирования прав кому-либо ещё. Отсюда прямо следует, чего Этап 1 **не** требует: самостоятельной регистрации (нет второго пользователя, который бы регистрировался), выдачи ролей другим людям/командам (нет других людей), блокировки/удаления учётных записей (некого блокировать, кроме себя, а удаление себя не входит в описанный сценарий), UI-приложения (`curl`/`HttpLogOutput` достаточно, чтобы «создавать»/«выпускать»/«наблюдать», раз в формулировке не названо конкретно графическое приложение).
    - **«Наблюдать за логами» закрывается и `GET /v1/logs`, и живым потоком (`GET /v1/logs/stream`, decisions 29–31) — по прямому требованию пользователя.** Пересмотрено дважды: первая формулировка этого decision оставляла SSE вне Этапа 1, рассуждая, что без графического клиента живой поток не имеет потребителя, который показал бы его пользователю иначе, чем `curl -N`; это рассуждение снято следующей же правкой, добавившей `structured_log_admin_client` в Этап 1 (см. следующий пункт) — раз GUI уже в Этапе 1, а именно в нём decision 30 специфицирует ленту-как-историю-чата поверх SSE, потребитель есть, и откладывать сам поток больше не для чего. Инфраструктура (broadcast, heartbeat-ревалидация, catch-up по `since_id`) не тривиальна, но уже полностью специфицирована (decision 29) и не имеет зависимости на отложенные фичи (регистрацию, аудит, email) — попадает в Этап 1 без дополнительного объёма сверх того, что и так специфицировано.
    - **`structured_log_admin_client`/`structured_log_admin_ui` (decisions 18–21, 32, 35–39) — в Этапе 1, но не целиком: только функциональный срез, покрывающий критерий Этапа 1.** По прямому требованию пользователя. `structured_log_admin_ui` входит автоматически, не как отдельный запрос — он твёрдая архитектурная зависимость `admin_client` (decision 39: Clean Architecture presentation layer композируется из его Atomic Design компонентов), собирать `admin_client` без него нельзя. Нужны экраны: вход (включая обязательный экран смены временного пароля, decision 42/49 — иначе `admin_client` не сможет провести root-администратора дальше первого входа), управление проектами и секретными ключами (`project_secret_keys`), просмотрщик логов, включая живую ленту по SSE в стиле истории чата (decision 30 — пересмотрено вместе с предыдущим пунктом: живой поток больше не откладывается, и именно этот экран — его единственный предусмотренный потребитель). Не нужны (переносятся на последующие этапы вместе с эндпоинтами, которые они обслуживают): самостоятельная регистрация, управление пользователями/командами/ролями (некого администрировать, кроме себя), экран просмотра аудита, экран ограничения частоты/блокировок (в Этапе 1 нет UI для управления самим ограничением — только защищённость, которую оно даёт, см. следующий пункт). Альтернатива — оставить GUI целиком в последующем этапе, как было решено первой формулировкой этого decision, и ограничиться `curl`/`HttpLogOutput`: отклонена по прямому уточнению пользователя, добавившего GUI в критерий Этапа 1.
    - **`log-server-auth`'s bootstrap (decision 49) и `log-server-forced-password-change` (decision 42) — в Этапе 1, но не целиком.** Decision 49 связала оба вместе: автосозданный пароль root-администратора всегда временный, а значит без enforcement-механизма decision 42 («вход разрешён, всё остальное — 403, пока не сменишь») зайти дальше входа с временным паролем было бы нечем. Это единственное место, где Этап 1 обязан взять **часть** более позднего capability, а не capability целиком — конкретно: middleware-проверку `must_change_password` и `POST /v1/auth/change-password` (задачи 26.4/26.5), но не `PATCH /v1/users/:id` (26.2) и не установку флага в `POST /v1/users` (26.3) — обоих этих эндпоинтов в Этапе 1 просто нет, редактировать в нём некого, кроме себя, а менять свой пароль уже умеет 26.5.
    - **Полная схема хранения — с первого этапа, не поэтапно расширяемая.** Все таблицы (`users`/`groups`/`teams`/`team_members`/`projects`/`project_secret_keys`/`role_assignments`/`refresh_tokens`/`password_reset_tokens`/`email_verification_tokens`/`audit_log_entries`/`project_usage`/`log_entries`, раздел 2 `tasks.md`) определяются сразу целиком, даже те, что Этап 1 не использует. Рассмотрена альтернатива — минимальная схема на Этап 1, остальные таблицы добавлять миграциями по мере того, как этапы, которым они нужны, начинаются. Отклонена: `drift`-миграции дёшевы написать один раз сейчас (схема уже полностью специфицирована в `specs/log-server-storage`) и рискованны добавлять неровно, порциями, без риска забыть индекс/constraint, специфицированный для более позднего этапа, но логически принадлежащий той же таблице.
    - **Ограничение частоты (decision 43) — в Этапе 1 целиком.** По прямому требованию пользователя. Это закрывает ровно тот риск, который первая формулировка этого decision принимала явно: `POST /v1/auth/token`/`POST /v1/auth/change-password` (нужные Этапу 1 для входа root-администратора и обязательной смены его временного пароля) — ровно те пути, которые decision 43 защищает от перебора. Механизм decision 43 самодостаточен (in-memory token bucket, без БД) и не имеет обязательной зависимости от аудита — попадает в Этап 1 без вытягивания за собой раздела 29 (auth-аудит `auth.throttled` и т.п., decision 44), который остаётся исключён, см. ниже. Раздел 30 (админский UI для просмотра/настройки ограничения частоты) в Этап 1 входит частично — см. Delivery Phases: сама защита работает без экрана управления ей, а сконфигурировать пороги можно через `ServerConfig`/CLI (decision 47), уже включённый в Этап 1 целиком.
    - **Аудит (decisions 26/44/46) — сознательно исключён из Этапа 1, с явным риском.** Hardening для многопользовательской, сетевой открытой системы, не входит в буквальную формулировку критерия Этапа 1 и не требуется ограничению частоты (см. выше — decision 43 самодостаточен без него). Единственное следствие: неудачные попытки входа/смены пароля в Этапе 1 нигде не протоколируются, только ограничиваются по скорости. Это принятый, а не проигнорированный риск (см. Risks ниже).
    - **`log-server-config` (decision 47) и собственное логирование (decision 48) — в Этапе 1 целиком, не частично.** Формулировка пользователя явно называет «инфраструктуру» в объёме Этапа 1, а не только функциональность конечного пользователя; оба decision — ровно инфраструктура (как сервер конфигурируется и как он сам себя диагностирует), не зависят ни от одной отложенной фичи, и полдороги их делать (например, только CLI-приоритет без `--print-config`, или логирование без ротации) означало бы позже возвращаться и доделывать то, что можно сразу специфицировать полностью — decision 47 уже это делает.
    Альтернатива — не делить на этапы вовсе, реализовать всю change одним PR/веткой перед первым мержем. Отклонена по прямому требованию пользователя — постановка задачи именно про поэтапность. Альтернатива — определить все этапы (2, 3, 4...) сейчас же, целиком. Отклонена: заранее раскладывать 49 decisions по гипотетическим этапам 2+ без обратной связи от реализации Этапа 1 — то же самое избыточное планирование, которого эта change уже избегает в других местах (см., например, decision 32's отказ фиксировать файловую раскладку заранее); следующий этап специфицируется, когда до него доходит очередь.

## Risks / Trade-offs

- [Риск] `drift` использует `package:sqlite3` под капотом (нативная библиотека через `dlopen`); поведение на Windows-раннерах исторически менее предсказуемо → [Митигейшн] новый CI job стартует только с `ubuntu-latest`, Windows добавляется отдельно после проверки на реальном раннере.
- [Риск] `drift`/`drift_dev`/`build_runner` — первый codegen-инструмент в монорепо → [Митигейшн] ограничен пакетом `structured_log_server`; `*.g.dart` не коммитится, CI выполняет `dart run build_runner build --delete-conflicting-outputs` перед `analyze`/`test`.
- [Риск] Один `QueryExecutor` в одном isolate — потолок пропускной способности при большом числе одновременных писателей → [Митигейшн] явный non-goal для MVP; путь апгрейда (`NativeDatabase.createInBackground`, шардирование) как открытый вопрос на будущее.
- [Риск] `LIKE`-поиск по `context_json` деградирует по производительности с ростом таблицы → [Митигейшн] задокументировать как ограничение MVP; путь апгрейда — FTS5, не реализуется сейчас.
- [Риск] Снапшот `roles` в claims access-токена (decision 10) может устареть в промежутке между выдачей токена и отзывом прав, если бы отзыв проверялся только сроком жизни токена → [Митигейшн] `token_version`-lookup на каждом запросе делает эту проблему не актуальной — любое изменение прав немедленно инвалидирует уже выданные токены пользователя, независимо от того, что записано в `roles`.
- [Риск] Токен растёт пропорционально числу эффективных грантов пользователя (`roles` — плоский список) → [Митигейшн] для типичного пользователя/owner список из нескольких групп/проектов не проблема; жёсткого лимита на MVP не вводится, но если у кого-то счёт пойдёт на сотни грантов — пересмотреть (например, не инлайнить весь список, а хранить в токене только хэш/версию набора грантов и резолвить полный список отдельным легковесным эндпоинтом) — не реализуется в этой change.
- [Риск] Каскадное обновление `token_version` всех участников команды при изменении team-scoped `RoleAssignment`/членства (decision 10) — при очень большой команде это bulk-`UPDATE` по потенциально многим строкам → [Митигейшн] это происходит только на редких административных операциях (owner/admin меняет права, не на каждый запрос логов), и это один SQL-запрос с индексированным `JOIN`/`IN`, а не N отдельных обновлений.

- [Риск] `DELETE /v1/auth/token` (decision 10) отзывает только refresh-токен — короткоживущий access-токен, выданный вместе с ним, остаётся технически валиден до истечения своего срока → [Митигейшн] задокументировано как принимаемое ограничение; срок жизни access-токена намеренно короткий (минуты, не часы) именно чтобы это окно было малым.
- [Риск] Открытая по умолчанию самостоятельная регистрация (decision 16) на публично доступном сервере может быть использована для массового создания пустых аккаунтов → [Митигейшн] `registrationEnabled` по умолчанию `false`; зарегистрированный аккаунт не имеет доступа ни к одному ресурсу без явного гранта, так что даже массовая регистрация не даёт доступа к чужим данным — риск ограничен ростом таблицы `users`, не утечкой логов.

- [Риск] `DELETE` с телом запроса (`refresh_token` в form-encoded теле) — не все HTTP-клиенты/прокси одинаково надёжно передают тело у `DELETE`-запросов → [Митигейшн] осознанный выбор вслед за трактовкой «токен — это ресурс, отзыв — его удаление»; альтернатива (токен в query-параметре) отклонена как худшая практика — секрет не должен попадать в URL (логи веб-сервера, история прокси); альтернатива (токен в заголовке `Authorization`) осталась бы несовместимой с тем, что тот же заголовок уже используется для access-токена на остальных эндпоинтах — путаница между «токеном для аутентификации запроса» и «токеном, который отзываем» хуже, чем менее распространённый, но однозначный form-encoded body на DELETE.
- [Риск] `bin/server.dart create-admin` (decision 12), выполненная более одного раза до появления первого admin по ошибке оператора, либо отсутствие защиты от параллельного вызова в двух процессах → [Митигейшн] проверка «существует ли уже admin» выполняется в той же транзакции, что вставка — гонка исключена на уровне БД; повторный вызов после появления первого admin явно завершается ошибкой, а не тихо создаёт второго.

- [Риск] `structured_log_admin_client` не имеет общего Dart-кода с `structured_log_server` (decision 19) — контракт запросов/ответов может незаметно разойтись, если сервер изменится, а клиент не обновится синхронно → [Митигейшн] `integration_test.dart` клиента (или его сетевого слоя) гоняется против реального запущенного сервера в CI, а не только против моков — расхождение ловится тестом, а не в проде; конкретная реализация — задача `tasks.md`.
- [Риск] `flutter_secure_storage` (decision 20) на некоторых платформах (в частности Linux desktop) требует наличия системного keyring/secret-service, который не всегда установлен в headless/CI-окружении → [Митигейшн] задокументировать как известное ограничение; для CI (виджет-тесты) секьюр-сторидж не требуется — она нужна только в реальном рантайме приложения, юнит/виджет-тесты используют мок реализации хранилища токенов, а не реальный `flutter_secure_storage`.
- [Риск] Собственная реализация просмотра логов в admin-клиенте (decision 21) вместо переиспользования `LogViewerController` — дублирование части логики фильтрации/UI-паттернов с уже существующими viewer-пакетами → [Митигейшн] осознанный trade-off ради простоты сейчас (см. decision 21, «не абстрагировать раньше второго потребителя»); объём дублирования небольшой (admin-клиент фильтрует через query-параметры на сервере, а не клиентским кодом, как делает `LogViewerController`), так что дублируется в основном UI-разметка, не бизнес-логика.
- [Риск] Реструктуризация в `emb`/`backend`/`frontend`/`packages` (decision 23) двигает четыре уже опубликованные на pub.dev пакета (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) — ломает локальные клоны/IDE-конфигурацию контрибьюторов и пути в CI/`melos.yaml`/`AGENTS.md`, тот же класс риска, что и при первом переходе на монорепо → [Митигейшн] один атомарный коммит с `git mv` + синхронным обновлением `melos.yaml`/`.github/workflows/ci.yml`/`AGENTS.md`/README в том же PR, явно помечено **BREAKING** в `proposal.md`, по той же схеме, что и первая реструктуризация (`openspec/changes/add-structured-log-flutter`); сами опубликованные на pub.dev артефакты (версия, API) не затрагиваются — ломается только путь в репозитории.
- [Риск] `packages/` вводится пустой, без единого пакета внутри — риск того, что директория останется декларативным намерением без реального использования → [Митигейшн] это осознанно: категория резервируется под будущее, не создаётся искусственный пакет-заглушка ради заполнения; если она долго останется пустой, это сигнал пересмотреть, нужна ли она вообще — не проблема, которую нужно решать сейчас.
- [Риск] `POST /v1/auth/password-reset` (decision 24) без rate-limiting может использоваться для рассылки нежелательных писем на произвольный `email`, вписанный атакующим (получателю ничего не раскрывается, кроме факта письма от этого сервиса) → [Митигейшн] задокументировано как ограничение MVP; ограничение частоты по `email`/IP — будущая работа.

- [Риск] Периодическая ревалидация авторизации SSE-соединения происходит по тику heartbeat (decision 29), не мгновенно при самом событии отзыва — между отзывом прав и следующим heartbeat есть окно, в течение которого уже отправленные (но ещё не доставленные до следующей проверки) события потока продолжают идти отозванному клиенту → [Митигейшн] окно ограничено интервалом heartbeat (секунды-десятки секунд, см. Open Questions), тот же порядок величины, что уже принятое окно для короткоживущего access-токена (decision 10) — не новая категория риска, продолжение уже принятого компромисса.
- [Риск] Point-lookup статуса блокировки проекта на каждое транслируемое SSE-событие (decision 29) — при очень высокой частоте приёма логов в масштабе группы это лишний запрос к БД на каждую запись сверх уже выполненной при её вставке проверки → [Митигейшн] задокументировано как ограничение MVP наравне с остальными «простота сначала» решениями этой change (LIKE-поиск вместо FTS5 и т.п.); путь оптимизации — in-memory кэш статуса блокировки проектов, обновляемый самими `block`/`unblock`-эндпоинтами, не реализуется сейчас.
- [Риск] Буфер накопленных во время паузы SSE-событий на стороне admin-клиента (decision 30) ограничен по размеру — при необычно долгой паузе часть событий будет потеряна из буфера (компенсируется перезагрузкой свежей страницы при возобновлении, а не молчаливым пропуском) → [Митигейшн] осознанный компромисс, тот же принцип, что уже принят для верхнего предела буфера `structured_log_http` (см. выше) — неограниченный буфер в памяти клиента хуже, чем явная перезагрузка при возобновлении после долгой паузы.
- [Риск] `freezed`/`json_serializable` (в обоих новых пакетах) и `retrofit_generator` (только в клиенте) — ранее заявленный принцип «`drift` — единственное codegen-исключение, не прецедент для остального воркспейса» (decision 2) теперь фактически расширен до трёх инструментов в двух новых пакетах → [Митигейшн] явно переформулировано в decision 34: исключение остаётся ограниченным `backend/`/`frontend`-пакетами этой change, три существующих `emb/`-viewer-пакета (`structured_log_flutter`/`material`/`fluent`) и `structured_log_http` этим не затрагиваются и не обязаны его перенимать — граница исключения сдвинута per-package, не снята вовсе.
- [Риск] `fpdart`'s `Either`-стиль обработки ошибок — незнакомая для контрибьютора, привыкшего к идиоматичным Dart-исключениям, параDигма; неверное применение (оборачивание в `Either` того, что должно остаться исключением, или наоборот) легко проскальзывает в code review → [Митигейшн] decision 33 явно фиксирует границу (ожидаемый исход vs. программная ошибка) как часть самого решения, а не оставляет её на усмотрение каждого PR; `openspec-verify-change`/ревью могут сверяться с этим критерием.
- [Риск] `cherrypick` (decision 35) — библиотека того же автора, что и сам этот воркспейс, со сравнительно небольшой историей использования вне его собственных проектов — риск обнаружить в процессе реализации пробел в возможностях (например, недостающий сценарий scope-жизненного цикла), которого более зрелая альтернатива (`get_it`) не имела бы → [Митигейшн] принято осознанно по прямому требованию пользователя; `structured_log_admin_client` — единственный потребитель этого выбора в воркспейсе, откат на другую DI-библиотеку при необходимости не затронул бы остальные пакеты.
- [Риск] `retrofit` не покрывает `GET /v1/logs/stream` (decision 37) — в одном приложении сосуществуют два разных стиля обращения к HTTP (кодогенерируемые типизированные интерфейсы и один вручную написанный потоковый клиент) → [Митигейшн] осознанная, единственная и явно задокументированная граница исключения, а не расползающаяся неконсистентность — SSE объективно не укладывается в модель `retrofit` «один запрос → один десериализованный ответ».
- [Риск] `fluent_ui` для всего `structured_log_admin_client` (decision 38) — не самый распространённый выбор UI-кита для Flutter-приложений (Material — де-факто умолчание большинства туториалов/библиотек сообщества); часть стороннего Flutter-тулинга (виджеты, ожидающие `MaterialApp`-контекст) может не работать без адаптации → [Митигейшн] принято осознанно по прямому требованию пользователя; тот же выбор уже сделан и обкатан в этом воркспейсе для `structured_log_fluent` (embeddable viewer), так что необходимость работать с Fluent-виджетами на Flutter — не новый для контрибьюторов этого репозитория опыт, даже если код между пакетами не переиспользуется.
- [Риск] `structured_log_admin_ui` (decision 39) — ещё один пакет с единственным потребителем (`structured_log_admin_client`) — тот же класс риска «пакет ради одного потребителя», который decisions 18/21 в других местах этой change сознательно избегают → [Митигейшн] мотивация здесь другая, не спекулятивное обобщение: проверяемая границей компилятора изоляция presentation-виджетов от бизнес-логики внутри одного приложения, по прямому требованию пользователя, а не ставка на будущее переиспользование — риск «пакет не окупится» здесь неприменим тем же образом, что и к пакету, заведённому «на всякий случай» под гипотетического второго потребителя.
- [Риск] Граница «atoms/molecules/organisms — без templates/pages» (decision 39) требует дисциплины контрибьютора — ничто автоматически не мешает по ошибке добавить в organism скрытую зависимость от конкретной фичи (например, захардкоженный текст, специфичный только для одного экрана) → [Митигейшн] сама компиляционная изоляция пакета (decision 39: `structured_log_admin_ui` не может импортировать код `structured_log_admin_client`) не устраняет этот конкретный риск, но делает большую часть случайных утечек (импорт `Bloc`/repository) невозможной технически, а не только предотвращает через код-ревью.
- [Риск] Единое правило «`email` задан → обязан быть подтверждён» (decision 40) впервые вводит трение для пути создания пользователя администратором: если админ указал `email` при `POST /v1/users`, этот пользователь не сможет войти, пока не подтвердит адрес — раньше `POST /v1/users` создавал сразу полностью рабочую учётную запись → [Митигейшн] принято осознанно по прямому требованию пользователя как более простая, единообразная альтернатива введению признака «как создан этот пользователь»; администратор может либо предупредить пользователя заранее, либо просто не указывать `email` при создании (он остаётся опциональным), если немедленный доступ важнее.
- [Риск] Расширение RFC 6749-конверта ошибки нестандартным полем `reason` (decision 40) — не предусмотрено самим RFC 6749, хотя и аддитивно (игнорируется конформными клиентами, не ломает совместимость, ради которой decision 10 вообще выбрал RFC-форму) → [Митигейшн] осознанный, точечный выбор ради UX собственного клиента (`structured_log_admin_client` должен отличить «неверный пароль» от «email не подтверждён»); задокументировано явно как non-standard extension, а не как часть самого RFC-контракта.
- [Риск] `POST /v1/auth/verify-email/resend` (decision 40) без rate-limiting — тот же класс риска, что уже принят для `POST /v1/auth/password-reset` (decision 24: рассылка нежелательных писем на произвольный email) → [Митигейшн] то же самое: получателю ничего не раскрывается сверх факта письма от этого сервиса; ограничение частоты — future work, не эта доработка.
- [Риск] Учётные записи с незаданным никогда не подтверждённым email навсегда остаются заблокированными для входа — механизма автоматической очистки/повторного напоминания нет → [Митигейшн] администратор уже может удалить любую учётную запись (`DELETE /v1/users/:id`, decision 27) или создать новую без `email`; отдельный механизм для этого конкретного случая не заводится — тот же принцип «явного действия человека вместо автоматической эвристики», что уже применён к передаче владения группой (decision 27).
- [Риск] `PATCH /v1/users/:id` (decision 41) даёт администратору возможность сменить пароль любого пользователя без подтверждения второй стороной — потенциал для злоупотребления (нежелательный сброс пароля активного пользователя) → [Митигейшн] тот же принцип, что уже принят для блокировки (decision 25, Risks): `admin` — уже безусловно доверенная роль с полным доступом, это действие не даёт ему прав, которых у него не было бы и так; действие попадает в аудит (`user.updated`), а немедленный отзыв refresh-токенов и `must_change_password` (decision 42) делают злоупотребление заметным пострадавшему при следующей попытке входа, а не тихим.
- [Риск] Единое правило «пароль от администратора → всегда временный» (decision 42), без возможности отключить, добавляет обязательный лишний шаг («смените пароль») в сценариях, где администратор и так доверяет себе выбранный пароль и не считает его временным (например, короткоживущий демо-аккаунт) → [Митигейшн] принято осознанно по прямому требованию пользователя — «всегда», без исключений; при необходимости пользователь всё равно может немедленно сменить пароль обратно на то же значение через `POST /v1/auth/change-password`, если это единственная цель.
- [Риск] Список эндпоинтов, доступных при `must_change_password = true` (decision 42), — фиксированный список путей, не декларативный атрибут на каждом хендлере — при добавлении новых auth-смежных эндпоинтов в будущем легко забыть внести их в список исключений (или наоборот — забыть, что новый обычный эндпоинт должен блокироваться) → [Митигейшн] тот же класс риска, что уже принят для закрытого списка аудируемых действий (decision 26, Risks) — `openspec-verify-change` может дополнительно сверять этот список при финализации; конкретный список, зафиксированный этой доработкой, стабилен, пока не появятся новые auth-эндпоинты.
- [Риск] Счётчики ограничителя частоты живут только в памяти (decision 43) → [Митигейшн] рестарт сервера обнуляет их, то есть злоумышленник, способный вызвать рестарт (или дождаться планового), получает свежий бюджет попыток; принято сознательно — тот, кто может перезапускать процесс, уже имеет доступ уровня оператора, а редкий плановый рестарт даёт атакующему один дополнительный всплеск, а не непрерывную свободу; вариант с персистентными счётчиками отклонён вместе с account lockout по выбору пользователя.
- [Риск] Ограничение по IP (decision 43) бьёт по всем за одним NAT/корпоративным прокси разом: один перебирающий пароли сотрудник может исчерпать IP-ведро для всего офиса → [Митигейшн] ведро субъекта расходуется только на неудачных попытках и полностью восстанавливается при успешном входе, поэтому легитимные пользователи из-за того же NAT продолжают входить, пока общий IP-бюджет не исчерпан; ёмкость IP-ведра настраивается, и весь ограничитель отключается (`rateLimitEnabled`), если сервис развёрнут за собственным шлюзом оператора.
- [Риск] Ключи субъекта заводятся по отправленной строке, а не по найденной записи (decision 43) — значит, объём карты ключей контролируется тем, кто шлёт запросы → [Митигейшн] жёсткий верхний предел размера карты с LRU-вытеснением и периодическая очистка полных вёдер; вытеснение равносильно сбросу ключа, но требует от злоумышленника генерировать уникальные ключи быстрее, чем его собственное (постоянно используемое и потому не вытесняемое) IP-ведро позволяет ему слать запросы.
- [Риск] `429` на token-эндпоинте отвечает не RFC-конвертом (decision 43) — единственное отступление от decision 10 → [Митигейшн] отличается по HTTP-статусу, а не по телу: конформный OAuth2-клиент и так обязан отличать `400` с телом ошибки от любого другого статуса, а `Retry-After` — стандартный HTTP-заголовок (RFC 9110), не наше изобретение; в `docs/api/errors.md` это зафиксировано явно, чтобы отступление не выглядело недосмотром.
- [Риск] Аутентификационные события (decision 44) меняют профиль роста `audit_log_entries` на порядки: неудачные входы и `auth.throttled` генерируются внешним, неаутентифицированным трафиком, тогда как прежний закрытый набор состоял только из редких административных действий, — а retention для аудита по-прежнему не спроектирован → [Митигейшн] `auth.throttled` пишется один раз на эпизод, а не на каждый отклонённый запрос, и сам ограничитель (decision 43) ставит потолок частоте, с которой внешний трафик вообще способен порождать `auth.login_failed`; retention остаётся открытым вопросом и, вероятно, первой будущей доработкой аудита.
- [Риск] `metadata` аутентификационных событий хранит `client_ip`/`user_agent` (decision 44) — это персональные данные, которых в системе до сих пор не было, с неограниченным сроком хранения → [Митигейшн] аудит доступен только роли `admin` (decision 26), пароли и неизвестные `username` не сохраняются ни в каком виде, а самостоятельное удаление аккаунта (decision 27) сохраняет аудит-записи намеренно — сам факт «этот аккаунт удалён» и должен остаться; оператору, которому нужен ограниченный срок хранения, понадобится тот же будущий retention-механизм, что и выше.
- [Риск] Throttling, выбранный вместо блокировки аккаунта (decision 43), принципиально не останавливает медленный распределённый перебор: злоумышленник с достаточным числом адресов и терпением укладывается в лимиты → [Митигейшн] осознанный размен, сделанный выбором пользователя (блокировка создавала бы DoS по чужому аккаунту); `auth.login_failed`/`auth.throttled` в аудите (decision 44) дают администратору увидеть такую атаку, даже когда ограничитель её не останавливает, — это и есть основная причина, по которой обе доработки спроектированы вместе, а не по отдельности.
- [Риск] Оба срока хранения по умолчанию отключены (decision 46), то есть из коробки поведение не меняется и `audit_log_entries` по-прежнему растёт неограниченно — в том числе за счёт `auth.*`, порождаемых внешним трафиком → [Митигейшн] осознанный выбор пользователя в пользу того, чтобы апгрейд никогда не удалял данные молча; действующая (в том числе пустая) политика видна администратору прямо в ответе `GET /v1/audit-log`, а не спрятана в конфигурации, — то есть «вечное хранение» остаётся видимым решением, а не незамеченным дефолтом.
- [Риск] Удаление порциями (decision 46) означает, что очистка большого накопленного объёма растянется на несколько проходов таймера, и всё это время таблица остаётся больше заявленного срока хранения → [Митигейшн] то же eventual-enforcement поведение, что уже принято для retention логов (decision 14, Risks выше); размер порции и интервал таймера конфигурируются, если оператору нужно быстрее.
- [Риск] Классификация по явному списку `action` (decision 46) — при добавлении нового `auth.*`-действия в будущем его легко забыть внести, и оно молча попадёт в административный класс с более долгим сроком → [Митигейшн] тест, требующий, чтобы каждое значение закрытого набора было отнесено ровно к одному классу, падает при добавлении неучтённого действия; ошибка в эту сторону к тому же безопасна — запись хранится дольше, а не удаляется раньше.
- [Риск] `audit.purged` фиксирует факт удаления, но не его содержимое — восстановить удалённое по нему нельзя → [Митигейшн] это и не цель: экспорт/архивация — явный Non-Goal (decision 46), а `audit.purged` отвечает на единственный вопрос, на который иначе ответить невозможно, — «это политика или кто-то вычистил следы».
- [Риск] Секрет, переданный через переменную окружения (decision 47), виден в `/proc/<pid>/environ` и в выводе `docker inspect` — то есть запрет CLI-флагов закрывает `ps` и историю shell, но не делает окружение по-настоящему секретным → [Митигейшн] для развёртываний, где это существенно, предусмотрен `*_FILE`-вариант: секрет лежит в файле, смонтированном оркестратором, и в окружении остаётся только путь; документация рекомендует именно его для продакшена.
- [Риск] Обязательный JWT-секрет без дефолта (decision 47) делает первый запуск «из коробки» невозможным без подготовки — порог входа выше, чем у сервиса, который просто стартует → [Митигейшн] сообщение об ошибке содержит готовую команду генерации секрета, а `create-admin` не требует его вовсе, так что первичная настройка не упирается в почту и токены одновременно; молчаливая генерация отклонена сознательно (см. decision 47).
- [Риск] Неизвестная переменная с префиксом `STRUCTURED_LOG_` только предупреждает (decision 47) — предупреждение легко потерять в логе старта, и опечатка останется незамеченной → [Митигейшн] `--print-config` показывает источник каждого значения, то есть даёт прямой способ убедиться, что параметр взят из ожидаемого места; падать из-за чужой переменной в общем окружении контейнера всё равно нельзя.
- [Риск] Собственный лог сервера пишется на тот же диск, что файл SQLite (decision 48) — на высокой нагрузке они конкурируют за I/O → [Митигейшн] файловый вывод асинхронный (`AsyncRotatingFileOutput`, сериализованная очередь), уровень по умолчанию `info`, а не `debug`, и файл вообще не включается, пока оператор не задал `--log-file`.
- [Риск] Наличие сразу двух журналов (аудит и собственный лог) на сервере провоцирует писать в лог то, что должно попасть в аудит, — и наоборот (decision 48) → [Митигейшн] граница сформулирована явно: аудит — факты, за которые кто-то отвечает и которые нельзя отключить; лог — диагностика процесса, которую можно приглушить уровнем; при сомнении событие идёт в аудит.
- [Риск] Зависимость клиента на `structured_log` (decision 48) ослабляет формулировку decision 19 «никакого общего Dart-кода» — граница теперь проходит не по пакетам, а по их смыслу, что труднее проверить автоматически → [Митигейшн] проверяемая часть осталась машинной: тест/`pubspec` фиксируют отсутствие зависимостей на `structured_log_server`/`structured_log_http`, а `structured_log` не содержит ни одного типа контракта API, так что рассинхрон контракта через него невозможен физически.
- [Риск] Сгенерированный пароль первого администратора попадает в журнал процесса (decision 48/49) — в контейнерной установке это `docker logs`, доступный шире, чем хотелось бы → [Митигейшн] пароль временный и до смены бесполезен для чего-либо, кроме собственной смены; оператору, которого это не устраивает, достаточно задать свой пароль через `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD(_FILE)` — тогда в лог не попадает ничего.
- [Риск] Имя первого администратора по умолчанию предсказуемо (`admin`), то есть известно злоумышленнику как цель перебора (decision 49) → [Митигейшн] ограничитель частоты (decision 43) действует на него так же, как на любую учётную запись, пароль случайный и высокоэнтропийный, а имя меняется одним параметром; предсказуемым остаётся только имя, но не креды.
- [Риск] Сгенерированный пароль печатается ровно один раз, и если эта строка потеряна до первого входа (лог не сохранён, вывод не прочитан), войти становится нечем: `create-admin` в этот момент уже не сработает — активный администратор существует → [Митигейшн] честная оговорка, а не мнимая защита: на этом этапе система пуста, и восстановление означает удалить файл базы и стартовать заново; оператору, которого такой сценарий не устраивает, следует задавать пароль через `STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD(_FILE)` — тогда он известен заранее. См. Open Questions про возможную команду перевыпуска.
- [Риск] Автосоздание выполняется при каждом старте на пустой базе — если оператор случайно укажет `--db-path` на несуществующий файл, сервер молча создаст новую базу с новым администратором вместо того, чтобы указать на ошибку (decision 49) → [Митигейшн] факт создания сопровождается заметной записью в логе (уровень `warning`) и аудит-записью `user.created` с `bootstrap: true`, так что «почему я не могу войти прежним паролем» диагностируется первой же строкой журнала старта.
- [Риск] Этап 1 (decision 50) сознательно не включает аудит (decisions 26/44/46) — неудачные попытки входа/смены пароля нигде не протоколируются (ограничение частоты, decision 43, при этом в Этапе 1 уже работает — защита от перебора есть, только без записи попыток) → [Митигейшн] принятый, названный вслух риск, не проглядка: Этап 1 предполагает эксплуатацию доверенным оператором (единственный пользователь — он сам), отсутствие протоколирования не открывает атаку, а лишь не даёт постфактум расследовать подозрительную активность; до тех пор — то же допущение, что и у множества self-hosted инструментов на раннем этапе разработки.
- [Риск] Полная схема хранения (decision 50) означает, что Этап 1 несёт в себе таблицы (`teams`, `role_assignments`, `password_reset_tokens`, `email_verification_tokens`, `audit_log_entries` и т.д.), которые он не использует и не заполняет → [Митигейшн] пустые неиспользуемые таблицы не создают функционального риска (drift-миграция их создаёт один раз, дальше они просто существуют); альтернатива (минимальная схема + миграции по этапам) создала бы больший риск — рассинхрон между тем, что специфицировано в `specs/log-server-storage`, и тем, что реально создано на диске в конкретный момент времени.

**Этап 2 — аудит: кто что сделал и кто пытался войти**

Выбран следующим не потому, что самый заметный, а потому, что самодостаточен и удешевляет то, что
пойдёт за ним. Управление пользователями выглядит более очевидным кандидатом, но задачи 3.3 и 5.1 —
его ядро — обе ссылаются на разделы 19 и 24: создание пользователя пишет аудит-запись и выпускает
токен подтверждения email. Сделать пользователей раньше аудита значит либо написать их без аудита и
вернуться, тронув каждый мутирующий эндпоинт дважды, либо втащить половину аудита в чужой этап.
Аудит же покрывает то, что **уже существует** после Этапа 1, и не тянет за собой ничего.

Остаются нераспределёнными полные версии выдачи ролей — owner группы и `subject_type: team` (4.3/5.6/13.5), команды (5.3/13.2) и email-флоу — восстановление пароля, подтверждение email, самостоятельная регистрация (разделы 3.3/12.2/17–18/24–25); их порядок между собой — решение при старте Этапа 4, и связь у них взаимная (регистрация требует подтверждения email). **Уточнение 13.5a, продолжение (17.09.2026):** форма выдачи роли была одноразовой (выдал — баннер «Роль выдана» — забыл) и односторонней (посмотреть/отозвать грант можно было только со стороны пользователя, никогда со стороны группы/проекта). В `EditUserDialog` форма выдачи роли стала списком с отзывом (иконка «Отозвать» у каждой строки) поверх той же формы. Симметрично на стороне ресурса — новый раздел «Доступ» на `GroupDetailPage`/`ProjectDetailPage`: список тех, у кого есть роль на эту группу/проект, с выдачей (диалог `GrantAccessDialog` — роль `owner`/`user`, получатель через `AdminSearchPicker` по имени) и отзывом. Выдача и отзыв — по-прежнему тот же периметр 4.3a/5.6a, `admin`-only; просмотр списка ниже уточнён отдельно.

**Уточнение 13.5a, видимость списка доступов (17.09.2026):** `GET /v1/role-assignments` фильтром `scope_type`+`scope_id` (раздел «Доступ» группы/проекта) открыт не только `admin`, но и `owner` этой конкретной области — `canReadRoleAssignmentsForScope` в `rbac/access_check.dart`, решение пользователя. Это ровно правило `canWrite` (админ или owner, покрывающий область, grant на группу покрывает и её проекты), просто под собственным именем: *читать* список и *управлять* им (`canManageRoleAssignments`, по-прежнему только `admin`) — разные вопросы, которые вольны разойтись дальше, даже совпадая сегодня. Фильтр по одному `subject_id` (Edit User dialog) остаётся `admin`-only без исключений — это не про «моя область», а про всю историю доступа конкретного человека. Живым прогоном подтверждено: `owner`, не имеющий роли `admin`, видит список своей группы (200), не видит чужой (403), не видит его через `subject_id` (403), и по-прежнему получает 403 на попытку выдать/отозвать роль оттуда же — выдача/отзыв не разрешились вслед за чтением.
