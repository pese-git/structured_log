## Context

Сейчас в воркспейсе (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`, все в корне репозитория плоско) нет ни одного способа доставить лог за пределы процесса, кроме локального файла — `OutputFunction`/`LogSink` (`structured_log/lib/src/processors.dart:58`, `structured_log/lib/src/sink.dart`) уже задают чистый контракт «функция, принимающая запись», но ни одна встроенная реализация не отправляет данные по сети. Единственный существующий образец неблокирующего output — `AsyncFileOutput`/`_SerializedAsyncOutput` (`structured_log/lib/src/async_file_output.dart`): сериализованная через `Future` очередь, `catchError` на каждом шаге, публичный `Future<void> get flushed`. Этот паттерн — прямой прототип для будущего HTTP-sender'а. (Эти пути — до реструктуризации репозитория, см. decision 23: после неё пакет живёт в `emb/structured_log/`.)

Все 4 существующих пакета — плоская раскладка, без единого codegen-инструмента во всём монорепо. У проекта уже есть явно зафиксированный принцип «никакой магии» (`openspec/changes/add-structured-log-flutter/design.md`, decision №4). Хранилище `structured_log_server` — первый пакет воркспейса, сознательно вводящий codegen (`drift`/`build_runner`) — решение принято по прямому указанию пользователя, ограничено этим одним пакетом.

Требование пользователя расширило объём с одного доверенного приёмника логов до полноценного мультитенантного сервиса: несколько пользователей, объединённых в группы и команды, с разграничением доступа к проектам и лимитами на объём хранимой истории. Это меняет модель аутентификации приёма логов (больше не плоский список серверных API-ключей — теперь секретный ключ привязан к конкретному проекту) и добавляет management/query API, требующий аутентификации людей (JWT), а не приложений.

## Goals / Non-Goals

**Goals:**
- Дать способ централизованно собирать структурированные логи с нескольких проектов/команд в одном self-hosted сервисе, без стороннего SaaS.
- Разграничить доступ так, чтобы приложение, отправляющее логи, не имело доступа ни к чему, кроме приёма в свой проект, а человек, читающий логи, видел только то, что ему разрешено.
- Не дать одному проекту исчерпать общее хранилище — квота на историю обязательна для каждого проекта, а не опциональна.
- Сохранить нулевые runtime-зависимости `structured_log` — новый функционал живёт в отдельных пакетах, ядро не трогается.
- Дать программный и HTTP-контракт, по форме зеркалящий существующую запись лога (`event`/`level`/`timestamp`/`category`/`logger`/поля корреляции/произвольный `context`), не изобретая параллельную модель данных для самой записи.
- Дать пользователям возможность самостоятельно зарегистрироваться (username/пароль) без участия администратора, при этом оставив оператору сервера возможность полностью выключить самостоятельную регистрацию (env/CLI), если инструмент используется как закрытый корпоративный сервис.
- Отделить аутентификацию от RBAC интерфейсом `IdentityProvider`, чтобы встроенную (local) реализацию можно было в будущем заменить на Keycloak или другой OIDC-провайдер без переделки авторизации — по прямому требованию пользователя.
- Дать людям (не только приложениям через `structured_log_http`) полноценный UI над всем функционалом сервера — аутентификацией, управлением пользователями/группами/командами/проектами/квотами/секретными ключами/ролями и просмотром/поиском логов — одним Flutter-приложением `structured_log_admin_client`, а не голым JSON API.
- Реструктурировать воркспейс под появившиеся категории пакетов (frontend/backend/встраиваемые библиотеки), а не продолжать наращивать плоский список в корне репозитория, который был осмыслен, пока в воркспейсе были только встраиваемые библиотеки — по прямому требованию пользователя.
- Дать пользователю возможность самостоятельно восстановить доступ к своей учётной записи при утере пароля через email, не обращаясь к администратору или owner'у группы — по прямому требованию пользователя.
- Дать администратору возможность немедленно заблокировать любого пользователя и/или любой проект (независимо от того, в чьей они группе), как средство реагирования на инцидент — по прямому требованию пользователя.
- Дать администратору доступ к аудиту административных действий в системе (кто/что/над каким ресурсом/когда) — по прямому требованию пользователя; пересматривает более раннюю ревизию Non-Goals этой же change («аудит-лог... только сам факт текущего состояния RoleAssignment»).
- Дать любому пользователю возможность безвозвратно удалить собственный аккаунт, с сохранением записи об этом в БД (soft-delete) и немедленным прекращением доступа удалённого аккаунта к системе — по прямому требованию пользователя.

**Non-Goals:**
- Конкретная реализация `IdentityProvider` для Keycloak/внешнего OIDC-провайдера — эта change вводит только интерфейс и рефакторит под него уже спроектированную local-реализацию; сам внешний адаптер, JIT-provisioning внешних пользователей и CLI/env для выбора провайдера — будущая работа за пределами этой change (см. decision 17).
- Server-rendered HTML/веб-UI на самом сервере — эту роль для людей теперь выполняет `structured_log_admin_client`, а не HTML, отдаваемый сервером.
- Интеграция `structured_log_admin_client` с существующими viewer-пакетами (`structured_log_flutter`/`material`/`fluent`) или переиспользование их виджетов/`LogViewerController` — разные источники данных (удалённый query API vs. локальный `LogBuffer`), объединение — отдельная будущая работа.
- Live-обновление/потоковый tail логов и офлайн-режим в `structured_log_admin_client` — только просмотр по запросу/поиску.
- FTS5-поиск — на MVP `LIKE`.
- Многопоточное/много-isolate масштабирование сервера; Windows в CI на старте.
- SSO/MFA — вне объёма MVP; создание пользователя администратором (`POST /v1/users`) остаётся доступно наравне с самостоятельной регистрацией и восстановлением пароля по email (см. decision 24).
- Верификация `email` при задании/смене (подтверждающее письмо) и самостоятельное изменение пользователем уже сохранённого `email` (`PATCH /v1/users/me`) — `email` задаётся только при регистрации или администратором (см. decision 24); смена собственного email самим пользователем — будущая работа, если понадобится (потребовала бы либо повторного ввода пароля, либо верификации нового адреса).
- Нативные deep link'и (кастомные URI-схемы/App Links/Universal Links) на восстановление пароля в мобильных/desktop сборках `structured_log_admin_client` — токен восстановления всегда можно ввести вручную; удобство через URL с query-параметром `token` работает только в web-сборке (см. decision 24).
- Rate-limiting запросов `POST /v1/auth/password-reset` — не реализуется в этой доработке (см. Risks).
- Блокировка целой `Group` одним действием, временная блокировка с автоматическим истечением/снятием по таймеру, блокировка проекта `owner`-ом (только `admin`, см. decision 25) — пользователь явно ограничил требование пользователем и/или проектом, не группой; блокировка группы достижима вручную — заблокировать каждый её проект по отдельности, если понадобится.
- Полная протокольная поверхность OIDC/Keycloak сверх token-эндпоинта: понятие OAuth2 `client`/`client_id`/`client_secret` и их регистрация, token introspection endpoint (RFC 7662), OIDC UserInfo endpoint, discovery-документ `.well-known/openid-configuration`, ID-токены (в терминах OIDC) — уникально для нашего единственного «клиента» (сам API) не нужны; см. decision 10.
- Аудит бизнес-данных: приём (`POST /v1/logs`) и запрос (`GET /v1/logs`) самих записей лога SHALL не попадать в аудит-лог — это высокочастотный поток данных, а не административное действие; аудит охватывает только мутирующие management-операции (см. decision 26).
- Аутентификационные события (успешный/неуспешный логин, logout, refresh токена) — вне объёма этой доработки аудита; это отдельная категория событий (аутентификация, не администрирование ресурсов), с другим профилем частоты и другими требованиями к хранению — future work, если понадобится.
- Retention/квота на сам аудит-лог, экспорт, свободный полнотекстовый поиск по нему, видимость аудита для `owner` (только `admin`, см. decision 26) — не реализуются в этой доработке (см. Risks/Open Questions).
- Алерты/уведомления о приближении к квоте — только жёсткий отказ при превышении.
- Кросс-групповые команды — `Team` принадлежит ровно одной `Group`; пользователь может состоять в нескольких командах разных групп по отдельности.
- Ротация серверного JWT-signing-secret без даунтайма (один текущий секрет из конфигурации; см. Risks).
- Публикация `structured_log_server`/`structured_log_http` на pub.dev в рамках этой change.
- Восстановление удалённого аккаунта (undelete) через API — удаление необратимо с точки зрения любого клиента этого API (см. decision 27).
- Каскадная очистка/переназначение `RoleAssignment`, членства в командах или владения группами/проектами удалённого пользователя — эти записи остаются как есть (ссылаются на существующего, но неактивного/удалённого пользователя); admin может вручную создать новые `RoleAssignment` на других пользователей при необходимости, но это не автоматизируется этой доработкой.
- Удаление аккаунта администратором от имени другого пользователя (только сам пользователь может удалить свой аккаунт через `DELETE /v1/users/me` — см. decision 27); принудительное удаление чужого аккаунта администратором, если понадобится, — future work, отдельное от блокировки (decision 25).
- Защита «последнего администратора» от самоудаления — не вводится; вместо этого CLI-bootstrap (`create-admin`, decision 12) явно пересматривается так, чтобы засчитывать только активных, неудалённых `admin` при проверке «уже есть ли admin» (см. decision 27), сохраняя путь восстановления.

## Decisions

1. **HTTP-фреймворк: `shelf` + `shelf_router`, не `dart_frog`.**
   Альтернатива — `dart_frog`. Отклонено: `dart_frog create` навязывает собственный скелет и CLI как основной воркфлоу — расходится с плоской раскладкой и отсутствием codegen во всех остальных пакетах монорепо. shelf соответствует принципу «никакой магии»; dart_frog внутри и так построен на shelf.

2. **Хранилище: `drift` поверх SQLite (`NativeDatabase`, embedded, файл на диске).**
   Решение принято по прямому указанию пользователя, пересматривая изначальный вариант raw `package:sqlite3` (отклонён именно чтобы не заводить в монорепо первый codegen-инструмент). `drift` даёт типобезопасные, проверяемые на этапе компиляции запросы и миграции схемы «из коробки» (`Migrator`, `onUpgrade`), что для сервиса с растущей мультитенантной схемой (7 таблиц, см. decision 6) перевешивает цену `build_runner`. Trade-off явно принимается (см. Risks): `build_runner` — dev-зависимость только `structured_log_server`, `*.g.dart` не коммитится.

3. **Полнотекстовый поиск на MVP — `LIKE '%term%'` через `customSelect`, не FTS5.**
   Отклонено заводить FTS5 сейчас: усложняет схему и путь миграции ради функциональности вне согласованного MVP. `LIKE`/`json_extract`-условия, не выразимые типизированным query-builder'ом drift, пишутся как сырые SQL-фрагменты через `customSelect`/`customStatement`.

4. **Параллелизм: один `QueryExecutor` drift (`NativeDatabase`), `PRAGMA journal_mode=WAL`, без явного шардирования по isolate.**
   shelf по умолчанию обслуживает запросы в одном isolate — единственный хэндл к базе безопасен без дополнительной синхронизации. Явный non-goal — пул воркеров/шардирование, пересмотреть при упоре в throughput.

5. **Клиентский sender — отдельный пакет `structured_log_http`, не расширение core `structured_log` и не часть `structured_log_server`.**
   Wire-контракт (эндпоинт, форма батча, auth) эволюционирует вместе с сервером, а не с ядром логирования — привязывать к этому независимо версионируемый, уже опубликованный core-пакет не стоит. Класть в `structured_log_server` тоже нельзя: клиентскому приложению не нужны серверные зависимости (`shelf`, `drift`, `dart_jsonwebtoken` и т.п.). `structured_log_http` — чистый Dart, единственная зависимость `structured_log`; `HttpLogOutput` по паттерну `_SerializedAsyncOutput`/`AsyncFileOutput`, плюс батчинг и retry с backoff на сетевых ошибках/5xx (не на 4xx).

6. **Модель мультитенантности: `User` / `Group` / `Team` / `Project` / `ProjectSecretKey` / `RoleAssignment`.**
   - `Group` владеет `Project`-ами (`group_id` на `Project`, NOT NULL — проект не может существовать вне группы).
   - `Team` — набор `User` внутри ровно одной `Group` (`team_id`/`group_id`), только для массовой выдачи прав нескольким пользователям сразу; создаётся `owner`-ом группы или `admin`. Отдельная сущность от `Group`, по прямому уточнению пользователя, а не переиспользование `Group` как «группы пользователей» — иначе одна и та же сущность одновременно и владела бы проектами, и была бы получателем прав, что смешивает два разных понятия и не позволило бы владельцу группы держать несколько независимых команд с разным набором прав внутри одной группы.
   - `RoleAssignment(subject_type: user|team, subject_id, role: admin|owner|user, scope_type: global|group|project, scope_id)` — единая таблица выдачи прав; `subject_type: team` разворачивается в проверке доступа через текущее членство пользователя в команде (см. decision 7), а не копируется в отдельные записи на каждого участника — так добавление/удаление участника команды меняет его эффективные права немедленно, без синхронизации дублирующихся `RoleAssignment`.
   - Альтернатива — хранить роль как одно enum-поле прямо на `User`/на паре `(user, group)`. Отклонено: не выражает произвольную комбинацию «эта команда — `user` на этом проекте, этот человек лично — `owner` той же группы», которая явно требуется постановкой.

7. **Правила выдачи ролей: кто кому какую роль может назначить.**
   - `admin` — может создать `RoleAssignment` с любой ролью на любой области видимости, для любого `User`/`Team`. Только `admin` создаёт новые `Group` и новых `User`.
   - `owner` (на группу `G`, т.е. есть `RoleAssignment(role: owner, scope: group:G)`, прямой или через команду) — может создавать/удалять `Project`/`Team` внутри `G`, менять квоты и ротировать секретные ключи проектов `G`, и создавать `RoleAssignment` с ролью `owner` или `user` на область `group:G` или `project:P` (где `P ∈ G`), для любого `User` или `Team` внутри `G`. Не может выдать роль `admin` — это зарезервированная за существующими `admin` роль, не привязанная ни к одной группе.
   - `user` — не может создавать `RoleAssignment` ни для кого (нет делегирования); имеет только доступ на чтение/поиск логов в рамках выданной ему области видимости.
   - Альтернатива — дать `owner` право выдавать `admin`. Отклонено: `admin` — глобальная суперпользовательская роль вне какой-либо группы, выдача её из контекста «владения одной группой» ломает изоляцию тенантов, которую вся эта модель призвана обеспечить.

8. **Проверка доступа при запросе (`GET /v1/logs`, management-эндпоинты): область видимости обязательна и явна в запросе, без «слияния» нескольких проектов по умолчанию.**
   `GET /v1/logs` обязан указывать ровно одну область — `project_id` или `group_id` — и сервер проверяет, что у вызывающего (напрямую или через членство в команде) есть `RoleAssignment` (`admin` глобально, либо `owner`/`user` с областью, покрывающей запрошенную: `global` покрывает всё, `group:G` покрывает `G` и все её проекты, `project:P` покрывает только `P`) для именно этой области; иначе 403. Запрос по `group_id` агрегирует логи всех проектов группы только если сам грант — на уровне `group`, а не является объединением нескольких отдельных `project`-грантов у вызывающего.
   Альтернатива — возвращать объединение логов всех доступных вызывающему проектов без явного `project_id`/`group_id`. Отклонено: неоднозначная семантика пагинации/курсора при слиянии нескольких таблиц-разделов, и молчаливое расширение того, что видит клиент, при выдаче ему новых прав — хуже для предсказуемости и аудита, чем явный параметр.

9. **Аутентификация приёма логов: секретный ключ, привязанный к проекту (не к серверу целиком).**
   `POST /v1/logs` аутентифицируется `Authorization: Bearer <project-secret-key>`; ключ однозначно резолвится в `project_id` через таблицу `ProjectSecretKey` (хранится как хэш, не plaintext — см. decision 11) — это заменяет более раннюю версию решения (плоский список серверных API-ключей, общий на весь сервер), которая была уместна только для однопроектного MVP до появления мультитенантности. У проекта может быть несколько одновременно активных ключей (ротация без даунтайма), каждый — с `label` и возможностью отзыва (`revoked_at`).

10. **Аутентификация management/query API: единый OAuth2/OIDC-совместимый token-эндпоинт (по образцу Keycloak `/protocol/openid-connect/token`), а не набор специальных путей; эффективные роли зашиты в claims access-токена, немедленный отзыв — через `token_version`.**
    По прямому указанию пользователя контракт auth API приведён к стандарту OAuth2 (RFC 6749) / OIDC, взяв Keycloak как эталон «общепринятого» API, вместо собственных придуманных путей и форматов из более ранней ревизии этого решения (`POST /v1/auth/tokens` + `POST /v1/auth/tokens/refresh` с JSON-телом). Конкретно принято:
    - **Один эндпоинт `POST /v1/auth/token`**, тело — `application/x-www-form-urlencoded` (как того требует RFC 6749 §4.3.2/§6 для token-эндпоинта; JSON-тело было бы нестандартным), различающий сценарий по полю `grant_type`:
      - `grant_type=password` (Resource Owner Password Credentials, RFC 6749 §4.3) — поля `username`/`password`, ровно та же семантика, что раньше называлась «создание токена».
      - `grant_type=refresh_token` (RFC 6749 §6) — поле `refresh_token`, та же семантика, что раньше была отдельным путём `/tokens/refresh`.
    - **Тело ответа** — JSON со стандартными полями RFC 6749 §5.1 и принятыми в Keycloak именами: `access_token`, `token_type` (`"Bearer"`), `expires_in` (секунды до истечения access-токена), `refresh_token`, `refresh_expires_in`.
    - **Формат ошибок именно этого эндпоинта** — RFC 6749 §5.2 (`{"error": "invalid_grant" | "invalid_request" | "unsupported_grant_type", "error_description": "..."}`), а не общий JSON-конверт ошибок остального API (`log-server-api`) — это осознанное, точечное исключение ради совместимости с готовыми OAuth2-клиентами, которые ожидают именно эту форму на token-эндпоинте.
    - **Отзыв токена — `DELETE /v1/auth/token`** (тот же путь, что и создание, но методом, выражающим удаление ресурса — по прямому уточнению пользователя, вместо отдельного пути `/logout`), тело — `application/x-www-form-urlencoded` с полем `refresh_token`. Вслед за RFC 7009 §2.2 (OAuth 2.0 Token Revocation) сервер отвечает 200 с пустым телом независимо от того, был ли токен валиден/уже отозван/не существовал — чтобы ответ не позволял проверять валидность чужого токена; единственная ошибка — отсутствие поля `refresh_token` в запросе (400, формат RFC 6749 §5.2).
    - Access-токен — JWT (`dart_jsonwebtoken`, HS256, подписывающий секрет из конфигурации сервера), короткоживущий (например, 15 минут), с claims `iss` (издатель — настраиваемый идентификатор сервера), `sub` (идентификатор пользователя), `iat`, `exp`, `jti` (уникальный id токена), `preferred_username`, **`tv`** (значение `User.token_version` на момент выдачи — см. ниже) и **`roles`** — плоский снапшот эффективных прав пользователя на момент выдачи (прямых `RoleAssignment` и унаследованных через членство в командах), в форме массива `{role, scope_type, scope_id}`, по духу ролевых claims Keycloak (`realm_access`/`resource_access`), но без деления на realm/client roles — этого деления у нас нет. Middleware авторизации на management/query-эндпоинтах читает права прямо из `roles`, не запрашивая `role_assignments`/`team_members`/`teams` на каждый запрос — в этом и есть операционный выигрыш решения относительно более ранней версии.
    - Refresh-токен — непрозрачная высокоэнтропийная строка (не JWT), хранится на сервере как хэш (та же логика, что для секретных ключей проектов — decision 11) в таблице `refresh_tokens (id, user_id, token_hash, created_at, expires_at, revoked_at)`; ротируется при каждом использовании (`grant_type=refresh_token` отзывает предъявленный и выдаёт новую пару) — типовая защита от повторного использования украденного refresh-токена. Предъявление уже отозванного refresh-токена трактуется как сигнал компрометации: сервер отзывает все refresh-токены этого пользователя, а не только предъявленный.
    - Явно НЕ повторяется вслед за Keycloak: понятие OAuth2 `client`/`client_id`/`client_secret` (у нас один неявный «клиент» — сам API, нет отдельной регистрации приложений), token introspection endpoint (RFC 7662), OIDC UserInfo endpoint, discovery-документ `.well-known/openid-configuration` — всё это добавляет протокольную полноту, не нужную ни одному текущему потребителю API этой change (см. Non-Goals).
    - **Немедленный отзыв при снапшоте ролей в токене — через `User.token_version`.** `token_version` — целочисленный счётчик на пользователе; при каждом запросе к management/query API сервер делает один дешёвый point-lookup `SELECT token_version FROM users WHERE id = sub` (индексированный PK) и сравнивает с claim `tv` — несовпадение немедленно даёт 401 («токен инвалидирован»), не читая `roles` из него. `token_version` инкрементируется атомарно при любом событии, которое должно обесценить уже выданные токены: создание/отзыв `RoleAssignment`, где subject — сам пользователь; изменение членства пользователя в команде; создание/отзыв `RoleAssignment`, где subject — команда (каскадный bulk-`UPDATE` по всем текущим участникам этой команды одним запросом); деактивация пользователя (`is_active = false`); смена пароля. Все эти события — редкие административные действия (owner/admin меняют права, пользователь меняет пароль), а не типовой запрос логов, поэтому цена каскадного обновления в разы меньше цены джойна `role_assignments`↔`team_members`↔`teams`, которую этот подход убирает с горячего пути `GET /v1/logs`.
    - И `grant_type=password`, и `grant_type=refresh_token` SHALL каждый раз заново резолвить `roles` и брать текущее значение `token_version` в `tv` — не копировать claims из предыдущего токена: иначе `roles` в новом токене оставался бы таким же устаревшим, каким был в старом, и весь смысл `token_version`-проверки терялся бы. Именно это делает связку «401 при устаревшем `tv`» + «клиент делает refresh» + «refresh пересчитывает roles/tv заново» эквивалентной немедленному отзыву: следующий же запрос клиента (после обязательного refresh) видит актуальные права.
    Альтернатива (прежняя версия этого решения) — не класть роли в claims вовсе, полностью резолвить `RoleAssignment`/членство в командах из БД на каждый запрос напрямую, без `roles`-claim и без `token_version`. Отклонена по прямому решению пользователя, пересматривающему более раннюю ревизию этого decision: тот вариант тоже даёт немедленный отзыв, но ценой джойна нескольких таблиц на каждый запрос вместо одного PK-lookup; цена оправдана только если это единственный способ получить немедленный отзыв — `token_version` даёт то же свойство дешевле.

11. **Хранение секретов: `bcrypt` для паролей пользователей, SHA-256 случайного токена для секретных ключей проектов — разные механизмы для разных угроз.**
    Пароль — низкоэнтропийный, выбираемый человеком секрет, для которого важна защита от офлайн-перебора по словарю — для этого нужен медленный, адаптивный алгоритм (`bcrypt`). Секретный ключ проекта — высокоэнтропийная случайная строка (генерируется сервером через `Random.secure()`, не запоминается человеком), для которой не требуется устойчивость к словарному перебору — медленный `bcrypt` был бы просто накладными расходами на каждый вызов `POST /v1/logs` (в отличие от логина, происходящего часто), а быстрый криптографический хэш (SHA-256) даёт то же свойство «в БД не хранится plaintext» без этой цены. Оба секрета показываются вызывающему только один раз, в момент создания.

12. **Bootstrap первого `admin`: явная CLI-команда, не автоматическое создание при первом запуске.**
    `bin/server.dart create-admin --username ... --password ...` (или аналогичный флаг), выполняемая оператором сервера отдельно от обычного `dart run bin/server.dart`; работает только если в БД ещё нет ни одного `admin` (защита от повторного использования как лазейки для повышения прав). Альтернатива — создавать admin автоматически при пустой БД по данным из переменных окружения при обычном старте сервера. Отклонено: неявное поведение при старте (риск случайно оставить сервер с дефолтными кредами, если оператор не подставил свои через env) хуже одной осознанной команды, которую оператор запускает сам.

16. **Аутентификация по `username` (не `email`); самостоятельная регистрация, переключаемая конфигурацией сервера.**
    `User.username` — обязательное уникальное поле, единственный идентификатор для логина. `User.email` — уникальное (если задано) поле, добавленное decision 24 исключительно для восстановления пароля; логин по нему не выполняется, идентификатором для входа остаётся только `username`. `POST /v1/auth/register` (username + пароль + **обязательный `email`**, опционально `display_name`) создаёт нового `User` без единого `RoleAssignment` — то есть без доступа ни к одному ресурсу, пока `owner`/`admin` явно не выдаст права; регистрация создаёт только учётную запись, не привилегии. Доступность этого эндпоинта управляется полем `ServerConfig.registrationEnabled` (`bool`), задаваемым CLI-флагом (например, `--enable-registration`/`--disable-registration`) или переменной окружения при старте сервера; по умолчанию — `false` (выключено), так как для self-hosted внутреннего инструмента более безопасно начинать с закрытой регистрации, включаемой оператором осознанно. `POST /v1/users` (создание пользователя `admin`-ом) остаётся доступным независимо от этого флага — два независимых пути создания учётной записи.
    Альтернатива — регистрация всегда включена, без флага. Отклонено: сервис может использоваться как закрытый корпоративный инструмент, где открытая регистрация недопустима; явный флаг даёт оператору выбор без необходимости патчить код.

17. **Аутентификация абстрагирована интерфейсом `IdentityProvider`, чтобы local-реализацию (decisions 10/16) можно было подменить на Keycloak/другой OIDC-провайдер, не переделывая RBAC.**
    По прямому требованию пользователя весь код, зависящий от «как проверен токен и откуда взялись роли», обращается не к конкретной local-реализации напрямую, а к интерфейсу:
    ```
    abstract class IdentityProvider {
      Future<VerifiedIdentity?> verifyAccessToken(String bearerToken);
    }
    class VerifiedIdentity {
      final String subject;       // провайдеро-специфичный id пользователя (у local — наш User.id)
      final String? username;     // preferred_username-эквивалент, для JIT-провижининга/отображения
      final List<EffectiveRole>? roles; // null = провайдер не поставляет роли — резолвить из role_assignments; non-null = доверять этому списку как есть
    }
    ```
    - **`roles == null`** — точка расширения для внешнего провайдера, который НЕ поставляет собственные роли (например, Keycloak используется только для идентификации, а права на `Group`/`Project` всё равно выдаются через наш `POST /v1/role-assignments` и хранятся в `role_assignments`, привязанные к JIT-провижненному локальному `User`). Тогда авторизация резолвит `roles` из БД — тем же кодом, что уже существовал как более ранняя (до decision 10) версия этого решения.
    - **`roles != null`** — точка расширения для внешнего провайдера, который сам поставляет права (например, маппинг ролей/групп Keycloak через protocol mappers/custom claims в `{role, scope_type, scope_id}` — конкретный маппинг специфичен для настройки конкретного Keycloak realm и не часть этого интерфейса). В этом режиме `role_assignments` в нашей БД может не использоваться вовсе для таких пользователей, либо использоваться как дополнение — это решает конкретная реализация внешнего провайдера, не эта change.
    - **`token_version`-проверка (decision 10) остаётся полностью внутренней деталью local-реализации** `IdentityProvider.verifyAccessToken` — она не часть интерфейса и не видна вызывающему коду; для local-провайдера несовпадение `tv` просто возвращает `null` (как любой другой невалидный токен), давая 401. Немедленный отзыв для внешнего провайдера, поставляющего собственные `roles`, зависит от его собственной модели ревокации (например, короткого TTL Keycloak-токенов) — эта change не даёт такой гарантии для чужих провайдеров, только для local.
    - Интерфейс экспортируется из публичного API `structured_log_server` (по аналогии с `OutputFunction`/`LogSink` в `structured_log`), чтобы будущий пакет вроде `structured_log_server_keycloak` мог реализовать его отдельно и быть передан при старте сервера (`startServer(identityProvider: ...)`), без форка или изменения `structured_log_server`.
    - Явно НЕ входит в эту change: сама реализация `IdentityProvider` под Keycloak (JWKS-верификация RS256, `iss`/`aud`-валидация, JIT-provisioning, маппинг ролей), схема `User.external_subject` под неё, CLI/env для выбора провайдера (сейчас единственная реализация — local, выбор не требуется). Эти поля/пакеты добавляются вместе с первой реальной внешней реализацией, не спекулятивно сейчас.
    Альтернатива — не вводить интерфейс, оставить local-реализацию единственной и жёстко зашитой. Отклонено по прямому требованию пользователя: тогда подмена на Keycloak в будущем означала бы переписывать код авторизации, а не подставлять новую реализацию одного интерфейса.

13. **Квоты проекта: `retention_days` (обязательное поле) + опциональные `max_entries`/`max_bytes`, с отдельным счётчиком использования.**
    Каждый `Project` обязан иметь `retention_days`. `max_entries`/`max_bytes` — опциональны (`null` = без лимита по этому измерению), задаются владельцем/админом при создании/редактировании проекта. Текущее использование хранится не как `COUNT(*)`/`SUM(size)` по требованию (дорого на большой таблице), а как отдельная строка `ProjectUsage(project_id, entry_count, total_bytes)`, обновляемая атомарно в той же транзакции, что вставка батча и что периодическая очистка по retention — так проверка квоты на приёме — это дешёвый point-lookup, а не агрегирующий запрос по всей таблице записей проекта.

14. **Enforcement квоты: retention — периodic purge job; entries/bytes — отказ конкретным записям батча при приёме.**
    Отдельный периодический таймер (например, раз в час) внутри процесса сервера удаляет записи `log_entries` старше `retention_days` каждого проекта и уменьшает соответствующий `ProjectUsage`. Проверка `max_entries`/`max_bytes` происходит на приёме (`POST /v1/logs`): если добавление записи из батча превысило бы лимит проекта, эта конкретная запись отклоняется (той же схемой частичного приёма батча, что и валидационные ошибки, — не весь батч целиком), с кодом ошибки `quota_exceeded` и HTTP `507 Insufficient Storage` (единственный статус из стандарта, чья семантика буквально «сервер не может сохранить представление [из-за нехватки места]» — точнее подходит, чем `413`, зарезервированный в этом API за превышением размера самого HTTP-тела).

15. **CI: отдельный новый job в существующем [.github/workflows/ci.yml](.github/workflows/ci.yml), не расширение текущего `test`-job.**
    Текущий `test`-job жёстко привязан к `working-directory: structured_log` (не матрица), в отличие от `flutter`-job'а. Новый job матрицей по пакету (`structured_log_server`, `structured_log_http`) через `dart-lang/setup-dart`, стартуя с `ubuntu-latest`, с шагом `dart run build_runner build` перед `analyze`/`test` для `structured_log_server`.

18. **`structured_log_admin_client` — самостоятельное Flutter-приложение под конкретный бэкенд этой change, не headless-ядро + скин по образцу `structured_log_flutter`/`structured_log_material`/`fluent`.**
    Три существующих Flutter-пакета устроены как headless `LogViewerController`/`LogBuffer` (не привязаны к конкретному бэкенду — источник данных всегда локальный `LogSink.output`) + отдельные пакеты-скины поверх них. Для admin-клиента это разделение неуместно: весь смысл приложения — быть UI именно над HTTP-контрактом `structured_log_server` (аутентификация, RBAC, квоты — понятия, которых не существует в headless-ядре просмотра логов), нет и не предвидится второго backend-контракта, под который стоило бы абстрагироваться. Поэтому — один пакет, Material 3, без разделения на core/skin.
    Альтернатива — вынести headless-слой (API-клиент, модели, состояние) в отдельный `structured_log_admin_core` и UI поверх него, по аналогии с viewer-пакетами. Отклонено сейчас: преждевременная абстракция при единственном потребителе (headless/skin-разделение оправдано, когда есть более одного скина, использующего одно ядро — см. `openspec/changes/add-structured-log-flutter/design.md`, decision 2, тот же принцип «не абстрагировать раньше второго потребителя»); пересмотреть, если понадобится второй UI-кит (Cupertino/Fluent) для этого же клиента.

19. **HTTP-клиент admin-клиента: `dio`, не `http` и не `dart:io` напрямую.**
    Нужны interceptor'ы: автоматическая подстановка `Authorization: Bearer <access-token>` в каждый запрос и единая точка перехвата 401 → `grant_type=refresh_token` → повтор исходного запроса. `package:http` не даёт interceptor-цепочки из коробки, это писалось бы вручную поверх него; `dio` даёт то же самое как штатный примитив (`Interceptor`/`InterceptorsWrapper`), не более тяжёлый по сути, чем `http`, но избавляющий от собственной обёртки с тем же результатом. Zero-dependency принцип `structured_log` (см. `AGENTS.md`) на Flutter-приложения не распространяется — это не библиотека, которую кто-то подключает транзитивно, а конечное приложение.
    `structured_log_admin_client` НЕ зависит от `structured_log_server`/`structured_log_http`/`structured_log` — общается с сервером только по документированному HTTP/JSON контракту (`specs/log-server-api`, `specs/log-server-auth`, ...), без единой строчки общего Dart-кода с бэкендом. Отклонённая альтернатива — общий пакет типов запроса/ответа между сервером и клиентом (снизил бы риск рассинхрона контракта, см. Risks) — отклонено сейчас: добавляет пакет ради типобезопасности одного клиента, а рассинхрон и так ловится интеграционными тестами, гоняющими клиентский код (или его логику) против реального сервера (задача в `tasks.md`), а не общим пакетом типов.

20. **Хранение токенов: `flutter_secure_storage`, не `shared_preferences`.**
    Access- и refresh-токены — секреты (особенно refresh-токен, долгоживущий и напрямую дающий переоформить сессию); `shared_preferences` на большинстве платформ хранит данные в незашифрованном виде (plist/XML/localStorage), `flutter_secure_storage` — обёртка над Keychain (iOS/macOS)/Keystore (Android)/Credential Manager (Windows)/аналогами на остальных платформах. Одноразовые секретные ключи проектов, которые оператор видит при создании через этот же клиент, в постоянное хранилище клиента не попадают вовсе (показываются один раз, копируются оператором вручную — см. `specs/admin-client-resource-management`), так что этот выбор касается только пользовательской auth-сессии.

21. **Логи проекта в admin-клиенте не переиспользуют `LogViewerController`/виджеты material/fluent — собственная простая реализация поверх `GET /v1/logs`.**
    `LogViewerController` (`structured_log_flutter`) фильтрует уже находящийся в памяти `List<Map<String, dynamic>>` из локального `LogBuffer` — синхронно, без пагинации, без сетевых вызовов. Источник данных admin-клиента принципиально другой: удалённый, постранично загружаемый, с серверной (не клиентской) фильтрацией через query-параметры. Подгонять `LogViewerController` под оба источника сразу — усложнение существующего, стабильного, уже опубликованного на pub.dev API `structured_log_flutter` ради одного нового потребителя. Проще и безопаснее — собственный, маленький state-слой в `structured_log_admin_client` (выбранная область видимости + текущие фильтры + список записей + курсор пагинации), не претендующий на переиспользование виджетов `structured_log_material`/`fluent`. Унификация (например, `LogViewerController` с pluggable источником данных) — явный Non-Goal, возможная будущая работа, если у `LogViewerController` появится более одного варианта загрузки данных.

22. **`GET /v1/projects/:id` дополнительно возвращает текущее использование квоты (`entry_count`/`total_bytes` из `ProjectUsage`).**
    Небольшое расширение уже спроектированного `log-server-quotas`/`log-server-api`, понадобившееся именно для admin-клиента: отображение «сколько уже использовано из лимита» требует, чтобы это было доступно через API, а не только использовалось сервером внутренне для enforcement на приёме. Не breaking — совместимое добавление полей в существующий ответ.

23. **Реструктуризация репозитория: категории верхнего уровня `emb/`/`backend/`/`frontend/`/`packages/` вместо единого плоского списка пакетов в корне.**
    До этой change все пакеты воркспейса были одного рода — библиотеки, встраиваемые в чужое приложение (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) — и жили плоско в корне репозитория явным списком в `melos.yaml`, по образцу [cherrypick](https://github.com/pese-git/cherrypick) (см. `openspec/changes/add-structured-log-flutter/design.md`, decision 1). С появлением `structured_log_server` (самостоятельный сервис, не встраиваемая библиотека) и `structured_log_admin_client` (самостоятельное приложение, тоже не встраиваемая библиотека) плоский список перестал отражать реальную структуру воркспейса — в нём появились категориально разные виды пакетов, а не только один. По прямому требованию пользователя вводится 4 категории верхнего уровня:
    - `emb/` — встраиваемые в приложения библиотеки: `structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`, `structured_log_http` (все существующие пакеты + новый клиентский sender — он такая же встраиваемая библиотека, как и остальные четыре).
    - `backend/` — серверные приложения: `structured_log_server`.
    - `frontend/` — клиентские приложения с UI: `structured_log_admin_client`.
    - `packages/` — зарезервировано под будущие пакеты, не подпадающие однозначно ни под одну из трёх категорий выше; пустая в рамках этой change (не создаётся как пакет — просто директория-заглушка, без записи в `packages:` `melos.yaml`, пока в ней ничего нет).
    Это явный пересмотр более раннего решения (плоская раскладка без вложенности, выбранная ради единообразия с `cherrypick`) — тогда «плоско» было оправдано однородностью пакетов; сейчас неоднородность (библиотека vs сервис vs приложение) стала реальной, а не гипотетической, и категоризация уже не «вложенность ради вложенности», отклонённая в той более ранней ревизии, а разделение по факту различной природы пакетов.
    Альтернатива — оставить плоскую раскладку, просто продолжив перечислять новые пакеты в корне рядом со старыми. Отклонено по прямому указанию пользователя: с ростом числа пакетов разных категорий плоский список в корне репозитория (и в `melos.yaml`) перестаёт сам по себе сообщать, что чем является, — категории делают это явным без необходимости запоминать/документировать отдельно.

24. **Восстановление пароля по email: отдельный pre-auth flow (`POST /v1/auth/password-reset` + `POST /v1/auth/password-reset/confirm`), не расширение `/v1/auth/token`; `User.email` — новое поле, обязательное при самостоятельной регистрации; отправка письма — через интерфейс `EmailSender`.**
    По прямому требованию пользователя добавлена возможность самостоятельно восстановить доступ к аккаунту при утере пароля, не обращаясь к администратору/owner'у группы — до этой доработки единственный способ сменить пароль пользователю был недоступен вовсе (Non-Goal более ранней ревизии). Конкретно принято:
    - **`User.email`** — новое уникальное (если задано) поле; не идентификатор для входа (им остаётся `username` — decision 16 не пересматривается), только контактный адрес для восстановления пароля. **Обязательно при самостоятельной регистрации** (`POST /v1/auth/register` SHALL требовать `email` наравне с `username`/паролем — 400 при отсутствии, 409 при уже занятом): пользователь, зарегистрировавшийся сам, — единственный, кто отвечает за восстановление собственного доступа, и без email эта возможность была бы для него недостижима с первого дня. При создании пользователя администратором (`POST /v1/users`) `email` остаётся опциональным — админ создаёт учётную запись осознанно и может сообщить пароль вне этого flow; поэтому колонка `User.email` в схеме хранения — `nullable`, а не `NOT NULL` (обязательность — валидация конкретно на `POST /v1/auth/register`, не ограничение на уровне таблицы). Самостоятельное изменение уже сохранённого `email` (`PATCH /v1/users/me`) — явный Non-Goal (см. выше): потребовало бы либо повторного ввода текущего пароля, либо верификации нового адреса подтверждающим письмом — отдельная будущая работа.
    - Альтернатива — оставить `email` опциональным и при самостоятельной регистрации (более ранняя ревизия этого decision). Отклонена по прямому требованию пользователя: опциональность означала бы, что часть самостоятельно зарегистрированных пользователей не смогут воспользоваться восстановлением пароля вовсе — ровно тот случай, который эта доработка призвана закрыть; обязательность на этом единственном пути устраняет пробел, не усложняя путь создания администратором, где email по-прежнему не нужен.
    - **`POST /v1/auth/password-reset`** (JSON-тело `{"email": "..."}"`, не form-encoded — этот эндпоинт не часть контракта `/v1/auth/token` и RFC 6749 на него не распространяется) SHALL всегда отвечать 202 с одинаковым телом независимо от того, существует ли пользователь с указанным `email` — по аналогии с `DELETE /v1/auth/token` (decision 10), чтобы ответ не позволял перебором `email` определять зарегистрированные адреса (user enumeration). Если активный пользователь с таким `email` найден — сервер инвалидирует все его ранее выданные неиспользованные токены восстановления и создаёт новый: высокоэнтропийная случайная строка (`Random.secure()`, тот же генератор, что и для секретных ключей проектов), хранится хэшем (SHA-256 — тот же выбор и по той же причине, что decision 11: токен не запоминается человеком, устойчивость к словарному перебору не нужна) в новой таблице `password_reset_tokens (id, user_id, token_hash, created_at, expires_at, used_at)`, с коротким сроком действия (например, 30 минут, настраивается). Письмо отправляется через `EmailSender`.
    - **`POST /v1/auth/password-reset/confirm`** (JSON-тело `{"token": "...", "new_password": "..."}"`) находит токен по хэшу и проверяет `expires_at`/`used_at IS NULL`; невалиден (не найден/истёк/уже использован) → 400 `invalid_token`, в общем JSON-конверте ошибок `log-server-api` (не в формате RFC 6749 — этот эндпоинт вне контракта `/v1/auth/token`); валиден → обновляет хэш пароля, помечает токен использованным (`used_at`), инвалидирует остальные неиспользованные токены восстановления этого пользователя и — как любая смена пароля — инкрементирует `User.token_version`. Это уже существующее правило (decision 10 перечисляет «смена пароля» среди инвалидирующих событий) — восстановление пароля не вводит новый механизм отзыва, а лишь использует уже спроектированный.
    - **Интерфейс `EmailSender`** (по образцу `IdentityProvider`, decision 17): `abstract class EmailSender { Future<void> send({required String to, required String subject, required String body}); }`, публично экспортирован из barrel-файла `structured_log_server`. Референс-реализация — `SmtpEmailSender` поверх `package:mailer` (SMTP host/port/username/password/from-адрес — новые поля `ServerConfig`, из CLI-флагов/переменных окружения, по аналогии с `registrationEnabled`). Абстракция введена по той же причине, что `IdentityProvider`: оператор может подставить другую реализацию (например, вызов API транзакционного email-провайдера) при старте сервера, не трогая код flow восстановления.
    - **Тело письма — сырой токен для ручного ввода, плюс необязательная ссылка.** Письмо содержит код восстановления как текст (для ввода в `structured_log_admin_client` вручную) и дополнительно URL вида `<passwordResetBaseUrl>?token=...` (адрес настраивается оператором — актуален только для web-сборки admin-клиента, которая может прочитать `token` из query-параметра при загрузке страницы и подставить его в форму). Нативные deep link'и (кастомные URI-схемы/App Links/Universal Links на mobile/desktop) — явный Non-Goal: платформенно-специфичная настройка ради удобства, не необходимость, раз токен всегда можно ввести вручную.
    Альтернатива — не вводить `email` вовсе, оставить сброс пароля обязанностью администратора (более ранняя ревизия Non-Goals). Отклонена по прямому требованию пользователя: самостоятельное восстановление — стандартное ожидание от системы аутентификации, а стоимость (одно опциональное поле + два pre-auth эндпоинта + интерфейс отправки почты) оправдана — тем более что механизм немедленного отзыва при смене пароля (`token_version`) уже существовал и не требует изменений.

25. **Блокировка пользователя/проекта — исключительно роль `admin`, отдельные action-эндпоинты (`block`/`unblock`), а не расширение `PATCH`.**
    По прямому требованию пользователя: `admin` (и только `admin` — не `owner`, даже в своей группе) может немедленно заблокировать любого пользователя или любой проект как средство реагирования на инцидент (скомпрометированный аккаунт/секретный ключ, злоупотребление квотой и т.п.), независимо от того, в чьей группе они находятся.
    - **Блокировка пользователя** — `POST /v1/users/:id/block` / `POST /v1/users/:id/unblock` (оба — `admin` only). `block` устанавливает `User.is_active = false` (уже существующее поле — decision 10 перечисляет деактивацию среди событий, инкрементирующих `token_version`; блокировка использует тот же переключатель, не вводит второе, параллельное поле состояния), **и дополнительно явно отзывает все refresh-токены этого пользователя** (`revoked_at` на всех непросроченных записях `refresh_tokens` этого `user_id`) — это заполняет пробел более ранней ревизии decision 10: там `token_version` инвалидирует только access-токены, но не рассматривался сценарий, где заблокированный пользователь предъявляет ещё не истёкший refresh-токен и получает новый access-токен с уже неактуальным (но формально корректным на момент выдачи) состоянием. Поэтому решение здесь дополнительно требует: `grant_type=refresh_token` SHALL проверять `is_active` пользователя, к которому привязан refresh-токен, и отклонять выдачу новой пары, если пользователь неактивен, — той же ошибкой `invalid_grant`, что и для отозванного/истёкшего токена, независимо от отзыва самих refresh-токенов (защита в глубину: даже если по какой-то причине конкретный refresh-токен не был отозван, неактивный пользователь всё равно не получит новый access-токен). `unblock` возвращает `User.is_active = true`; заблокированный пользователь при этом не теряет свои `RoleAssignment` — они восстанавливаются автоматически вместе с возможностью снова аутентифицироваться.
    - **Блокировка проекта** — новое поле `Project.is_blocked` (bool, по умолчанию `false`) + `POST /v1/projects/:id/block` / `POST /v1/projects/:id/unblock` (оба — `admin` only, в отличие от остального управления проектом, доступного `owner`/`admin` — decision 7/`log-server-rbac`: блокировка — единственное действие над проектом, которое `owner` совершить не может даже над своим собственным проектом, потому что это инструмент реагирования на инцидент поверх иерархии обычных прав, а не рутинное управление). Пока `is_blocked = true`: `POST /v1/logs` (приём по секретному ключу этого проекта) SHALL отклоняться с кодом `project_blocked` (403), не проверяя и не сохраняя ни одной записи батча; `GET /v1/logs?project_id=<заблокированный>` SHALL отклоняться тем же кодом, даже для вызывающего с действительным доступом по RBAC — блокировка перекрывает обычную авторизацию, а не дополняет её. `GET /v1/logs?group_id=G`, где `G` содержит заблокированный проект среди прочих, SHALL молча исключать записи заблокированного проекта из агрегированного результата, не отклоняя запрос целиком — иначе один заблокированный проект в группе останавливал бы просмотр логов всех остальных, ничем не провинившихся проектов той же группы.
    - Секретный ключ заблокированного проекта не отзывается и не удаляется — блокировка обратима (`unblock` немедленно возвращает приём и запрос к норме без необходимости пересоздавать ключи), в отличие от отзыва конкретного ключа (`revoked_at`), который необратим по конструкции (decision 11).
    Альтернатива — не выделять блокировку в отдельное действие, а разрешить `PATCH /v1/users/:id`/`PATCH /v1/projects/:id` с полем `is_active`/`is_blocked` наравне с остальными редактируемыми полями. Отклонено: блокировка — операция другого характера, чем обычное редактирование (у пользователя явно другие права её совершать — только `admin`, тогда как `PATCH /v1/projects/:id` в остальном доступен и `owner`), смешение полей с разной авторизацией в одном универсальном `PATCH` создало бы почву для ошибки (например, per-field авторизацию внутри одного эндпоинта проще упустить в реализации, чем при физически разных путях).

26. **Аудит: отдельная таблица `audit_log_entries`, фиксированный (закрытый) набор типов действий, запись в той же транзакции, что и само действие; чтение — только `admin`, без квоты/retention на сам аудит-лог в этой доработке.**
    По прямому требованию пользователя — пересматривает более раннюю ревизию Non-Goals этой же change («аудит-лог изменений прав доступа... только сам факт текущего состояния `RoleAssignment`»): теперь это полноценная возможность, а не «состояние без истории».
    - **Схема**: `audit_log_entries(id, actor_user_id — nullable, action, target_type, target_id — nullable, metadata — JSON-текст, created_at)`. `actor_user_id` — `nullable`, потому что не для каждого события есть аутентифицированный админ/owner в контексте вызова (см. ниже про self-registration); `target_type`/`target_id` — полиморфная ссылка (на `users`/`groups`/`teams`/`projects`/`project_secret_keys`/`role_assignments`), так как единая таблица должна охватывать разнородные ресурсы; `metadata` — JSON-текст, а не типизированные колонки на каждое действие: набор релевантных деталей разный для каждого `action` (например, для `role_assignment.created` — `{role, scope_type, scope_id, subject_type, subject_id}`, для `project.quota_updated` — `{before: {...}, after: {...}}`), заводить отдельную таблицу/набор колонок под каждый тип действия было бы избыточно ради типобезопасности, которая здесь не incrementally полезна (аудит-запись не участвует в бизнес-логике, только читается человеком/UI).
    - **Закрытый набор `action`**: `user.created`, `user.blocked`, `user.unblocked`, `user.deleted`, `group.created`, `team.created`, `team.member_added`, `team.member_removed`, `project.created`, `project.quota_updated`, `project.blocked`, `project.unblocked`, `secret_key.created`, `secret_key.revoked`, `role_assignment.created`, `role_assignment.revoked`, `password.reset_confirmed` — то есть каждая мутирующая management-операция, спроектированная в этой change (decisions 6, 7, 13, 14, 24, 25, 27). Явно не входят: сам приём/запрос логов (`POST`/`GET /v1/logs` — бизнес-данные, не административное действие, и на порядки более частые), события аутентификации (успешный/неуспешный логин, `logout`, `refresh`) — другая категория событий с другим профилем частоты, не входящая в эту доработку (см. Non-Goals).
    - **Запись в той же транзакции, что мутация** — если сама операция (например, отзыв `RoleAssignment`) откатывается, аудит-запись не должна была создаться отдельно от неё; drift-транзакция вокруг каждой мутирующей операции покрывает и её собственное изменение, и вставку в `audit_log_entries`.
    - **`actor_user_id` для самостоятельной регистрации** — сама создаваемая учётная запись (пользователь буквально совершил действие над собой), а не `null`; для действий администратора/owner — их `user_id` из аутентифицированного access-токена.
    - **`GET /v1/audit-log`** — `admin` only (глобально, не привязано к конкретной группе/проекту — не у всех типов действий есть проект/группа как область), с фильтрами `actor_user_id`/`action`/`target_type`/`target_id`/`from`/`to` и keyset-пагинацией по `id`, тем же паттерном, что `GET /v1/logs`.
    - **Без quota/retention на сам аудит-лог** в этой доработке — он растёт неограниченно (см. Risks); в отличие от `log_entries`, где квота обязательна с самого начала (decision 13), административных мутаций на порядки меньше, чем записей лога, так что немедленная необходимость в retention для аудита менее очевидна — явный Non-Goal, а не забытая деталь.
    Альтернатива — переиспользовать `log_entries` (записывать аудит-события как обычные лог-записи в какой-то служебный проект). Отклонено: `log_entries` спроектирована под пользовательские структурированные логи приложений (с `project_id`, квотами, произвольным `context`) — административные события этой семантике не соответствуют (нет владеющего проекта, не должны подчиняться пользовательским квотам/retention проекта), а смешение доменов усложнило бы обе модели ради экономии одной таблицы.

27. **Самоудаление аккаунта (`DELETE /v1/users/me`): переиспользует переключатель `is_active` block/unblock (decision 25), необратимо через API, требует подтверждения паролем.**
    По прямому требованию пользователя: любой аутентифицированный пользователь может безвозвратно удалить свой собственный аккаунт; удалённые аккаунты помечаются в БД (soft-delete), не удаляются физически, и немедленно теряют доступ к системе.
    - **Новое поле `User.deleted_at`** (nullable timestamp), отдельно от `is_active`: `is_active` описывает «может ли учётная запись сейчас аутентифицироваться» (общий переключатель для блокировки admin'ом и удаления), `deleted_at` — «была ли эта учётная запись когда-либо самостоятельно удалена» (более сильное, постоянное состояние). `DELETE /v1/users/me` устанавливает оба атомарно: `deleted_at = now()`, `is_active = false`, плюс отзывает все refresh-токены пользователя и инкрементирует `token_version` — тот же самый набор действий, что и `POST /v1/users/:id/block` (decision 25), с добавлением `deleted_at`. Это осознанное переиспользование: удалённый аккаунт должен быть недоступен для входа точно так же, как заблокированный, а весь механизм немедленного отзыва (`grant_type=password`/`refresh_token` проверяют `is_active`, `token_version` инвалидирует текущий access-токен) уже спроектирован под это — новой логики проверки доступа для удалённых аккаунтов не требуется.
    - **Подтверждение паролем**: `DELETE /v1/users/me` принимает текущий пароль в теле запроса и не выполняет удаление при его несовпадении — короткоживущий access-токен сам по себе (например, украденный или оставленный в открытой сессии) недостаточен для необратимого действия; та же логика, что уже применяется к другим последствиям при знании пароля (грант `grant_type=password`).
    - **Необратимо через API**: сервер не предоставляет способ снять `deleted_at`. `POST /v1/users/:id/unblock` (decision 25) SHALL явно отказывать (400), если у пользователя установлен `deleted_at` — иначе block/unblock, задуманный как обратимый инструмент, стал бы лазейкой, отменяющей необратимость удаления.
    - **`username`/`email` удалённого аккаунта освобождаются для повторной регистрации**: уникальность в схеме (decision 16/24) ограничивается условием `deleted_at IS NULL` — иначе человек, удаливший аккаунт, навсегда занимал бы своё имя пользователя/email, не имея возможности зарегистрироваться заново. Записи `role_assignments`/`team_members`/владения проектами удалённого пользователя не переносятся и не удаляются каскадно — они остаются ссылаться на существующую (просто неактивную) строку `users`; это осознанно вне рамок этой доработки (см. Non-Goals) — переназначение ролей/владения при уходе человека предполагается ручным действием admin/owner при необходимости.
    - **Восстановление bootstrap-пути**: проверка «уже существует ли admin» в `create-admin` (decision 12) уточняется до «существует ли **активный, неудалённый** admin» — иначе если единственный admin удалит свой аккаунт (самоудаление не имеет специальной защиты «последнего admin» — см. Non-Goals), оператор не смог бы повторно воспользоваться `create-admin` для восстановления доступа.
    Альтернатива — сделать удаление отдельным от блокировки переключателем без переиспользования `is_active`/`token_version`/отзыва refresh-токенов, с собственной параллельной логикой инвалидации доступа. Отклонено: удвоило бы код и тестовое покрытие ради состояния, которое с точки зрения «может ли пользователь сейчас войти» ничем не отличается от уже существующей блокировки — единственное новое свойство удаления — необратимость и пометка `deleted_at`, оба добавляются поверх существующего механизма, а не рядом с ним.

## Risks / Trade-offs

- [Риск] `drift` использует `package:sqlite3` под капотом (нативная библиотека через `dlopen`); поведение на Windows-раннерах исторически менее предсказуемо → [Митигейшн] новый CI job стартует только с `ubuntu-latest`, Windows добавляется отдельно после проверки на реальном раннере.
- [Риск] `drift`/`drift_dev`/`build_runner` — первый codegen-инструмент в монорепо → [Митигейшн] ограничен пакетом `structured_log_server`; `*.g.dart` не коммитится, CI выполняет `dart run build_runner build --delete-conflicting-outputs` перед `analyze`/`test`.
- [Риск] Один `QueryExecutor` в одном isolate — потолок пропускной способности при большом числе одновременных писателей → [Митигейшн] явный non-goal для MVP; путь апгрейда (`NativeDatabase.createInBackground`, шардирование) как открытый вопрос на будущее.
- [Риск] `LIKE`-поиск по `context_json` деградирует по производительности с ростом таблицы → [Митигейшн] задокументировать как ограничение MVP; путь апгрейда — FTS5, не реализуется сейчас.
- [Риск] Снапшот `roles` в claims access-токена (decision 10) может устареть в промежутке между выдачей токена и отзывом прав, если бы отзыв проверялся только сроком жизни токена → [Митигейшн] `token_version`-lookup на каждом запросе делает эту проблему не актуальной — любое изменение прав немедленно инвалидирует уже выданные токены пользователя, независимо от того, что записано в `roles`.
- [Риск] Токен растёт пропорционально числу эффективных грантов пользователя (`roles` — плоский список) → [Митигейшн] для типичного пользователя/owner список из нескольких групп/проектов не проблема; жёсткого лимита на MVP не вводится, но если у кого-то счёт пойдёт на сотни грантов — пересмотреть (например, не инлайнить весь список, а хранить в токене только хэш/версию набора грантов и резолвить полный список отдельным легковесным эндпоинтом) — не реализуется в этой change.
- [Риск] Каскадное обновление `token_version` всех участников команды при изменении team-scoped `RoleAssignment`/членства (decision 10) — при очень большой команде это bulk-`UPDATE` по потенциально многим строкам → [Митигейшн] это происходит только на редких административных операциях (owner/admin меняет права, не на каждый запрос логов), и это один SQL-запрос с индексированным `JOIN`/`IN`, а не N отдельных обновлений.
- [Риск] Один JWT-signing-secret без встроенной ротации без даунтайма (decision 10, в отличие от секретных ключей проектов, где ротация заложена явно) → [Митигейшн] задокументировано как MVP-ограничение; смена секрета инвалидирует все текущие сессии одновременно — приемлемо для внутреннего инструмента, эксплуатируемого редко.
- [Риск] `DELETE /v1/auth/token` (decision 10) отзывает только refresh-токен — короткоживущий access-токен, выданный вместе с ним, остаётся технически валиден до истечения своего срока → [Митигейшн] задокументировано как принимаемое ограничение; срок жизни access-токена намеренно короткий (минуты, не часы) именно чтобы это окно было малым.
- [Риск] Открытая по умолчанию самостоятельная регистрация (decision 16) на публично доступном сервере может быть использована для массового создания пустых аккаунтов → [Митигейшн] `registrationEnabled` по умолчанию `false`; зарегистрированный аккаунт не имеет доступа ни к одному ресурсу без явного гранта, так что даже массовая регистрация не даёт доступа к чужим данным — риск ограничен ростом таблицы `users`, не утечкой логов.
- [Риск] `/v1/auth/token` (`POST` и `DELETE`, form-encoded, RFC 6749/7009-формат ошибок и ответов) сосуществует в том же API с остальными эндпоинтами (JSON-тело, общий конверт ошибок из `log-server-api`) → [Митигейшн] расхождение изолировано ровно в одном пути `/v1/auth/token` (два метода одного ресурса), явно задокументировано в `specs/log-server-auth` и в README сервера как осознанное исключение ради совместимости с готовыми OAuth2-клиентами, а не непоследовательность дизайна.
- [Риск] `DELETE` с телом запроса (`refresh_token` в form-encoded теле) — не все HTTP-клиенты/прокси одинаково надёжно передают тело у `DELETE`-запросов → [Митигейшн] осознанный выбор вслед за трактовкой «токен — это ресурс, отзыв — его удаление»; альтернатива (токен в query-параметре) отклонена как худшая практика — секрет не должен попадать в URL (логи веб-сервера, история прокси); альтернатива (токен в заголовке `Authorization`) осталась бы несовместимой с тем, что тот же заголовок уже используется для access-токена на остальных эндпоинтах — путаница между «токеном для аутентификации запроса» и «токеном, который отзываем» хуже, чем менее распространённый, но однозначный form-encoded body на DELETE.
- [Риск] `bin/server.dart create-admin` (decision 12), выполненная более одного раза до появления первого admin по ошибке оператора, либо отсутствие защиты от параллельного вызова в двух процессах → [Митигейшн] проверка «существует ли уже admin» выполняется в той же транзакции, что вставка — гонка исключена на уровне БД; повторный вызов после появления первого admin явно завершается ошибкой, а не тихо создаёт второго.
- [Риск] Периодический purge job (decision 14) может не успевать за темпом вставки при очень высокой нагрузке, временно превышая заявленную квоту retention → [Митигейшн] задокументировать как приемлемое eventual-enforcement поведение MVP (не hard real-time limit); частоту таймера сделать конфигурируемой, чтобы оператор мог ускорить при необходимости.
- [Риск] Батчинг/retry в `structured_log_http` может замаскировать постоянную недоступность сервера (записи копятся в памяти без верхнего предела) → [Митигейшн] верхний предел буфера в памяти с вытеснением самых старых записей при переполнении и логом события через `stderr`.
- [Риск] Рассинхрон между `timestamp` записи и `received_at` может путать при отладке инцидентов на нескольких устройствах → [Митигейшн] хранить оба поля явно, в query API дать сортировку/фильтрацию по обоим.
- [Риск] Интерфейс `IdentityProvider` (decision 17) спроектирован без реальной второй реализации — форма `VerifiedIdentity`/`EffectiveRole` может оказаться неудобной, когда появится настоящий Keycloak-адаптер (например, понадобятся дополнительные поля вроде `email`/`groups` из Keycloak-claims) → [Митигейшн] это осознанный риск любого «проектирования под будущее расширение» без немедленной второй реализации; интерфейс — публичный экспортируемый API пакета, а не приватная деталь, поэтому его придётся версионировать как breaking change при необходимости расширить, но это дешевле, чем не иметь точки расширения вовсе.
- [Риск] Немедленный отзыв прав через `token_version` (decision 10) гарантирован только для local-провайдера; если будущий Keycloak-адаптер выберет режим «доверять `roles` из токена напрямую» (decision 17), отзыв прав, выданных через наш `role_assignments`, для таких пользователей не будет мгновенным способом, который здесь спроектирован → [Митигейшн] задокументировано как явное ограничение расширения, а не этой change; конкретный Keycloak-адаптер сам решает этот компромисс (доверять claims vs резолвить из нашей БД) при реализации.
- [Риск] `structured_log_admin_client` не имеет общего Dart-кода с `structured_log_server` (decision 19) — контракт запросов/ответов может незаметно разойтись, если сервер изменится, а клиент не обновится синхронно → [Митигейшн] `integration_test.dart` клиента (или его сетевого слоя) гоняется против реального запущенного сервера в CI, а не только против моков — расхождение ловится тестом, а не в проде; конкретная реализация — задача `tasks.md`.
- [Риск] `flutter_secure_storage` (decision 20) на некоторых платформах (в частности Linux desktop) требует наличия системного keyring/secret-service, который не всегда установлен в headless/CI-окружении → [Митигейшн] задокументировать как известное ограничение; для CI (виджет-тесты) секьюр-сторидж не требуется — она нужна только в реальном рантайме приложения, юнит/виджет-тесты используют мок реализации хранилища токенов, а не реальный `flutter_secure_storage`.
- [Риск] Собственная реализация просмотра логов в admin-клиенте (decision 21) вместо переиспользования `LogViewerController` — дублирование части логики фильтрации/UI-паттернов с уже существующими viewer-пакетами → [Митигейшн] осознанный trade-off ради простоты сейчас (см. decision 21, «не абстрагировать раньше второго потребителя»); объём дублирования небольшой (admin-клиент фильтрует через query-параметры на сервере, а не клиентским кодом, как делает `LogViewerController`), так что дублируется в основном UI-разметка, не бизнес-логика.
- [Риск] Реструктуризация в `emb`/`backend`/`frontend`/`packages` (decision 23) двигает четыре уже опубликованные на pub.dev пакета (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) — ломает локальные клоны/IDE-конфигурацию контрибьюторов и пути в CI/`melos.yaml`/`AGENTS.md`, тот же класс риска, что и при первом переходе на монорепо → [Митигейшн] один атомарный коммит с `git mv` + синхронным обновлением `melos.yaml`/`.github/workflows/ci.yml`/`AGENTS.md`/README в том же PR, явно помечено **BREAKING** в `proposal.md`, по той же схеме, что и первая реструктуризация (`openspec/changes/add-structured-log-flutter`); сами опубликованные на pub.dev артефакты (версия, API) не затрагиваются — ломается только путь в репозитории.
- [Риск] `packages/` вводится пустой, без единого пакета внутри — риск того, что директория останется декларативным намерением без реального использования → [Митигейшн] это осознанно: категория резервируется под будущее, не создаётся искусственный пакет-заглушка ради заполнения; если она долго останется пустой, это сигнал пересмотреть, нужна ли она вообще — не проблема, которую нужно решать сейчас.
- [Риск] `POST /v1/auth/password-reset` (decision 24) без rate-limiting может использоваться для рассылки нежелательных писем на произвольный `email`, вписанный атакующим (получателю ничего не раскрывается, кроме факта письма от этого сервиса) → [Митигейшн] задокументировано как ограничение MVP; ограничение частоты по `email`/IP — будущая работа.
- [Риск] Обязательный `email` при самостоятельной регистрации (decision 24) добавляет трение по сравнению с более ранней ревизией (только `username`/пароль) → [Митигейшн] это прямое следствие требуемой цели «самостоятельное восстановление пароля» — без email на этом единственном пути она недостижима; путь без email остаётся доступен через создание пользователя администратором (`POST /v1/users`).
- [Риск] В отличие от `POST /v1/auth/password-reset` (сознательно не раскрывающего существование email), `POST /v1/auth/register` (decision 24) отвечает 409 на уже занятый `email` — раскрывает, что этот адрес зарегистрирован → [Митигейшн] принято осознанно: это стандартное и ожидаемое поведение формы регистрации (та же логика уже применяется к занятому `username`), не тот же сценарий атаки, что password-reset — там раскрывается чужой email, здесь пользователь проверяет свой собственный ввод.
- [Риск] Доставка письма восстановления зависит от корректной настройки SMTP оператором; `POST /v1/auth/password-reset` всегда отвечает 202 даже если письмо не удалось отправить (decision 24, анти-enumeration) → [Митигейшн] осознанный компромисс; сбои `EmailSender` логируются на сервере отдельно от HTTP-ответа, оператор мониторит их сам.
- [Риск] Единственный `admin` (или скомпрометированный `admin`-аккаунт) может заблокировать любого пользователя/проект без подтверждения второй стороной (decision 25) — потенциал для злоупотребления самой возможностью блокировки → [Митигейшн] осознанно принято как часть модели угроз этой change: `admin` — уже безусловно доверенная, самая привилегированная роль (полный доступ ко всему), блокировка не даёт ему никаких прав, которых у него не было бы и так; действие теперь попадает в аудит-лог (decision 26, `user.blocked`/`project.blocked`) — не предотвращает злоупотребление, но делает его прослеживаемым постфактум.
- [Риск] Заблокированный `owner`, у которого при этом остаются нетронутыми `RoleAssignment` на группу, не может быть заблокирован на уровне группы одним действием (только поштучно как пользователь + каждый его проект) — при инциденте с недобросовестным owner'ом администратору придётся заблокировать сам аккаунт пользователя (что уже останавливает его собственный доступ) и, отдельно, каждый проект группы, который нужно остановить → [Митигейшн] заблокированный пользователь уже не может аутентифицироваться и, соответственно, не может сам вредить дальше через API — блокировка конкретных проектов нужна отдельно только если требуется остановить приток данных, которые могут поступать не только от этого человека (например, по секретным ключам, которые он ранее выдал другим). Групповая блокировка одним действием — явный Non-Goal (см. Non-Goals), можно добавить позже, если понадобится.
- [Риск] `audit_log_entries` (decision 26) растёт неограниченно — без retention/квоты, в отличие от `log_entries` → [Митигейшн] осознанный Non-Goal этой доработки: объём административных мутаций на порядки меньше объёма пользовательских логов, так что срочность retention для аудита ниже; путь апгрейда (ручная очистка оператором/будущая политика хранения) не заблокирован текущей схемой (нет ничего, что помешало бы добавить `retention_days`-подобное поле позже).
- [Риск] Закрытый список `action` в decision 26 требует ручной дисциплины — каждая новая мутирующая management-операция, добавленная в будущем, должна не забыть записать соответствующую аудит-запись; пропуск не ловится автоматически (нет теста, требующего 1:1 соответствия эндпоинтов и `action`) → [Митигейшн] `openspec-verify-change` (задача 16.3/финализация) явно сверяет каждое мутирующее требование спецификаций с наличием аудит-записи как часть штатной процедуры проверки соответствия кода и спек; это ловит пропуски при ревью этой change, но не защищает от регрессии в будущих изменениях за её пределами.
- [Риск] `GET /v1/audit-log` без права чтения для `owner` (только `admin`, decision 26) — owner не может провести собственное расследование по своей группе, не привлекая admin → [Митигейшн] осознанное сужение по прямому требованию пользователя («администратор должен иметь доступ»); owner-scoped видимость аудита — Non-Goal, возможная будущая работа.
- [Риск] Единственный `admin` может удалить собственный аккаунт (decision 27) без специальной защиты «последнего администратора», оставив систему без активного `admin` → [Митигейшн] `create-admin` (decision 12) пересмотрен так, чтобы проверять именно наличие активного, неудалённого `admin` — оператор всегда может восстановить доступ той же bootstrap-командой, которой создавал первого администратора.
- [Риск] Освобождение `username`/`email` удалённого аккаунта для повторной регистрации (decision 27) означает, что новый человек может зарегистрироваться под именем/почтой, ранее принадлежавшими кому-то другому — возможна путаница при чтении старых `audit_log_entries`/старых `RoleAssignment`, всё ещё ссылающихся на прежнего владельца этого `user_id`, если полагаться на отображаемые `username`/`email`, а не на `user_id` → [Митигейшн] все внутренние ссылки (`role_assignments.subject_id`, `audit_log_entries.actor_user_id`/`target_id`) используют неизменяемый `id`, а не `username`/`email` — переиспользование имени не путает саму систему, только потенциально человека, читающего историю задним числом; явный, принимаемый компромисс.
- [Риск] Отсутствие каскадной очистки `role_assignments`/`team_members`/владения проектами удалённого пользователя (decision 27) оставляет «висящие» ссылки на неактивную учётную запись → [Митигейшн] осознанный Non-Goal; эти ссылки безвредны (удалённый пользователь не может аутентифицироваться и воспользоваться ими), а автоматическое переназначение владения — гораздо более сложная задача (кому переназначить?), не решаемая этой доработкой.

## Migration Plan

1. Реструктуризация репозитория (decision 23): `git mv` четырёх существующих пакетов в `emb/` (`structured_log`, `structured_log_flutter`, `structured_log_material` + `example/`, `structured_log_fluent` + `example/`) одним коммитом; создание `backend/`, `frontend/`, `packages/` (последняя — пустая, без записи в `melos.yaml`, пока пуста); обновление путей в `melos.yaml`, `.github/workflows/ci.yml`, `AGENTS.md`, корневых README. `dart run melos bootstrap`/`analyze`/`test` — подтвердить, что перенос не сломал существующие пакеты.
2. Скаффолдинг `backend/structured_log_server/` (зависимости `drift`, `sqlite3`, `shelf`, `shelf_router`, `dart_jsonwebtoken`, `bcrypt`; dev-зависимости `drift_dev`, `build_runner`) и `emb/structured_log_http/` + добавление обоих путей в `melos.yaml`/CI.
3. Storage-слой: мультитенантная схема (`users`/`groups`/`teams`/`team_members`/`projects`/`project_secret_keys`/`role_assignments`/`project_usage`/`log_entries` с `project_id`) как drift `Table`-классы, миграция при старте, юнит-тесты.
4. `log-server-auth`: интерфейс `IdentityProvider`/`VerifiedIdentity`/`EffectiveRole` (decision 17); `LocalIdentityProvider` — его реализация, инкапсулирующая всё, что было ранее спроектировано под decisions 10/16 (хэширование паролей/ключей/refresh-токенов, `POST /v1/auth/register`, резолвинг эффективных ролей в claims `roles` при выдаче/обновлении токена, `POST /v1/auth/token`, `DELETE /v1/auth/token`, `token_version`-проверка — всё это теперь за интерфейсом, не напрямую); аутентификация секретным ключом проекта для приёма (отдельный путь, не через `IdentityProvider`).
5. `log-server-rbac`: правила выдачи ролей из decision 7, каскадное обновление `token_version` при изменении `RoleAssignment`/членства в командах (внутренняя часть `LocalIdentityProvider`), middleware авторизации для management-эндпоинтов, читающее `VerifiedIdentity.roles` — если `null`, резолвящее из `role_assignments`/`team_members` (fallback-путь, требуемый интерфейсом для провайдеров без собственных ролей).
6. Management API: `User`/`Group`/`Team`/`Project`/`ProjectSecretKey`/`RoleAssignment` CRUD-эндпоинты по правилам RBAC.
7. `log-server-quotas`: `ProjectUsage`, enforcement на приёме (`max_entries`/`max_bytes`), периodic purge job по `retention_days`.
8. HTTP-слой логов: `POST /v1/logs` (секретный ключ), `GET /v1/logs` (JWT + проверка области видимости), `GET /healthz`.
9. `bin/server.dart`: обычный запуск сервера + отдельная `create-admin` команда (decision 12), graceful shutdown.
10. `emb/structured_log_http`: `HttpLogOutput` (аутентификация секретным ключом проекта, батчинг, retry/backoff, `flushed`).
11. `integration_test.dart` — сквозной сценарий: bootstrap admin → создание группы/проекта/секретного ключа → приём логов по ключу → самостоятельная регистрация пользователя (при включённом `registrationEnabled`) → выдача роли `user` на проект → создание токена → query с проверкой RBAC (доступ разрешён/запрещён) → refresh → `DELETE /v1/auth/token` → повторное использование отозванного refresh-токена отклоняется.
12. Скаффолдинг `frontend/structured_log_admin_client/` (Flutter, зависимости `dio`, `flutter_secure_storage`) + добавление в `melos.yaml`/матрицу `flutter`-job'а CI.
13. Admin-клиент — слой доступа к API (`ApiClient` на `dio`: interceptor'ы подстановки токена и авто-`refresh` на 401) и экраны аутентификации (логин/регистрация/logout, secure storage токенов).
14. Admin-клиент — экраны управления ресурсами: пользователи/группы (admin), команды и состав (owner/admin), проекты с квотой и использованием (decision 22), секретные ключи (создание с одноразовым показом/список/отзыв), выдача/отзыв ролей.
15. Admin-клиент — экран просмотра/поиска логов: выбор области, фильтры, пагинация курсором, детальный просмотр записи.
16. Документация, CI, `openspec-verify-change`.
17. Восстановление пароля (decision 24): `User.email` (`nullable` в схеме, обязательное поле именно на `POST /v1/auth/register`) + таблица `password_reset_tokens`; интерфейс `EmailSender`/референс-реализация `SmtpEmailSender` (`package:mailer`) + SMTP-поля `ServerConfig`; `POST /v1/auth/password-reset` и `POST /v1/auth/password-reset/confirm` на сервере (переиспользует инкремент `token_version` из decision 10); в admin-клиенте — экран «Забыли пароль?» (запрос по email) и экран установки нового пароля (ввод токена вручную или из query-параметра ссылки в web-сборке).
18. Блокировка пользователей/проектов (decision 25): `Project.is_blocked`; `POST /v1/users/:id/block`/`unblock` и `POST /v1/projects/:id/block`/`unblock` (`admin` only); `grant_type=refresh_token` дополнительно проверяет `is_active` пользователя; отзыв всех refresh-токенов при блокировке пользователя; enforcement `is_blocked` на `POST /v1/logs`/`GET /v1/logs` (жёсткий отказ по `project_id`, молчаливое исключение по `group_id`); в admin-клиенте — действия блокировки/разблокировки на экранах пользователя и проекта.
19. Аудит (decision 26): таблица `audit_log_entries`; запись аудит-записи в той же транзакции, что и каждая из мутирующих операций разделов 6/7 (users/groups/teams/projects/secret-keys/role-assignments), блокировки (18) и подтверждения восстановления пароля (17); `GET /v1/audit-log` (`admin` only, фильтры, keyset-пагинация); в admin-клиенте — экран просмотра аудит-лога с теми же фильтрами.
20. Самоудаление аккаунта (decision 27): `User.deleted_at`; частичные unique-индексы `username`/`email` на `deleted_at IS NULL`; `DELETE /v1/users/me` (подтверждение паролем, переиспользует отзыв refresh-токенов/инкремент `token_version` из decision 25); `POST /v1/users/:id/unblock` отклоняет удалённых пользователей; `create-admin` (decision 12) проверяет наличие активного, неудалённого admin; в admin-клиенте — действие удаления аккаунта в настройках, с подтверждением и вводом пароля.
21. Откат: `structured_log_server`/`structured_log_http`/`structured_log_admin_client` — новые пакеты, не публикуются в рамках этой change, откат сводится к `git revert`. Реструктуризация (шаг 1) — тоже `git revert` того же атомарного коммита; т.к. переносятся директории, а не переиздаются пакеты на pub.dev, откат не затрагивает уже опубликованные версии.

## Open Questions

- Публиковать ли `structured_log_server`/`structured_log_http` на pub.dev по готовности — решение мейнтейнера, как и для предыдущих пакетов.
- Значение `retention_days` по умолчанию при создании проекта, если явно не указано владельцем (обязательное поле, но нужен разумный дефолт для API-эргономики) — уточнить в `specs/log-server-quotas` или оставить обязательным без дефолта.
- Нужна ли в этом MVP возможность у `owner` временно понижать/повышать `max_entries`/`max_bytes` без пересоздания секретных ключей — предполагается да (обычный `PATCH /v1/projects/:id`), явно зафиксировать в `specs/log-server-quotas`.
- Когда появится реальный Keycloak-адаптер: отдельный пакет (`structured_log_server_keycloak`?) или часть `structured_log_server`; нужен ли CLI/env для выбора провайдера, или передача `IdentityProvider` остаётся программной (только через Dart API) — решение мейнтейнера в будущей change, не в этой.
- Публиковать ли `structured_log_admin_client` на pub.dev — вероятно нет (это конечное приложение, не переиспользуемый пакет), но по аналогии с остальными пакетами `publish_to: none` вместо жёсткого исключения — решение мейнтейнера.
- Нужен ли `structured_log_admin_client` как web-приложение в первую очередь (по аналогии с `structured_log_material_example`/`structured_log_fluent_example`, оба поддерживают web) или сразу многоплатформенно (desktop) — не влияет на архитектуру, влияет только на то, какие платформы `flutter create --platforms=...` подключить в `tasks.md`.
- Провайдер email по умолчанию (SMTP через `package:mailer`, decision 24) или сразу поддержать транзакционного провайдера (SendGrid/SES/Postmark и т.п. через отдельную реализацию `EmailSender`) — решение мейнтейнера, интерфейс `EmailSender` этот выбор не блокирует.
- Срок жизни токена восстановления пароля (decision 24 предполагает ~30 минут как отправную точку) — уточнить в `specs/log-server-password-reset` или оставить конфигурируемым без жёсткого дефолта.
- Нужна ли owner-scoped видимость аудита (owner видит записи только по своей группе) в будущей доработке, или аудит так и останется исключительно admin-only — решение мейнтейнера (см. Non-Goals/Risks decision 26).
- Retention/архивация `audit_log_entries`, когда объём станет ощутимым — решение мейнтейнера в будущей доработке, не в этой (см. Risks).
- Нужен ли когда-либо принудительное удаление чужого аккаунта администратором (в дополнение к самостоятельному удалению из decision 27) — решение мейнтейнера в будущей доработке, не в этой.
