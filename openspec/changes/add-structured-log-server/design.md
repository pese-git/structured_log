## Context

Сейчас в воркспейсе (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) нет ни одного способа доставить лог за пределы процесса, кроме локального файла — `OutputFunction`/`LogSink` (`structured_log/lib/src/processors.dart:58`, `structured_log/lib/src/sink.dart`) уже задают чистый контракт «функция, принимающая запись», но ни одна встроенная реализация не отправляет данные по сети. Единственный существующий образец неблокирующего output — `AsyncFileOutput`/`_SerializedAsyncOutput` (`structured_log/lib/src/async_file_output.dart`): сериализованная через `Future` очередь, `catchError` на каждом шаге (чтобы одна неудача не остановила следующие записи), публичный `Future<void> get flushed`. Этот паттерн — прямой прототип для будущего HTTP-sender'а.

Все 4 существующих пакета — плоская раскладка, без единого codegen-инструмента во всём монорепо, тестирование через голый `dart test`/`flutter test`. У проекта уже есть явно зафиксированный принцип «никакой магии» (`openspec/changes/add-structured-log-flutter/design.md`, decision №4) — отказ от авто-регистрирующих вызовов в пользу явного подключения синков.

## Goals / Non-Goals

**Goals:**
- Дать способ централизованно собирать структурированные логи с нескольких инстансов/устройств в одном self-hosted сервисе, без стороннего SaaS и без тяжёлой инфраструктуры (ELK и т.п.).
- Сохранить нулевые runtime-зависимости `structured_log` — новый сетевой функционал живёт в отдельных пакетах, ядро не трогается.
- Дать программный и HTTP-контракт, по форме зеркалящий существующую запись лога (`event`/`level`/`timestamp`/`category`/`logger`/поля корреляции/произвольный `context`), не изобретая параллельную модель данных.
- Довести MVP до состояния «можно реально использовать для отладки»: приём, устойчивое хранение, фильтрация/поиск по сети через curl или собственный клиент.

**Non-Goals:**
- Server-rendered HTML/веб-UI для просмотра логов. В репозитории уже есть два production-ready Flutter-виджета просмотра (`structured_log_material`, `structured_log_fluent`) поверх headless `LogViewerController` — обучение их брать данные с этого сервера как источника (вместо/в дополнение к локальному `LogBuffer`) — отдельный будущий change, не эта.
- FTS5 или любой другой полнотекстовый индекс — на MVP полнотекстовый поиск через `LIKE`.
- Многопоточное/много-isolate масштабирование сервера, шардирование, кластеризация.
- Поддержка Windows в CI нового job'а на старте (см. Risks).
- Публикация `structured_log_server`/`structured_log_http` на pub.dev в рамках этой change — решение о публикации, как и для предыдущих пакетов, за мейнтейнером после обкатки.

## Decisions

1. **HTTP-фреймворк: `shelf` + `shelf_router`, не `dart_frog`.**
   Альтернатива — `dart_frog`. Отклонено: `dart_frog create` навязывает собственный скелет (`routes/` file-based routing, `dart_frog.yaml`, генерируемый `.dart_frog_gen/`) и свой CLI как основной воркфлоу — расходится с тем, как устроены все 4 существующих пакета (плоская раскладка `lib/src/*.dart`, никакого codegen во всём монорепо). shelf устроен как явная сборка `Handler`/`Middleware`/`Pipeline` в коде — соответствует принципу «никакой магии», уже зафиксированному для этого репозитория. dart_frog внутри и так построен на shelf, так что принципиальных возможностей не теряем — только удобный scaffolding, который для API из 3–4 маршрутов не окупает разницу в структуре проекта.

2. **Хранилище: `package:sqlite3` напрямую (raw SQL), без ORM/кодогенерации (не `drift`).**
   Альтернатива — `drift`. Отклонено: тянет `build_runner`-кодогенерацию — это был бы первый codegen-инструмент во всём монорепо, разрыв конвенции без веской причины. `sqlite3` — embedded, self-hosted (просто файл на диске, без внешней инфраструктуры), даёт прямой доступ к JSON1 (`json_extract`) для фильтрации по произвольным полям `context`, которые не имеют фиксированной схемы — с ORM это было бы менее прозрачно.
   Альтернатива — простой append-only JSON-lines файл + линейный скан. Отклонено: не даёт приемлемой производительности поиска/фильтрации уже при умеренном объёме логов, а MVP явно требует query API, а не только приём.

3. **Схема `log_entries`: типизированные колонки под частые фильтры + `context_json` как source of truth.**
   Колонки: `id` (PK автоинкремент, keyset-пагинация), `received_at` (когда сервер принял запись — отдельно от клиентского `timestamp`, чтобы не терять порядок при рассинхроне часов/задержках доставки), `timestamp`, `level`, `event`, `category`, `logger`, `session_id`, `request_id`, `connection_generation`, `tool_call_id`, `message_id`, `operation_id` (все поля корреляции из `LogCorrelation.toContext()`, `structured_log/lib/src/correlation.dart`), `context_json` (вся исходная запись целиком). Индексы: `level`, `timestamp`, `category`, `session_id`, `request_id`, составной `(level, timestamp)`.
   Альтернатива — хранить только `context_json`, фильтровать всё через `json_extract` без выделенных колонок. Отклонено: типизированные колонки с индексами нужны именно для самых частых фильтров (уровень, диапазон времени, correlation id) — JSON1-фильтрация остаётся, но только для непредсказуемых пользовательских ключей `context.*`.

4. **Полнотекстовый поиск на MVP — `LIKE '%term%'` по `event`/`context_json`, не FTS5.**
   Альтернатива — виртуальная таблица SQLite FTS5, синхронизируемая при вставке. Отклонено сейчас: усложняет схему и путь миграции ради функциональности, которая не входит в объём MVP, согласованный с пользователем (базовый поиск, не полноценный free-text engine). Явный путь апгрейда на будущее, не реализуется в этой change.

5. **Параллелизм: один `Database`-хэндл, `PRAGMA journal_mode=WAL`, без явного шардирования по isolate.**
   shelf по умолчанию обслуживает запросы в одном isolate — единственный хэндл к sqlite3 безопасен без дополнительной синхронизации при таком запуске. Alternative — пул isolate-воркеров с общим доступом к БД. Отклонено: ненужная сложность для объёма MVP; явный non-goal, см. Non-Goals.

6. **Клиентский sender — отдельный пакет `structured_log_http`, не расширение core `structured_log` и не часть `structured_log_server`.**
   Технически `dart:io`-`HttpClient` не нарушил бы нулевую runtime-зависимость core (уже используется в `logger.dart`/`async_file_output.dart`). Тем не менее отклонено класть `HttpLogOutput` в `structured_log`: wire-контракт (эндпоинт, форма батча, auth) эволюционирует вместе с сервером, а не с ядром логирования — привязывать к этому независимо версионируемый core-пакет (уже опубликован на pub.dev) означало бы синхронизировать его релизный цикл с ещё не стабилизированным API сервиса. Тот же довод, по которому viewer-функциональность вынесена в отдельные пакеты, а не встроена в core.
   Также отклонено класть sender в `structured_log_server`: клиентскому Dart/Flutter-приложению, которому нужно только отправлять логи (в т.ч. на мобильных/web-таргетах), не должны быть нужны серверные зависимости (`shelf`, `shelf_router`, `sqlite3`).
   Итог: `structured_log_http` — чистый Dart-пакет, единственная зависимость — `structured_log`; `HttpLogOutput` реализован по паттерну `_SerializedAsyncOutput`/`AsyncFileOutput` (сериализованная очередь, `catchError` на шаг, `flushed`), плюс батчинг (по размеру/таймеру) и retry с backoff на сетевых ошибках/5xx — явно не на 4xx (чтобы не зациклиться на неверном API-ключе или отклонённом батче).

7. **Аутентификация: статический Bearer/API-key, конфигурируемый на старте сервера (env/аргумент), без пользовательской модели/сессий.**
   Альтернатива — полноценная система пользователей/токенов с ротацией. Отклонено для MVP: единственный сценарий использования — доверенный набор приложений/сервисов, а не многопользовательская публичная площадка; усложнение не оправдано объёмом, согласованным с пользователем.

8. **CI: отдельный новый job в существующем [.github/workflows/ci.yml](.github/workflows/ci.yml), не расширение текущего `test`-job.**
   Текущий `test`-job жёстко привязан к `working-directory: structured_log` (не матрица по пакетам), в отличие от `flutter`-job'а. Расширять его до матрицы задело бы существующую, проверенную конфигурацию ради двух новых пакетов с другим профилем рисков (нативная зависимость sqlite3). Новый job матрицей по пакету (`structured_log_server`, `structured_log_http`) через `dart-lang/setup-dart`, стартуя с `ubuntu-latest` — см. Risks.

## Risks / Trade-offs

- [Риск] `package:sqlite3` требует нативную библиотеку через `dlopen`; поведение на Windows-раннерах исторически менее предсказуемо → [Митигейшн] новый CI job стартует только с `ubuntu-latest` (по аналогии с тем, как Flutter-job уже ограничен одной ОС в этом репозитории), Windows добавляется отдельно после проверки на реальном раннере.
- [Риск] Один `Database`-хэндл в одном isolate — потолок пропускной способности при большом числе одновременных писателей → [Митигейшн] явный non-goal для MVP (см. Non-Goals), задокументировать предел и путь апгрейда (пул воркеров/шардирование) как открытый вопрос на будущее.
- [Риск] `LIKE`-поиск по `context_json` деградирует по производительности с ростом таблицы (full scan без индекса) → [Митигейшн] задокументировать как явное ограничение MVP в README/dartdoc; путь апгрейда — FTS5, зафиксирован здесь, не реализуется сейчас.
- [Риск] Статический API-key в конфиге сервера — при компрометации ключа нет встроенной ротации/отзыва без рестарта → [Митигейшн] задокументировать как MVP-ограничение; поддержка нескольких одновременно активных ключей (для ротации без даунтайма) — заложить в `ServerConfig` как список, а не единственное значение, чтобы не потребовалось breaking change позже.
- [Риск] Батчинг/retry в `structured_log_http` может замаскировать постоянную недоступность сервера (записи копятся в памяти без верхнего предела) → [Митигейшн] явный верхний предел буфера в памяти с политикой сброса самых старых записей при переполнении (аналогично кольцевому буферу `LogBuffer` в `structured_log_flutter`) и лог этого события через `stderr`, как это уже делает `_SerializedAsyncOutput` при ошибках записи.
- [Риск] Рассинхрон между `timestamp` записи (клиентские часы) и `received_at` (серверные часы) может путать при отладке инцидентов на нескольких устройствах → [Митигейшн] хранить оба поля явно (decision 3), в query API дать возможность сортировать/фильтровать по обоим.

## Migration Plan

1. Скаффолдинг `structured_log_server/` и `structured_log_http/` (pubspec, barrel-файлы) + правки `melos.yaml`/`.github/workflows/ci.yml` — пустые пакеты, проходящие `dart analyze`/CI.
2. Storage-слой `structured_log_server`: `LogStore`-интерфейс, `SqliteLogStore` (схема, индексы, миграция при старте, WAL), юнит-тесты.
3. HTTP-слой `structured_log_server`: auth middleware, `POST /v1/logs`, `GET /v1/logs`, `GET /healthz`, сборка `server.dart` + `bin/server.dart` (CLI, graceful shutdown), юнит-тесты хендлеров.
4. `structured_log_http`: `HttpLogOutput` (батчинг, retry/backoff, `flushed`) — wire-контракт уточняется совместно с шагом 3, юнит-тесты на сервере порта 0.
5. `integration_test.dart` в `structured_log_server` — сквозная проверка ingest → storage → query на реальном `HttpServer`.
6. Документация: `AGENTS.md` (разделы «Структура»/«CI»), корневые README, `example/` в обоих пакетах.
7. Откат: оба пакета новые и не публикуются в рамках этой change — откат сводится к `git revert` соответствующих коммитов; риска для уже опубликованных пакетов (`structured_log` и три Flutter-пакета) нет, т.к. они не изменяются.

## Open Questions

- Публиковать ли `structured_log_server`/`structured_log_http` на pub.dev по готовности кода, или сначала обкатать в репозитории отдельным циклом — решение мейнтейнера, как и для предыдущих пакетов.
- Нужна ли в этом MVP поддержка нескольких одновременно активных API-ключей (ротация без даунтайма) сразу, или список из одного элемента достаточно на старте (см. Risks, decision 7) — уточнить перед `tasks.md`.
- Формат пагинации query API (`GET /v1/logs`) — курсор по `id` (keyset) или `limit`/`offset`; keyset предпочтительнее для append-only таблицы, но стоит явно зафиксировать в `specs/log-server-api`.
