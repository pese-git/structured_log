## Context

Сейчас в воркспейсе (`structured_log`, `structured_log_flutter`, `structured_log_material`, `structured_log_fluent`) нет ни одного способа доставить лог за пределы процесса, кроме локального файла — `OutputFunction`/`LogSink` (`structured_log/lib/src/processors.dart:58`, `structured_log/lib/src/sink.dart`) уже задают чистый контракт «функция, принимающая запись», но ни одна встроенная реализация не отправляет данные по сети. Единственный существующий образец неблокирующего output — `AsyncFileOutput`/`_SerializedAsyncOutput` (`structured_log/lib/src/async_file_output.dart`): сериализованная через `Future` очередь, `catchError` на каждом шаге, публичный `Future<void> get flushed`. Этот паттерн — прямой прототип для будущего HTTP-sender'а.

Все 4 существующих пакета — плоская раскладка, без единого codegen-инструмента во всём монорепо. У проекта уже есть явно зафиксированный принцип «никакой магии» (`openspec/changes/add-structured-log-flutter/design.md`, decision №4). Хранилище `structured_log_server` — первый пакет воркспейса, сознательно вводящий codegen (`drift`/`build_runner`) — решение принято по прямому указанию пользователя, ограничено этим одним пакетом.

Требование пользователя расширило объём с одного доверенного приёмника логов до полноценного мультитенантного сервиса: несколько пользователей, объединённых в группы и команды, с разграничением доступа к проектам и лимитами на объём хранимой истории. Это меняет модель аутентификации приёма логов (больше не плоский список серверных API-ключей — теперь секретный ключ привязан к конкретному проекту) и добавляет management/query API, требующий аутентификации людей (JWT), а не приложений.

## Goals / Non-Goals

**Goals:**
- Дать способ централизованно собирать структурированные логи с нескольких проектов/команд в одном self-hosted сервисе, без стороннего SaaS.
- Разграничить доступ так, чтобы приложение, отправляющее логи, не имело доступа ни к чему, кроме приёма в свой проект, а человек, читающий логи, видел только то, что ему разрешено.
- Не дать одному проекту исчерпать общее хранилище — квота на историю обязательна для каждого проекта, а не опциональна.
- Сохранить нулевые runtime-зависимости `structured_log` — новый функционал живёт в отдельных пакетах, ядро не трогается.
- Дать программный и HTTP-контракт, по форме зеркалящий существующую запись лога (`event`/`level`/`timestamp`/`category`/`logger`/поля корреляции/произвольный `context`), не изобретая параллельную модель данных для самой записи.

**Non-Goals:**
- Server-rendered HTML/веб-UI — чистый JSON API; интеграция Flutter-виджетов просмотра — отдельный будущий change.
- FTS5-поиск — на MVP `LIKE`.
- Многопоточное/много-isolate масштабирование сервера; Windows в CI на старте.
- Self-service регистрация пользователей, сброс пароля по email, SSO/MFA — пользователей создаёт только `admin` через management API.
- Refresh-токены/ротация JWT-сессий — один access-токен с ограниченным сроком жизни, повторный логин после истечения.
- Аудит-лог изменений прав доступа (кто кому что выдал/отозвал и когда) — только сам факт текущего состояния `RoleAssignment`.
- Алерты/уведомления о приближении к квоте — только жёсткий отказ при превышении.
- Кросс-групповые команды — `Team` принадлежит ровно одной `Group`; пользователь может состоять в нескольких командах разных групп по отдельности.
- Ротация серверного JWT-signing-secret без даунтайма (один текущий секрет из конфигурации; см. Risks).
- Публикация `structured_log_server`/`structured_log_http` на pub.dev в рамках этой change.

## Decisions

1. **HTTP-фреймворк: `shelf` + `shelf_router`, не `dart_frog`.**
   Альтернатива — `dart_frog`. Отклонено: `dart_frog create` навязывает собственный скелет и CLI как основной воркфлоу — расходится с плоской раскладкой и отсутствием codegen во всех остальных пакетах монорепо. shelf соответствует принципу «никакой магии»; dart_frog внутри и так построен на shelf.

2. **Хранилище: `drift` поверх SQLite (`NativeDatabase`, embedded, файл на диске).**
   Решение принято по прямому указанию пользователя, пересматривая изначальный вариант raw `package:sqlite3` (отклонён именно чтобы не заводить в монорепо первый codegen-инструмент). `drift` даёт типобезопасные, проверяемые на этапе компиляции запросы и миграции схемы «из коробки» (`Migrator`, `onUpgrade`), что для сервиса с растущей мультитенантной схемой (7 таблиц, см. decision 6) перевешивает цену `build_runner`. Trade-off явно принимается (см. Risks): `build_runner` — dev-зависимость только `structured_log_server`, `*.g.dart` не коммитится.

3. **Полнотекстовый поиск на MVP — `LIKE '%term%'` через `customSelect`, не FTS5.**
   Отклонено заводить FTS5 сейчас: усложняет схему и путь миграции ради функциональности вне согласованного MVP. `LIKE`/`json_extract`-условия, не выразимые типизированным query-builder'ом drift, пишутся как сырые SQL-фрагменты через `customSelect`/`customStatement`.

4. **Параллелизм: один `QueryExecutor` drift (`NativeDatabase`), `PRAGMA journal_mode=WAL`, без явного шардирования по isolate.**
   shelf по умолчанию обслуживает запросы в одном isolate — единственный хэндл к базе безопасен без дополнительной синхронизации. Явный non-goal — пул воркеров/шардирование, пересмотреть при упоре в throughput.

5. **Клиентский sender — отдельный пакет `structured_log_http`, не расширение core `structured_log` и не часть `structured_log_server`.**
   Wire-контракт (эндпоинт, форма батча, auth) эволюционирует вместе с сервером, а не с ядром логирования — привязывать к этому независимо версионируемый, уже опубликованный core-пакет не стоит. Класть в `structured_log_server` тоже нельзя: клиентскому приложению не нужны серверные зависимости (`shelf`, `drift`, `dart_jsonwebtoken` и т.п.). `structured_log_http` — чистый Dart, единственная зависимость `structured_log`; `HttpLogOutput` по паттерну `_SerializedAsyncOutput`/`AsyncFileOutput`, плюс батчинг и retry с backoff на сетевых ошибках/5xx (не на 4xx).

6. **Модель мультитенантности: `User` / `Group` / `Team` / `Project` / `ProjectSecretKey` / `RoleAssignment`.**
   - `Group` владеет `Project`-ами (`group_id` на `Project`, NOT NULL — проект не может существовать вне группы).
   - `Team` — набор `User` внутри ровно одной `Group` (`team_id`/`group_id`), только для массовой выдачи прав нескольким пользователям сразу; создаётся `owner`-ом группы или `admin`. Отдельная сущность от `Group`, по прямому уточнению пользователя, а не переиспользование `Group` как «группы пользователей» — иначе одна и та же сущность одновременно и владела бы проектами, и была бы получателем прав, что смешивает два разных понятия и не позволило бы владельцу группы держать несколько независимых команд с разным набором прав внутри одной группы.
   - `RoleAssignment(subject_type: user|team, subject_id, role: admin|owner|user, scope_type: global|group|project, scope_id)` — единая таблица выдачи прав; `subject_type: team` разворачивается в проверке доступа через текущее членство пользователя в команде (см. decision 7), а не копируется в отдельные записи на каждого участника — так добавление/удаление участника команды меняет его эффективные права немедленно, без синхронизации дублирующихся `RoleAssignment`.
   - Альтернатива — хранить роль как одно enum-поле прямо на `User`/на паре `(user, group)`. Отклонено: не выражает произвольную комбинацию «эта команда — `user` на этом проекте, этот человек лично — `owner` той же группы», которая явно требуется постановкой.

7. **Правила выдачи ролей: кто кому какую роль может назначить.**
   - `admin` — может создать `RoleAssignment` с любой ролью на любой области видимости, для любого `User`/`Team`. Только `admin` создаёт новые `Group` и новых `User`.
   - `owner` (на группу `G`, т.е. есть `RoleAssignment(role: owner, scope: group:G)`, прямой или через команду) — может создавать/удалять `Project`/`Team` внутри `G`, менять квоты и ротировать секретные ключи проектов `G`, и создавать `RoleAssignment` с ролью `owner` или `user` на область `group:G` или `project:P` (где `P ∈ G`), для любого `User` или `Team` внутри `G`. Не может выдать роль `admin` — это зарезервированная за существующими `admin` роль, не привязанная ни к одной группе.
   - `user` — не может создавать `RoleAssignment` ни для кого (нет делегирования); имеет только доступ на чтение/поиск логов в рамках выданной ему области видимости.
   - Альтернатива — дать `owner` право выдавать `admin`. Отклонено: `admin` — глобальная суперпользовательская роль вне какой-либо группы, выдача её из контекста «владения одной группой» ломает изоляцию тенантов, которую вся эта модель призвана обеспечить.

8. **Проверка доступа при запросе (`GET /v1/logs`, management-эндпоинты): область видимости обязательна и явна в запросе, без «слияния» нескольких проектов по умолчанию.**
   `GET /v1/logs` обязан указывать ровно одну область — `project_id` или `group_id` — и сервер проверяет, что у вызывающего (напрямую или через членство в команде) есть `RoleAssignment` (`admin` глобально, либо `owner`/`user` с областью, покрывающей запрошенную: `global` покрывает всё, `group:G` покрывает `G` и все её проекты, `project:P` покрывает только `P`) для именно этой области; иначе 403. Запрос по `group_id` агрегирует логи всех проектов группы только если сам грант — на уровне `group`, а не является объединением нескольких отдельных `project`-грантов у вызывающего.
   Альтернатива — возвращать объединение логов всех доступных вызывающему проектов без явного `project_id`/`group_id`. Отклонено: неоднозначная семантика пагинации/курсора при слиянии нескольких таблиц-разделов, и молчаливое расширение того, что видит клиент, при выдаче ему новых прав — хуже для предсказуемости и аудита, чем явный параметр.

9. **Аутентификация приёма логов: секретный ключ, привязанный к проекту (не к серверу целиком).**
   `POST /v1/logs` аутентифицируется `Authorization: Bearer <project-secret-key>`; ключ однозначно резолвится в `project_id` через таблицу `ProjectSecretKey` (хранится как хэш, не plaintext — см. decision 11) — это заменяет более раннюю версию решения (плоский список серверных API-ключей, общий на весь сервер), которая была уместна только для однопроектного MVP до появления мультитенантности. У проекта может быть несколько одновременно активных ключей (ротация без даунтайма), каждый — с `label` и возможностью отзыва (`revoked_at`).

10. **Аутентификация management/query API: JWT, авторизация всегда пересчитывается из БД.**
    `POST /v1/auth/login` (email + пароль) → JWT (`dart_jsonwebtoken`, HS256, подписывающий секрет — конфигурация сервера), содержащий только идентификатор пользователя (`sub`) и срок действия — не список ролей. При каждом запросе сервер заново резолвит `RoleAssignment`/членство в командах по `sub` из валидного токена. Альтернатива — зашивать снапшот ролей в claims токена (быстрее, не требует запроса к БД на каждый вызов). Отклонено: список ролей пользователя может измениться (отозванный доступ, удалённый пользователь) быстрее, чем истечёт токен — а бизнес-требование именно про разграничение доступа не должно допускать окна, где отозванное право всё ещё действует до истечения токена.

11. **Хранение секретов: `bcrypt` для паролей пользователей, SHA-256 случайного токена для секретных ключей проектов — разные механизмы для разных угроз.**
    Пароль — низкоэнтропийный, выбираемый человеком секрет, для которого важна защита от офлайн-перебора по словарю — для этого нужен медленный, адаптивный алгоритм (`bcrypt`). Секретный ключ проекта — высокоэнтропийная случайная строка (генерируется сервером через `Random.secure()`, не запоминается человеком), для которой не требуется устойчивость к словарному перебору — медленный `bcrypt` был бы просто накладными расходами на каждый вызов `POST /v1/logs` (в отличие от логина, происходящего часто), а быстрый криптографический хэш (SHA-256) даёт то же свойство «в БД не хранится plaintext» без этой цены. Оба секрета показываются вызывающему только один раз, в момент создания.

12. **Bootstrap первого `admin`: явная CLI-команда, не автоматическое создание при первом запуске.**
    `bin/server.dart create-admin --email ... --password ...` (или аналогичный флаг), выполняемая оператором сервера отдельно от обычного `dart run bin/server.dart`; работает только если в БД ещё нет ни одного `admin` (защита от повторного использования как лазейки для повышения прав). Альтернатива — создавать admin автоматически при пустой БД по данным из переменных окружения при обычном старте сервера. Отклонено: неявное поведение при старте (риск случайно оставить сервер с дефолтными кредами, если оператор не подставил свои через env) хуже одной осознанной команды, которую оператор запускает сам.

13. **Квоты проекта: `retention_days` (обязательное поле) + опциональные `max_entries`/`max_bytes`, с отдельным счётчиком использования.**
    Каждый `Project` обязан иметь `retention_days`. `max_entries`/`max_bytes` — опциональны (`null` = без лимита по этому измерению), задаются владельцем/админом при создании/редактировании проекта. Текущее использование хранится не как `COUNT(*)`/`SUM(size)` по требованию (дорого на большой таблице), а как отдельная строка `ProjectUsage(project_id, entry_count, total_bytes)`, обновляемая атомарно в той же транзакции, что вставка батча и что периодическая очистка по retention — так проверка квоты на приёме — это дешёвый point-lookup, а не агрегирующий запрос по всей таблице записей проекта.

14. **Enforcement квоты: retention — периodic purge job; entries/bytes — отказ конкретным записям батча при приёме.**
    Отдельный периодический таймер (например, раз в час) внутри процесса сервера удаляет записи `log_entries` старше `retention_days` каждого проекта и уменьшает соответствующий `ProjectUsage`. Проверка `max_entries`/`max_bytes` происходит на приёме (`POST /v1/logs`): если добавление записи из батча превысило бы лимит проекта, эта конкретная запись отклоняется (той же схемой частичного приёма батча, что и валидационные ошибки, — не весь батч целиком), с кодом ошибки `quota_exceeded` и HTTP `507 Insufficient Storage` (единственный статус из стандарта, чья семантика буквально «сервер не может сохранить представление [из-за нехватки места]» — точнее подходит, чем `413`, зарезервированный в этом API за превышением размера самого HTTP-тела).

15. **CI: отдельный новый job в существующем [.github/workflows/ci.yml](.github/workflows/ci.yml), не расширение текущего `test`-job.**
    Текущий `test`-job жёстко привязан к `working-directory: structured_log` (не матрица), в отличие от `flutter`-job'а. Новый job матрицей по пакету (`structured_log_server`, `structured_log_http`) через `dart-lang/setup-dart`, стартуя с `ubuntu-latest`, с шагом `dart run build_runner build` перед `analyze`/`test` для `structured_log_server`.

## Risks / Trade-offs

- [Риск] `drift` использует `package:sqlite3` под капотом (нативная библиотека через `dlopen`); поведение на Windows-раннерах исторически менее предсказуемо → [Митигейшн] новый CI job стартует только с `ubuntu-latest`, Windows добавляется отдельно после проверки на реальном раннере.
- [Риск] `drift`/`drift_dev`/`build_runner` — первый codegen-инструмент в монорепо → [Митигейшн] ограничен пакетом `structured_log_server`; `*.g.dart` не коммитится, CI выполняет `dart run build_runner build --delete-conflicting-outputs` перед `analyze`/`test`.
- [Риск] Один `QueryExecutor` в одном isolate — потолок пропускной способности при большом числе одновременных писателей → [Митигейшн] явный non-goal для MVP; путь апгрейда (`NativeDatabase.createInBackground`, шардирование) как открытый вопрос на будущее.
- [Риск] `LIKE`-поиск по `context_json` деградирует по производительности с ростом таблицы → [Митигейшн] задокументировать как ограничение MVP; путь апгрейда — FTS5, не реализуется сейчас.
- [Риск] Авторизация пересчитывается из БД на каждый запрос (decision 10) — дополнительная нагрузка на БД на каждый вызов management/query API по сравнению с ролями внутри JWT → [Митигейшн] это чтение по индексированному `user_id`/`team_id`, дешёвое по сравнению с самим query по `log_entries`; принимается ради немедленного действия отозванных прав.
- [Риск] Один JWT-signing-secret без встроенной ротации без даунтайма (decision 10, в отличие от секретных ключей проектов, где ротация заложена явно) → [Митигейшн] задокументировано как MVP-ограничение (см. Non-Goals); смена секрета инвалидирует все текущие сессии одновременно — приемлемо для внутреннего инструмента, эксплуатируемого редко.
- [Риск] `bin/server.dart create-admin` (decision 12), выполненная более одного раза до появления первого admin по ошибке оператора, либо отсутствие защиты от параллельного вызова в двух процессах → [Митигейшн] проверка «существует ли уже admin» выполняется в той же транзакции, что вставка — гонка исключена на уровне БД; повторный вызов после появления первого admin явно завершается ошибкой, а не тихо создаёт второго.
- [Риск] Периодический purge job (decision 14) может не успевать за темпом вставки при очень высокой нагрузке, временно превышая заявленную квоту retention → [Митигейшн] задокументировать как приемлемое eventual-enforcement поведение MVP (не hard real-time limit); частоту таймера сделать конфигурируемой, чтобы оператор мог ускорить при необходимости.
- [Риск] Батчинг/retry в `structured_log_http` может замаскировать постоянную недоступность сервера (записи копятся в памяти без верхнего предела) → [Митигейшн] верхний предел буфера в памяти с вытеснением самых старых записей при переполнении и логом события через `stderr`.
- [Риск] Рассинхрон между `timestamp` записи и `received_at` может путать при отладке инцидентов на нескольких устройствах → [Митигейшн] хранить оба поля явно, в query API дать сортировку/фильтрацию по обоим.

## Migration Plan

1. Скаффолдинг `structured_log_server/` (зависимости `drift`, `sqlite3`, `shelf`, `shelf_router`, `dart_jsonwebtoken`, `bcrypt`; dev-зависимости `drift_dev`, `build_runner`) и `structured_log_http/` + правки `melos.yaml`/CI.
2. Storage-слой: мультитенантная схема (`users`/`groups`/`teams`/`team_members`/`projects`/`project_secret_keys`/`role_assignments`/`project_usage`/`log_entries` с `project_id`) как drift `Table`-классы, миграция при старте, юнит-тесты.
3. `log-server-auth`: хэширование паролей/ключей, `POST /v1/auth/login`, выдача/валидация JWT, аутентификация секретным ключом проекта для приёма.
4. `log-server-rbac`: резолвинг эффективных прав пользователя (прямые + через команды), middleware авторизации для management-эндпоинтов, правила выдачи ролей из decision 7.
5. Management API: `User`/`Group`/`Team`/`Project`/`ProjectSecretKey`/`RoleAssignment` CRUD-эндпоинты по правилам RBAC.
6. `log-server-quotas`: `ProjectUsage`, enforcement на приёме (`max_entries`/`max_bytes`), периodic purge job по `retention_days`.
7. HTTP-слой логов: `POST /v1/logs` (секретный ключ), `GET /v1/logs` (JWT + проверка области видимости), `GET /healthz`.
8. `bin/server.dart`: обычный запуск сервера + отдельная `create-admin` команда (decision 12), graceful shutdown.
9. `structured_log_http`: `HttpLogOutput` (аутентификация секретным ключом проекта, батчинг, retry/backoff, `flushed`).
10. `integration_test.dart` — сквозной сценарий: bootstrap admin → создание группы/проекта/секретного ключа → приём логов по ключу → создание пользователя с ролью `user` на проект → логин → query с проверкой RBAC (доступ разрешён/запрещён).
11. Документация, CI, `openspec-verify-change`.
12. Откат: пакеты новые, не публикуются в рамках этой change — откат сводится к `git revert`; риска для уже опубликованных пакетов нет.
