## ADDED Requirements

### Requirement: Выбор backend'а хранения задаётся конфигурацией при старте
Сервер SHALL определять backend хранения (`sqlite` или `postgres`) из конфигурации, читаемой один раз при старте, и SHALL не менять его в течение жизни процесса. По умолчанию — `sqlite`, и при этом backend'е поведение SHALL быть неотличимо от поведения сервера, не знающего о выборе backend'а вовсе.

#### Scenario: Без явного выбора backend поведение не меняется
- **WHEN** сервер запущен без `--db-backend`/`STRUCTURED_LOG_DB_BACKEND`
- **THEN** используется SQLite, и наблюдаемое поведение идентично поведению до появления этой возможности

#### Scenario: Явный выбор PostgreSQL
- **WHEN** задан `--db-backend=postgres` вместе с обязательными настройками подключения (`log-server-config`)
- **THEN** сервер хранит и читает все данные из указанной базы PostgreSQL, а не из локального файла SQLite

### Requirement: Настройки подключения к Postgres обязательны только при выбранном backend'е Postgres
При `--db-backend=postgres` сервер SHALL требовать host/port/database/username и пароль (секрет, `log-server-config`); при `--db-backend=sqlite` или отсутствии явного выбора backend'а эти настройки SHALL быть необязательными и SHALL игнорироваться, если заданы.

#### Scenario: Postgres без обязательной настройки отклоняется при старте
- **WHEN** задан `--db-backend=postgres` без обязательной настройки подключения (например, без имени базы данных)
- **THEN** сервер отказывается стартовать с ошибкой конфигурации (код выхода `78`), явно называющей отсутствующую настройку

#### Scenario: Настройки Postgres не мешают SQLite-развёртыванию
- **WHEN** заданы настройки подключения к Postgres, но `--db-backend` не задан или равен `sqlite`
- **THEN** сервер стартует с SQLite и не проверяет и не использует заданные настройки Postgres

#### Scenario: create-admin с backend'ом Postgres не требует пути к SQLite
- **WHEN** выполняется `create-admin` с `--db-backend=postgres` и заданными настройками подключения к PostgreSQL
- **THEN** команда создаёт администратора в указанной базе PostgreSQL без запроса пути к файлу SQLite (`log-server-config`)

### Requirement: Недоступный Postgres на старте — ошибка конфигурации, не сбой во время работы
При `--db-backend=postgres` сервер SHALL проверить возможность подключения до открытия HTTP-порта. Недоступность (сетевая ошибка, неверные учётные данные) SHALL приводить к отказу старта с кодом выхода `78`, а не к ошибке на первом обслуживаемом запросе.

#### Scenario: Недоступный Postgres останавливает старт, а не первый запрос
- **WHEN** настроенный сервер PostgreSQL недоступен в момент старта (сеть, неверные креды)
- **THEN** процесс завершается с кодом `78` до открытия HTTP-порта; ни один запрос не мог бы дойти до обработчика

### Requirement: Пул соединений Postgres — отдельная настройка от пула чтения SQLite
`--db-read-pool-size` SHALL применяться только при `--db-backend=sqlite` (или его отсутствии) и SHALL игнорироваться при `--db-backend=postgres`, с предупреждением, записанным в собственный лог сервера при старте. Для PostgreSQL SHALL существовать отдельная настройка размера пула соединений.

#### Scenario: Пул чтения SQLite игнорируется под Postgres
- **WHEN** заданы одновременно `--db-backend=postgres` и `--db-read-pool-size`, отличный от значения по умолчанию
- **THEN** сервер стартует, использует собственный пул соединений PostgreSQL, а в собственный лог диагностики пишет предупреждение о том, что `--db-read-pool-size` не применяется к выбранному backend'у

#### Scenario: Пул соединений Postgres настраивается независимо
- **WHEN** задан `--db-backend=postgres` с размером пула соединений PostgreSQL, отличным от значения по умолчанию
- **THEN** сервер использует заданный размер пула для подключений к PostgreSQL

### Requirement: TLS-режим подключения к Postgres конфигурируется отдельно от учётных данных
Сервер SHALL принимать настройку режима TLS для подключения к PostgreSQL, независимую от host/port/database/username/password, со значением по умолчанию, отличным от полного отключения TLS.

#### Scenario: TLS включён по умолчанию
- **WHEN** `--db-backend=postgres` задан без явной настройки режима TLS
- **THEN** сервер использует режим TLS по умолчанию, отличный от полного отключения шифрования соединения

#### Scenario: TLS можно явно отключить для локальной разработки
- **WHEN** оператор явно задаёт настройку режима TLS как отключающую его
- **THEN** сервер подключается к PostgreSQL без TLS — для локальной разработки без сертификатов

### Requirement: Поведение приёма и запроса логов не зависит от выбранного backend'а хранения
Наблюдаемый вызывающим результат `POST /v1/logs`/`GET /v1/logs` — порядок id вставленных записей, сохранность и доступность произвольных полей `context` без потери данных, результат фильтрации по ним — SHALL быть одинаковым независимо от того, какой backend хранения выбран.

#### Scenario: Идентичный результат фильтрации по context на обоих backend'ах
- **WHEN** один и тот же батч записей с одинаковым пользовательским полем `context`, не входящим в типизированные колонки, принят и затем запрошен фильтром по значению этого поля — один раз на сервере с `--db-backend=sqlite`, независимо — на сервере с `--db-backend=postgres`
- **THEN** оба сервера возвращают одинаковый по составу набор совпавших записей

#### Scenario: Порядок id сохраняется при конкурентной вставке на обоих backend'ах
- **WHEN** несколько батчей логов одного проекта вставлены конкурентно (`log-server-api`, группировка одновременных запросов) на сервере с любым из двух backend'ов
- **THEN** каждая вставленная запись получает уникальный возрастающий `id`, и порядок id совпадает с порядком фактического коммита вставившей её транзакции — независимо от backend'а
