## MODIFIED Requirements

### Requirement: Хранение записи лога с привязкой к проекту и сохранением исходного контекста
Каждая принятая запись SHALL сохраняться в настроенном backend'е хранения (SQLite или PostgreSQL — выбор оператора, `log-server-postgres-backend`) с обязательной привязкой к `project_id` (проект, определённый секретным ключом, которым была аутентифицирована запись) и с полным исходным JSON-содержимым (включая произвольные пользовательские поля `context`, не имеющие фиксированной схемы) без потери данных, одинаково независимо от выбранного backend'а.

#### Scenario: Произвольное пользовательское поле переживает round-trip
- **WHEN** сохранена запись с пользовательским полем `context`, отсутствующим в типизированных колонках схемы
- **THEN** это поле присутствует и доступно в исходном виде при последующем запросе этой записи вызывающим с доступом к её проекту

#### Scenario: Запись всегда привязана к ровно одному проекту
- **WHEN** запись сохранена через `POST /v1/logs`, аутентифицированный секретным ключом проекта `P`
- **THEN** сохранённая запись имеет `project_id = P`, и запрос с `project_id`, отличным от `P`, эту запись не возвращает

### Requirement: Фильтрация по произвольным полям context через JSON1
Хранилище SHALL поддерживать точное совпадение по значению произвольного пользовательского ключа внутри сохранённого JSON-контекста без необходимости заранее объявлять этот ключ в схеме. Название требования сохранено по исторической причине (JSON1 — механизм SQLite, действовавший на момент его формулировки); конкретный механизм — JSON1 у SQLite, `jsonb`-операторы у PostgreSQL — деталь выбранного backend'а хранения (`log-server-postgres-backend`), а не часть этого требования: обязательно только наблюдаемое поведение фильтрации, одинаковое для обоих.

#### Scenario: Запрос по незаранее известному ключу контекста
- **WHEN** сохранены записи одного проекта с разными значениями пользовательского ключа `context.order_id`, не входящего в типизированные колонки
- **THEN** запрос с фильтром на конкретное значение `order_id` возвращает только записи с этим значением

### Requirement: Режим журналирования WAL
Backend хранения SHALL быть сконфигурирован так, чтобы чтение через query API не блокировалось конкурентной вставкой батча. Название требования сохранено по исторической причине (`journal_mode=WAL` — механизм SQLite, действовавший на момент его формулировки); под PostgreSQL то же наблюдаемое поведение достигается его собственной моделью конкурентности (MVCC), не требующей отдельной настройки (`log-server-postgres-backend`) — конкретный механизм не фиксируется этим требованием, обязательно только отсутствие блокировки, одинаковое для обоих backend'ов.

#### Scenario: Запрос не блокируется параллельной вставкой
- **WHEN** выполняется `GET /v1/logs` одновременно с выполняющейся вставкой батча через `POST /v1/logs`
- **THEN** запрос на чтение успешно завершается без ошибки блокировки базы данных
