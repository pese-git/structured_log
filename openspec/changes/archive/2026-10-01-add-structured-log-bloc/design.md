## Context

`bloc` (основа `flutter_bloc`) уведомляет глобальный `Bloc.observer` о каждом создании, событии, смене состояния, ошибке, завершении обработчика и закрытии любого блока или кубита. `structured_log` уже умеет маршрутизировать записи по категориям и уровням в консоль, файл, встроенный просмотрщик и на сервер. Не хватает моста между ними.

## Goals / Non-Goals

**Goals:**
- Подключение одной строкой, без изменений в самих блоках.
- Каждая запись пригодна для любого вывода, включая JSON (`fileOutput`, `HttpLogOutput`).
- Наблюдатель никогда не ломает блок.

**Non-Goals:**
- Flutter-специфика (виджеты, `BuildContext`) — её здесь нет.
- Логирование отдельных блоков через миксины или базовые классы.
- Автоматическое распознавание секретов в состояниях.

## Decisions

1. **Зависимость от `bloc`, а не от `flutter_bloc`.** `BlocObserver` и `Bloc.observer` объявлены в `bloc`; `flutter_bloc` их только реэкспортирует. Пакет поэтому работает в Flutter-приложении как есть и при этом остаётся чистым Dart: тестируется `dart test`, в CI идёт через `setup-dart`, а не через Flutter-матрицу. Альтернатива — зависеть от `flutter_bloc` ради имени — отклонена: она притянула бы Flutter SDK, ничего не добавив.

2. **Событие блока — в поле `bloc_event`, имя записи хука `onEvent` — `bloc_event_added`.** В `structured_log` ключ `event` — имя самой записи; поле с тем же именем его перезаписало бы. Первая редакция так и сделала, поймано тестом.

3. **`onChange` пишется только для кубитов.** Для блока `bloc` вызывает и `onTransition`, и `onChange` на одну и ту же смену состояния; переход несёт событие, поэтому пишется он, а `onChange` у блока пропускается. Каждая смена состояния — ровно одна запись.

4. **Значения — через `toString()` с обрезкой, функция заменяема.** Произвольный объект состояния не сериализуется `jsonEncode`, поэтому по умолчанию в запись идёт строка (до 1000 символов). Тип (`state_type`, `bloc_event_type`, `error_type`) пишется всегда. Функция `describe` заменяема; `null` из неё убирает поле, но не тип. Альтернатива — по умолчанию писать только типы — отклонена: тогда лог блоков почти бесполезен для разбора, а ожидание пользователей `BlocObserver` — `toString()`. Риск утечки секретов вынесен в README отдельным разделом.

5. **Логгер берётся на каждом хуке, если не передан.** `BoundLogger` держит конфигурацию, с которой создан, а наблюдатель ставится один раз и переживает повторный `StructlogConfiguration.configure`. `getLogger` — копия небольшой карты, цена приемлема; запись при этом строится только после проверки уровня и фильтра.

6. **Исключения из описания не выходят из хука.** Хуки выполняются внутри `emit`/`add`; бросивший `toString()` превращается в заглушку (`describeBlocValue`), бросивший `describe` — в поле `describe_failed` с типом исключения. Исключения выводов `structured_log` гасит сам (`tryLog`).

7. **Уровни по умолчанию:** создание/событие/смена/переход/закрытие — `debug`, ошибка — `error`, `onDone` — `trace` (повторяет событие каждого обработчика; `minLevel` вывода по умолчанию его отсекает). `onDone` с ошибкой не повторяет стек — его уже записал `onError`.

## Risks / Trade-offs

- Состояния с секретами по умолчанию попадают в лог → раздел «Как не пустить секреты в лог» в README, пример `describe`.
- `identityHashCode` как `bloc_instance` не уникален гарантированно → достаточно для различения живых экземпляров в логе; это не ключ.
- `bloc` 10.x может поменять сигнатуры хуков → констрейнт `^9.0.0`, пересмотр при выходе мажорной версии.
