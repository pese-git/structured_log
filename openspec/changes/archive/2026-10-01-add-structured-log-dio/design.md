## Context

`dio` пропускает каждый вызов через цепочку `Interceptor`: `onRequest` перед отправкой, затем `onResponse` для статуса, который принял `validateStatus`, либо `onError` для всего остального (отвергнутый статус как `badResponse`, таймауты, ошибки соединения, отмена). `structured_log_bloc` уже задал форму для таких мостов: одна запись на событие, своя категория, уровень на событие, заменяемое описание значений, «никогда не ломать хозяина».

## Goals / Non-Goals

**Goals:**
- Подключение одной строкой, без изменений в вызывающем коде.
- Секреты не попадают в лог без явного решения пользователя.
- Перехватчик не меняет исход ни одного вызова.

**Non-Goals:**
- Логирование других HTTP-клиентов (`http`, `HttpClient`).
- Подключение в `structured_log_admin_client`.
- Распознавание секретов в телах.

## Decisions

1. **Две записи на вызов, а не одна на итоге.** Запись на отправке показывает зависший запрос, у которого итога ещё нет; итог несёт длительность. Связь — `http_request_id`, счётчик в экземпляре перехватчика. Альтернатива — одна запись на итоге — отклонена: висящий запрос в ней невидим, а именно он чаще всего и нужен. Если запись на отправке не нужна, её выключает `HttpLogLevels(request: null)`.

2. **Состояние вызова — в `options.extra`.** Номер и `Stopwatch` кладутся в `extra` на запросе и читаются на итоге. Так пара не зависит от карты в перехватчике, которая утекала бы на запросах без итога. Следствие: отфильтрованный запрос не даёт и итога; исключение с чужими `RequestOptions` итога не даёт — штатные адаптеры передают опции самого запроса.

3. **Уровень — по статусу, а не по пути.** 404 приходит в `onResponse` или в `onError` в зависимости от `validateStatus` — настройки, которая говорит о вызывающем коде, а не о серьёзности. Поэтому статус < 400 — `success`, 4xx — `clientError` (`warning`), 5xx — `serverError` (`error`), нет ответа — `failure` (`error`), отмена — `cancel` (`debug`: это решение приложения, а не сбой).

4. **Заголовки и тела выключены по умолчанию; маскирование — по спискам имён.** Заголовки несут `Authorization`, тела — пароли и токены; включать их — решение пользователя. Даже включённые заголовки маскируются по `defaultRedactedHeaders`. Query-параметры маскируются всегда, потому что URL пишется всегда. Маскированное значение — `REDACTED`: `<redacted>` в query перекодировался бы в `%3Credacted%3E`. Тела не маскируются по ключам (структура тела произвольна), вместо этого — `describeBody` и `filter`.

5. **`error` не пишется для `badResponse`.** Сообщение `dio` в этом случае — абзац шаблонного текста вокруг статуса, который уже лежит в `status_code`.

6. **Никакое исключение не выходит из перехватчика, `handler.next` вызывается всегда.** Перехватчик стоит в пути каждого запроса; бросивший `filter` или `describeBody` стоит записи, а не вызова.

7. **Чистый Dart, тесты без сокета.** `dio` не требует Flutter SDK; тесты отвечают через подставной `HttpClientAdapter`, пример поднимает `HttpServer` на loopback, чтобы прогон примера в CI не зависел от внешней сети.

## Risks / Trade-offs

- Включённые тела пишутся как есть → раздел о секретах в README, пример `describeBody`, рекомендация `filter` для вызовов входа.
- Список маскируемых query-параметров не покрывает всех имён → набор заменяем, значения по умолчанию задокументированы.
- Перехватчик, добавленный не последним, видит не итоговый запрос → в README и доке класса: добавлять последним.
