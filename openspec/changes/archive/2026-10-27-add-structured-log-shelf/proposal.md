## Why

Все HTTP-адаптеры `emb/` сейчас стоят на стороне клиента (`structured_log_dio`, `structured_log_http_client`), а у
серверного Dart на `shelf` записи запросов, совместимой с `structured_log`, нет: штатный `logRequests()` печатает
строку текстом через `print`, без уровня, без полей и без связи с остальными записями того же запроса. Главное, чего
не хватает, — **корреляции**: запись обработчика («пользователь не найден», «квота исчерпана») не несёт `request_id`, и
связать её с запросом, который её вызвал, при разборе инцидента нечем.

Задача уже решена один раз — внутри `structured_log_server` (`http/logging_middleware.dart`, decision 48): одна запись на
запрос, уровень по статусу, `request_id` из словаря `LogCorrelation`, тело и `Authorization` не пишутся никогда. Но
решена наполовину: логгер с `request_id` живёт только внутри middleware, обработчики о нём не знают, и их записи
остаются без корреляции. Пакет обобщает этот middleware и доводит корреляцию до обработчика — так же, как
`structured_log_cherrypick` обобщил наблюдатель, дважды живший копией в сервере и admin-клиенте.

## What Changes

- Новый пакет `emb/structured_log_shelf/` с middleware для `shelf` (`Middleware` — обычная функция, встаёт в `Pipeline`
  одной строкой):
  - одна запись на итог запроса с `category: 'http'`, `method`, путём, статусом и `duration_ms`; уровень — по статусу
    (успех / 4xx / 5xx / исключение обработчика, `null` выключает), исключение — отдельной записью со стеком и затем
    пробрасывается дальше, ответ не подменяется;
  - **корреляция запроса**: у каждого запроса есть `request_id` в поле `request_id` словаря `LogCorrelation`;
    обработчик получает логгер, уже привязанный к нему (`request.context`, с функцией-доступом), и id в заголовке
    ответа;
  - **входящий `X-Request-Id` по умолчанию не принимается**: значение от клиента — непроверенный ввод, который иначе
    уехал бы в журнал как есть (подделка корреляции, мусор в поле). Принимать его — явная настройка (за доверенным
    прокси), и даже тогда значение проверяется по длине и набору символов, а непрошедшее заменяется сгенерированным;
  - секреты не пишутся: тела запросов и ответов — никогда (в отличие от клиентских адаптеров, включить их нельзя:
    сервер принимает пароли и данные пользователей), заголовки — по умолчанию нет, при включении `authorization`/
    `cookie`/`set-cookie`/`x-api-key` и подобные маскируются; query-параметры с токенами маскируются всегда;
  - фильтр запросов (не писать health check), свой логгер и категория; бросивший фильтр стоит записи, а не запроса
    (fail-closed, как у остальных адаптеров), сбой логирования никогда не ломает ответ.
- Регистрация в `melos.yaml`, CI-джоба по образцу `dio-interceptor` (чистый Dart: format/analyze/test с покрытием,
  прогон `example/main.dart`), порог в `tool/coverage_floors.json`, второй прогон тестов на нижней границе `shelf`.
- Документация: README пакета (EN/RU), раздел «Related packages»/«Связанные пакеты» во всех README пакетов `emb/`,
  корневые README, `AGENTS.md`, `docs/guides/embedding-guide.md`, страница пакета на сайте.
- Вне рамок:
  - **перевод `structured_log_server` на пакет.** Имена событий и полей сервера (`request.completed`/`request.failed`,
    `status`, `path`) — часть его наблюдаемого журнала, на них опираются тесты; совпадут ли они с именами пакета,
    решает design, а переход сервера с возможным переименованием — отдельной заявкой;
  - публикация на pub.dev (отдельный шаг релиза, как у остальных адаптеров);
  - распространение `request_id` в исходящие запросы (связка с `_dio`/`_http_client`) и трассировка (OpenTelemetry);
  - `shelf_router`-специфика — шаблон маршрута вместо пути: middleware стоит снаружи роутера и шаблона не видит.

## Capabilities

### New Capabilities
- `shelf-request-logging`: middleware `shelf`, превращающий каждый запрос в запись `structured_log` и дающий
  обработчику логгер, привязанный к `request_id` запроса, без утечки тел, заголовков авторизации и токенов.

### Modified Capabilities
(нет)

## Impact

- Новый пакет `emb/structured_log_shelf/` (версия `0.1.0-dev.0`); зависимости — `shelf` (нижняя граница выбирается в
  design и проверяется в CI), `structured_log: ^0.3.2+2`.
- `melos.yaml`, `.github/workflows/ci.yml`, `tool/coverage_floors.json`.
- README всех живых пакетов `emb/` (раздел «Related packages»), `site/` (страница пакета, оглавление пакетов).
- `structured_log_server` не меняется.
