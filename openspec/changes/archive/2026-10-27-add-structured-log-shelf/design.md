## Context

`shelf` строит сервер из `Handler` (`FutureOr<Response> Function(Request)`) и `Middleware` (`Handler Function(Handler)`),
собранных в `Pipeline`. У запроса есть `context` — неизменяемая карта, которую middleware дополняет через
`request.change(context: ...)`, и по соглашению `shelf` ключи в ней называются с префиксом пакета. Обработчик,
забравший сокет себе (WebSocket, `shelf_web_socket`), бросает `HijackException`, и middleware, ловящий исключения,
обязан пропустить её дальше без изменений — так прямо требует документация `Middleware`.

В репозитории это уже сделано один раз — `requestLoggingMiddleware` сервера
(`backend/structured_log_server/lib/src/http/logging_middleware.dart`, decision 48 `add-structured-log-server`):

- одна запись на запрос — `request.completed` (`method`, `path`, `status`, `duration_ms`) или `request.failed` со
  стеком, после чего исключение пробрасывается;
- уровень по статусу: `info` / `warning` для 4xx / `error` для 5xx;
- `request_id` — 12 случайных hex-символов, привязанный через `withCorrelation(requestId:)`;
- тело и `Authorization` не пишутся никогда, заголовков в записи нет вовсе;
- middleware стоит в `Pipeline` снаружи всех, поэтому пишет статус, который клиент действительно получил, включая
  ответы middleware ошибок.

Чего у него нет: логгер с `request_id` остаётся внутри middleware, и записи обработчиков корреляции не несут; входящий
`X-Request-Id` он не читает, а свой id клиенту не возвращает. Имена `request.completed` проверяют тесты сервера
(`test/bin/server_integration_test.dart`, `test/logging/diagnostics_isolation_test.dart`).

`shelf` 1.4.0 требует Dart `>=2.17`, 1.4.2 — `^3.4.0`, 1.4.3 — `^3.9.0`. Пакету не нужно ничего, что появилось позже
1.0: `Request.change(context:)`, `HijackException`, `Response.change(headers:)`.

**Проверено пробной программой до кода** (задача 1.1, `shelf` 1.4.0 и 1.4.3 на Dart 3.13.3, `shelf_io.serve` на loopback
плюс `shelf_router`). На обеих версиях результат одинаковый:
- `shelf` 1.4.0 разрешается на текущем стабильном Dart.
- Под `Router.mount('/api/', …)` внешний middleware видит `url=api/items`, а middleware внутри монтирования —
  `url=items`. `requestedUri.path` в обоих случаях `/api/items`.
- `context`, положенный внешним middleware через `request.change`, доходит до обработчика под `mount`.
- `Cascade` отдаёт внешнему middleware только итоговый ответ, а не 404 предыдущих обработчиков.
- `Response.change(headers:)` не бросает и доходит до клиента.
- Захват сокета приходит в middleware как `HijackException` со стеком. После `rethrow` соединение остаётся у
  обработчика: клиент получает то, что записал обработчик, а заголовка `X-Request-Id` в ответе нет, потому что
  `Response` не было.

## Goals / Non-Goals

**Goals:**
- Подключение одной строкой в `Pipeline`, без изменений в обработчиках, которым корреляция не нужна.
- Каждая запись обработчика, сделанная через логгер запроса, несёт `request_id` этого запроса.
- Пакет не меняет исход ни одного запроса: ни статус, ни тело, ни исключение, ни захват сокета.
- Секреты не попадают в лог: тела никогда, заголовки только явным включением и с маскированием, токены в query —
  маскированными всегда.

**Non-Goals:**
- Перевод `structured_log_server` на пакет (отдельная заявка, см. решение 2).
- Неявная корреляция через `Zone`, при которой `getLogger()` в любом месте кода сам подхватывал бы `request_id`.
- Передача `request_id` в исходящие запросы и трассировка (OpenTelemetry).
- Шаблон маршрута `shelf_router` (`/users/<id>`) вместо пути: middleware стоит снаружи роутера и не видит, какой
  маршрут совпал.
- Измерение времени до конца тела ответа.

## Decisions

1. **Одна запись на итог запроса, запись о получении — необязательная.** На стороне клиента `structured_log_dio` пишет
   пару записей, потому что зависший исходящий запрос — частая находка при разборе инцидента. На сервере обычный запрос
   длится миллисекунды, и запись о получении удвоила бы объём журнала ради редкого случая. Поэтому итог —
   `http_request_handled` (есть ответ) или `http_request_failed` (обработчик бросил), а запись `http_request_received`
   выключена по умолчанию (`ShelfLogLevels.received: null`) и включается для долгих запросов вроде SSE.
   Альтернатива «всегда пара» отклонена из-за объёма, «никогда» — из-за того, что висящий запрос тогда не виден ничем.

2. **Словарь записей — как у адаптеров `emb/`, а не как у сервера.** События пишутся в snake_case с префиксом `http_`
   (как `http_request`/`http_response` у `_dio`/`_http_client`), поля — `method`, `path`, `status_code`, `duration_ms`,
   `category: 'http'`. Так одно условие (`status_code >= 500`) одинаково фильтрует записи клиента и сервера на
   `structured_log_server`. Имена сервера (`request.completed`, `status`) остаются только у сервера. Цена в том, что
   его переход на пакет переименует события, которые проверяют его тесты и которые видят операторы. Поэтому переход —
   отдельная заявка с явным решением о переименовании, а не побочный эффект этой. Альтернатива «взять имена сервера» отклонена:
   пакет создаётся для внешних пользователей, а у них уже есть записи `_dio` со словарём `status_code`.

3. **Логгер запроса — в `request.context`, доступ через расширение, отсутствие middleware — `StateError`.**
   Middleware кладёт `BoundLogger`, уже привязанный к `request_id`, и сам `request_id` под ключами
   `structured_log_shelf.logger` и `structured_log_shelf.request_id`. Обработчик читает их через расширение
   `request.logger` / `request.requestId`. Если middleware не подключён, getter бросает `StateError` с подсказкой. Тихий
   откат на `getLogger()` без корреляции отклонён: именно так ошибка подключения остаётся незамеченной — тесты
   зелёные, а записи без `request_id`, то есть та проблема, ради которой пакет и создаётся.
   Цена в том, что тест обработчика без middleware падает. Тест оборачивает обработчик тем же middleware, и README
   показывает, как. Ключ `context` с префиксом пакета взят по соглашению `shelf`.
   Неявную корреляцию через `Zone` рассматривали и отложили. Чтобы её поддержать, `getLogger()` ядра должен читать зону.
   Это изменение `structured_log`, которое касается каждого вызова лога, и ему нужна своя заявка.

4. **`request_id`: генерируется, возвращается в ответе, входящий по умолчанию не принимается.** По умолчанию это 12
   случайных hex-символов (48 бит), как у сервера, через `Random`, а не `Random.secure`: id не секрет и нужен только
   чтобы связать записи. Функция генерации заменяется (`requestIdGenerator`), например на UUID. Id возвращается в
   заголовке ответа `X-Request-Id` (`responseHeader`, `null` выключает), чтобы пользователь мог назвать его в обращении.
   Входящий заголовок принимается только при `trustIncomingRequestId: true`. Включать это стоит, когда перед сервером
   стоит прокси, который сам ставит id: иначе клиент подставил бы id чужого запроса или вписал бы в поле журнала
   произвольный текст. Принятое значение проверяется: 1–128 символов из `[A-Za-z0-9._:-]`, этому соответствуют UUID и
   типовые id прокси. Значение, не прошедшее проверку, заменяется сгенерированным, а в запись ставится
   `request_id_rejected: true`, сам отвергнутый текст не пишется.

5. **Путь — полный, query — отдельным полем и с маскированием.** `path` берётся из `request.requestedUri.path`, а не
   из `request.url`: `url` отсчитывается от точки монтирования (`Router.mount`, `Cascade`), и один и тот же маршрут
   выглядел бы по-разному в зависимости от того, где стоит middleware. Непустой query пишется полем `query`, при этом
   значения из `redactedQueryParameters` заменяются на `REDACTED`. Набор по умолчанию тот же, что у
   `_dio`/`_http_client`. Секрет в сегменте пути (`/reset/<token>`) так не замаскировать: шаблона маршрута middleware
   не знает. Для таких путей есть `filter` и описание этого в README.

6. **Тела не пишутся никогда, заголовки — по `logHeaders` и с маскированием.** У клиентских адаптеров тела
   включаются, потому что разработчик клиента сам решает, что видит в логе своего приложения. Сервер принимает пароли,
   токены и данные пользователей, а читатели его журнала — не обязательно те, кому эти данные адресованы. Поэтому
   настройки, которая включала бы тела, нет вовсе. Заголовки включаются через `logHeaders`, тогда `request_headers` и
   `response_headers` пишутся с маскированием по `redactedHeaders`. Набор тот же, что у `_dio`, сравнение
   регистронезависимое.
   Набор маскирования — **своя копия** в пакете, а не импорт из `_dio`: общего пакета правил по-прежнему нет, и ни один
   адаптер не тянет другой. Это уже пятая копия правил маскирования URL. Вынести их в ядро — отдельный вопрос
   (см. Open Questions).

7. **Уровень — по статусу; исключение пишется и пробрасывается; захват сокета — не сбой.** `ShelfLogLevels`
   задаёт уровень для каждого исхода, `null` выключает запись:
   - `success` — статус ниже 400, по умолчанию `info`;
   - `clientError` — 4xx, `warning`;
   - `serverError` — 5xx, `error`;
   - `failure` — обработчик бросил, `error`;
   - `received` — запись о получении, `null`.

   Исключение обработчика пишется записью `http_request_failed` через
   `tryLog(error:, stackTrace:)` ядра (поля `error_type`, `error`, `stack_trace`), и затем выполняется `rethrow`, чтобы
   стек не менялся. `HijackException` сбоем не считается: middleware пишет `http_request_handled` с `hijacked: true`, без
   `status_code`, на уровне `success`, и пробрасывает исключение без изменений.

8. **Время — до возврата `Response`, а не до конца тела.** `duration_ms` (дробное, как у `_drift`) — время до момента,
   когда обработчик вернул ответ, то есть до отправки заголовков. Тело ответа не оборачивается. У SSE и долгих
   загрузок тело может не закончиться никогда, а обёртка потока меняла бы буферизацию (`shelf_io` смотрит на тип тела)
   и захват сокета. Время до конца тела отложено, пока его не попросят.

9. **Сбой логирования не ломает запрос, фильтр не отнимает корреляцию.** Всё, что middleware делает ради записи, обёрнуто
   защитой: построение записи, `filter`, маскирование, сам вызов лога. Бросивший `filter` стоит записи (fail-closed,
   как у остальных адаптеров), а не запроса. Важно, что `filter` решает только судьбу записей самого middleware:
   отфильтрованный запрос всё равно получает `request_id`, логгер в `context` и заголовок ответа. Иначе health check,
   исключённый ради тишины в журнале, остался бы без корреляции и в записях обработчика. Добавление заголовка к ответу
   защищено так же: ответ, к которому заголовок не добавился, уходит как есть.

10. **Логгер берётся на каждом запросе, если его не передали.** Без явного `logger` middleware зовёт
   `getLogger(loggerName)` на каждом запросе и привязывает к нему корреляцию. Так конфигурация, заданная после сборки
   `Pipeline`, применяется, как у остальных адаптеров. Явно переданный `logger` используется как есть.

11. **Чистый Dart; тесты без сокета, кроме захвата.** `shelf` не тянет Flutter, поэтому пакет проверяется `dart test`
   и встаёт в CI джобой по образцу `dio-interceptor`. Поведение проверяется вызовом обработчика напрямую с
   `Request('GET', Uri.parse('http://localhost/...'))`. `HijackException` проверяется через `shelf_io.serve` на
   loopback, потому что без адаптера захватить запрос нельзя. Пример `example/main.dart` тоже поднимает сервер на loopback, чтобы
   прогон в CI не зависел от сети. Констрейнт — `shelf: ^1.4.0`. Второй прогон тестов в CI на `shelf: 1.4.0` проверяет
   нижнюю границу, как у `_drift`/`_logging`/`_riverpod`.

## Risks / Trade-offs

- [Секрет в сегменте пути пишется как есть] → `filter` для таких маршрутов, раздел о секретах в README с примером.
- [Текст исключения обработчика может цитировать данные] (как `SqliteException` с `parameters:` у `_drift`) → пакет
  пишет ошибку формой ядра, как сервер сейчас. README предупреждает, что исключения, несущие данные, нужно
  перехватывать раньше. Скрывать текст по умолчанию не стали: без него запись о сбое не говорит, что случилось.
- [`request.logger` без middleware бросает] → цена ловли ошибки подключения на первом же вызове. Сообщение
  `StateError` называет middleware, README показывает тест обработчика с ним.
- [`duration_ms` не включает отдачу тела] → это задокументировано в README и в doc-комментарии поля. Для SSE есть
  `http_request_received`, а записи о конце потока пишет сам обработчик.
- [Пятая копия правил маскирования] → наборы совпадают с `_dio`/`_http_client` и это закреплено тестом на равенство
  значений по умолчанию. Вынос в ядро — открытый вопрос.
- [Middleware, поставленный не снаружи, пишет не тот статус, который получил клиент] → в README и doc-комментарии:
  ставить первым в `Pipeline`, до middleware ошибок.
- [Ответ 500 на непойманное исключение уходит без `X-Request-Id`] (найдено прогоном примера, задача 1.8). Этот ответ
  строит `shelf_io` снаружи всех middleware, после `rethrow`. Запись `http_request_failed` при этом есть, но клиенту
  назвать нечего. → README: внутри middleware ставится обработчик ошибок, превращающий исключение в ответ, как в
  `structured_log_server`. Тогда ответ проходит через middleware и получает заголовок, а записью итога становится
  `http_request_handled` со статусом 500.
- [Записи обработчика через `request.logger` пишутся с `logger: shelf`]: это логгер middleware, к которому привязан id.
  → README называет это прямо, а своё имя логгера задаётся через `logger:`.

## Migration Plan

Пакет новый, существующий код не меняется. Сервер продолжает пользоваться своим `requestLoggingMiddleware`. Переход
сервера — отдельная заявка: она решит, переименовывать ли `request.completed` в `http_request_handled`, и обновит
тесты сервера. Откат — удаление пакета из `melos.yaml` и CI.

## Open Questions

- Выносить ли наборы маскирования заголовков и query (`_dio`, `_http_client`, `_go_router`, `_auto_route`, `_shelf`) в
  `structured_log` рядом с `defaultSensitiveKeys`? Это вне этой заявки: такое изменение трогает четыре опубликованных
  пакета.
- Нужна ли неявная корреляция через `Zone` (решение 3)? Если да, нужна заявка на ядро. Тогда этот пакет поставит зону
  в одну строку.
