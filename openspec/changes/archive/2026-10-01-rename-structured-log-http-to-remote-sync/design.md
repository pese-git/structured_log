## Context

`structured_log_http` опубликован на pub.dev без издателя (загружен с личного аккаунта мейнтейнера), версии `0.1.0-dev.1` и `0.1.0`, линия тегов `structured_log_http-v*`. Внутри репозитория от него зависит только `packages/e2e`; сервер и admin-клиент его не используют. pub.dev не умеет переименовывать пакет: новое имя — новый пакет, а старый можно лишь пометить discontinued, по желанию с полем «Replaced by».

## Goals / Non-Goals

**Goals:**
- Новое имя на pub.dev и в репозитории, поведение без изменений.
- Пользователь старого пакета, сделавший `dart pub upgrade`, не получает сломанную сборку, а получает предупреждение с новым именем.
- Страница старого пакета на pub.dev однозначно говорит о переименовании.

**Non-Goals:**
- Переименование капабилити OpenSpec и внутренних имён (`_HttpBatchSender` — это действительно HTTP-транспорт).
- Поддержка `structured_log_http` после прослойки: новых версий не будет.

## Decisions

1. **Прослойка, а не просто баннер.** pub.dev показывает README последней версии; без нового релиза на странице старого пакета осталось бы старое описание, а у зависимых — никакого сигнала в коде. Прослойка `0.1.1` реэкспортирует новый пакет и потому не может разойтись с ним по поведению, в отличие от релиза «тот же код, новый README». Альтернатива «только discontinued» отвергнута по той же причине — README.
2. **`@Deprecated` на библиотеке и на `typedef`.** `@Deprecated library;` заставляет анализатор пометить сам импорт, `@Deprecated typedef HttpLogOutput = RemoteSyncLogOutput;` — каждое использование старого имени. Конструктор через `typedef` вызывается как обычно, поэтому код пользователя компилируется без правок. `BatchSender`/`BatchResult` реэкспортируются без пометки: их имена не изменились, устаревший в них только путь импорта, а его уже помечает библиотека.
3. **Переименовывается только `HttpLogOutput`.** Это единственное публичное имя с транспортом в названии. `BatchSender`/`BatchResult` названы по роли, и переименование превратило бы однострочный переход в многострочный без выигрыша в смысле.
4. **`structured_log_remote_sync` начинает с `0.1.0`.** Это первая версия нового пакета; код тот же, что в `structured_log_http 0.1.0`, кроме имени класса. Перенесённый `CHANGELOG.md` сохраняется без правок — правило репозитория: перенос не меняет CHANGELOG, а пишет его только `melos version`.
5. **Порядок публикации — по уровням.** Прослойка зависит от `structured_log_remote_sync` как hosted-пакета, поэтому сначала публикуется новый пакет, потом прослойка; пакетная публикация обоих сразу упадёт на разрешении версий. Пометка discontinued — последним шагом, когда прослойка уже на pub.dev: иначе страница с баннером показывала бы README без уведомления.
6. **Прослойка остаётся в workspace.** Она перечислена в `melos.yaml`, чтобы `melos bootstrap` подставлял путь к `structured_log_remote_sync` и анализ/тест прослойки шли против рабочей копии. В CI у неё свой короткий шаг в джобе нового пакета (analyze + test), без порога покрытия: исполняемых строк в ней нет.

## Risks / Trade-offs

- [Риск] Зависимые, закрепившие `structured_log_http: 0.1.0` точно, прослойку не получат и баннера в коде не увидят → [Митигейшн] баннер discontinued на pub.dev и `dart pub outdated` («discontinued») покажут переименование и им.
- [Риск] Первая версия нового пакета не находит тега `structured_log_remote_sync-v*`, и `melos version` для него посчитает всю историю каталога → [Митигейшн] после публикации `0.1.0` поставить тег `structured_log_remote_sync-v0.1.0` на опубликованный коммит, как у остальных пакетов.
