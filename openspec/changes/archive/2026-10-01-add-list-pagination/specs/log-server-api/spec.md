## MODIFIED Requirements

### Requirement: Перечисление доступных проектов плоским списком
Сервер SHALL предоставлять `GET /v1/projects`, возвращающий проекты, которые вызывающий вправе читать (`log-server-rbac`), одним плоским списком — независимо от того, чем выдана роль: на группу или на отдельный проект — по общему контракту пагинации (`log-server-pagination`). Список SHALL принимать необязательные `group_id`, сужающий его до одной группы, и `name` — подстроку имени; оба комбинируются с `limit`/`cursor`. Условие видимости SHALL накладываться на запрос к хранилищу (`log-server-pagination`, «Перечисление доступных групп постранично»), а не на загруженные строки. Ответ SHALL включать `is_blocked` и SHALL **не** включать счётчики использования (`entry_count`/`total_bytes`) — они остаются у `GET /v1/projects/:id` (`log-server-quotas`).

#### Scenario: Роль на отдельный проект даёт его увидеть
- **WHEN** `GET /v1/projects` выполнен пользователем, у которого есть роль только на один проект и никакой роли на его группу
- **THEN** в ответе присутствует этот проект — именно поэтому список плоский: роль на проект не покрывает его группу, и такой пользователь не увидел бы её в перечне групп, то есть не смог бы добраться до проекта вовсе

#### Scenario: Роль на группу покрывает её проекты
- **WHEN** `GET /v1/projects` выполнен пользователем с ролью на группу `G`
- **THEN** в ответе присутствуют все проекты `G` (по страницам, если их больше `limit`) и отсутствуют проекты других групп, на которые у него роли нет

#### Scenario: Заблокированный проект остаётся в списке
- **WHEN** в области видимости вызывающего есть проект с `is_blocked = true`
- **THEN** он присутствует в ответе с `is_blocked: true` — скрытие существующего проекта читалось бы как его удаление; что делать с этим признаком, решает тот, кто показывает список

#### Scenario: Список не считает использование
- **WHEN** выполнен `GET /v1/projects`
- **THEN** элементы ответа не содержат `entry_count`/`total_bytes` — подсчёт по каждому видимому проекту сделал бы запрос селектора самым дорогим в API

#### Scenario: Список ограничен одной страницей
- **WHEN** `admin` выполняет `GET /v1/projects` без параметров в базе, где проектов больше 50
- **THEN** ответ содержит 50 проектов и `next_cursor`, а не все проекты

#### Scenario: Видимость и порядок страниц совпадают с проверкой доступа к одному проекту
- **WHEN** пользователь обходит `GET /v1/projects` страницами до конца, а затем запрашивает `GET /v1/projects/:id` для каждого проекта базы
- **THEN** множество проектов из обхода равно множеству тех, для которых `GET /v1/projects/:id` не ответил `403` — условие видимости в SQL и проверка доступа к одному проекту не расходятся

### Requirement: Пагинация результатов запроса
Эндпоинт `GET /v1/logs` SHALL поддерживать пагинацию по общему контракту (`log-server-pagination`): `limit` (по умолчанию 50, верхний предел 200) и курсорный параметр, основанный на `id` записи; ответ SHALL включать `next_cursor`, равный `null` на последней странице. Без курсора запрос SHALL возвращать записи по убыванию `id` (самые новые из подходящих под фильтр — первыми); курсор следующей страницы SHALL продвигать выборку к более ранним (меньшим `id`) записям.

#### Scenario: Запрос следующей страницы через курсор
- **WHEN** первый запрос `GET /v1/logs?project_id=P&limit=50` возвращает курсор следующей страницы, и этот курсор передан в повторном запросе
- **THEN** второй запрос возвращает следующие записи проекта `P`, не пересекающиеся с уже полученными

#### Scenario: Первая страница без курсора возвращает самые новые записи
- **WHEN** отправлен `GET /v1/logs?project_id=P&limit=50` без курсора, для проекта `P` с более чем 50 записями
- **THEN** ответ содержит 50 записей с наибольшими `id` среди подходящих под фильтр, а не начиная с самой старой

#### Scenario: Следующая страница содержит более ранние записи
- **WHEN** курсор следующей страницы из предыдущего ответа передан в повторном запросе
- **THEN** все записи второй страницы имеют `id` меньше, чем наименьший `id` первой страницы

#### Scenario: Последняя страница не выдаёт курсор
- **WHEN** проект `P` содержит ровно 50 записей и отправлен `GET /v1/logs?project_id=P&limit=50`
- **THEN** ответ содержит 50 записей и `next_cursor: null` — раньше курсор выдавался всякий раз, когда страница непуста, и клиент узнавал о конце списка только из пустого ответа

#### Scenario: Слишком большой limit приводится к пределу
- **WHEN** отправлен `GET /v1/logs?project_id=P&limit=1000000`
- **THEN** ответ содержит не более 200 записей
