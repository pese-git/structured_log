## Context

`structured_log` задумывался как «сломанный логгер ничего не роняет»: `tryLog` ловит исключение выхода и пишет в `stderr`. Но защита стоит только вокруг `sink.output`, а всё, что до него — склейка контекста, процессоры, сериализация внутри выхода, — либо не защищено, либо защищено ценой потери записи. Интеграции (`_dio`, `_http_client`) превращают структуру в строку раньше, чем её видит `redactKeys`, и маскирование, на которое рассчитывает пользователь, молча не срабатывает.

Заявка закрывает четыре группы замечаний внешнего обзора (см. `proposal.md`), сверенных с кодом. Общий принцип решений: **при выборе между потерей записи и утечкой — терять запись, но видимо**; при выборе между обратной совместимостью и корректностью данных — корректность, пока пакет в `0.x`.

## Goals / Non-Goals

**Goals:**
- Ни одно исключение внутри `structured_log` не выходит в место вызова лога — ни на VM, ни на web.
- Значение в контексте, которое `jsonEncode` не принимает, стоит не больше одного поля, а не записи и не пакета.
- Секрет, переданный структурой в теле HTTP-запроса, маскируется тем же набором имён, что и в контексте.
- Метка времени однозначна.
- Главная библиотека `structured_log` не импортирует `dart:io`.

**Non-Goals:**
- Ленивый контекст (`context: () => {...}`). `isEnabled` покрывает горячие циклы без второго способа передать контекст; вернуться, если замер покажет, что склейка контекста при принятом уровне — узкое место.
- Белые списки заголовков/query (п. 5 обзора), расширяемая `LogCorrelation` (п. 11), диапазон `go_router` (п. 16) — отдельные заявки.
- Сброс буфера при уходе приложения в фон и путь к файлу для мобильных через `path_provider` — требуют жизненного цикла Flutter и новой зависимости; отдельная заявка.
- Маскирование состояний `bloc`: `toString()` непрозрачен, распознавать секреты в произвольном тексте заявка не берётся. Защита остаётся прежней — `describe` (возврат `Map` уже проходит через `redactKeys`, это документируется явно).
- Web для `structured_log_remote_sync` (транспорт — `dart:io` `HttpClient`).

## Decisions

1. **Бросивший процессор → заглушка, а не исходная запись (fail-closed).** Альтернатива «доставить запись как есть» отклонена: бросить мог именно маскирующий процессор, и доставка немаскированного — утечка. Альтернатива «молча отбросить» отклонена: пропажа записи невидима. Заглушка: `event`, `level`, `timestamp`, `logger` (если был), `category` (если был) и `processor_failed: <тип исключения>`; текст исключения не пишется — он может цитировать значение. Плюс одно сообщение внутреннему репортёру (decision 4). Процессоры после бросившего не выполняются; sink'и получают заглушку по обычным правилам фильтрации.

2. **`redactKeys` переносит циклы.** Обход держит множество посещённых контейнеров по идентичности; повторный вход заменяется на `'<cycle>'`. Копия по пути изменения сохраняется (контракт «нечего маскировать — тот же объект» не меняется). Цикл без маскирующего процессора дальше обработает кодировщик (decision 3).

3. **Один безопасный кодировщик на всех: `encodeLogEntry(entry)`.** Публичная функция ядра, `String`. `toEncodable`: `DateTime` → `toUtc().toIso8601String()`, `Duration` → микросекунды числом, `Enum` → `name`, `Uri` → `toString()`, остальное → `toString()`; бросивший `toString()` → `'<Type>'`. Цикл (`JsonCyclicError`) и любой другой сбой кодирования → запись-заглушка с `encoding_failed: <тип>` (те же поля, что в decision 1). Использование: все встроенные выходы ядра, `structured_log_remote_sync`, `debugPrintOutput`. Альтернатива «процессор-нормализатор» отклонена: его можно забыть включить или поставить не туда, а выход, который получил несериализуемое, обязан справиться сам. Нормализация происходит только в момент кодирования; запись, которую видят процессоры и выходы вроде `LogBuffer`, остаётся с исходными объектами.

4. **Внутренний репортёр без `dart:io` в главной библиотеке.** `reportInternalError(String)` через условный импорт: `dart.library.io` → `stderr.writeln`, иначе → `print`. Сам вызов обёрнут в `try` — репортёр не имеет права бросать. Используется вместо прямых `stderr.writeln` в `logger.dart`, `async_file_output.dart` и (через ядро) в `remote_sync`.

5. **UTC по умолчанию.** `toIso8601String()` у локального `DateTime` не пишет смещение, и такую метку нельзя прочитать однозначно; сервер читает её как своё локальное время (`DateTime.tryParse`), что измеримо смещает записи на разницу часовых поясов. Опция `StructlogConfiguration(timestampMode: TimestampMode.utc | TimestampMode.localWithOffset)`; локальный режим пишет смещение (`+03:00`) вручную, а не прежний формат без него — прежний формат не воспроизводится вовсе, он и есть дефект. Явный `timestamp` в контексте по-прежнему перезаписывается: метка — свойство записи, а не прикладное поле, и два формата в одном журнале хуже отсутствия выбора.

6. **Ранний выход по уровню.** `tryLog` первым делом спрашивает `isEnabled(level)`: есть ли включённый sink с `minLevel <= level`. Если нет — ни склейки, ни процессоров. Категорию заранее проверять нельзя (она известна только после склейки), поэтому `isEnabled(level, {category})` для вызывающего принимает категорию необязательно, а ранний выход внутри `tryLog` — только по уровню. Следствие, которое фиксируется явно: процессор с побочным эффектом (счётчик, метрика) больше не видит записи, которые ни один sink не примет. Это и есть цель.

7. **`error`/`stackTrace` — именованные параметры всех методов уровня и `tryLog`.** Поля: `error` (`toString()`, бросивший → `'<Type>'`), `error_type` (`runtimeType`), `stack_trace` (`toString()`). Имена совпадают с тем, что уже пишут `_bloc` (`error`/`error_type`/`stack_trace`) и `_cherrypick` (`stack_trace`) — интеграции на них не переводятся в этой заявке, но и расходиться не будут. Явный параметр перекрывает одноимённый ключ контекста; корреляция по-прежнему перекрывает всё.

8. **Ленивая конфигурация (BREAKING).** `getLogger()` возвращает логгер без захваченной конфигурации; на каждой записи он читает `StructlogConfiguration.current`, и `initialContext` склеивается в момент записи (низший приоритет, как раньше). `BoundLogger(config, ...)` с явной конфигурацией ведёт себя как прежде — это путь для DI и для изолированных тестов. Альтернатива «объект `Structlog` вместо глобального состояния» отклонена в этой заявке: ломает каждое место вызова, а ленивое чтение закрывает конкретную ловушку (логгер в `static final`) без этого. Обратная сторона — код, который *рассчитывал* на захват (держит старый логгер, чтобы писать в старую конфигурацию), меняет поведение; в репозитории такого нет (`_bloc` уже берёт логгер на каждом хуке), в `CHANGELOG` это попадёт через `BREAKING CHANGE:` коммита.

9. **Рендереры становятся выходами.** `jsonLineOutput` (`print(encodeLogEntry(entry))`) и `logfmtOutput` — `OutputFunction`. Процессоры `jsonRenderer`/`logfmtRenderer` остаются, помечены `@Deprecated` с отсылкой на выходы, и тоже переходят на безопасный кодировщик и экранирование — удаляются в следующем минорном. `addLogLevel`/`addTimestamp` — `@Deprecated` без замены.

10. **Экранирование logfmt.** Ключ: всё, кроме `[A-Za-z0-9_.-]`, заменяется на `_`. Значение: строки — в кавычках всегда (как сейчас), с экранированием `\` → `\\`, `"` → `\"`, `\n`/`\r`/`\t` → `\n`/`\r`/`\t`, прочие управляющие символы → `\uXXXX`. Не-строки — через `toEncodable` из decision 3; `Map`/`List` — их JSON в кавычках с тем же экранированием. Перевод строки в выводе невозможен, значит, и подделка строки лога.

11. **Маскирование тел — внутри интеграции, до сериализации.** Обрезка до 1000 символов делает передачу структуры в запись невозможной (обрезать JSON можно только строкой), поэтому структура маскируется *перед* `jsonEncode` тем же `redactKeys` ядра с набором `redactedBodyFields` (по умолчанию `defaultSensitiveKeys`). Строковое тело разбирается, если `Content-Type` — JSON (`application/json`, `*+json`) или `application/x-www-form-urlencoded`; не разобралось — пишется заглушка `'<unparseable body>'`, а не исходная строка. Строка неизвестного типа: в `_dio` и `_http_client` пишется только при `logUnrecognizedBodies: true` (по умолчанию `false`) — включённый `logRequestBody` больше не означает «любая строка как есть». Пользовательский `describeBody` получает **уже замаскированное** тело. Это меняет поведение по умолчанию для тех, кто включил тела, — в сторону меньшей записи, а не утечки; версии интеграций — `-dev`, ломать допустимо.

12. **`io.dart` и web-совместимая главная библиотека (BREAKING).** `package:structured_log/structured_log.dart` перестаёт экспортировать `fileOutput`, `rotatingFileOutput`, `AsyncFileOutput`, `AsyncRotatingFileOutput`; они — в `package:structured_log/io.dart`. Условный экспорт (`if (dart.library.io)`) отклонён: API библиотеки различался бы по платформе, и ошибка «нет такого символа» всплывала бы только при сборке под web. Миграция — одна строка импорта; в репозитории её требует только сервер. Страж — тест, который проверяет, что ни один файл, достижимый из главной библиотеки, не импортирует `dart:io`.

13. **Размер файла с ротацией — в памяти.** Размер читается один раз при создании выхода (`length` существующего файла или 0) и увеличивается на длину записанных байт (`utf8.encode(line).length`); ротация сбрасывает его в 0. Внешнее изменение файла (кто-то обрезал лог) не отслеживается — задокументировано; цена — одна лишняя ротация или одна запоздалая, не потеря данных.

14. **`LogBuffer`: `ListQueue`, снимок по чтению и одно уведомление за ход цикла.** Захват кладёт запись в `ListQueue` (вытеснение спереди без сдвига) и сбрасывает снимок; `entries.value` собирает неизменяемый снимок (`List.unmodifiable`) при первом чтении после изменения, так что копия одна на прочитанную пачку, а не на запись. Уведомление слушателей планируется через `scheduleMicrotask` один раз на пачку. Первоначально предполагалось откладывать и само значение; от этого отказались при реализации: значение, отстающее от `capture`, ломало бы синхронное чтение (`LogViewerController.paused` замораживает именно `entries.value`), а выигрыш даёт отложенное уведомление, а не отложенное значение. Контракт «прочитанный список не меняется» сохраняется. Микрозадача, а не кадр (`SchedulerBinding`): `structured_log_flutter` тестируется и используется вне живого `WidgetsBinding`, а пачка логов за один синхронный участок всё равно схлопывается. `clear()` уведомляет синхронно и гасит ожидающее уведомление — это действие пользователя, и UI должен увидеть пустоту сразу.

15. **`debugPrintOutput` в `structured_log_flutter`.** Одна строка: `HH:mm:ss.SSS LEVEL event key=value…` с экранированием `formatLogfmt` ядра, без ANSI, через `debugPrint`. `debugPrint` ценен здесь троттлингом: при всплеске Android не теряет строки. Длинную строку он не переносит (переноса без `wrapWidth` нет, а с ним строка перестала бы быть одной), и logcat режет строку длиннее ~4 КБ — это задокументировано. Выход по умолчанию ядра не меняется — ядро не знает про Flutter.

16. **`BatchSender` не меняется, хотя буфер теперь из строк.** Тип публичный: его экспортирует `structured_log_remote_sync`, а за ним и прослойка `structured_log_http`. Поэтому внутренний шов принимает закодированные строки, настоящий транспорт отправляет их как есть (`[` + `join(',')` + `]`), а подставной `BatchSender` получает их **декодированными** картами — то, что прочитал бы сервер. Альтернатива «сменить тип на `List<String>`» отклонена: это ломающее изменение ради шва, который, по собственной документации, нужен только тестам. Цена — `jsonDecode` на каждую запись у подставного отправителя, то есть в тестах.

17. **У `structured_log_http_client` заглушка — `<N bytes>`, и тело JSON/формы читается до 64 КиБ.** Тело там — байты, а у ответа, пока его читает читатель, известно только их число, так что «символов» назвать нечем. Разобрать можно только целое тело, а прежний захват (4000 байт — запас под обрезку до 1000 символов) резал любой ответ токен-эндпоинта посередине: замаскировать такой нельзя, и он стал бы `<unparseable body>`. Поэтому для JSON и форм захват — 64 КиБ, для прочего текста — прежний; длиннее 64 КиБ — `<unparseable body>`. Цена — до 64 КиБ памяти на ответ в полёте, и только при включённом `logResponseBody`. Три прежних теста на обрезку и на поток событий (`text/plain`, `text/event-stream`) теперь явно включают `logUnrecognizedBodies`: без него такие тела пишутся размером, и проверяли эти тесты обрезку, а не маскирование.

## Risks / Trade-offs

- Ленивая конфигурация и UTC меняют поведение без ошибки компиляции → `BREAKING CHANGE:` в коммитах, раздел миграции в README ядра (EN/RU), `0.3.0`.
- Заглушка вместо записи при сбое процессора прячет содержимое, нужное для разбора → в заглушке тип исключения и логгер; репортёр пишет стек.
- Ранний выход скрывает записи от процессоров с побочными эффектами → decision 6, задокументировано у `Processor`.
- Разбор строковых тел стоит CPU на каждом логируемом вызове → только при включённых телах, только для JSON/form, тело уже ограничено обрезкой на выходе.
- Каскад `^0.3.0` по всем пакетам — один релиз через `melos version`/`melos publish` по уровням, как у скинов поверх `structured_log_flutter`.

## Migration Plan

1. Ядро (`0.3.0`) публикуется первым; затем интеграции и `remote_sync`; затем сервер/клиент (не публикуются). Констрейнты `structured_log: ^0.3.0` у потребителей поднимает сам `melos version` — так было и в прошлом релизе (`^0.2.2` → `^0.2.2+1` в `c431102`). Поднимать их вручную до выпуска нельзя: локальное ядро ещё `0.2.2+1`, не удовлетворяет `^0.3.0`, и `melos bootstrap` перестал бы подставлять его по пути. До выпуска пакеты, которые уже опираются на новое API ядра (`remote_sync` — на `encodeLogEntry`, `structured_log_flutter` — на `formatLogfmt`), собираются только против рабочей копии; CI подставляет её всем джобам, и Flutter-матрице тоже.
2. Пользователю: `import 'package:structured_log/io.dart';` там, где нужны файловые выходы; метки теперь UTC (вернуть локальные — `timestampMode: TimestampMode.localWithOffset`); `jsonRenderer` в процессорах → `jsonLineOutput` в sink.
3. Откат — предыдущие версии на pub.dev; данных и форматов хранения заявка не меняет.
