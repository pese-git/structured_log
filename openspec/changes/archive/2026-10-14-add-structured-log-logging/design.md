## Context

`package:logging` (1.2/1.3) устроен так:
- `Logger(name).log(level, message, [error, stackTrace])` создаёт `LogRecord` (поля `level`, `message`, `object`, `loggerName`, `time`, `sequenceNumber`, `error`, `stackTrace`, `zone`), но только если `isLoggable(level)`.
- Запись публикуется в broadcast-поток `onRecord` с `sync: true`: слушатель выполняется **внутри** вызова `log()` у того, кто логирует.
- Если `hierarchicalLoggingEnabled == false` (по умолчанию), все записи идут в `Logger.root.onRecord`, а `onRecord` любого другого логгера возвращает тот же поток корня.
- Уровень корня по умолчанию — `Level.INFO`. Записи ниже него не создаются вовсе.
- При `recordStackTraceAtLevel` ≤ уровня записи без стека библиотека сама подставляет `StackTrace.current`. Если `error` при этом `null`, она подставляет строку `'autogenerated stack trace for $level $message'`.

`structured_log` уже умеет маршрутизировать записи по уровню и категории в консоль, файл, встроенный просмотрщик и на сервер, а `BoundLogger.tryLog(level, event, context:, error:, stackTrace:)` никогда не бросает. Не хватает моста между ними.

## Goals / Non-Goals

**Goals:**
- Подключение одной строкой, без правок в библиотеках, которые пишут через `package:logging`.
- Запись моста неотличима по форме от записи, сделанной через `BoundLogger`: те же `error`/`error_type`/`stack_trace`, та же фильтрация sink'ами.
- Мост никогда не бросает в код, вызвавший `Logger.log`, и не зацикливается.
- Чистый Dart, работает под web.

**Non-Goals:**
- Обратное направление (`structured_log` → `package:logging`).
- Управление уровнями `package:logging` (`Logger.root.level`, `hierarchicalLoggingEnabled`) — это глобальное состояние приложения.
- Автоматическое распознавание секретов в тексте сообщений.

## Decisions

1. **Подписка на `onRecord`, а не обёртка логгеров.** Мост слушает поток одного логгера (по умолчанию `Logger.root`, параметр `source`). Чужие библиотеки создают свои `Logger` сами, и обернуть их нельзя; поток корня — единственный шов, который видит всё. Параметр `source` имеет смысл только при `hierarchicalLoggingEnabled == true`; без него поток любого логгера и так совпадает с корневым. Это пишется в dartdoc и README.

2. **Мост не трогает `Logger.root.level`.** По умолчанию корень пропускает только `INFO` и выше, поэтому `FINE` и ниже до моста не доходят: записи не создаются. Выставлять `Level.ALL` внутри `attach()` — значит молча включить вычисление ленивых сообщений во всех библиотеках приложения, и это решение не моста. README показывает строку `Logger.root.level = Level.ALL` рядом с `attach()` и объясняет цену. Отклонённая альтернатива — параметр `rootLevel` у `attach()`: он выглядел бы как настройка моста, хотя меняет поведение всего процесса.

3. **Уровень — по числовому значению `Level`, с заменяемой функцией.** Пороги по умолчанию:

   | `Level.value` | `LogLevel` | Стандартные уровни |
   |---|---|---|
   | < 500 | `trace` | `FINEST` (300), `FINER` (400) |
   | 500–699 | `debug` | `FINE` (500) |
   | 700–899 | `info` | `CONFIG` (700), `INFO` (800) |
   | 900–999 | `warning` | `WARNING` (900) |
   | 1000–1199 | `error` | `SEVERE` (1000) |
   | ≥ 1200 | `critical` | `SHOUT` (1200) |

   Пороги, а не таблица по именам, потому что `Level` открыт: пользовательский `Level('NOTICE', 850)` получает разумный уровень без настройки. `levelOf: LogLevel? Function(Level)` заменяет сопоставление; `null` отбрасывает запись. `CONFIG` отнесён к `info`, а не к `debug`: в экосистеме им пишут однократные сообщения о конфигурации на старте, их ожидают видеть при уровне `info`.

4. **Сообщение — это `event`, имя логгера — это `logger`.** В `structured_log` `event` — короткий идентификатор, а в `package:logging` — свободный текст. Другого места для текста нет, и именно его показывает просмотрщик в строке списка. Запись пишется через `getLogger(record.loggerName)` (корень с пустым именем — `getLogger('root')`). Поэтому поле `logger` совпадает с тем, что пользователь видит в `package:logging`, а конфигурация `structured_log` читается в момент записи (мост ставится один раз и переживает повторный `configure`, как наблюдатель bloc). `category` по умолчанию — `logging`, и это даёт sink'у фильтр «только чужие библиотеки» или «всё, кроме них». `null` убирает поле.

5. **`error` и `stackTrace` передаются в `tryLog` как есть.** Ядро само пишет `error` (через `toString()`), `error_type` и `stack_trace`, поэтому форма совпадает с `BoundLogger.error`, и никакой своей сериализации у моста нет. Исключение одно: если `error` — строка, в точности равная `'autogenerated stack trace for ${record.level} ${record.message}'`, её подставила сама библиотека (`recordStackTraceAtLevel`), и мост её не передаёт, оставляя только `stack_trace`. Сравнение точное, а не по префиксу: настоящая ошибка с таким началом не теряется. `record.object` не пишется — его `toString()` уже лежит в `message`, а сам объект может нести то, что автор сообщения не собирался печатать.

6. **Время записи ставит ядро, а не `record.time`.** `tryLog` сам добавляет `timestamp` в выбранном `TimestampMode`. Слушатель синхронный, поэтому разница с `record.time` — время вызова одного обработчика. Альтернатива — дополнительное поле `logging_time` — отклонена как шум. `sequenceNumber` и `zone` по умолчанию не пишутся. Для них есть `context: Map<String, Object?>? Function(LogRecord)`: дополнительные поля, например id запроса из `record.zone?[#requestId]`, добавляются к записи.

7. **Исключение не выходит из слушателя.** Слушатель выполняется внутри чужого `log()`. Исключение синхронного слушателя не возвращается в `log()`, а уходит в обработчик необработанных ошибок зоны подписки (поведение `dart:async`, закрепляется тестом), а во Flutter это отчёт об ошибке или падение теста. Поэтому `filter`, `levelOf` и `context` вызываются внутри `try`:
   - бросивший `filter` или `levelOf` — запись не пишется;
   - бросивший `context` — запись пишется без дополнительных полей и с полем `bridge_failed`, равным типу исключения.

   Текст исключения не пишется, только тип: он может цитировать значение. Это правило ядра для бросивших процессоров. Само поведение `dart:async` проверено пробой до реализации и закреплено тестом: `log()` возвращается нормально, а исключение слушателя без защиты ушло бы в корневую зону и уронило процесс. `filter` и `levelOf` — это места, где запись отсекается, и README предлагает ими отсекать слишком откровенные логгеры. Поэтому их сбой отбрасывает запись (fail-closed): записать её значило бы пропустить ровно то, что они должны были не пустить. Так же поступают остальные адаптеры с бросившим фильтром (`dio`, `http`, `go_router`, `bloc`). `context` только добавляет поля, и его сбой стоит записи этих полей, а не самой записи (fail-open). Первая редакция писала запись и при сбое `filter`/`levelOf`, с уровнем по умолчанию; это найдено ревью и исправлено до выпуска. Урок `structured_log_bloc`, где `filter` стоит вне `try` (найдено анализом 05.10.2026), учтён с первой редакции.

8. **Рекурсию отсекает сам `package:logging`, и мост на это опирается.** Первая редакция держала флаг «идёт доставка» и отбрасывала записи, пришедшие при поднятом флаге. Мутация показала, что флаг недостижим: пока слушатель моста работает, broadcast-поток `package:logging` ещё рассылает текущую запись, а синхронный контроллер `dart:async` отказывается начинать новую рассылку посреди текущей. Поэтому вложенный `Logger.log` из sink'а или процессора не входит в мост повторно, а бросает `StateError: Cannot fire new event. Controller is already firing an event` тому, кто его вызвал. Флаг удалён, а поведение закреплено тестом. Следствие для пользователя, которое описывается в README: код, вызванный из sink'а или процессора `structured_log` и пишущий через `package:logging` (например, sink поверх HTTP-клиента, который логирует через `logging`), получает этот `StateError` во время доставки моста. Запись, сделанная асинхронно, после завершения доставки, проходит как обычно. Отклонённая альтернатива — асинхронная доставка (`scheduleMicrotask`). Она сняла бы `StateError`, но записи `package:logging` приходили бы позже записей `structured_log`, сделанных в том же синхронном участке, а запись непосредственно перед `exit()` или падением изолята терялась бы. Для журнала, который читают как раз после падения, это хуже.

9. **`attach()`/`detach()` идемпотентны.** Повторный `attach()` на подключённом мосте ничего не делает, и записи не удваиваются. `detach()` отменяет подписку, после него мост можно подключить снова. Форма та же, что у `StructuredLogGoRouter`.

10. **`logging: ^1.2.0`.** Поля `LogRecord`, нужные мосту, неизменны с 1.0. Нижняя граница — 1.2.0, потому что это младшая версия, на которой будут гоняться тесты. CI-джоба запускает тесты второй раз с `logging: 1.2.0` в `pubspec_overrides.yaml`, по образцу второго прогона `cherrypick-observer`. Иначе нижняя граница ничем не подтверждена: анализ 05.10.2026 нашёл это у всех пяти существующих адаптеров.

## Risks / Trade-offs

- **Секреты в тексте сообщений.** Чужие библиотеки иногда пишут в `message` URL, SQL с аргументами или заголовки, и текстовое сообщение `redactKeys` не разбирает. → В README отдельный раздел: `filter` по `loggerName`, `levelOf`, возвращающий `null`, для шумных логгеров и процессор `structured_log`, переписывающий `event`.
- **Нагрузка.** Мост платит за каждую запись внутри `log()` вызывающего. При `Level.ALL` и болтливом драйвере это заметно. → Ранний выход ядра по уровню: если ни один sink не принимает уровень, `tryLog` не склеивает контекст. `filter` вызывается до `getLogger`.
- **Сообщение как `event`.** Агрегация по `event` на сервере для таких записей бессмысленна: каждое сообщение уникально. → Это записано в README, а категория `logging` позволяет отделить такие записи.
- **`package:logging` 2.x может изменить `LogRecord` или поток.** → Констрейнт `^1.2.0`, пересмотр при выходе мажорной версии.
