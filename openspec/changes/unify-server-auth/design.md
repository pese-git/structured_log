## Context

`buildHandler` ([lib/src/http/server.dart](../../../backend/structured_log_server/lib/src/http/server.dart)) собирает 15 маршрутов, навешивая на каждый одну из трёх комбинаций обёрток вручную:

- `jwtAuthGated(...)` — `authMiddleware` + `mustChangePasswordMiddleware` (10 маршрутов);
- `jwtAuth(...)` — только `authMiddleware` (`POST /v1/auth/change-password`);
- `projectKeyAuth(...)` — `projectKeyMiddleware` (`POST /v1/logs`);
- без обёртки — `POST`/`DELETE /v1/auth/token`, `GET /healthz`.

Причина, по которой это не один общий `Pipeline`, зафиксирована в комментарии `buildHandler` и в `tasks.md` 6.4 change `add-structured-log-server`: `GET /v1/logs` и `POST /v1/logs` — один путь, разные методы, разные схемы аутентификации, поэтому схему нельзя выбрать по префиксу пути.

Оба креденшела при этом приезжают в одном заголовке. Спека фиксирует `Authorization: Bearer <access-token>` для management-эндпоинтов и `GET /v1/logs` (`log-server-auth`) и `Authorization: Bearer <project-secret-key>` для `POST /v1/logs` (`log-server-api`, `structured-log-http-sender`). То есть единому middleware не нужно менять транспорт — только уметь отличить один токен от другого.

Существенная деталь текущего кода: авторизация (RBAC) в этом сервере **уже** живёт внутри хендлеров, а не отдельным слоем (decision 4.4 change `add-structured-log-server`). Каждый из 10 JWT-маршрутов первой же строкой дёргает `request.verifiedIdentity`, чтобы резолвить роли — 10 маршрутов, ровно 10 обращений в `lib/src/http/routes/*.dart`. Перенос проверки схемы аутентификации в тело хендлера не вводит новый паттерн, а ложится на существующий.

## Goals / Non-Goals

**Goals:**

- Одна точка аутентификации: ровно один middleware в `Pipeline`, знающий про заголовок `Authorization`, вместо двух поточечных плюс третьего гейта.
- Таблица маршрутов в `buildHandler` сводится к «метод + путь → хендлер», без обёрток.
- Невозможность «забыть гейт» перестаёт зависеть от внимательности автора маршрута и обеспечивается типом (`Principal`) плюс табличным тестом по всей таблице маршрутов.
- Список исключений гейта смены пароля перестаёт быть списком путей.

**Non-Goals:**

- `shelf_router_generator` — унификация его разблокирует (генератор не умеет аннотировать middleware), но внедрять его в рамках этой change не будем; это отдельное решение со своей ценой (хендлеры в классы, path-параметры только `String`).
- Изменение RBAC, модели ролей, выдачи/отзыва токенов, `token_version`.
- Rate limiting и квоты (`log-server-rate-limit`, `log-server-quotas`) — они привязаны к принципалу, но их реализация вне объёма.
- Поддержка legacy-ключей без префикса (см. Migration Plan — их не существует).

## Decisions

1. **Один резолвящий middleware, а не один отвергающий.**
   Middleware читает `Authorization`, определяет тип креденшела, кладёт `Principal` в контекст и **всегда** передаёт запрос дальше — включая случай «заголовка нет» и «токен недействителен». Альтернатива — отвергать прямо в middleware, со списком публичных путей-исключений. Отклонено: публичные маршруты есть уже сейчас (`GET /healthz`, `POST`/`DELETE /v1/auth/token`), а по спеке добавятся `POST /v1/auth/register`, `/v1/auth/password-reset`, `/v1/auth/password-reset/confirm`, `/v1/auth/verify-email`, `/v1/auth/verify-email/resend` — то есть отвергающий middleware немедленно завёл бы внутри себя список путей, вернув в auth-слой ровно то знание о роутинге, ради выноса которого всё и затевается.

2. **`Principal` — sealed-иерархия из трёх вариантов, не `VerifiedIdentity?`.**
   `UserPrincipal(VerifiedIdentity)`, `ProjectPrincipal(int projectId)`, `AnonymousPrincipal()`. Альтернатива — класть в контекст nullable-личность и nullable-`projectId` двумя ключами. Отклонено: два независимых nullable-поля допускают состояния, которых не существует (оба заданы; оба пусты, но креденшел был предъявлен и оказался мусорным), и заставляют каждый хендлер проверять два поля вместо одного `switch`. Явный `AnonymousPrincipal` вместо `null` — чтобы «креденшел не предъявлен» было значением, а не отсутствием значения.
   `AnonymousPrincipal` покрывает и «заголовка нет», и «токен предъявлен, но недействителен/отозван/истёк»: с точки зрения хендлера это один и тот же ответ 401, а различать их в контексте значило бы тащить причину отказа через весь стек ради текста сообщения.

3. **401 выдаёт хендлер, через `ApiError`, а не middleware.**
   Типизированные аксессоры на `Request`: `requireUser({bool allowTemporaryPassword = false})` → `VerifiedIdentity` и `requireProject()` → `int`, оба бросают `ApiError.unauthorized(<сообщение>)`. `errorHandlingMiddleware` уже превращает `ApiError` в JSON-конверт `log-server-api`, так что новой машинерии не требуется. Это согласовано с тем, как в этом сервере устроен RBAC (внутри хендлера, decision 4.4 `add-structured-log-server`) — аутентификационная и авторизационная проверки оказываются в одном месте и в одном стиле, а не в двух разных слоях.
   Различающиеся сообщения текущих middleware («Missing project secret key.» / «Missing bearer access token.» / «Invalid, expired, or revoked access token.») сохраняются: их формирует аксессор, который знает, какой тип принципала требуется.

4. **Дискриминатор креденшела — фиксированный префикс `slk_` у секретного ключа проекта.**
   Порядок распознавания: `slk_` → поиск по хэшу в `project_secret_keys`; иначе → верификация JWT через `IdentityProvider`; заголовка нет → `AnonymousPrincipal`.
   Коллизия исключена конструктивно: JWT — это base64url от JSON-объекта, поэтому всегда начинается с `eyJ`.
   Альтернативы:
   - *Различать по форме токена* (JWT — три сегмента через точку; ключ — `base64UrlEncode` без padding, точек не содержит). Отклонено: работает, но это неявный контракт, который ломается молча при любой смене формата любой из двух сторон, и не читается в месте, где формат задаётся.
   - *Отдельный заголовок для ключа* (`X-Project-Key`). Отклонено: меняет wire-контракт, зафиксированный в трёх спеках (`log-server-api`, `structured-log-http-sender`, `log-server-auth`), ради того же результата.
   - *Пробовать JWT, при неудаче идти в БД за хэшем.* Отклонено: даёт лишний запрос к `project_secret_keys` на каждый мусорный токен, то есть превращает неаутентифицированный трафик в нагрузку на БД.
   Побочная выгода префикса, не бывшая целью, но существенная: ключ становится узнаваемым для secret-scanning и при разборе инцидентов — ровно так работают `ghp_`/`sk-`/`AKIA`.

5. **Префикс — только у секретных ключей проектов, не у всего, что генерирует `generateRandomToken()`.**
   Той же функцией генерируются refresh-токены, но они никогда не попадают в `Authorization` (передаются в теле `POST /v1/auth/token` как `refresh_token`) и дискриминировать их не от чего. `generateRandomToken()` остаётся как есть; добавляется тонкая `generateProjectSecretKey()` = `'slk_' + generateRandomToken()`. Хэшируется (`hashToken`) значение **вместе с префиксом** — то есть присланный заголовок хэшируется целиком, без предварительного отрезания префикса, и в `key_hash` нечего мигрировать при возможной смене префикса в будущем.

6. **Гейт смены пароля — параметр аксессора, а не слой и не список путей.**
   `requireUser()` по умолчанию бросает 403 `must_change_password`, если у личности взведён флаг; `requireUser(allowTemporaryPassword: true)` — явный opt-out. Альтернатива — оставить отдельный middleware, применяемый глобально, со списком путей-исключений. Отклонено по той же причине, что и в decision 1: список исключений по спеке уже четыре эндпоинта (`POST /v1/auth/change-password`, `DELETE /v1/users/me`, `POST` и `DELETE /v1/auth/token`), из которых реализован один, и он будет пополняться — в виде флага он живёт в теле того хендлера, который является исключением, и читается вместе с ним, а не в списке строк в чужом файле.

7. **Fail-closed обеспечивается табличным тестом по таблице маршрутов, а не обозримостью `buildHandler`.**
   Это цена, которую change платит осознанно: сейчас «на каком маршруте какой гейт» видно глазами в одном файле, после унификации — нет. Заменяется механической проверкой: тест перечисляет все не-публичные маршруты (метод + путь) и для каждого проверяет, что предъявление принципала неверного типа и отсутствие креденшела дают 401. Правило для новых маршрутов — любой не-публичный хендлер начинается с `require*`, публичный перечислен в списке публичных маршрутов этого теста. Список публичных маршрутов в тесте — единственное место, где «публичность» проговаривается явно, и добавление туда маршрута — заметное в ревью действие.
   Структурно риск и так невелик: все 10 JWT-хендлеров обращаются к личности в первых строках ради RBAC, то есть не вызвать `requireUser()` можно только в хендлере, которому личность не нужна вообще — таких среди реализованных нет.

## Risks / Trade-offs

- **Новый хендлер, которому личность не нужна, окажется доступен по секретному ключу проекта** (низкодоверенный креденшел, раздаваемый клиентским приложениям) → табличный тест из decision 7 падает на таком маршруте, пока он не попал либо под `require*`, либо в явный список публичных.
- **Потеря «одного взгляда» на таблицу маршрутов** → принимается; компенсация — decision 7. Обратная сторона того же трейдоффа: таблица маршрутов становится тривиальной и перестаёт быть местом, где можно ошибиться в чём-либо, кроме пути.
- **Мусорный `Authorization` теперь всегда проходит через дискриминатор до хендлера** → стоимость ограничена одним индексированным lookup (префикс есть) либо одной проверкой подписи (префикса нет), то есть не больше, чем сейчас делает соответствующий поточечный middleware.
- **Спека `log-server-auth` живёт в незаархивированной change `add-structured-log-server`** → delta этой change читается поверх той; архивировать строго в порядке «сначала `add-structured-log-server`, потом `unify-server-auth`».
- **Ранее выданные секретные ключи перестают работать** → в проде сервер не развёрнут; локальные dev-базы — пересоздать ключ через `POST /v1/projects/:id/secret-keys`. См. Migration Plan.

## Migration Plan

1. Изменение формата ключа не требует миграции схемы: `project_secret_keys.key_hash` хранит SHA-256 от присланной строки, длина и тип не меняются.
2. Ключи, выданные до этой change, после неё не аутентифицируются (у них нет префикса, значит они уходят в JWT-ветку и не проходят верификацию). Развёрнутых инсталляций нет — `structured_log_server` находится в разработке (Этап 1), `structured_log_http` ещё не реализован и ни один клиент ключ не хранит. Действие для локальных баз: выдать ключ заново.
3. Порядок работ внутри change — сначала `Principal` + middleware + аксессоры с сохранением существующего поведения маршрутов, затем снятие обёрток в `buildHandler`, затем табличный тест. На каждом шаге `dart test` пакета зелёный.
4. Откат — обычный revert коммита; внешних потребителей, кроме локальных dev-ключей, нет.

## Open Questions

- Нужен ли переходный режим «ключ без префикса тоже принимается»? Предлагается нет (Migration Plan п. 2); вопрос закрывается вместе с принятием этой change.
- Формально `AnonymousPrincipal` схлопывает «креденшела нет» и «креденшел недействителен» — если позже потребуется различать их в `log-server-audit` (запись неудачных попыток аутентификации), в `AnonymousPrincipal` добавится причина отказа. На текущий объём аудита это не требуется.
