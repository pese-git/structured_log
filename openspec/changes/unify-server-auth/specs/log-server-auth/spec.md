## ADDED Requirements

### Requirement: Единая точка аутентификации резолвит предъявленный креденшел в тип принципала
Сервер SHALL обрабатывать заголовок `Authorization: Bearer <...>` ровно в одном месте, общем для всех эндпоинтов, и SHALL резолвить предъявленное значение в один из трёх типов принципала запроса: **пользователь** (действительный access-токен — см. требование про `token_version`), **проект** (действительный, не отозванный секретный ключ проекта, резолвящий `project_id`) или **аноним** (заголовок отсутствует, либо предъявленное значение не является ни действительным access-токеном, ни действительным секретным ключом проекта). Эта точка SHALL не отклонять запрос сама по себе — отсутствие или недействительность креденшела SHALL резолвиться в принципала «аноним» и передаваться эндпоинту, поскольку часть эндпоинтов (`GET /healthz`, `POST`/`DELETE /v1/auth/token`, а также `POST /v1/auth/register`, `/v1/auth/password-reset`, `/v1/auth/verify-email` и их производные) обслуживается без аутентификации.

Каждый эндпоинт, требующий аутентификации, SHALL объявлять требуемый тип принципала и SHALL отвечать 401 с общим JSON-конвертом ошибок (`log-server-api`), если тип принципала запроса не совпадает с требуемым — включая случай принципала «аноним». Требование о типе принципала SHALL проверяться до любой проверки прав (`log-server-rbac`) и до валидации тела запроса.

#### Scenario: Секретный ключ проекта не открывает management-эндпоинт
- **WHEN** запрос к management-эндпоинту или `GET /v1/logs` отправлен с заголовком `Authorization: Bearer <действующий секретный ключ проекта>` вместо access-токена
- **THEN** сервер отвечает 401 и не выполняет действие эндпоинта

#### Scenario: Access-токен не открывает приём логов
- **WHEN** `POST /v1/logs` отправлен с заголовком `Authorization: Bearer <действительный access-токен пользователя, имеющего права на этот проект>` вместо секретного ключа проекта
- **THEN** сервер отвечает 401 и не сохраняет ни одной записи

#### Scenario: Публичный эндпоинт обслуживается без креденшела
- **WHEN** `GET /healthz` или `POST /v1/auth/token` отправлен без заголовка `Authorization`
- **THEN** сервер обрабатывает запрос штатно, не отвечая 401 по причине отсутствия креденшела

#### Scenario: Недействительный креденшел неотличим от отсутствующего
- **WHEN** запрос к эндпоинту, требующему аутентификации, отправлен с заголовком `Authorization: Bearer <значение, не являющееся ни действительным access-токеном, ни действующим секретным ключом проекта>`
- **THEN** сервер отвечает 401 — так же, как если бы заголовок отсутствовал

## MODIFIED Requirements

### Requirement: Аутентификация приёма логов по секретному ключу проекта
Секретные ключи проектов SHALL храниться как криптографический хэш случайно сгенерированного токена (не пароль пользователя, не JWT); при аутентификации `POST /v1/logs` (см. `log-server-api`) сервер SHALL находить соответствующий `project_id` по хэшу присланного ключа, отклоняя запрос, если совпадение не найдено или найденный ключ отозван (`revoked_at` не `null`).

Выдаваемое значение секретного ключа SHALL начинаться с фиксированного префикса `slk_`, отличающего его от access-токена в общем для обеих схем заголовке `Authorization: Bearer <...>`; префикс SHALL быть частью значения ключа (формат заголовка не меняется) и SHALL входить в хэшируемую строку. Значение, предъявленное без этого префикса, SHALL не рассматриваться как секретный ключ проекта и SHALL не приводить к поиску по `project_secret_keys`.

#### Scenario: Секретный ключ показывается только один раз
- **WHEN** владелец группы или администратор создаёт новый секретный ключ проекта
- **THEN** ответ API содержит ключ в открытом виде ровно один раз (в ответе на создание); последующие запросы (например, список ключей проекта) возвращают только метаданные (`label`, `created_at`, `revoked_at`), не сам ключ

#### Scenario: Несколько активных ключей позволяют ротацию без даунтайма
- **WHEN** у проекта есть два одновременно активных, не отозванных секретных ключа, и приложение продолжает слать логи со старым ключом, пока новый уже выдан
- **THEN** приём логов успешен с обоих ключей, пока старый явно не отозван

#### Scenario: Выданный ключ несёт префикс схемы
- **WHEN** владелец группы или администратор создаёт новый секретный ключ проекта
- **THEN** возвращённое в открытом виде значение начинается с `slk_`, и приём логов с этим значением в заголовке `Authorization: Bearer <...>` успешен
