## Context

`StructuredLogDatabase` (`lib/src/storage/database.dart`) — один `drift`-класс поверх `NativeDatabase`, и SQLite-специфика вплетена в него и в четыре соседних файла не как одно место, а как несколько независимых:

- **Открытие БД**: `NativeDatabase.createInBackground(File(path), readPool: N, setup: ...)` — `setup` ставит `PRAGMA journal_mode=WAL`/`foreign_keys=ON`/`busy_timeout=5000`/`synchronous=NORMAL`; `readPool` — изоляты-читатели, обходящие то, что у SQLite одно файловое соединение-писатель (`technology-stack.md`).
- **DB-side значение по умолчанию `currentDateAndTime`** — 10 колонок `createdAt` (`Users`, `Groups`, `Teams`, `Projects`, `ProjectSecretKeys`, `RoleAssignments`, `RefreshTokens`, `PasswordResetTokens`, `EmailVerificationTokens`, `AuditLogEntries`) полагаются на это SQLite-выражение как значение по умолчанию на стороне БД.
- **Булевы литералы в сыром SQL**: `WHERE is_primary_admin = 1` (уникальный частичный индекс в `database.dart`), `is_active = 1`, `is_primary_admin = 1` (`create_admin.dart`, проверки перед bootstrap) — SQLite не различает `BOOLEAN`/`INTEGER`, Postgres различает строго: `= 1` там не сравнится с булевой колонкой вообще.
- **`last_insert_rowid()` + чтение диапазоном id** (`log_store.dart`, `DriftLogStore._insert`) — горячий путь приёма логов, сознательно не `insertReturning` на запись (в этой же сессии измерено: один батч-`INSERT` + одно чтение диапазона против `insertReturning` на каждую запись — прямая причина роста с 6,7 до 22 тыс. записей/с, `AGENTS.md`). Опирается на то, что `AUTOINCREMENT` растёт монотонно на единственном соединении внутри транзакции, которая его держит.
- **`json_extract`** (`log_filter.dart`) и весь `buildLogQuerySql`/`buildAuditQuerySql` (`query.dart`, `audit_query.dart`) — собраны как один сырой SQL-фрагмент с `?`-плейсхолдерами именно потому, что `LIKE`/`json_extract` не выражаются типизированным query-builder'ом drift (`design.md` decision 3 в `add-structured-log-server`).
- **Миграции**: `MigrationStrategy` использует только `Migrator.createAll()` (создание) и сырые `customStatement` (`CREATE INDEX`/`CREATE UNIQUE INDEX`) для добавления индексов при `onUpgrade` — `Migrator.alterTable`, о неподдержке которого под Postgres прямо предупреждает документация `drift`, в этом коде вообще не используется. Это существенно сужает риск: то, что реально ломается под Postgres, — это не факт использования `MigrationStrategy` как таковой, а конкретные литералы внутри сырых `customStatement`/`customSelect` выше.

`drift_postgres` (официальный, `simolus3/drift`) даёт `PgDatabase` как второй `QueryExecutor` и обещает, что тот же Dart DSL таблиц/запросов генерирует Postgres-совместимый SQL «без изменения кода запросов» для типизированной части — но explicitly не для сырых фрагментов и не для `DateTime`-колонок с SQLite-специфичным дефолтом.

## Goals / Non-Goals

**Goals:**
- Оператор выбирает backend хранения при развёртывании (`--db-backend=sqlite|postgres`); SQLite остаётся дефолтом и не меняет поведения ни на бит при отсутствии флага.
- Каждое из перечисленных выше SQLite-специфичных мест портируется осознанно, с явным решением по каждому, а не одним общим «drift разберётся».
- Поведение, видимое вызывающему API (round-trip произвольных `context`-полей, порядок id, отсутствие блокировки чтения при конкурентной записи), остаётся одинаковым независимо от backend'а — расходится только механизм.

**Non-Goals:**
- Миграция данных из уже работающей SQLite-инсталляции в Postgres — вне объёма (см. proposal.md).
- Переключение backend'а на лету/без перезапуска — не рассматривается, тем же принципом, что и вся остальная конфигурация.
- Шардирование/репликация/HA-топология Postgres — это ответственность инфраструктуры оператора, не этого сервиса.
- Полное дублирование тестового набора против Postgres — только та часть, что реально зависит от диалекта (см. Decisions, CI).

## Decisions

**1. Выбор executor'а — фабрика в `StructuredLogDatabase`, выбираемая конфигурацией, а не два параллельных класса.**
`StructuredLogDatabase.open(path, readPool:)` остаётся как есть (SQLite, поведение не меняется); рядом — новый `StructuredLogDatabase.openPostgres(...)`, конструирующий `PgDatabase`. `bin/server.dart` вызывает нужный по `ServerConfig.dbBackend`. Один класс `StructuredLogDatabase` (`_$StructuredLogDatabase`), не два — иначе весь остальной код (`LogStore`, роуты, DI-модули) должен был бы знать о двух типах БД, а не об одном.

**1a. `--db-path` становится обязательным только при `--db-backend=sqlite` — тем же механизмом, что уже делает per-command обязательность параметров (`log-server-config`), не отдельным правилом.**
Найдено при сверке с уже существующей спекой: «Requirement: Набор обязательных параметров зависит от выполняемой команды» сейчас буквально говорит «для `create-admin` обязателен только путь к базе данных» — это верно только для SQLite. И `serve`, и `create-admin` резолвят конфигурацию одним и тем же `ConfigResolver`, так что правило «обязательность зависит от команды» расширяется до «обязательность зависит от команды **и** от выбранного `db-backend`»: `db-path` обязателен при `sqlite`, host/port/database/username Postgres — при `postgres`, для обеих команд одинаково (delta в `specs/log-server-config`).

**2. `createdAt` перестаёт полагаться на DB-side default — задаётся explicit при вставке через уже существующий паттерн инъекции часов.**
`currentDateAndTime` — SQLite-only выражение; вместо диалект-специфичного дефолта (`DialectAwareSqlType`/`PgTypes.timestampWithTimezone`) — убрать `.withDefault(currentDateAndTime)()` у всех 10 колонок и передавать `createdAt: Value(clock())` в момент вставки. `DateTime Function() clock` уже используется как внедряемая зависимость в нескольких местах сервера (`purge_job.dart`, `rate_limit_middleware.dart`, `logging_middleware.dart`, `http/server.dart`, `bucket_store.dart`) — тот же приём, не новый. Решение диалект-агностично: код вставки не знает, какой backend под ним, и не нужно поддерживать два разных DB-side выражения по умолчанию.

**3. Булевы литералы в сыром SQL (`= 1`) заменяются на связанные переменные (`Variable.withBool`), а не на диалект-условие.**
`is_active = 1`/`is_primary_admin = 1` в `create_admin.dart` — заменить на параметризованное сравнение (`is_active = ?`, `Variable.withBool(true)`). drift сам сериализует `bool`-переменную под правильный тип целевого диалекта — фрагмент становится переносимым автоматически, без `if (dialect == postgres)`. Тот же приём уже используется в `query.dart` для остальных условий.

**4. Частичный уникальный индекс (`WHERE is_primary_admin = 1`) — единственное место, которому *нужна* диалект-ветка, потому что DDL не параметризуется.**
`CREATE UNIQUE INDEX ... WHERE is_primary_admin = 1` в `database.dart` — DDL-выражение, `Variable` сюда не подставить. Решение: список индексных выражений в `database.dart` получает диалект-осведомлённый вариант (`WHERE is_primary_admin = 1` для SQLite, `WHERE is_primary_admin = true` для Postgres), выбираемый по `db.dialect` в момент миграции — единственная точка ветвления такого рода во всей схеме.

**5. Батч-вставка логов (`DriftLogStore._insert`) — отдельная реализация под Postgres, не расширение SQLite-ветки диалект-условием.**
Это единственный по-настоящему hot-path кусок SQL, и он написан именно так ради измеренной пропускной способности (см. Context). Под Postgres — не range-based чтение после `last_insert_rowid()` (SQLite-специфичная функция, и сама предпосылка «одно соединение держит диапазон id» для Postgres неверна общем случае), а один multi-row `INSERT ... VALUES (...), (...), ... RETURNING *` — тоже один round-trip, и корректность не опирается на диапазон: возвращённые строки и есть вставленные, безо всякого предположения о соседях по id. `DriftLogStore._insert` ветвится по `db.dialect` на приватный SQLite- и Postgres-метод; интерфейс `LogStore` не меняется — он и заведён как «поведение, не `drift` напрямую» (существующий doc-comment).

**6. `PRAGMA`-настройка (`journal_mode`/`busy_timeout`/`synchronous`) — не переносится на Postgres ни в каком виде, потому что переносить нечего.**
SQLite-тюнинг в `setup:` существует ради компромиссов, которые у Postgres не стоят так же: WAL-режим, таймаут занятости файла, `synchronous=NORMAL` — всё это про то, что SQLite-файл может держать только один писатель. У Postgres MVCC и конкурентная запись — базовое поведение сервера, а не то, что нужно включать. `StructuredLogDatabase.openPostgres` не содержит эквивалента `setup:` вообще — только параметры пула соединений (Decision 8) и, отдельно, TLS-режим (Decision 9).

**7. Миграции: используется существующий механизм drift (`MigrationStrategy`/`schemaVersion`/`beforeOpen`) без изменений формы — под Postgres он опирается на собственную таблицу версии drift (`__schema`), не на наш код.**
Сам код `add-postgres-backend` не вызывает `Migrator.alterTable` ни разу (см. Context) — то есть предупреждение документации drift про неподдержку `alterTable` под Postgres не задевает этот кодопуть напрямую. `onCreate`/`onUpgrade` остаются как есть, с точечными диалект-ветками из Decision 4. Явно принимается предупреждение авторов drift, что их `__schema`-подход «не годится для больших развёртываний» — тем же принципом, каким в своё время отклонили FTS5 (decision 3, `add-structured-log-server`): проще, чем нужно для MVP, пересмотреть при реальном упоре.

**8. Пул соединений Postgres — новая настройка, отдельная от `--db-read-pool-size`, а не его переиспользование.**
Семантика разная: `--db-read-pool-size` — изоляты только-для-чтения *рядом* с одним писателем (обход ограничения SQLite). Под Postgres запись и чтение равноправно делят один пул `package:postgres`'s `Pool` — нет отдельного «читательского» пула. Новая настройка — `--db-postgres-pool-size` (дефолт — открытый вопрос, ближе к типичным 10 для сервиса такого размера). При `--db-backend=postgres` `--db-read-pool-size` игнорируется с предупреждением при старте (тот же принцип, что «неизвестная переменная с префиксом только предупреждает» — `log-server-config`); при `--db-backend=sqlite` (или неявном дефолте) новая настройка, наоборот, ничего не делает.

**9. Секреты и TLS для подключения к Postgres следуют уже существующему конвенту, не изобретают новый.**
`--db-postgres-host`/`-port`/`-database`/`-username` — обычные аргументы (не секреты, видны в `--print-config`); пароль — `STRUCTURED_LOG_DB_POSTGRES_PASSWORD`/`_FILE`, тот же файловый паттерн, что у JWT-секрета/SMTP/bootstrap-пароля админа (`log-server-config`, «Секреты не принимаются в аргументах командной строки»). TLS-режим — отдельная настройка (`--db-postgres-ssl-mode`, дефолт — открытый вопрос, но не `disable`: управляемые Postgres почти всегда требуют TLS, а разработческий localhost должен уметь явно его выключить).

**10. CI получает отдельный тег тестов, не полное дублирование прогона.**
Основной набор тестов сервера остаётся против SQLite (быстрый, без внешней зависимости — как сейчас). Новый тег (`postgres`, по образцу уже существующего `integration` в `dart_test.yaml`) покрывает только диалект-чувствительный код: создание схемы, батч-вставка логов (Decision 5), фильтр по `context`, проверки перед bootstrap (Decision 3/4). GitHub Actions service-контейнер `postgres:` для джобы `structured_log_server`, тем же паттерном ожидания готовности, что уже есть для `chromedriver` в джобе `admin-client-flow`.

## Risks / Trade-offs

- **[Риск] Перенос `?`-плейсхолдеров сырых `customSelect`/`customStatement` на Postgres (`$1`/`$2` у него внутри) — предположение, не проверенное на этом кодовом пути.** → Митигейшн: первая задача реализации — спайк, доказывающий на настоящем Postgres, что хотя бы один представительный сырой фрагмент (динамический `WHERE` из `buildAuditQuerySql`) отрабатывает без изменения текста запроса; если нет — тексты фрагментов ветвятся по диалекту явно, объём растёт, но контролируемо (список мест уже перечислен в Context).
- **[Риск] Два backend'а — два пути, которые схемное изменение обязано учитывать одновременно.** → Митигейшн: диалект-чувствительный тег в CI (Decision 10) ловит регрессию сразу; в `AGENTS.md` фиксируется короткий чеклист «что проверить при добавлении колонки/индекса» (DB-side default → `clock()`, булев литерал в сыром SQL → `Variable`, DDL-литерал → диалект-ветка).
- **[Риск] `__schema`-подход drift к версионированию схемы под Postgres сами авторы называют не годящимся для больших развёртываний.** → Митигейшн: осознанно принято для MVP-объёма этой доработки, тем же принципом, что decision 3 (`add-structured-log-server`) отклонил FTS5; пересмотр — если реальный оператор столкнётся с ограничением на практике, не заранее.
- **[Trade-off] Два backend'а — две операционные истории (бэкап/восстановление, мониторинг), документируемые отдельно в `docs/operations/`.** Смешивать их в один текст хуже, чем держать раздельно, несмотря на дублирование структуры документа.
- **[Риск] Недоступный Postgres на старте (сеть/креды) должен отказывать так же, как сейчас отказывает плохой путь к SQLite-файлу — не позже, не рантайм-крашем на первом запросе.** → Митигейшн: попытка подключения — часть уже существующей фазы «ничего не стартует, пока всё не проверено» (`log-server-config`), отчитывается через тот же код выхода `78`.

## Migration Plan

Чисто аддитивно: без `--db-backend` (или с явным `--db-backend=sqlite`) поведение и конфигурация не меняются ни в одном байте. Postgres — осознанный opt-in оператора, начинающего с пустой базы; пути «сконвертировать существующую SQLite-базу в Postgres» этот change не даёт (см. proposal.md, «Вне периметра»). Откат — предыдущий бинарь/конфигурация; поскольку выбор backend'а нигде не хранится, кроме конфигурации запуска, откат безопасен, пока оператор не успел записать в Postgres данные, которые хочет сохранить.

## Open Questions

- Дефолт `--db-postgres-pool-size` и `--db-postgres-ssl-mode` — конкретные значения решаются в `tasks.md`/реализации, не здесь.
- Держится ли перенос `?`-плейсхолдеров без изменений (первый риск в «Risks / Trade-offs») — решает спайк в начале реализации; если нет, `tasks.md` получает дополнительные задачи на диалект-ветки в `query.dart`/`audit_query.dart`.
- GitHub Actions hosted `services: postgres:` против `docker run postgres` вручную с явным wait-for-healthy шагом — решается на этапе правки `.github/workflows/ci.yml`, ориентир — уже принятый в репозитории паттерн для `chromedriver`.
