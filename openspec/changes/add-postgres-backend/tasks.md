## 2. Schema portability

- [x] 2.1/2.2 ~~Remove `.withDefault(currentDateAndTime)()` from the 10 `createdAt` columns; thread `Value(clock())` through every insert call site~~ — **verified unnecessary, no code change.** Tried this exact refactor first: it compiled (after removing the default, drift makes `createdAt` a required field on 10+ generated `*Companion.insert()` factories) but broke ~200 existing call sites, almost all pre-existing test fixtures that never cared about the exact value. Before grinding through all of them, re-verified the premise directly against a real Postgres instance: `Migrator.createAll()` creates all 10 columns with `currentDateAndTime` as their default with no complaint, and inserting without an explicit `createdAt` returns a row with a real, DB-assigned timestamp. Root cause of the original (wrong) assumption, confirmed against `drift`'s own source (`query_builder/expressions/datetimes.dart`): `currentDateAndTime` picks one of two SQL forms based on the `store_date_time_values_as_text` **builder option** (not the dialect) — `strftime('%s', CURRENT_TIMESTAMP)` (SQLite-only `strftime`) when off, plain `CURRENT_TIMESTAMP` (portable ANSI SQL) when on. This package already has `store_date_time_values_as_text: true` in `build.yaml`, for an unrelated reason (fractional-second precision for `structured_log` timestamps) — so the SQLite-only branch was never reachable here in the first place. Reverted the schema/generated-code change; `dart analyze`/`dart test --exclude-tags integration` (906 tests) back to clean/green. See `design.md` Decision 2 for the full writeup.

## 4. Hot-path ports

- [x] 4.1 `DriftLogStore._insert` (`log_store.dart`) branches on `executor.dialect`: `_insertSqlite` unchanged (`last_insert_rowid()` + range read); `_insertPostgres` builds one multi-row `INSERT INTO log_entries (...) VALUES (...), (...), ... RETURNING *` (`customWriteReturning`) — one round trip, like the SQLite path, but no id-range assumption. Column values come off each `LogEntriesCompanion` positionally; a `null` field is written as the literal `NULL` in the SQL text rather than attempted as a bound `Variable` (which has no null form — `T extends Object`); every non-null value goes through a small `_boundValue` dispatch (`int`/`String`/`DateTime`/`bool`) and the finished SQL's `?`s are numbered by the same `placeholdersForDialect` every other raw fragment uses (decision 3a).
- [x] 4.2 `test/storage/postgres_log_store_test.dart` (tag `postgres`, 6 tests): ties entries to the given project with consecutive ids in input order; nullable fields round-trip (including every one left absent); an unstorable batch leaves nothing behind (atomicity); `insertRows` respects each companion's own pre-set `projectId`; concurrent batches each get back exactly their own rows with no id collisions (the id-adjacency risk `_insertPostgres` specifically avoids); an empty batch is a no-op. Not a shared/parameterized suite with the SQLite tests in the end — `test/storage/log_store_test.dart` leans on SQLite-only tooling (a `QueryExecutor`-intercepting `Recorder`, for statement-count assertions) that has no Postgres equivalent, so the Postgres file asserts the same *behavioral* properties independently instead.
- [x] 4.3 `LogFilter.appendConditions` (`log_filter.dart`) takes a `required SqlDialect dialect` after all (`appendConditions` itself, not just its callers — `contextEquals` needed the branch, everything else didn't) and, for Postgres, rewrites `json_extract(context_json, ?)` (a SQLite/JSON1 function, absent on Postgres) to `(context_json::jsonb #>> ?::text[])` — `#>>` returns text directly by a `jsonb` path array, built by splitting the dotted key the same way SQLite's own `$.a.b` path syntax already does. One accepted, documented asymmetry carried over: a JSON boolean context value renders as `1`/`0` under SQLite (no boolean type, comment already explains this as "surprising, not something to improve on") but as the text `true`/`false` under Postgres — `LogFilter.matches` (the in-memory predicate the live stream uses) has no dialect to consult, so it always renders the SQLite way; documented on `_asSqlText`, not fixed. `test/storage/postgres_log_filter_test.dart` (tag `postgres`, 5 tests): number/string equivalence, JSON null never matching, a missing key, a nested (dotted) key, and the boolean asymmetry itself (asserting the Postgres-side behavior explicitly, the mirror image of the assertion already pinned on the SQLite side).

**Found while running the Postgres-tagged suite as a whole (not per file): the three `postgres`-tagged test files share one physical Postgres database with no per-file isolation** (unlike SQLite's `NativeDatabase.memory()`, a fresh instance per test) — each file's own `TRUNCATE` in `setUp` collided with another file's fixtures at `dart test`'s default concurrency, and several tests failed on leftover or missing rows that belonged to a *different* file's `setUp` racing in the same window. Every file passes run individually; the fix is `--concurrency=1` for this tag, not a code change — documented on the tag itself (`dart_test.yaml`) and something section 6's CI wiring needs to carry.
