# Развёртывание

Самостоятельный `structured_log`: API и admin-клиент за одним nginx, на одном
origin. За полной эксплуатационной картиной (выбор backend'а хранения,
конфигурация, резервное копирование, безопасность, диагностика) — см.
[docs/guides/admin-guide.ru.md](../docs/guides/admin-guide.ru.md); этот файл
остаётся сфокусирован на том, что специфично именно для поставляемой
связки Compose.

```bash
cd deploy
./deploy.sh
```

Дальше открыть `http://localhost:8080`. Сгенерированный пароль первого
администратора печатается один раз, предупреждением:

```bash
docker compose logs server | grep -i 'temporary password'
```

Его придётся сменить при первом входе — до этого сервер отвечает
`403 must_change_password` на всё остальное.

## Что поднимается

| Сервис | Образ | Что делает |
|---|---|---|
| `server` | из `backend/structured_log_server/Dockerfile` | API. Наружу не публикуется — доступен только через `proxy`. |
| `web` | из `frontend/structured_log_admin_client/Dockerfile` | nginx: только статика клиента. Не знает о существовании `server` — тоже не публикуется наружу. |
| `proxy` | `nginx:1.27-alpine`, готовый образ, настроен через [`proxy/nginx.conf.template`](proxy/nginx.conf.template) | Ставит `web` и `server` за один origin, на котором публикуется клиент — `/v1/` на `server`, всё остальное на `web`. |

SQLite живёт на именованном томе `data`. Больше ничего не сохраняется.

## Почему один origin

**Сервер не отдаёт CORS-заголовков.** Это не упущение compose-файла: CORS нет
нигде — ни в сервере, ни в его спеках, ни в design.md. Браузерный клиент,
отданный с другого хоста, не сможет обратиться к API вообще: preflight
останется без ответа, и запрос не уйдёт.

Поэтому клиент отдаётся *рядом* с API, а не направляется на него — `proxy`
ставит оба за один origin, а `web` и `server` вообще не знают друг о друге.
Бандл клиента собирается с пустым base URL, каждый запрос уходит относительно
страницы, и один и тот же образ работает на любом домене без пересборки.

Если API когда-нибудь понадобится снаружи — это изменение сервера
(CORS-middleware и решение о допустимых origin), а не настройка прокси.

## Конфигурация

`.env` — копируется из `.env.example` при первом запуске, читается compose:

| | |
|---|---|
| `STRUCTURED_LOG_PUBLIC_PORT` | Порт хоста, на котором отвечает клиент. По умолчанию 8080. |
| `STRUCTURED_LOG_LOG_LEVEL` | `debug`/`info`/`warning`/`error`. |
| `STRUCTURED_LOG_BOOTSTRAP_ADMIN_*` | Создавать ли первого администратора при старте и под каким именем. |

Остальное задано в `docker-compose.yml`, потому что относится к форме этого
развёртывания, а не к хосту: путь к базе, JSON-вывод логов и
`TRUSTED_PROXY_HOPS=1` для стоящего впереди nginx.

Последнее важно. Сервер отсчитывает хопы **справа** от `X-Forwarded-For`,
чтобы найти адрес вызывающего, и по нему же раскладывает лимиты частоты.
Значение больше нужного позволяет подделать адрес своим заголовком, меньше —
сваливает всех в одну корзину. Один прокси впереди означает `1`.

### Секрет подписи

`deploy/secrets/jwt_secret` — генерируется при первом запуске,
монтируется только на чтение, в git не попадает.

Это файл, а не переменная окружения, потому что любой секрет этого сервера
принимается через `<VAR>_FILE`, а файл не виден ни в `docker inspect`, ни в
списке процессов. Замена секрета обесценивает все выданные токены и выкидывает
всех из системы; утечка позволяет выпустить токен для любой учётной записи.

## Эксплуатация

```bash
docker compose logs -f server        # JSON-строки, по одной на запрос
docker compose ps                    # со статусом здоровья
docker compose down                  # остановить, том с данными сохранить
docker compose down -v               # остановить и удалить базу
```

Создать администратора на базе, где уже есть пользователи — автосоздание при
старте там не срабатывает:

```bash
docker compose run --rm \
  -e STRUCTURED_LOG_BOOTSTRAP_ADMIN_PASSWORD='...' \
  server create-admin --bootstrap-admin-username=admin
```

## Пересборка

`./deploy.sh` пересобирает изменившееся. После обновления Dart- или
Flutter-SDK, либо если образ выглядит несвежим — `./deploy.sh --rebuild`
собирает оба с нуля.

Web-бандл клиента собирается **на хосте**, тем самым Flutter SDK, который
пинит репозиторий, и копируется в nginx-образ. Официального Docker-образа
Flutter не существует, а сообществнный — не то, что стоит добавлять в цепочку
деплоя не глядя; SDK и так уже здесь.
