# structured_log_admin_client

[![CI](https://github.com/pese-git/structured_log/actions/workflows/ci.yml/badge.svg)](https://github.com/pese-git/structured_log/actions/workflows/ci.yml)

*Read in [English](README.md).*

**Веб-админка для
[`structured_log_server`](../../backend/structured_log_server/): здесь
операторы и их команды читают логи, ищут по ним, следят за ними вживую и
решают, кому что видно.**

Не публикуется — это приложение, а не библиотека.

## Зачем

Сервер говорит на HTTP и JSON — скриптам этого достаточно, людям мучение:
разбирать инцидент, собирая команды `curl`, копируя токены руками и
листая JSON, не хочет никто. Admin-клиент помещает весь сервер во вкладку
браузера — ленту логов с фильтрами и живым потоком, группы, проекты и
ключи за ней, пользователей, команды и роли, которые определяют доступ.
Оператор входит и работает, а разработчик, которому дали доступ к одному
проекту, видит логи этого проекта — и ничего больше.

## Возможности

- **Вход и смена пароля** — временный пароль, заданный администратором,
  нужно сменить, прежде чем откроется что-то ещё; потом пароль меняется
  в настройках аккаунта, по желанию — не выходя на других устройствах.
- **Дашборд** — доступные вам группы и проекты, число записей и переход
  к логам каждого проекта.
- **Группы, проекты и секретные ключи** — создание групп и проектов, квота
  и срок хранения проекта, блокировка и разблокировка проекта, выпуск
  ключей (значение показывается ровно один раз) и их отзыв.
- **Просмотр логов** — выберите проект или группу, отфильтруйте по уровню,
  категории, логгеру, интервалу времени и correlation id, найдите по
  событию и откройте любую запись, чтобы увидеть все поля, которые
  прислало приложение, с копированием.
- **Живая лента** — новые записи появляются внизу по мере поступления;
  поставьте ленту на паузу, чтобы читать без прыгающего списка, и
  продолжите с того же места. После обрыва соединение восстанавливается
  само, без пропусков.
- **Пользователи** — администратор создаёт, редактирует, блокирует,
  разблокирует и удаляет учётные записи.
- **Команды и роли** — команды группы и их состав; раздел **«Доступ»**
  группы или проекта выдаёт `owner`/`user` пользователю или целой команде
  и отзывает их.
- **Аудит** — для администраторов: административные действия и попытки
  входа в одной таблице под одним набором фильтров.
- **Настройки аккаунта** — профиль, пароль, язык и удаление собственной
  учётной записи.
- **Английский и русский** — пока язык не выбран, следует языку браузера.

## Состояние

Все перечисленные экраны уже работают с сервером. Самостоятельной
регистрации, восстановления пароля и подтверждения email здесь нет, потому
что их пока нет на сервере, — а пункт меню, открывающий пустой экран, хуже,
чем никакого пункта. Что именно сделано, видно в
[tasks.md](../../openspec/changes/add-structured-log-server/tasks.md).

## Место в проекте

Приложения отправляют логи в
[`structured_log_server`](../../backend/structured_log_server/) через
[`structured_log_remote_sync`](https://pub.dev/packages/structured_log_remote_sync),
а этот клиент — то, чем люди их читают и управляют доступом к ним. Это
веб-приложение на Flutter поверх библиотеки компонентов
[`structured_log_admin_ui`](../structured_log_admin_ui/), которое отдаётся
статикой рядом с API: [deploy/](../../deploy/) запускает оба за одним nginx
на одном origin командой `./deploy.sh`. Руководства на
[structured-log.openidealab.com](https://structured-log.openidealab.com/ru/):
[пользователя](https://structured-log.openidealab.com/ru/guides/user-guide/)
(работа в этом клиенте, со скриншотами),
[администратора](https://structured-log.openidealab.com/ru/guides/admin-guide/)
(запуск сервера и клиента),
[разработчика](https://structured-log.openidealab.com/ru/guides/developer-guide/)
(отправка логов из приложения).

**Перед запуском против сервера на другом хосте нужно знать одно: по
умолчанию так не получится.** CORS-заголовков сервер не шлёт, пока оператор
явно не включит их (`--cors-allowed-origins`, см. README самого сервера) —
без этого браузер отклоняет запрос, не отправив его. Клиент отдаётся рядом
с API за одним origin ([deploy/](../../deploy/)), а его бандл собирается с
пустым base URL — это остаётся эталонным способом развёртывания и там, где
CORS доступен.

## Разработка

Для тех, кто дорабатывает само приложение; команды и соглашения всего
репозитория — в [AGENTS.md](../../AGENTS.md).

### Запуск

```bash
flutter run -d chrome --dart-define=STRUCTURED_LOG_BASE_URL=https://logs.example.com
```

Base URL — compile-time define, по умолчанию `http://localhost:8080`.

### Кодогенерация

`*.g.dart` и `*.freezed.dart` не коммитятся:

```bash
dart run build_runner build --delete-conflicting-outputs
```

или `dart run melos run generate` из корня репозитория. В CI шаг идёт до
`analyze`/`test`.

### Языки

Пока язык не выбран, приложение следует языку браузера (для любого другого —
английский); выбрать можно в **Настройки аккаунта → Язык** (или
переключателем English / Русский в углу экранов входа и принудительной смены
пароля), выбор хранится в `localStorage` браузера. Тексты лежат в
`lib/l10n/*.arb` и читаются через `context.l10n`; после правки ARB запустите
`flutter gen-l10n` (сгенерированные файлы коммитятся).

### Подсказка, а не проверка доступа

Выдача роли в разделе «Доступ» группы или проекта сужает список ролей до
того, что разрешают claim'ы токена вызывающего, — это подсказка, а не
проверка: решает всё равно сервер. Урезанная форма на экране пользователя
остаётся только для `admin`, по одному пользователю за раз.

### Экран аудита

Административные действия и события аутентификации одной таблицей под одним
набором фильтров: разбирающий инцидент оператор задаёт один вопрос, и вход,
предшествовавший изменению, — часть ответа.

Пункт навигации появляется, только если claim `roles` токена содержит `admin` в
глобальной области. Claim читается без проверки подписи, и это допустимо ровно по
одной причине: он решает, что **предложить**, а не что разрешить. Сервер
переопределяет роли на каждом запросе и отвечает 403 независимо от токена, а
экран рисует это как отказ. Подделав токен, можно получить разве что пункт меню и
сообщение об ошибке. Одно следствие стоит оговорить: claim — снимок на момент выпуска токена,
поэтому отозванная в середине сессии роль оставит пункт до обновления.

Запись без инициатора называет, какого именно «никого»: попытка под
несуществующей учётной записью или сам сервер, — и запроса за именем не уходит,
потому что учётной записи нет. В теге действия стоит проводное значение
(`project.quota_updated`) — то, по чему фильтруют и что документирует API;
человекочитаемое имя на текущем языке интерфейса — тултип.

### Архитектура

Послойно внутри каждой фичи — `domain` / `application` / `infrastructure` /
`presentation`, плюс `lib/shared/` для сквозного. Директории появляются вместе
с первым файлом, а не заводятся пустыми.

| Задача | Выбор | Где |
|---|---|---|
| UI-кит | `fluent_ui`, компонуется из `structured_log_admin_ui` | `lib/app/`, `presentation/` фич |
| HTTP | `dio` + `retrofit`; SSE вручную на том же инстансе | `lib/shared/api/` |
| Ожидаемые ошибки | `fpdart` `Either`, но не для программных ошибок | `lib/shared/api/api_failure.dart` |
| Модели | `freezed` + `json_serializable` | `lib/shared/api/dto/` |
| DI | `cherrypick` | `lib/shared/di/` |
| Состояние | `flutter_bloc` | `presentation/` фич |
| Сессия | access-токен в `sessionStorage` (на вкладку); refresh-токен в cookie `HttpOnly` сервера, если он её ставит, иначе в `flutter_secure_storage`; никогда не shared preferences | `lib/shared/auth/` |
| Диагностика | `structured_log` | `lib/shared/logging/` |

#### Три инстанса Dio, а не один

Это стоит знать до того, как трогать `ApiClient`:

- основной несёт перехватчик аутентификации — подставляет access-токен и один
  раз обновляет его при 401;
- клиент обновления идёт без перехватчика: refresh, которому ответили 401 на
  основном инстансе, вошёл бы обратно в тот самый перехватчик, который его и
  запустил;
- клиент повтора повторяет исходный запрос уже с новым токеном.

Токен-эндпоинт исключён не только по флагу, но и по пути: 401 от него означает
неверный пароль или израсходованный refresh-токен, и обновление в ответ на
любое из двух превращает неудачный вход в попытку продлить сессию.

Параллельные 401 делят одно обновление. Без этого каждый запрос тратил бы
refresh-токен, и на сервере, который их ротирует, все кроме первого предъявили
бы только что отозванный.
