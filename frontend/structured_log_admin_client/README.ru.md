# structured_log_admin_client

[![CI](https://github.com/pese-git/structured_log/actions/workflows/ci.yml/badge.svg)](https://github.com/pese-git/structured_log/actions/workflows/ci.yml)

*Read in [English](README.md).*

**Веб-админка для
[`structured_log_server`](../../backend/structured_log_server/): здесь
операторы и их команды читают логи, ищут по ним, следят за новыми записями
в реальном времени и решают, кому что видно.**

Не публикуется — это приложение, а не библиотека.

## Зачем

Сервер общается по HTTP и JSON: скриптам этого достаточно, а людям
неудобно. Никто не хочет разбирать инцидент, собирая команды `curl`,
копируя токены вручную и пролистывая JSON. Admin-клиент собирает весь
сервер в одной вкладке браузера: ленту логов с фильтрами и обновлением в
реальном времени, группы, проекты и ключи, к которым относятся логи, а
также пользователей, команды и роли, от которых зависит доступ. Оператор
входит и сразу работает, а разработчик с доступом к одному проекту видит
логи только этого проекта.

## Возможности

- **Вход и смена пароля** — временный пароль, заданный администратором,
  нужно сменить, прежде чем откроется что-то ещё; позже пароль можно
  сменить в настройках аккаунта, при желании оставив сессии на других
  устройствах.
- **Дашборд** — группы и проекты, к которым у вас есть доступ, число
  записей в них и быстрый переход к логам каждого проекта.
- **Группы, проекты и секретные ключи** — создание групп и проектов, квота
  и срок хранения проекта, блокировка и разблокировка проекта, выпуск
  ключей (значение показывается ровно один раз) и их отзыв.
- **Просмотр логов** — выберите проект или группу, отфильтруйте по уровню,
  категории, логгеру, интервалу времени и correlation id, найдите по
  событию и откройте любую запись: там видны все поля, которые прислало
  приложение, и их можно скопировать.
- **Живая лента** — новые записи появляются внизу по мере поступления;
  поставьте ленту на паузу, чтобы список не сдвигался во время чтения, а
  потом продолжите с того же места. После обрыва соединение
  восстанавливается само, и записи не теряются.
- **Пользователи** — администратор создаёт, редактирует, блокирует,
  разблокирует и удаляет учётные записи.
- **Команды и роли** — команды группы и их состав; в разделе **«Доступ»**
  группы или проекта роль `owner`/`user` выдаётся пользователю или целой
  команде и там же отзывается.
- **Аудит** — для администраторов: административные действия и попытки
  входа в одной таблице с общим набором фильтров.
- **Настройки аккаунта** — профиль, пароль, язык и удаление собственной
  учётной записи.
- **Английский и русский** — пока язык не выбран, используется язык
  браузера.

## Состояние

Все перечисленные экраны уже работают с сервером. Самостоятельной
регистрации, восстановления пароля и подтверждения email здесь нет, потому
что их пока нет на сервере, а пункт меню, который открывает пустой экран,
хуже, чем его отсутствие. Что уже сделано — в
[tasks.md](../../openspec/changes/add-structured-log-server/tasks.md).

## Место в проекте

Приложения отправляют логи в
[`structured_log_server`](../../backend/structured_log_server/) через
[`structured_log_remote_sync`](https://pub.dev/packages/structured_log_remote_sync),
а через этот клиент люди их читают и управляют доступом к ним. Это
веб-приложение на Flutter, построенное на библиотеке компонентов
[`structured_log_admin_ui`](../structured_log_admin_ui/); оно раздаётся как
статика вместе с API: каталог [deploy/](../../deploy/) командой
`./deploy.sh` поднимает оба за одним nginx на общем origin. Руководства на
[structured-log.openidealab.com](https://structured-log.openidealab.com/ru/):
[пользователя](https://structured-log.openidealab.com/ru/guides/user-guide/)
(работа в этом клиенте, со скриншотами),
[администратора](https://structured-log.openidealab.com/ru/guides/admin-guide/)
(запуск сервера и клиента),
[разработчика](https://structured-log.openidealab.com/ru/guides/developer-guide/)
(отправка логов из приложения).

**Если клиент должен работать с сервером на другом хосте, учтите: по
умолчанию это не получится.** Сервер не отправляет CORS-заголовков, пока
оператор явно их не включит (`--cors-allowed-origins`, см. README самого
сервера), а без них браузер отклоняет запрос, даже не отправив его. Клиент
раздаётся вместе с API с одного origin ([deploy/](../../deploy/)), а его
бандл собирается с пустым base URL; даже там, где CORS можно включить, это
остаётся рекомендуемым способом развёртывания.

## Разработка

Раздел для тех, кто дорабатывает само приложение; команды и соглашения
всего репозитория описаны в [AGENTS.md](../../AGENTS.md).

### Запуск

```bash
flutter run -d chrome --dart-define=STRUCTURED_LOG_BASE_URL=https://logs.example.com
```

Base URL — compile-time define, по умолчанию `http://localhost:8080`.

### Кодогенерация

`*.g.dart` и `*.freezed.dart` не коммитятся:

```bash
dart run build_runner build --delete-conflicting-outputs
```

или `dart run melos run generate` из корня репозитория. В CI шаг идёт до
`analyze`/`test`.

### Языки

Пока язык не выбран, приложение берёт язык браузера (если он не английский
и не русский — английский); выбрать можно в **Настройки аккаунта → Язык** (или
переключателем English / Русский в углу экранов входа и принудительной смены
пароля), выбор хранится в `localStorage` браузера. Тексты лежат в
`lib/l10n/*.arb` и читаются через `context.l10n`; после правки ARB запустите
`flutter gen-l10n` (сгенерированные файлы коммитятся).

### Подсказка, а не проверка доступа

При выдаче роли в разделе «Доступ» группы или проекта список ролей
ограничен тем, что разрешают claim'ы токена текущего пользователя. Это
подсказка, а не проверка: окончательно решает сервер. Упрощённая форма на
экране пользователя доступна только `admin` и выдаёт роль одному
пользователю за раз.

### Экран аудита

Административные действия и события аутентификации показаны в одной таблице
с общим набором фильтров: оператор, который разбирает инцидент, ищет ответ
на один вопрос, и вход, после которого случилось изменение, — часть этого
ответа.

Пункт навигации появляется, только если claim `roles` токена содержит `admin` в
глобальной области. Claim читается без проверки подписи, и это допустимо ровно по
одной причине: он определяет, что **предложить**, а не что разрешить. Сервер
заново вычисляет роли при каждом запросе и в любом случае отвечает 403, а
экран показывает это как отказ. Подделав токен, можно получить разве что пункт меню и
сообщение об ошибке. Одно следствие стоит оговорить: claim отражает роли на момент выпуска токена,
поэтому если роль отозвали посреди сессии, пункт останется до обновления токена.

Для записи без инициатора видно, что это было: попытка входа под
несуществующей учётной записью или действие самого сервера; запрос за именем
при этом не отправляется, потому что учётной записи нет. В теге действия
показано значение в том виде, в каком оно передаётся по API
(`project.quota_updated`), — по нему фильтруют, и именно его описывает
документация API; понятное название на текущем языке интерфейса появляется в
тултипе.

### Архитектура

Каждая фича разбита на слои `domain` / `application` / `infrastructure` /
`presentation`, а общий для всех фич код лежит в `lib/shared/`. Директории
появляются вместе с первым файлом, а не заводятся заранее пустыми.

| Задача | Выбор | Где |
|---|---|---|
| UI-кит | `fluent_ui`, компонуется из `structured_log_admin_ui` | `lib/app/`, `presentation/` фич |
| HTTP | `dio` + `retrofit`; SSE вручную на том же инстансе | `lib/shared/api/` |
| Ожидаемые ошибки | `fpdart` `Either`, но не для программных ошибок | `lib/shared/api/api_failure.dart` |
| Модели | `freezed` + `json_serializable` | `lib/shared/api/dto/` |
| DI | `cherrypick` | `lib/shared/di/` |
| Состояние | `flutter_bloc` | `presentation/` фич |
| Сессия | access-токен в `sessionStorage` (на вкладку); refresh-токен в cookie `HttpOnly` сервера, если он её ставит, иначе в `flutter_secure_storage`; никогда не shared preferences | `lib/shared/auth/` |
| Диагностика | `structured_log` | `lib/shared/logging/` |

#### Три инстанса Dio, а не один

Это стоит знать до того, как трогать `ApiClient`:

- у основного есть перехватчик аутентификации — он подставляет access-токен и
  один раз обновляет его при 401;
- клиент обновления работает без перехватчика: refresh, которому ответили 401 на
  основном инстансе, вошёл бы обратно в тот самый перехватчик, который его и
  запустил;
- клиент повтора повторяет исходный запрос уже с новым токеном.

Токен-эндпоинт исключён не только по флагу, но и по пути: 401 от него означает
неверный пароль или израсходованный refresh-токен, и обновление в ответ на
любой из этих случаев превратило бы неудачный вход в попытку продлить сессию.

На несколько одновременных 401 выполняется одно общее обновление. Иначе
каждый запрос тратил бы свой refresh-токен, и на сервере, который их
ротирует, все запросы, кроме первого, предъявили бы уже отозванный токен.
